附录 F · 扩展 artifact 速查：能力 → 依赖

这一页只回答两个问题：这个能力要引哪个 artifact，以及它对应哪一章。 模型 id、provider 名称和 artifactId 不是一回事：同一个 artifact 可能承载多个 provider id，同一种能力也可能拆成 core、扩展和 starter 三层。 表里的 artifactId 都来自各模块自己的 pom.xml，版本统一跟站点一致：2.0.4 pom.xml:30。

读完你能做到

  • 按能力直接找到 artifactId，不再把 provider id 当成依赖坐标
  • 分清「核心扩展」「具体后端」「Spring Boot starter」三层，知道什么时候只引扩展、什么时候还要引 starter
  • 识别已经标记 legacy 的 MySQL 旧类，新项目直接走 JDBC
  • 把站点章节、artifact 与源码 pom.xml 对上，升级时能自己复核

怎么用这一页

  • 先找能力，再看 artifact：例如「要接 Redis」在「状态 / 分布式存储」组，不在「模型」组
  • 再判断要不要 starter：普通 Java 应用只引扩展；Spring Boot 想要自动装配，再引对应 starter
  • 一个 artifact 可能覆盖多个 id：OpenAI 兼容模块同时承载 openai、deepseek、glm、kimi、minimax
  • 旧类只做兼容：MysqlDistributedStore、MysqlAgentStateStore、MysqlSkillRepository 的旧构造器都不要写进新代码
  • 每一行的 pom.xml 出处都可以点开复核；artifactId 与目录名一致，便于在 IDE 里搜

版本与选型提醒

  • 版本统一：所有 artifact 跟根 revision 走，当前是 2.0.4pom.xml:30；不要给单个扩展写别的版本。
  • 先扩展，后 starter：普通 Java 应用不需要 starter；Spring Boot 只有在需要自动装配时才加。
  • 模型看 id，不看 artifact：deepseek: 等五个 id 共用 OpenAI 兼容 artifact。
  • 关系型存储优先 JDBC：MysqlDistributedStore / MysqlAgentStateStore 都是兼容层。
  • RAG / 记忆是 legacy：适配器可用，但新项目优先应用层集成。
