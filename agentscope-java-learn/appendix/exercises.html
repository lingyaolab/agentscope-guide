附录 G · 动手练习答案

这不是唯一答案，而是「参考做法 + 检查点」。同一道练习可以有不同的实现， 重点是你能不能解释每一步为什么这样做、失败时该看哪里。建议先自己写，再对照。

怎么用这份答案

  • 先跑通自己的版本，再对照参考做法，不要直接抄。
  • 重点看「检查点」：它们比代码更能说明你有没有理解。
  • 如果代码能跑但检查点答不上来，回到对应章节重读。

第 01–04 章：装配、第一个 Agent、Reactor 与消息事件

01 的三个观察可以放在同一个工程里：先加模块看 canResolve， 再写错模型名看「解析成功、调用失败」，最后去掉 key 看两层异常。 

ModelRegistry.resolve("dashscope:qwen-plus");
// 前缀能匹配不等于服务端有这个模型；key 缺失时异常在 resolve 之后才出现
agent.streamEvents(msg, ctx)
        .doOnNext(event -> {
            if (event instanceof TextBlockDeltaEvent delta) {
                System.out.print(delta.getDelta());
            }
        })
        .blockLast();

检查点：

  • canResolve 只做前缀/注册表匹配；dashscope:qwen-not-exist 仍可能返回 true，真正报错在服务端。
  • 缺 key 的异常是两层：外层 Failed to create model for id，内层才是环境变量缺失；先看 getCause()。
  • 02 的记忆来自磁盘状态，不是进程内存；换一个 sessionId 就应该「失忆」。
  • 工作区里的 AGENTS.md 会参与系统提示拼装；写完要重跑，不是热更新。
  • 03 的两种「没输出」不同：没有订阅（没有 blockLast）与没有副作用（没有 doOnNext）。
  • 04 的事件普查里，带工具的问题会让 MODEL_CALL_START 从 1 变 2；首字延迟看第一个 TextBlockDeltaEvent。

第 05–08 章：模型、工具、状态与权限

05 的关键是分清「字符串 id 的缓存」与「自己 builder 的新实例」； 07 的关键是看清 agent_state.json 里到底存了什么。 

AgentStateStore store = new JsonFileAgentStateStore(Path.of("state"));
// 跑一轮后打开 state/<uid>/<sid>/agent_state.json
// 对照 context、tool_context 与 summary 三段

检查点：

  • ModelRegistry.resolve 连续两次返回同一对象；自己 builder() 每次都新建。
  • 无效 key + maxRetries(2) 如果「立刻失败」，说明是鉴权错误，不是可重试错误。
  • 工具方法里不带 @ToolParam 的参数不会进 schema，运行时值是 null。
  • 两个类注册同名 @Tool(name="search") 会静默覆盖，没有警告；多 MCP server 必须加前缀。
  • ToolGroup(active=false) 要等模型调用 reset_equipped_tools 后才可见。
  • 不传 sessionId 会落到 __anon__ 桶；不同 userId 仍隔离，去掉 userId 才会串号。
  • clearContext(uid, sid) 清对话但保留工具组与 todo；换 sessionId 则是全新会话。
  • 拒绝是一次正常工具结果，不是异常；带理由的拒绝会让模型换方案。
  • 确认时附带的 PermissionRule 只在当前会话内存里；setPermissionMode 重建引擎后规则消失。
  • EXPLORE 对非只读工具直接 DENY；BYPASS 也不会绕过工具自检的 DENY。

第 09–11 章：中间件、ReAct vs Harness 与综合案例

09 的「总账」中间件只做观察：order() 越小越靠外， 用 doFinally 统计算子耗时，用事件类型统计模型调用次数。 

public int order() {
    return 10;
}

// onAgent 里挂 doFinally，统计整次 call 的耗时与 ModelCallEndEvent 数
// maxIters=1 时，触顶后还会多一次摘要调用，所以事件数比预期多 1

检查点：

  • 预算守卫返回 MIDDLEWARE_STOP_REQUESTED；计数存在 RuntimeContext 里，换 ctx 才会重置。
  • StopOnAllDeniedMiddleware 只在「全部工具被拒」时触发；只拒一部分不会触发 AllToolsDeniedEvent。
  • 10 章触顶时：正常推理 2 次、ExceedMaxItersEvent 1 次、摘要调用 1 次；摘要不经过 onReasoning。
  • 无参 interrupt() 已废弃，原因是无法指定上下文；用带 RuntimeContext 的重载。
  • 11 章的综合案例把工具、状态、权限、流式四块接缝都跑了一遍；先跑通再换 Harness。
  • 11 章的只读工具在 DEFAULT 下直接执行；切到 EXPLORE 后它仍能跑，delete_note 则从 ASK 变成直接拒绝。
  • 「本会话免问」的规则存在会话槽位里；/new 之后会恢复询问。

第 12–15 章：工作区、沙箱、子 Agent 与压缩

12 的 namespace 真相：宿主侧有 alice/、bob/ 两层， 模型侧只看到自己的桶；workspaceFor 返回的是带身份的文件系统视图。 

var ws = agent.workspaceFor("alice", "alice-s1");
ws.getFilesystem().ls(RuntimeContext.empty(), "/");
// 即便传 empty，BakedContextFilesystem 仍会把 alice 的身份盖回去

检查点：

  • overlay 的读是并集、写是单层；第一次 edit 会把文件复制到 workspace 上层。
  • 空 AGENTS.md 不算「不存在」，回落只发生在读出空串那一支。
  • maxContextTokens 只截 MEMORY.md 那一段，不截 AGENTS.md 与 knowledge。
  • 13 章默认没有快照；docker rm -f 后重建容器，文件就没了。加 snapshotSpec 才会恢复。
  • SESSION / USER / AGENT / GLOBAL 四种 scope 对应 3 / 2 / 1 / 1 个容器。
  • workspace spec 由 applier 写宿主，投影才进容器；timeout=0 仍会按 30 秒被杀。
  • 14 章 workspace.mode: shared 的子 Agent 不新建目录，直接用主工作区。
  • 任务记录在 <workspace>/agents/<name>/tasks/<sessionId>.json，重启后仍可读。
  • 15 章 prune 在压缩之前；日志顺序是先 Pruned ... 再 Compaction triggered。
  • reserved(100_000) 配 32K 模型会被 clamp；逐出与压缩可以独立关闭。

第 16–18 章：技能、计划模式与网关

16 的技能 ID 与 files-root 都能从 DEBUG 日志里抄出来； skill_manage 创建的文件先落在草稿区，下一轮 prompt 里看不到。 

agent.promoteSkill(name, "me", ctx).block();
// 默认闸门返回 deferred，目录仍在 skills/_drafts/
// 自定义 gate 返回 Approve 后才会 move 到 skills/<name>/

检查点：

  • 四层技能合并按 namespaced upper → project → workspace → overlay；同名时 alice 的覆盖共用版。
  • curator 只归档不删除；.curator_reports 里没有 LLM 结论，只有前缀聚类与空的 consolidations。
  • 17 章 plan 模式的拦截发生在 onActing；被拒的调用会合成一条 DENIED 工具结果。
  • allowShellInPlanMode 只放行 execute，并追加一段 system-reminder。
  • tools.json 的 allow/deny 与平台默认名单交叉；拼错的名字只会在日志里 warn 一次。
  • 未声明 readOnlyHint 的 MCP 工具在 plan 阶段默认非只读，会被 DENIED。
  • 18 章 previewRoute 能提前看到 canonicalKey、agentId 与 matchedBy。
  • extra 里的 traceId 会打散会话；要保留记忆就放 RuntimeContext。
  • 异步工具超时先返回占位结果；成功会回灌 HintBlockEvent，失败只有 warn，没有唤醒。

第 19–21 章：Service 入门、Endpoint/SSE 与 Managed Agent

19 先验证端口映射与「restart 不重建」这两件事：宿主 18080 映射到容器 8080， 改 GATEWAY_PORT 后只 restart 不会生效，必须 up -d --wait。 

docker compose ps
curl http://localhost:18080/actuator/health
docker compose port gateway 8080
docker compose up -d --wait

检查点：

  • restart 只重启容器，不重新读取 .env；改端口要重建。
  • 容器端口与宿主端口可以不同；改端口后 BUILDER_OAUTH_PUBLIC_URL 也要跟着改。
  • 20 章一条 job 要保存 invocationId、statusUrl、eventsUrl 与凭据四个值。
  • SSE 断线用最后一条事件 id 作为 Last-Event-ID 续传，不需要重新提交 job。
  • 同一个 Idempotency-Key 重发返回同一个 invocation；输入变化后重发才是 409。
  • 21 章按「模型 → Instructions/迭代上限 → Workspace/Environment → Memory → Vault」逐层加，一次只改一层。
  • Memory 是按需读取，不是自动塞进上下文；要从工具记录里确认 memory_store_read。
  • Vault 变量必须在 MCP header 里显式引用；配了 Vault 不会自动替代模型 provider 的连接配置。

第 22–23 章：External Agent 与 Hosted Agent

22 的验收顺序是「先合约、再注册、再会话、最后任务」； 23 的顺序是「先 provider 自己跑、再 connect、再创建 Agent、最后派 Issue」。 

agentId      → 同一个 Agent
bindingId    → 同一个注册绑定
instanceId   → 同一个进程实例
generation   → 每次重启递增

检查点：

  • 不注册时，/agentscope/health 与 /agentscope/info 仍可访问，但目录里没有卡片。
  • 重启保持 instanceKey 不变：agentId / bindingId 不变，generation 变化。
  • 扩副本只改 instanceKey：同一个 Agent 下多一个实例，不是多一个 Agent。
  • 23 章 Host 离线约 45 秒后标 offline；期间提交的 Issue 保持 queued。
  • 容量降到 1 时第二个任务排队；drain 后不再领取新任务，resume 恢复。
  • 能力不被 provider 支持时，会在 provider 启动前以能力错误结束，不会跑到一半才失败。

第 24–26 章：团队、工作流与生产运维

24 的团队练习先单独验证三个 Agent，再建队；重点是「Leader 按需委派」， 不是一次叫齐所有人。 

Run succeeded   ≠ Task succeeded
Task succeeded  ≠ Issue done
Execution 完成  ≠ 验收通过
Inbox 读到消息  ≠ 做出决策

检查点：

  • 成员被禁用时 Team 变 Degraded；恢复后回到 Ready。
  • maxChildIssues=1 时创建第二个子 Issue 会得到预算错误。
  • 根 Issue 进入 in_review 不等于完成，还要在 Inbox 接受。
  • 25 章先故意留一个未知边引用，确认发布校验会失败；修复后才能发布 revision。
  • Workflow 的 draft 可改，revision 不可变；新启动可以继续选旧 revision。
  • 审批先拒绝一次，确认节点失败并按 fail_fast 收敛；再用新幂等键 Rerun。
  • Acceptance 要求 artifact 但没上传时，Accept 会被阻断。
  • Webhook 同一幂等键两次，第二次是 duplicate；事件筛选不匹配则 delivery ignored。
  • 26 章备份必须同批：数据库、两个卷、Secret 与版本号缺一不可。
  • 恢复要在空库上做，用同批卷与密钥；恢复验收不是「Pod Ready」。
  • 升级演练要记录 Chart 与镜像版本；故意用不存在的 tag 验证 ImagePullBackOff 与恢复时间。

第 27–29 章：扩展选型、模型 provider 与记忆接入

27 的产出不是「装了多少模块」，而是一份三行选型记录： 接口选了什么、后端为什么是它、部署形态还缺什么。 

接口：AgentStateStore / Knowledge / Channel / Model
后端：JDBC / Redis / 外部平台，为什么
部署：单机 / 多副本 / 托管，还缺什么

检查点：

  • 先选接口层，再看后端；不要从「我想用 Redis」倒推架构。
  • 加一个 provider artifact 后，用 ModelRegistry.resolve 跑最小调用；手写 builder 与 starter 只差装配。
  • 换模型时 Agent 代码不变，变的是 id、artifact、凭证与能力开关。
  • 28 章至少对比两家：工具调用、结构化输出、思考模式、流式四项能力逐项记录。
  • 两个不同 apiKey context 解析同一个 id，不应复用同一个模型实例。
  • 29 章先分三层：当前对话、长期偏好、任务结论；不要把三者都塞进长期记忆。
  • STATIC_CONTROL 与 AGENT_CONTROL 的差异是「自动记录/检索」还是「模型主动调工具」。
  • 记忆注入是 role=USER、name=long_term_memory，追加在消息末尾。
  • 记忆后端失败通常静默降级：Agent 仍回复，检索变空；要看日志而不是等报错。

第 30–32 章：分布式存储、Agent 状态与 RAG

30 先把「状态、文件 KV、快照、锁」四件东西分开画，再选后端； 31 先看一次 agent_state.json 的加载与写回，再谈 CAS。 

var redis = RedisDistributedStore.fromJedis(jedis);
var jdbc = JdbcDistributedStore.create(dataSource);
var state = new RedisAgentStateStore(jedis);

检查点：

  • OSS 适合大快照，但不做锁；多副本要把锁补到 Redis / JDBC / Mongo。
  • 混合后端只要求「状态 + 基础 KV」在同一个 store，其余能力可以拆。
  • 同一个 key 连续两次 putIfVersion：第一次成功，第二次失败；OSS 没有版本化。
  • 31 章 Redis key 是 agentscope:session:<user>/<session>:agent_state 与 _keys。
  • 第二轮回写拿第一轮版本做 CAS；冲突策略 OVERWRITE / FAIL / APPEND_MERGE 行为不同。
  • 压缩轮不能用 APPEND_MERGE，因为它不是简单追加消息。
  • 32 章先决定索引归谁：Simple 自建，还是百炼/Dify/HayStack/RAGFlow 托管。
  • GENERIC 模式把 <retrieved_knowledge> 注入消息末尾；AGENTIC 模式让模型主动调 retrieve_knowledge。
  • 空结果时 Hook 会静默，工具会返回字符串；这是两种不同的失败形态。
  • 不是所有后端都支持 addDocuments；写入前先确认能力。

第 33–35 章：协议、渠道与技能仓库

33 先列调用方，再选协议：浏览器聊天 UI 看 AG-UI， CI/任务系统看 Agent Protocol，另一个 Agent 平台看 A2A。 

AG-UI            → 浏览器事件流 + HITL
Agent Protocol   → /tasks 任务 API + 轮询/等待
A2A              → AgentCard + 远端 Agent

检查点：

  • AG-UI 要确认 RUN_STARTED / TEXT / RUN_FINISHED 三类事件都到。
  • Agent Protocol 的 task 有 pending / running / success / error / cancelled 五态。
  • SSE 续传用 from_seq 或 Last-Event-ID；断线后补发范围要验证。
  • 34 章 GitHub 渠道要同时验证验签、comment.id 去重、bot 自激过滤与回复 API。
  • peer id 是 owner/repo#number，不同线程会话独立。
  • 多副本要把默认 JVM 内去重存储换成共享存储。
  • 35 章 Git 仓库只读；save 返回 false，不会提交。
  • MySQL / PostgreSQL 仓库有两张表，删除技能要确认级联。
  • metadata_json 有完整模式与兼容模式；旧表没有该列时要走兼容。
  • 多仓库同名技能后注册的覆盖先注册的；writeable=false 时 save/delete 都返回 false。

第 36 / 36A 章：基础设施与集成落地

36 的产出是一张边界图：请求入口、工具出口、状态存放、观测点， 分别标出「本进程」还是「外部服务」。 

谁触发：Scheduler / Webhook / Chat / CLI
谁治理：Higress / Nacos / 自建网关
谁观测：Studio / OTel / 日志
谁兜底：Agent、网关，还是调用方

检查点：

  • Nacos A2A 注册的是 AgentCard 与端点，不是进程实例。
  • Nacos Prompt 的缓存键只有 promptKey；第二次换 version/label 仍返回旧值。
  • Nacos Skill 不传 knownSkillNames 时列表为空。
  • Higress 工具最终要进 Toolkit 才生效；网关只负责治理与转发。
  • Quartz 默认 autoStart，但默认调度模式 NONE 什么也不做。
  • XXL-Job 只注册 JobHandler，排程要在控制台做。
  • Studio 初始化会自动挂 Hook 与 Tracer；它推的是 PostCall 最终消息，不是每条 token。
  • Training 是影子流量，生产响应不等待影子 Agent；默认 10% 采样、300 秒 commit。
  • Chat Completions Web 只提供适配器，HTTP/SSE 路由由 starter 或自写 Controller 提供。
  • 36A 每条链路只看一个硬指标：A2A 能解析、Higress 工具进 Toolkit、Scheduler 真触发、Studio 收到最终消息、Training 只采到该采的样本。
