附录 E · 勘误汇总：官方文档 vs 2.0.4 源码

这是全站最「不客气」的一页：把 19 章写作时逐条核对出来的偏差集中成一张表。左边是 docs/v2/zh/** 的原话，右边是 agentscope-java-2.0.4 里真正执行的代码，中间那句是「照文档写会怎么坑你」。 一共 60 条，去掉三组跨章重复后是 57 条独立偏差。每条都带文档与源码两套行号，可以自己复核。

怎么用这一页

  • 遇到「文档说可以、实际不生效」先来这里查：按章找，比翻 19 页正文快
  • 看「影响」那一列决定要不要改代码：写了会编译不过的，优先级最高；只是默认值不同的，知道就行
  • 两套出处都能点：文档那侧是 docs/v2/zh/** 的 md，源码那侧是 agentscope-java-2.0.4 的 Java 文件
  • 结论只对 2.0.4 负责：升级后先重新核对，别把这里的「未接线」当成永远成立
三类偏差，处理方式不同

写错了：按文档写会编译不过或配置无效，以源码为准；写旧了：文档比代码旧，先搜类名确认缺口是否已补； 没写全：文档只写 happy path，默认值、分支和隐藏字段要自己去源码里找。下面的表格里，三种都会遇到。

为什么会有这些差异

把 60 条放在一起看，成因其实只有三类，认出类型就能猜出该信哪边：

  1. 文档滞后于代码
    2.0.x 迭代快，文档按某个早期提交写成，后来行为改了、字段补了，文档没跟上。典型：17 章「子 agent 不继承 plan 模式」的缺口已经修了， 文档还留着「已知缺口」。这类先搜类名/方法名，看源码里有没有新 API。
  2. 示例从 1.x 或别的语言搬来
    1.x 的 memory.addMessage()、StaticLongTermMemoryHook、Python 部署页的示例，都还在文档站里。典型：09 章示例缺 RuntimeContext 参数（07 章 1.x 记忆 API 整包换成新接口，不在这 60 条里，正文有专段说）。这类先看包级 @Deprecated 与签名。
  3. 只写 happy path，不写默认值与兜底
    文档说「可以配」，没说「不配时是什么」。典型：15 章压缩默认开启、12 章 Docker 镜像有默认值、18 章 dispatchStream 默认直接报错。 这类必须去 build() 和字段初始化处看默认值。

自己核对的三步

这张表会过期。升级版本或怀疑某条结论时，按下面三步复核，比记结论可靠：

  1. 搜「读取点」，不只看定义
    字段和 setter 存在，不代表有人读。搜字段名在 build()、中间件、引擎里的出现次数；只有赋值 + getter 的，就是空接线。 08 章的四项、12 章的 useLegacyXmlWorkspaceContext 都是这样确认的。
  2. 先找字段默认值，再找 build() 的覆盖
    spec 字段写 null，build() 可能落一个完全不同的默认值（isolationScope 就是这样从 SESSION 变成 USER 的）。 两处都要看，只看一处就会得出相反结论。
  3. 跑一个最小用例，看日志与事件流
    默认值、触发时机、返回结构这三类偏差，跑一次比读十遍快：打开 DEBUG 日志、打印事件类型、把返回值原样贴出来。 本页每条「影响」都描述了预期现象，可以直接当验收标准。
别把这张表当成「官方文档不可信」

大部分偏差是「文档没写全」，不是「文档写错」。真正的用法是：文档负责告诉你有什么，源码负责告诉你现在怎么跑。 遇到冲突时以 2.0.4 的代码为准，并把版本号记在结论旁边——没有版本号的结论，下个月就可能变成谣言。
