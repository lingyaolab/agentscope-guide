附录 D · 源码地图：core 20 个包 + harness 15 个子包

这一页不解释功能，只回答一个问题：我现在该打开哪个目录。统计口径是 2.0.4 源码里的 .java 文件数（递归含子包、不含测试）：agentscope-core 有 308 个，agentscope-harness 的 agent 包下有 269 个。数字只用来看「这个包有多重」，不是质量指标。

怎么用这一页

  • 别从头读。先看下面的「症状 → 包」，带着问题跳进去，读完一个类就回来
  • 每一行给出「管什么」和「先看哪个类」。类名是入口，不是全部：真正的细节往往在它的内部类里
  • 包里文件多不代表重要，只代表可变体多。比如 tool 有 57 个文件，是因为它同时包含注解、注册表、执行器、MCP、内置工具五摊事
  • 在 IDEA 里 Ctrl+N 直接搜类名，比顺着目录点快得多；本页的作用是告诉你搜什么
一个反直觉的结论：最大的包不是 agent

tool 57 个文件、model 40 个，而 agent 只有 27 个。 这说明框架的核心不是「agent 这个类」，而是它调用的那些零件：模型适配、工具协议、消息与状态。 ReActAgent 本身只负责把零件串成循环——所以遇到问题时，先怀疑零件，再怀疑循环。

先建立一张分层图

两个模块的关系不是「大模块包含小模块」，而是同一个引擎 + 不同外壳： HarnessAgent 内部持有一个 ReActAgent，把自己装配的中间件挂到它的循环上。

agentscope-harness · io.agentscope.harness.agent
外壳：工作区、文件系统、沙箱、子 agent、技能、计划模式、消息总线。 它不重新实现循环，只往 ReActAgent 上装中间件。
agentscope-core 根 · agent · middleware · hook
循环与编排：ReActAgent 的主循环、AgentBase 的生命周期与 Hook 分发、 MiddlewareBase 的四类包裹点。
message · event · formatter · model · tool · memory · state · permission · rag · skill
零件：这一层才是日常改代码最常碰的。第 04 ~ 09 章讲的就是它们。

core 的唯一入口类：ReActAgent.java:218；harness 的入口：HarnessAgent.java:169

为什么 workspace 是个空包

它只留了一份 package-info.java 说明「工作区是 Harness 的概念」。这不是没写完，而是模块边界： core 只承诺「状态可存可取」，不承诺「工作区目录长什么样」。所以你在 core 里永远找不到 WorkspaceManager。

六条「症状 → 包」的追踪路线

这六条覆盖了前 18 章会遇到的绝大多数问题。每条都按从外到内的顺序排，先看最外层。

  1. 模型返回的东西不对
    model.transport（HTTP / SSE 原样）→ formatter.AbstractBaseFormatter（转成 ContentBlock）→ message.Msg。断点打在 formatter 上，能立刻分清是「厂商没给」还是 「框架没解析」。
  2. 工具没被调用，或参数是空的
    tool.Toolkit（注册）→ tool.ToolSchemaGenerator（给模型看的 schema）→ tool.ToolExecutor（真正执行）→ ToolResultBlock。MCP 工具先看 tool.mcp.McpTool，它的调用链多一层客户端。
  3. agent 为什么停了
    先读 Msg.getGenerateReason() 的 12 个值，再进 ReActAgent 主循环找对应分支， 最后才看 event.AgentEndEvent。别先怀疑模型：一半的「它不继续了」是 MAX_ITERATIONS 或 PERMISSION_ASKING。
  4. 重启后状态没了
    state.AgentStateStore（存在哪、key 是什么）→ memory.StateBackedMemory （怎么读回）→ ReActAgent 的加载与保存。Harness 还要多查一层 workspace.WorkspaceManager：状态和工作区是两个地方。
  5. Harness 多出来的行为从哪来
    harness.agent.middleware 的 20 个类，名字就是功能。最快的办法是在 HarnessAgent.build() 里搜 inner.middleware，能看到它们的安装顺序—— 顺序决定谁先看到消息。
  6. 渠道消息没回复，或后台结果永远不回来
    gateway.channel.ChannelRouter（选了哪个 agent、哪个会话键）→ gateway.HarnessGateway（sessionId、轮次锁）→ bus.MessageBus （inbox / 唤醒队列）→ gateway.WakeupDispatcher（谁被叫醒）→ middleware.InboxMiddleware（结果什么时候被注入）。断点先打在 resolveRoute：五成问题是 routing binding 写错后静默落到了主 agent。

中间件安装位置（搜 inner.middleware）：HarnessAgent.java:2520；消息与原因枚举：GenerateReason.java:36

找扩展代码的最快办法：从 SPI 反查

核心只认两个 SPI：model.spi.ModelProvider 和 AgentStateStore。 在 IDEA 里对接口按 Ctrl+Alt+B（Show Implementations），所有扩展实现会一次列出来， 比按模块名猜路径可靠。

读源码的三条建议

  • 先读接口，再读唯一实现。Agent 只有四个承诺，Model 只有几个方法；读完契约再看实现，不会被 27 个辅助类淹掉
  • 把 builder 当功能清单。ReActAgent 43 个、HarnessAgent 97 个方法，按能力分组就是一份路线图（见附录 C）
  • 测试是最好的用例。agentscope-core/src/test 与 agentscope-harness/src/test 里有大量「最小可复现」，比读实现快
关于这一页的数字

308 与 269 是 2.0.4 快照下 src/main/java 里 .java 文件的递归计数， 不含测试与扩展模块；同一个文件只算一次。换版本后数字一定会变，但包的划分很少变—— 这页真正有用的是「哪个包管什么」，不是具体数字。
