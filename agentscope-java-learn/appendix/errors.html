附录 B · 报错速查：看到什么错，改什么地方

这份表只收真的会挡住你的错：每一条都能在 2.0.4 源码里找到抛出点，错误文本与源码节选/前缀一致。 顺序按「从写代码到跑起来」排：构建 → 权限 → 工具 → 状态 → 响应式 → 模型 HTTP。最后给一套三步定位法， 遇到表里没有的错也能自己查。

怎么用这一页

  • 先在页面里搜报错文本的前半句（比如 Agent is paused for），别搜整行——里面的 id 每次都不一样
  • 每张卡的结构固定：你会看到 → 因为 → 改成。先看「因为」，再看「改成」，否则容易照着改但没改到根因
  • 卡底的「相关章节」指向真正讲这件事的小节（带源码行号）；想弄懂机制而不是背结论，顺着点过去
  • Java 的异常是套娃的：先看最下面那个 Caused by，那才是真正的抛出点
  • 表里标 很常见 的是新手第一周几乎一定会撞上的
  • 每张卡右上角的 # 是这一条自己的链接，复制给别人会直接落到这条错上
一个反直觉的前提：很多「报错」其实是正常结束

PERMISSION_ASKING、MAX_ITERATIONS、TOOL_SUSPENDED 这些 不是异常，它们是 GenerateReason。框架只是把「停下来等你」当成一种正常结果返回， 真正会抛异常的，是你的代码违反了某个约定（id 对不上、状态没配、线程里 block）。

构建与启动

1. 很常见 UnsupportedClassVersionError
你会看到
java.lang.UnsupportedClassVersionError: io/agentscope/core/ReActAgent has been compiled by a more recent version of the Java Runtime (class file version 61.0), this version ... recognizes ... 52.0
因为
2.0.4 的 class 文件是 Java 17（61.0），你用的是 Java 8（52.0）或 11（55.0）在跑。
改成
把 maven.compiler.release 设成 17，并确认 IDEA 的 Project SDK 和 Run 配置里的 JRE 都是 17+。用 JDK 21 编译、release 定 17 也没问题。
相关章节：01 环境与依赖 · 陷阱与窍门（JDK 17）
2. 很常见 Cannot resolve model: "qwen-plus"
你会看到
后面还跟着一段 Possible causes:，列出命名模型、SPI provider、各家扩展模块和环境变量。
因为
模型 id 的格式是 <provider>:<model-name>。只写 qwen-plus 没有前缀，ModelRegistry 不知道找谁；或者写了前缀但 pom.xml 里没引对应扩展。
改成
补前缀：.model("dashscope:qwen-plus")；同时确认依赖里有 agentscope-extensions-model-dashscope（OpenAI / Gemini / Anthropic / Ollama 同理，换对应扩展）。
相关章节：05 模型层 · 一个字符串怎么变成模型对象
3. Environment variable DASHSCOPE_API_KEY is required to auto-create model: dashscope:qwen-plus
你会看到
构建 agent 或第一次调用时直接抛 IllegalStateException，不是 HTTP 401。
因为
provider 是用 System.getenv 读的。IDEA 从桌面图标启动时继承不到你刚在 PowerShell 里 setx 的变量；改完环境变量不重启 IDE 也读不到。
改成
三条路任选：① 在 IDEA 的 Run Configuration → Environment variables 里显式加；② 完全退出 IDEA 再启动；③ 不走字符串 id，直接 ModelRegistry.register("my-model", 自己 new 的实例) 或 .model(Model) 传实例。
相关章节：02 第一个 Agent · 第 2 步：设一个 API Key
4. IllegalArgumentException: modelId must not be blank
你会看到
构建阶段就失败，堆栈里是 ModelRegistry.resolve。
因为
.model("")、.model(" ") 会得到 modelId must not be blank；传 null 则先走 Objects.requireNonNull，抛 NullPointerException: modelId。
改成
给一个合法的 id。完全不写 .model(...) 时 build() 仍能成功，但首次 call() 会因 model == null 抛 NPE，所以本质上仍必须给模型。
相关章节：05 模型层 · 一个字符串怎么变成模型对象

权限与 HITL

这一组的共同点：它们都在你「第二次调用」的时候才炸。第一次调用是正常返回的，reason 是 PERMISSION_ASKING；你没接这个信号，拿同一份状态又调了一次，于是撞上校验。

5. 很常见 一长串 Agent is paused for human-in-the-loop confirmation
你会看到
java.lang.IllegalStateException: Agent is paused for human-in-the-loop confirmation: the following
 tool call(s) are in ASKING state and need your approval before the agent can continue:
 [delete_note (id=call_abc123)]. This call supplied no confirmation, so it cannot proceed.
To resume, send a follow-up message that carries a List<ConfirmResult> under the metadata
key "agentscope_confirm_results", e.g.:
    UserMessage.builder()
        .metadata(Map.of(Msg.METADATA_CONFIRM_RESULTS,
            List.of(new ConfirmResult(true, toolCall))))
        .build();
Tip: capture the ToolUseBlocks from the RequireUserConfirmEvent emitted when the agent paused.
因为
上一次调用停在了 ASKING，而这一次你送进去的消息没有携带 ConfirmResult。 常见三种触发：① 用 for 循环无脑重试；② 把 UserMessage(input) 当新输入又发了一遍； ③ 换了个进程/重启后，同一个 (userId, sessionId) 从磁盘读回了「等待中」的状态。
改成
按错误里的提示做：从 RequireUserConfirmEvent.getToolCalls() 拿原件，包成 ConfirmResult 塞进下一条消息的 Msg.METADATA_CONFIRM_RESULTS。 如果是「上次没答完，这次想重新开始」，清掉该 session 的状态或换 sessionId（第 11 章的 /new 就是干这个的）。
相关章节：08 权限与人机交互 · 事件流版本·11 综合案例 · PERMISSION_ASKING 是结局
6. ConfirmResult references non-ASKING tool call ID: xxx. Expected: [yyy]
你会看到
后半句的 Expected 里列出当前真正挂起的 id，通常只有一个，且和你传的不一样。
因为
恢复是靠 id 精确匹配的。你很可能新造了一个 ToolUseBlock （工具名、参数都一样也没用），或者手里拿的是上一次会话留下的旧 id。
改成
只用事件或结果消息里筛出来的 ASKING 原件。要改参数，用 ToolUseBlock.builder().id(原 id).name(...).input(新参数).build() 重建并保留 id。
相关章节：11 综合案例 · ConfirmResult 必须拿原件·08 · ConfirmResult 的四个字段
7. Duplicate ConfirmResult for tool call ID: xxx / ConfirmResult.toolCall.id must not be empty.
你会看到
同一个 id 被回传了两次，或者 id 是空串。
因为
前者常常是把「结果消息里的 ASKING 工具」和「事件里的工具」合在一起传了； 后者是自己 new ToolUseBlock(...) 时没填 id。
改成
每个挂起的 id 只回一条 ConfirmResult；去重后再发。
相关章节：08 权限与人机交互 · ConfirmResult 的四个字段
8. Pending tool calls exist without results. Enable enablePendingToolRecovery or provide tool results. Pending IDs: [...]
你会看到
没有 ASKING 字样，只有 pending id。
因为
这是「外部工具」那条路：模型调了 externalTool = true 的工具（或 SchemaOnlyTool）， 框架不执行、把调用挂起，等你自己跑完再回填；而你把 enablePendingToolRecovery 关掉了。
改成
要么打开 pending 恢复，要么按 RequireExternalExecutionEvent 的约定把 ExternalExecutionResult 回填进去。别在「外部工具」状态下手动再发一条普通用户消息。
相关章节：10 两种入口 · 陷阱 3：中断后同 session 重试
9. 被拒绝后模型反复重试
你会看到
你回了 n，模型换个说法又调一次 delete_note，来回好几轮。
因为
拒绝时没写 reason，模型只看到默认文案「Permission denied by user」，不知道你是误操作还是永久禁止， 只能换个说法再试一次。顺带纠正一个常见误解：stopOnReject 在 2.0.4 里只被赋进 ReactConfig， 主循环没有任何读取点，写了也不会「一拒就停」。
改成
用 new ConfirmResult(false, call, null, "用户拒绝，请不要重试") 把意图写清楚； 真要「全拒就停」，用中间件：onActing 里识别 AllToolsDeniedEvent，再在流尾接一个 RequestStopEvent（第 09 章的「我想…」表里就是这一行）。
相关章节：08 · 拒绝之后模型看到什么·stopOnReject 设了没人读

工具

10. IllegalArgumentException: Tool not found: xxx（自己抛的）
你会看到
堆栈指向 Toolkit.addToolToGroup 或 Toolkit.updateToolPresetParameters。
因为
这是配置错误，不是模型乱调工具：你往一个分组里加工具、或改预设参数时，那个工具还没注册 / 名字拼错。
改成
先 toolkit.getToolNames() 把真实名字打出来核对。工具名以 @Tool(name = "...") 为准，没写 name 才用方法名。
相关章节：06 工具系统 · 建组、归组、开 meta tool
11. 很常见 模型调了一个不存在的工具
你会看到
事件流里出现 [tool] get_weather -> ERROR，结果内容是第一行 Tool not found: get_weather。不会抛异常。
因为
框架把它当成一次「工具执行失败」写回上下文，让模型有机会换方案。真正的根因通常是：工具没注册、被工具分组隐藏了、或者名字和 schema 不一致。
改成
对照 getToolNames() 和当前激活的分组（getActiveGroups()）。注意：同名工具后注册的会静默覆盖前面的，不报错——两个类都写了 @Tool(name = "search") 时，只有一个生效。
相关章节：06 工具系统 · 一次工具调用的 9 件事
12. IllegalStateException: Failed to create converter from @Tool annotation
你会看到
堆栈里带着 Caused by，通常指向你的方法签名。
因为
返回值类型没有可用的转换器：传了泛型擦除后信息不全的类型、返回了一个既不是 String 也不是可序列化 POJO 的对象，或者参数类型不支持生成 JSON Schema。
改成
先用 String 返回人话（这也是第 11 章 NotesTools 的做法），确实要结构化就返回简单 POJO / Map。
相关章节：06 工具系统 · 返回值怎么变成 ToolResultBlock
13. 工具抛异常，模型收到一串 InvocationTargetException
你会看到
ToolResultState.ERROR，结果文本是 Tool execution failed: <cause message>； 框架会解包 InvocationTargetException，通常不含反射类名。
因为
工具方法声明了 throws 并真的抛了受检异常，框架用反射调用后包装了一层。
改成
在工具内部 try/catch，把失败翻译成一句人和模型都能懂的话返回： return "写入失败：" + e.getMessage();。这样模型还有机会换方案。
相关章节：06 工具系统 · 兜底：异常变 error 结果

状态与存储

14. IllegalArgumentException: sessionId must not be blank
你会看到
堆栈指向 JsonFileAgentStateStore 或 InMemoryAgentStateStore。
因为
调用时既没给 RuntimeContext 的 sessionId，builder 里也没配 defaultSessionId； 此时会回退到 name，再回退到 "ReActAgent"，通常不会空白。只有显式 name("") 或直接调 getAgentState(userId, null) 这类路径才会触发。
改成
给一个稳定的 id：RuntimeContext.builder().userId("local").sessionId("cli").build()， 或者在 builder 上 .defaultSessionId("cli")。
相关章节：07 记忆与上下文 · 不传 sessionId 会怎样·02 · RuntimeContext 与 sessionId
15. ConcurrentSessionModificationException: Concurrent modification of session state (userId=..., sessionId=..., key=agent_state, expectedVersion=...)
你会看到
另一个副本/进程刚好也在写同一个会话，其中一个成功，另一个拿到这个异常。
因为
你把 conflictPolicy 设成了 FAIL，而乐观锁版本对不上。APPEND_MERGE 也可能在合并重试后失败。
改成
先问自己「同一个 session 会不会被两个实例同时写」。会：要么在网关层按 session 粘性路由，要么接受 OVERWRITE（后写覆盖）， 要么用 APPEND_MERGE 并确保压缩/摘要轮次不走这条路——它不适合会重写历史的轮次。
相关章节：07 记忆与上下文 · 并发与隔离（ConflictPolicy）
16. 不报错，但「重启就失忆」
你会看到
进程内聊得很好，重启后模型完全不记得刚才说过什么。没有任何异常。
因为
两种情况：① 没配 stateStore，状态只在内存；② 每次都新建不同的 sessionId（比如拿时间戳当 id）， 每次都是新会话。
改成
配 JsonFileAgentStateStore（或 Redis / MySQL），并把 (userId, sessionId) 固定下来。 验证方法：退出重进，问「我刚才让你记了什么」。
相关章节：07 记忆与上下文 · 一次 call 从加载到落盘
17. 状态目录里出现看不懂的目录名
你会看到
state/5L2g5aW9/... 这样的路径，而不是你的 userId 原文。
因为
JsonFileAgentStateStore 会把带特殊字符的 userId / sessionId 做 Base64-URL 安全编码， 避免路径穿越和非法字符。
改成
不用改。想肉眼可读就用纯 ASCII 的 id；~/.notes-agent/state/local/cli/ 这种就能原样保留。
相关章节：07 记忆与上下文 · 目录布局与 Base64 编码

Reactor 与响应式

18. 很常见 block()/blockFirst()/blockLast() are blocking, which is not supported in thread reactor-http-nio-2
你会看到
一到 .block() 或 .blockLast() 就炸，堆栈里全是 Reactor 的调度器。
因为
你正跑在 Reactor 的非阻塞线程上（WebFlux controller、SSE handler、某个 publishOn 之后）， 而 block 会占住这个只能容纳少量线程的线程池。
改成
① 返回 Mono / Flux 让框架订阅，不要在中间 block；② 真必须同步，就 .subscribeOn(Schedulers.boundedElastic()) 挪到弹性线程池；③ 命令行程序里在 main 线程 block 是安全的。
相关章节：03 响应式必修 · 陷阱 2：doOnNext 里 block()
19. TimeoutException: Did not observe any item or terminal signal within 300000ms
你会看到
一次调用卡 5 分钟后失败，共 3 次尝试（1 次首发 + 2 次重试）还是一样。
因为
模型默认的 ExecutionConfig 是「5 分钟超时 + 3 次尝试」，工具是「5 分钟 + 1 次」。超时被算作可重试错误，所以你会看到三次。
改成
长回答 / 慢模型用 .modelExecutionConfig(ExecutionConfig.builder().timeout(Duration.ofMinutes(2)).maxAttempts(2).build()) 明确写出来； 先确认不是网络代理拦住了请求。
相关章节：05 模型层 · 重试与降级（5 分钟超时）
20. 异常被包成 reactor.core.Exceptions$ReactiveException
你会看到
真正的错误信息躲在 getCause() 里，日志看起来像框架乱抛。
因为
Reactor 会把回调里的受检异常包装一层再往下传。
改成
用 reactor.core.Exceptions.unwrap(e) 拆开再判断类型；打印日志时打 unwrap 之后的结果。
相关章节：03 响应式必修 · 陷阱与窍门（异常处理）
21. 什么都没发生：不报错、也不输出
你会看到
agent.call("...") 这一行执行完了，但模型没被调用。
因为
Mono / Flux 是冷流：不订阅就不执行。忘记 .block()、 .subscribe() 或返回给框架，就什么都不会发生。
改成
同步场景 .block()；异步场景 .subscribe(...) 并把返回的 Disposable 管好；Web 场景直接返回 Mono。
相关章节：03 响应式必修 · 冷流不订阅就不执行

模型 HTTP 与参数

22. HTTP 401 / AuthenticationException
你会看到
消息里带 401 和响应体片段，例如 Incorrect API key provided。
因为
key 错、过期，或者读的是另一个环境变量名（OpenAI 是 OPENAI_API_KEY，DashScope 是 DASHSCOPE_API_KEY）。
改成
换 key 后重启进程；别把 key 写进代码或提交到仓库。
相关章节：02 第一个 Agent · 设一个 API Key
23. HTTP 429 或 5xx
你会看到
共 3 次尝试（1 次首发 + 2 次重试）后失败，错误里带状态码；日志里能看到退避间隔从 2 秒涨到 30 秒。
因为
限流或服务端抖动，都属于可重试错误。
改成
降并发、加长 maxBackoff，或者换 fallbackModel。别把 maxAttempts 调到很大——重试也是有成本的。
相关章节：05 模型层 · 哪些错误才会重试
24. HTTP 400：模型不支持 tools / response_format
你会看到
400，消息里提到 tools、tool_choice 或 response_format 不支持。
因为
你用的模型不支持工具调用，或 provider 不支持原生结构化输出。结构化输出会先试原生路径，失败后回退到「合成工具」路径——但工具本身不支持就没救了。
改成
换支持 tools 的模型；结构化输出遇到这类 400 时，框架已经会自动回退，不要去手动关掉。
相关章节：05 模型层 · 结构化输出与合成工具回退

Hook、中间件与 Harness

25. Hooks must not inject SYSTEM messages into PreCallEvent.inputMessages. Use event.setSystemMessage() ...
你会看到
在 onEvent(PreCallEvent) 里往消息列表塞了 SystemMessage 之后抛这个。
因为
消息列表的「尾巴」会被持久化进记忆，SYSTEM 消息一旦进去就会越积越多。
改成
改用 event.setSystemMessage(...) 或 event.appendSystemContent(...)，让框架把它放在正确的位置。
相关章节：09 Middleware 与 Hook · Hook 整包废弃
26. Agent returned null message
你会看到
调用结束时报这个错，堆栈在 AgentBase.notifyPostCall。
因为
某个 Hook 在 PostCallEvent 里把最终消息改成了 null，或者你的 doCall 返回了空流。
改成
Hook 里只做「修改」不做「清空」；自定义 agent 时确保最终有一个 Msg。
相关章节：09 Middleware 与 Hook · PostCall 能改最终 Msg
27. IllegalArgumentException: workspace path must not be blank（Harness）
你会看到
构建 HarnessAgent 时抛，指向 HarnessAgent.Builder.workspace。
因为
.workspace("") 或 .workspace(" ")。
改成
给一个真实目录，优先绝对路径：.workspace(home.resolve("workspace"))。相对路径会按进程工作目录解析，IDEA 里和命令行里可能不是同一个地方。
相关章节：12 工作区与文件系统 · workspace 不能空白
28. IllegalArgumentException: maxIters must be > 0 / maxRetries must be > 0
你会看到
构建阶段直接失败，不用等到调用。
因为
把上层配置（比如 yml 里的 0 或负数）原样传了进来。
改成
做一次兜底：Math.max(1, configured)；同时检查是不是把「不限制」误写成了 0——框架里没有「0 表示无限」的约定。
相关章节：10 两种入口 · 触顶：多调一次模型写总结·05 模型层 · maxRetries 不是「重试 3 次」
29. IllegalStateException: At least one agent must be registered via agent(...)
你会看到
GatewayBootstrap.builder().build() 时直接抛，堆栈停在 build()。
因为
只写了 .channel(...) 或 .distributedStore(...)，一个 agent 都没注册。
改成
至少加一个 .agent("main", agent)（或 lambda 版 .agent("main", b -> ...)）。
相关章节：18 网关、渠道与异步 · GatewayBootstrap 装配
30. IllegalStateException: mainAgent('sales') not found in registered agents
你会看到
同上，在 build() 阶段抛出，括号里就是你写的那串名字。
因为
.mainAgent("sales") 用的是注册时的 key（agent(String, ...) 的第一个参数），而注册表里没有这个 key。
改成
核对 key 的拼写与大小写——agent(...) 只有「key + 实例」与「key + lambda」两种重载，没有单参实例版；不写 .mainAgent(...) 时取第一个注册的（按插入顺序），不会报错但可能指错 agent。

31. IllegalStateException: ChatUiChannel has no gateway. Use GatewayBootstrap.chatUiChannel(), or construct with ChatUiChannel.create(gateway).
你会看到
调 send(...) / sendToSubagent(...) 时抛，而构造对象本身不报错。
因为
ChatUiChannel 的 gateway 字段必须由外部注入；resolveGateway() 发现为 null 就抛。
改成
走 gw.chatUiChannel(config) 或 ChatUiChannel.create(gateway)；单 agent 场景直接用 agent.channel(ChatUiChannel.perPeer())。

三步定位法：表里没有的错怎么办

  1. 第一步：先确定它属于「异常」还是「结束原因」
    把结果消息的 getGenerateReason() 打出来。是 PERMISSION_ASKING / MAX_ITERATIONS / TOOL_SUSPENDED 就不是 bug，是流程问题；真的是异常，再往下走。
  2. 第二步：把事件流打开，看它停在哪一类事件
    streamEvents(...).doOnNext(ev -> System.out.println(ev.getType()))，先看最后一条事件是 MODEL_CALL_*、TOOL_* 还是 REQUIRE_USER_CONFIRM。 停在不同家族，排查方向完全不同（模型/网络 vs 工具/参数 vs 权限）。
  3. 第三步：解包 + 最小复现
    用 Exceptions.unwrap(e) 找到真正的异常类，再按类名回源码搜 throw new 该类，直接看到抛出的那一行和它的判断条件。 然后把上下文缩到「一个工具 + 一句输入 + 内存存储」，能复现就基本定位了。
两个不花钱的调试开关

① 把日志级别开到 DEBUG，框架里大量关键分支都有 logger.debug/info（比如工具注册、CAS 冲突、确认恢复）； ② 先换成 InMemoryAgentStateStore 再试——如果换了就不报错，问题几乎一定在「持久化状态和新代码不匹配」上。
