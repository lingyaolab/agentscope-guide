06 · 工具系统

模型只会说话，工具才是它伸向世界的手。这一章解决四件事：怎么把一个 Java 方法写成模型能正确调用的工具、五条注册路径怎么选、一次工具调用在框架里到底走了哪几步、以及工具多了以后怎么用分组和 MCP 管住上下文。

读完你能做到

  • 用 @Tool / @ToolParam 写出 schema 正确的工具，并说清哪些参数是给模型的、哪些是框架注入的
  • 在「注解扫描 / ToolBase / 只给 schema / MCP / 子 Agent」五条注册路径里选对一条
  • 画出一次 tool call 从模型吐 JSON 到结果回填的完整链路，并解释工具报错为什么不会中断对话
  • 用 ToolGroup + meta tool 做按需披露，接一个 MCP server 并知道它真实的命名规则

先说为什么：工具不是「函数」，是给模型看的说明书

写普通 Java 方法时，调用者是你：参数类型编译期就检查，异常自己 try-catch。工具不一样——调用者是一个从没看过你源码的模型，它只能看到 name、description 和一段 JSON Schema，然后决定调不调、传什么。

普通方法：给人用

  • 谁调用：你的代码，调用点固定
  • 参数：编译期检查，IDE 会提示
  • 返回值：你自己消费
  • 失败：抛异常，调用栈往上冒
  • 重点在实现

工具：给模型用

  • 谁调用：模型在运行时决定，可能根本不调
  • 参数：模型生成 JSON，框架按 schema 校验后再反射填充
  • 返回值：序列化后当成消息喂回模型
  • 失败：转成 ToolResultBlock.error，对话继续
  • 重点在描述与 schema，实现反而简单

所以这一章会反复出现一个判断标准：这段代码是写给模型看的，还是写给 JVM 看的？ description、参数名、枚举值、返回文本都是写给模型的；类型转换、并发、超时、重试是 JVM 和框架的事。两者混在一起想，就会写出「能编译但模型永远调不对」的工具。

最小可跑：三个注解，让 Agent 自己选工具

先不碰 MCP、不碰分组，只写一个最普通的类：

import io.agentscope.core.tool.Tool;
import io.agentscope.core.tool.ToolParam;

public class WeatherTools {

    @Tool(
            name = "get_weather",
            description = "查询指定城市的当前天气。用户问气温、下雨、穿衣建议时调用。",
            readOnly = true)
    public String getWeather(
            @ToolParam(name = "city", description = "城市名，例如 杭州") String city,
            @ToolParam(name = "unit", description = "温度单位：c 或 f", required = false) String unit) {
        double celsius = "杭州".equals(city) ? 24.5 : 18.0;
        boolean fahrenheit = unit != null && unit.equalsIgnoreCase("f");
        double value = fahrenheit ? celsius * 9 / 5 + 32 : celsius;
        return String.format("%s：%.1f°%s", city, value, fahrenheit ? "F" : "C");
    }
}

注册只需要一行，然后把 toolkit 交给 agent：

先看 schema，再调模型

调试工具时最省时间的一步：注册完立刻打印 toolkit.getToolSchemas().get(0).getParameters()。模型看到的就是这段 JSON；如果参数没出现、类型不对、必填项不对，模型再聪明也调不对。

逐行解读：注解、参数、返回值

1. @Tool 的 11 个属性（文档只列了 7 个）

属性默认值作用与容易踩的点
name方法名暴露给模型的工具名。建议 snake_case；不写就用方法名。
description"Tool: " + name模型判断「什么时候调」的唯一依据。不写会得到一个毫无信息量的默认串。
strictfalse为 true 时把 strict 放进 schema，支持的服务商会更严格地约束参数。
readOnlyfalse声明无副作用。EXPLORE 模式下只读工具自动放行（第 08 章）。
concurrencySafetrue是否可并发调用。文档表格写的是 false，代码里是 true；要串行执行必须显式写 false。

dangerousDirectories{}追加敏感目录名，按路径段匹配。

全部定义：Tool.java:70；concurrencySafe 默认值：Tool.java:117；returnDirect 语义：Tool.java:140

2. @ToolParam 与「参数三分法」

@ToolParam 只有三个属性，但有一个硬约束：name() 没有默认值，不写就编译不过。原因写在注释里——Java 默认不保留参数名（除非加 -parameters），框架不能靠反射名去猜。

属性默认值说明
name无（必填）写进 schema 的属性名，也是从模型 JSON 里取值的 key。
description""写清楚格式和取值范围，比在方法里做二次校验更有效。
requiredtrue为 false 时，模型可以省略；方法会收到 null（对象）或默认值（基本类型）。

真正决定「参数从哪来」的不是注解本身，而是参数类型 + 有没有注解。框架的判断顺序是这样的：

参数长什么样从哪来会不会出现在 schema
带 @ToolParam模型生成的 JSON会
ToolEmitter框架注入（流式进度）不会
Agent / AgentState / RuntimeContext框架注入不会
用户自定义 POJO（无注解）RuntimeContext.get(类型)不会
基本类型 / String / Msg / ContentBlock，且没注解仍按参数名去 JSON 里取——但 schema 里没有它不会，所以通常永远是 null

注入顺序与用户 POJO 判定：ToolMethodInvoker.java:149、:218；AgentState 参数的三条校验：ReflectiveFunctionTool.java:84

自定义 POJO 的用法很实用：调用方按类型放进去，所有需要它的工具都能拿到，而且模型完全看不到这个参数。

import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.tool.Tool;
import io.agentscope.core.tool.ToolParam;

public record UserContext(String username, String locale) {}

public class GreetingTools {

    @Tool(name = "greet", description = "用当前用户名向用户打招呼。")
    public String greet(
            @ToolParam(name = "greeting", description = "问候语，例如 你好") String greeting,
            UserContext user) {                 // 无 @ToolParam → 由 RuntimeContext 注入
        String who = user == null ? "访客" : user.username();
        return greeting + "，" + who + "！";
    }
}
RuntimeContext ctx =
        RuntimeContext.builder()
                .put(UserContext.class, new UserContext("alice", "zh-CN"))
                .userId("alice")
                .build();

agent.call("跟我打个招呼", ctx).block();

3. 返回值怎么变成 ToolResultBlock

默认转换器（DefaultToolResultConverter）的规则只有五条，记住就不会意外：

方法返回值最终回给模型的文本
null字符串 "null"
void字符串 "Done"
本来就是 ToolResultBlock原样返回（想完全控制输出就返回它）
任意 POJO / List / MapJSON 字符串
序列化失败退化成 toString()，并打一条 warn 日志

转换规则：DefaultToolResultConverter.java:44；方法支持 String、Mono、CompletableFuture 三种返回形态：ToolMethodInvoker.java:69

想截断或脱敏，不必改方法，写一个转换器挂到注解上即可：

import io.agentscope.core.message.ToolResultBlock;
import io.agentscope.core.tool.ToolResultConverter;
import java.lang.reflect.Type;

public class ShortTextConverter implements ToolResultConverter {

    @Override
    public ToolResultBlock convert(Object result, Type returnType) {
        String text = String.valueOf(result);
        String clipped = text.length() > 200 ? text.substring(0, 200) + "…" : text;
        return ToolResultBlock.text(clipped);
    }
}
@Tool(
        name = "fetch_page",
        description = "抓取网页正文，返回前 200 个字符。",
        converter = ShortTextConverter.class)
public String fetchPage(@ToolParam(name = "url", description = "完整 URL") String url) {
    return httpGet(url);
}

4. 一个容易忽略的扫描范围

registerTool(Object) 用的是 getClass().getDeclaredMethods()——只扫本类声明的方法，父类里的 @Tool 不会被继承注册。把公共工具方法抽到基类后，记得在子类要么重新声明，要么直接注册基类实例。

扫描实现：Toolkit.java:188

端到端：五条注册路径，选一条就够

工具最终都进同一个注册表，但入口有五种，差别在「schema 谁写」和「执行谁做」：

路径入口schema 来源执行适合
注解扫描registerTool(Object)反射方法签名框架反射调用90% 的业务工具
ToolBase / AgentToolregisterTool(...) / registerAgentTool(...)你手写 Map你实现 callAsync要自定义权限、schema 动态生成
只给 schemaregisterSchema(ToolSchema)你手写不执行，返回 suspended外部系统/人工执行的工具
MCPregisterMcpClient(...) 或 registration().mcpClient(...)MCP server 提供MCP client 转发复用现成工具生态
子 Agentregistration().subAgent(...)固定两参数内嵌一个 agent把「专家」封装成工具

带配置时用流式 API toolkit.registration()，它把「注册 + 分组 + 预设参数 + MCP 过滤」收进一个链式调用： 

import io.agentscope.core.tool.Toolkit;
import java.util.Map;

Toolkit toolkit = new Toolkit();

toolkit.registration()
        .tool(new DatabaseTools())
        .group("database")
        // preset 参数不会出现在 schema 里，执行时强制覆盖模型给的值
        .presetParameters(Map.of("db_query", Map.of("tenant", "acme")))
        .apply();

registration()：Toolkit.java:151；apply() 的四种分支与互斥校验：Toolkit.java:1237

预设参数是「覆盖」，不是「默认值」

ToolExecutor 合并输入的顺序是「模型参数 → 预设参数」，后者用 putAll 直接盖掉前者ToolExecutor.java:269。所以 tenant 这类参数适合放租户身份、API key、固定目录——不要拿它做「用户可以改的默认值」，模型改不动。

注册表内部只做四件事，顺序固定：

  • 注册
    把对象变成 AgentTool：注解式包成 ReflectiveFunctionTool，ToolBase 子类直接用。
  • 建 schema
    只收集带 @ToolParam 的参数；泛型交给 JsonSchemaUtils；嵌套类型的 $defs 会被提升到根节点。
  • 存表
    ToolRegistry.registerTool(name, ...)——底层是 Map.put，同名直接覆盖，不报错。
  • 取用
    Agent 构建时 toolkit.copy() 复制注册表；每次推理按当前会话的激活组过滤出 List<ToolSchema>。

schema 生成：ToolSchemaGenerator.java:59；同名覆盖：ToolRegistry.java:52；构建期复制：Toolkit.java:946

端到端：一次工具调用，框架替你做了 9 件事

  • 模型
    在回复里给出 tool_calls：工具名 + 一段 JSON 参数，框架把它解析成 ToolUseBlock。
  • 权限
    权限引擎给出 ALLOW / ASK / DENY；只有放行的调用才继续（第 08 章展开）。
  • 合并配置
    ExecutionConfig 按「Agent 级 > Toolkit 级 > TOOL_DEFAULTS」合并，得到超时与重试预算。
  • 排序
    并行为 true 时，连续的 concurrencySafe 工具并发执行，不安全的单独占一个串行槽位；最终顺序与模型给出的一致。
  • 查找
    按名字取工具；取不到 → 直接返回 ToolResultBlock.error("Tool not found: ...")，不抛异常。
  • 校验
    激活组检查（未激活 → Unauthorized tool call）+ JSON Schema 校验；可选参数里的显式 null 会先被剪掉。
  • 执行
    外部工具 → 返回 suspended；否则合并预设参数、注入上下文，调 callAsync 或反射方法。
  • 兜底
    业务异常 → error 结果；ToolSuspendException → suspended；空返回 → error 结果。超时、重试、停机守卫都在这一层。
  • 回填
    Agent 侧推导最终状态（SUCCESS / ERROR / RUNNING），写进消息与历史，下一轮推理喂回模型。

执行核心：ToolExecutor.java:201；并行分槽：:405；INFRA（超时/重试/停机）：:472

工具失败不会炸掉整轮对话，这是设计而不是巧合

executeWithInfrastructure 最后有一个 onErrorResume：任何漏出来的异常都会被包成 ToolResultBlock.error("Tool execution failed: ...") 并带上 tool idToolExecutor.java:481。ReActAgent 那层还会再兜一次，保证每个 ToolUseBlock 都有配对的 ToolResultBlock——否则历史里会出现「有调用没结果」的坏状态。

工具默认不重试

这是与模型调用最大的差别：模型默认 maxAttempts=3，工具的 TOOL_DEFAULTS 是 5 分钟超时 + 1 次尝试。而且要注意：工具方法自己抛的异常在 executeCore 里已经被转成「正常的 error 结果」，不再是错误信号，所以即使你调大 maxAttempts，业务异常也不会触发重试；只有超时这类真正以 error 信号结束的情况才会重试。

工具默认值：ExecutionConfig.java:163；重试只作用于错误信号：ToolExecutor.java:514

工具分组：把「上下文预算」当回事

工具一多，最先撑爆的不是显存，是上下文：每个工具都要把 name、description、JSON Schema 塞进系统提示，二十个工具就是几千 token，模型还更容易选错。分组解决的就是这件事——默认只给常驻工具，其余按需披露。

不分组

  • 注册即常驻，每一轮都在 schema 里
  • 工具少于 8 个时最省事
  • 工具多起来只能靠超长 description 硬撑区分度

分组 + meta tool

  • 组没激活 → schema 里根本不出现，模型不知道有这个能力
  • 模型自己调 reset_equipped_tools 开关
  • 按业务域切（数据库 / 工单 / 计费），适合 8 个以上

关键机制只有一句：没归组的工具视为常驻；归了组的工具，只有所属组处于激活状态时才会进 schemaToolSchemaProvider.java:83。上一章说的「每轮推理前按激活组过滤」就是指这一段。

1. 建组、归组、开 meta tool

import io.agentscope.core.ReActAgent;
import io.agentscope.core.tool.Toolkit;

Toolkit toolkit = new Toolkit();

// ① 建组：名字 + 给模型看的描述 + 默认是否激活
//    两参/三参重载的 scope 都是 META（模型可通过 meta tool 管理）
toolkit.createToolGroup("database", "查库：表结构、只读 SQL、慢查询分析", false);

// ② 注册时归组；不写 .group() 就是常驻工具
toolkit.registration()
        .tool(new DatabaseTools())
        .group("database")
        .apply();

// ③ 打开 meta tool，模型才有开关组的手段
ReActAgent agent =
        ReActAgent.builder()
                .name("DBAssistant")
                .sysPrompt("需要查库时先激活 database 工具组。")
                .model("dashscope:qwen-plus")
                .toolkit(toolkit)
                .enableMetaTool(true)
                .build();

2. 模型看到的是什么

enableMetaTool(true) 会往注册表里塞一个名为 reset_equipped_tools 的工具MetaToolFactory.java:51。它只有一个参数 to_activate，类型是字符串数组，枚举值只列出 META 域里的组名——模型没法激活一个你没建的组。 

{
  "name": "reset_equipped_tools",
  "arguments": { "to_activate": ["database"] }
}
  • 首轮
    schema 里只有常驻工具 + reset_equipped_tools；database 组的工具一个都不出现。
  • 模型
    判断「要查库」，调用 reset_equipped_tools，传 ["database"]。
  • 框架
    把这次激活写进本会话的 ToolContextState，返回一段文本告诉模型现在激活了哪些组。
  • 次轮
    重新取 schema，这次带上了 database 组——模型才第一次看见 db_query 这些工具名。
组的 description 会变成给模型的指令

激活成功后，meta tool 会把每个组的 description 包进 <tool-instructions> 一起返回MetaToolFactory.java:190。所以别写「数据库工具」这种废话，写「什么场景该用、什么场景别用」，这是你唯一能影响模型取舍的地方。

to_activate 是「最终清单」，不是「增量」

它走的是替换语义：replaceActivatedGroups 会把你没列出来的 META 组全部关掉MetaToolFactory.java:169。传空数组 [] 等于「把 META 组全关」。这跟很多人直觉里的「激活一个」正好相反，写系统提示时要提醒模型一次列全。

3. META 与 EXTERNAL：谁有权动这个组

ToolGroupScope 在 2.0.4 里只有两个值，没有 SESSION、没有 GLOBAL：

scope谁管理进 meta tool 的 enum被 reset_equipped_tools 影响
META（默认）模型，经 meta tool是是：不在清单里的全被关掉
EXTERNAL你的代码否否：模型既看不见也改不了

枚举定义与语义注释：ToolGroupScope.java:29；EXTERNAL 组被校验拦下：MetaToolFactory.java:154 

import io.agentscope.core.tool.ToolGroup;
import io.agentscope.core.tool.ToolGroupScope;

// ① 直接建一个 EXTERNAL 组：模型看不见它，也就关不掉它
toolkit.createToolGroup(
        "billing", "计费工具，仅在结算会话中由代码开启", false, ToolGroupScope.EXTERNAL);

// ② 需要自己持有 ToolGroup 对象（比如继承做自定义组）时走 builder + registerToolGroup
toolkit.registerToolGroup(
        ToolGroup.builder()
                .name("reports")
                .description("报表导出")
                .active(false)
                .scope(ToolGroupScope.EXTERNAL)
                .build());

ToolGroup 没有 public 构造器，只能 builder：ToolGroup.java:59；builder 默认 active=true / scope=META：ToolGroup.java:187

分组这块有三处文档和代码对不上

① 文档里写 ToolGroupScope.SESSION——不存在，只有 META / EXTERNAL；
② 文档里用 new ToolGroup(name, desc, scope, false)——构造器是 protected，编译不过，要用 ToolGroup.builder() 或 toolkit.createToolGroup(...)；
③ 文档说 registerTool(Object) 会把工具放进 "basic" 组——全仓库没有 "basic" 这个组名，不归组就是常驻。

最后一个容易踩的点：updateToolGroups(List, boolean) 是旧版单会话 API，改的是共享的激活标记，多会话并发时会互相污染Toolkit.java:792。真正的按会话隔离靠 AgentState 里的 ToolContextState——这也是为什么手动调 reset_equipped_tools 时如果 RuntimeContext 里没有 AgentState，它会直接返回 Error: reset_equipped_tools requires a per-session runtime context，而不是退回去改共享状态MetaToolFactory.java:162。

顺便记住激活组检查的报错文本：工具存在但组没激活，ToolExecutor 返回的是 Unauthorized tool callToolExecutor.java:221，不是 Tool not found。看到前者去查分组，别去查注册代码。两种错在 附录 B · 模型调了不存在的工具 有对照。

MCP：把别人的工具服务器挂进来

MCP（Model Context Protocol）是「工具服务」的标准协议：server 端暴露一堆工具，client 端把它们翻译成 AgentTool。对框架来说 MCP 工具和你手写的工具在注册表里没有区别——同样进 schema、同样走上面那 9 步，区别只在 callAsync 里做的是网络请求或子进程通信。

传输builder 方法典型场景生命周期
StdIOstdioTransport(command, args...)本地 MCP server（npx / python / 自己的 jar）框架拉起子进程，close() 时结束
SSEsseTransport(url)有状态的长连接 HTTP server连接常驻，适合需要推送的 server
StreamableHTTPstreamableHttpTransport(url)无状态 HTTP server，最容易水平扩展每请求独立

1. 本地 server：四行接进来

import io.agentscope.core.tool.mcp.McpClientBuilder;
import io.agentscope.core.tool.mcp.McpClientWrapper;

McpClientWrapper filesystem =
        McpClientBuilder.create("filesystem")
                .stdioTransport(
                        "npx", "-y", "@modelcontextprotocol/server-filesystem", "D:/tmp")
                .buildSync();          // 也可以 buildAsync().block()

// 注册时框架会自己 initialize() + listTools()，你不用手动连
toolkit.registerMcpClient(filesystem).block();

create：McpClientBuilder.java:119；stdioTransport：:133；buildSync：:542；注册即初始化 + 列举工具：McpClientManager.java:246

Windows 上 stdio 的第一个参数

stdioTransport 拼的是真实进程，Windows 下 npx / pnpm 这类脚本通常要写成 npx.cmd，否则会收到「找不到命令」。报错发生在 registerMcpClient(...).block() 那一刻，不是编译期。

2. 远程 server：过滤、加前缀、归组

import io.agentscope.core.tool.Toolkit;
import java.time.Duration;
import java.util.List;

Toolkit toolkit = new Toolkit();
toolkit.createToolGroup("remote", "公司内网 MCP 工具：工单查询与创建", false);

McpClientWrapper remote =
        McpClientBuilder.create("corp-mcp")
                .streamableHttpTransport("https://mcp.example.com/http")
                .header("Authorization", "Bearer " + System.getenv("MCP_TOKEN"))
                .timeout(Duration.ofSeconds(60))
                .buildSync();

toolkit.registration()
        .mcpClient(remote)
        .enableTools(List.of("search_ticket", "get_ticket"))   // 留空/不写 = 全开
        .mcpToolNamePrefix("corp_")                             // 默认是空串
        .group("remote")
        .apply();

apply() 内部对 MCP 分支是 registerMcpClient(...).block()，所以这一步是同步且会真的去连的Toolkit.java:1264。放在应用启动路径上时要给它包一层 try-catch——server 挂了不该让整个服务起不来。

3. 四个容易误判的细节

细节真实行为
工具名toolNamePrefix + mcpTool.name()，没有 mcp__{server}__{tool} 这种命名空间，默认前缀是空串
同名冲突底层 Map.put，后注册的静默覆盖，不报错不打日志
只读判定取 server 返回的 annotations().readOnlyHint()；只读工具权限层放行，其余默认 ASK
并发McpTool 固定 concurrencySafe(false)，所以 MCP 调用永远串行——即使 ToolkitConfig 开了并行

命名与前缀：McpClientManager.java:307；readOnlyHint：:300；固定不可并发：McpTool.java:114；权限 allow/ask：:194

多 server 场景一定加前缀，否则工具会凭空消失

两个 server 都有 search 时，后注册的那个把前一个直接覆盖（ToolRegistry.registerTool 就是一次 tools.putToolRegistry.java:52）。现象是：你明明接了两个 server，getToolSchemas() 里却只有一个 search，而且描述来自不是你预期的那台。

还有一个安全开关值得知道：默认情况下 RuntimeContext 里登记的 McpMeta 和本次调用的 tool-call id 会作为 meta 字段发给 server。接第三方不可信 server 时，在注册处加 .propagateMeta(false)，整条连接就不再外发元数据；也可以只对单个工具关（propagateMeta("toolName", false)）。三层是逻辑与：工具级 > 注册级 > 连接级，连接级是实时读取的，改一次立刻对已注册工具生效。

陷阱与窍门

1. 参数没加 @ToolParam，运行时永远是 null
你会看到
方法能跑，但 String type 这个参数总是 null，模型说「我传了」。
因为
schema 只收集带 @ToolParam 的参数，没有它的参数根本不在 schema 里，模型没地方填。
改成
凡是该由模型给的参数，一律写 @ToolParam(name = ..., description = ...)；改完先打印 toolkit.getToolSchemas() 核对。
2. 同名工具静默覆盖
你会看到
注册了 6 个工具，模型只看到 5 个；或者某个工具的行为跟源码对不上。
因为
ToolRegistry 底层是 Map.put，同名直接覆盖，不校验、不打日志。
改成
工具名加业务前缀（crm_search / kb_search）；启动时打一遍全部工具名做查重，这是最便宜的防线。
3. 以为 maxRetries 管工具
你会看到
模型调用配了重试，工具却不重试；调大之后还是不重试。
因为
工具走自己的 TOOL_DEFAULTS（5 分钟 + 1 次尝试）；而且业务异常在 executeCore 里已转成正常 error 值，不再是错误信号，Retry 根本收不到。
改成
想在工具内部重试就自己写循环（记得幂等）；只靠框架的话，只有超时这类以 error 信号结束的情况才会被重试。
4. 以为抛异常能中断对话
你会看到
工具里抛了 RuntimeException，可模型下一轮还在继续说话，只是变成了「抱歉工具失败了」。
因为
框架保证每个 ToolUseBlock 都有配对的 ToolResultBlock，异常会被包成 error 结果喂回模型。
改成
要真的停下，用 ToolSuspendException（→ suspended，等外部执行）或让权限层 deny；不要靠抛异常「炸掉」循环。
5. 父类的 @Tool 不会被注册
你会看到
把公共工具方法抽到基类后，子类注册了，但那些工具消失了。
因为
registerTool(Object) 用 getDeclaredMethods()，只扫本类声明的方法。
改成
要么把基类实例也注册一遍，要么在子类重写并重新标注。
6. stateInjected 和方法签名不匹配
你会看到
工具注册那一刻就抛 IllegalArgumentException，agent 起不来。
因为
构建 ReflectiveFunctionTool 时有四条校验：AgentState 参数不能带 @ToolParam、最多一个、开了 stateInjected 必须有、有 AgentState 参数就必须开。
改成
两个方向对齐即可；参考 TodoTools.todoWrite 的写法。

自检三问

下面哪个参数不会出现在 schema 里：String city（带 @ToolParam）、String unit（带 @ToolParam）、AgentState state、int retries（带 @ToolParam）？

只有 AgentState 不会。它是框架按类型注入的，永远不进 schemaToolMethodInvoker.java:149。另外注意题干里的陷阱：int retries 如果不带注解，同样不会进 schema，运行时因为取不到值会落到基本类型的默认值（0），不会报错——这类 bug 最难查。

工具方法里抛了 RuntimeException，这一轮对话会怎样？

不会中断。异常在 executeCore 里被转成带 tool id 的 ToolResultBlock.error，模型看到错误文本后可以换个参数重试、或者向用户解释。所以工具里的报错信息要写给模型看：告诉它错在哪、下次该怎么传，而不是丢一段堆栈。

当前激活的是 [web, database]，模型调 reset_equipped_tools 传 ["database"]，结果是什么？

web 被关闭，只剩 database。这是替换语义而不是增量语义，也是新手最容易误判的一处；传 [] 会把所有 META 组关掉。EXTERNAL 组完全不受影响——它压根不在 to_activate 的枚举里。

20 分钟动手练习

  1. 亲眼看 schema 少了什么
    给 getWeather 加一个不带注解的 String traceId 参数，先打印 toolkit.getToolSchemas() 里 get_weather 的 parameters（确认没有它），再在方法里打印这个参数的值（会是 null）。这比读十遍文档都管用。
  2. 复现一次静默覆盖
    写两个类，各有一个 @Tool(name = "search") 的方法，注册进同一个 toolkit，然后打印 getToolSchemas().size() 和那条 schema 的 description。你会看到只有一个 search，且没有警告——这就是为什么多 MCP server 一定要加前缀。
  3. 跑通一次按需披露
    建一个 database 组（active=false），agent 开 enableMetaTool(true)，用 agent.streamEvents(msg, ctx) 遍历事件ReActAgent.java:1160，把工具名和 tool_calls 里的名字打出来。你应该能看到：第一轮没有组内工具 → 出现 reset_equipped_tools 调用 → 之后才出现组内工具。
