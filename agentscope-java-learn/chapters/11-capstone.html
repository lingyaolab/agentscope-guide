11 · 综合案例：一个能用的命令行笔记 Agent

前面十章都是零件：消息、模型、工具、状态、权限、中间件。这一章把它们装成一台能用的机器——四个文件、 一百多行 Java 的命令行笔记助手：能调工具、能看到流式输出、删笔记前会停下来问你、关掉再打开还记得上次聊了什么。 代码全部按 2.0.4 的签名写，可以直接粘进 Maven 工程跑。

读完你能做到

  • 独立写出一个「工具 + 状态 + 权限 + 流式」四件套齐全的最小 Agent 工程，知道每个文件负责什么
  • 用 streamEvents 同时做三件事：打增量文本、显示工具执行结果、接住 RequireUserConfirmEvent
  • 写对 HITL 闭环：从暂停判定到 ConfirmResult 续跑，中间不丢 ToolUseBlock 原件
  • 让会话跨进程存活：JsonFileAgentStateStore 放进哪个目录、磁盘上长什么样、什么时候会「失忆」
  • 把这个 core 版案例迁到 HarnessAgent，知道要改哪三行、又多拿到什么

先说清楚：这个案例到底做什么

需求只有一句话：在终端里跟一个笔记助手聊天，它能记住你说的话，能读写一个本地文件，删文件前必须问你。 听起来像玩具，但它把 SDK 里最难拼的四块接缝全用上了——工具注册、会话状态、权限确认、事件流。把这四块拼对， 换成真实业务只是把 NotesTools 里的三个方法换掉。 

notes-agent/
├── pom.xml
└── src/main/java/com/example/notes/
    ├── NotesTools.java     
    ├── NotesAgent.java     
    └── Cli.java            

运行后产生（都在用户目录下，不污染项目）：
~/.notes-agent/
├── notes/notes.txt          ← 笔记正文
└── state/local/cli/         ← 会话状态：agent_state.json + memory_messages.jsonl

一次「删笔记」的完整链路长这样，六步里有三步是普通 CRUD 应用里没有的：

  1. 读一行输入
    Cli 从 System.in 读一句「把笔记清空」，连同同一个 RuntimeContext 交给 agent。
  2. 流式跑第一轮
    streamEvents(text, ctx) 持续吐 TextBlockDeltaEvent；模型决定调 delete_note，进入 acting。
  3. 权限引擎拦下
    规则命中 ASK，这一轮以 PERMISSION_ASKING 结束，同时发出 RequireUserConfirmEvent 与携带 ASKING 工具的 AgentResultEvent。
  4. 就地提问
    Cli 读到 reason 是 PERMISSION_ASKING，用 BufferedReader 问一句「允许吗？」——注意这里没有回调、没有阻塞等待，agent 早就返回了。
  5. 带答案再跑一轮
    把 ConfirmResult 塞进新 UserMessage 的 metadata，拿同一个 ctx 再调一次 streamEvents；框架按 id 找到挂起的工具，这次真的执行。
  6. 存盘
    本轮结束后，stateStore 把 AgentState 与消息列表写进磁盘；下次启动同 sessionId，模型能看到上次的上下文。
为什么用 core 而不是 Harness 写这个案例

因为案例要「每一行都看得见源头」。HarnessAgent 会自动挂十几个中间件、一批内置工具和默认落盘， 调试审批回路时分不清是谁在暂停。第 10 章已经讲清两者是同一颗引擎，这里用 ReActAgent 显式装配；最后一节给出换成 Harness 的 diff。

文件二：NotesTools.java——三个工具，一个要审批

工具类就是普通 Java 类，方法上标 @Tool、参数上标 @ToolParam，然后整类注册进 Toolkit。这里刻意做了三个不同性质的工具：写（有副作用但不危险）、读 （幂等）、删（不可恢复，必须问人）。 

package com.example.notes;

import io.agentscope.core.tool.Tool;
import io.agentscope.core.tool.ToolParam;

import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.StandardOpenOption;
import java.util.List;

public class NotesTools {

    private final Path dir;

    public NotesTools(Path dir) {
        this.dir = dir;
    }

    @Tool(name = "write_note", description = "把一条笔记追加到 notes.txt，返回写入的文件路径")
    public String write(@ToolParam(name = "text", description = "笔记正文") String text) {
        try {
            Files.createDirectories(dir);
            Path file = dir.resolve("notes.txt");
            Files.writeString(file, text + System.lineSeparator(),
                    StandardOpenOption.CREATE, StandardOpenOption.APPEND);
            return "已写入 " + file.toAbsolutePath();
        } catch (IOException e) {
            return "写入失败：" + e.getMessage();
        }
    }

    @Tool(name = "list_notes", description = "按行列出 notes.txt 的全部内容；没有笔记时返回 (空)")
    public String list() {
        Path file = dir.resolve("notes.txt");
        try {
            if (!Files.exists(file)) {
                return "(空)";
            }
            List<String> lines = Files.readAllLines(file);
            return lines.isEmpty() ? "(空)" : String.join("\n", lines);
        } catch (IOException e) {
            return "读取失败：" + e.getMessage();
        }
    }

    @Tool(name = "delete_note", description = "删除整个 notes.txt，不可恢复")
    public String delete() {
        Path file = dir.resolve("notes.txt");
        try {
            return Files.deleteIfExists(file) ? "已删除 " + file : "文件本来就不存在";
        } catch (IOException e) {
            return "删除失败：" + e.getMessage();
        }
    }
}

@Tool / @ToolParam 的扫描规则：Toolkit.java:159；工具方法返回值会变成 ToolResultBlock：ToolExecutor.java

工具里自己 catch，别让受检异常飞出去

这三个方法都没有 throws IOException：读写失败一律变成一句人话返回。原因是工具抛出的异常会被框架包成 ToolResultState.ERROR 的结果再喂给模型——能用，但错误信息经过反射包装后往往变成一串 InvocationTargetException，模型看不懂、你也难排查。自己接住并给出可读原因，模型才有机会换方案（比如先建目录再写）。

还有一个设计取舍：write_note 没有做「追加还是覆盖」的参数。工具的参数 schema 越简单， 模型调对的概率越高；需要覆盖时它会先调 delete_note（触发审批）再写，行为反而是安全的。

文件三：NotesAgent.java——五行装配，三个都不能省

装配类的职责只有一个：把所有可变配置集中到一处，让 Cli 只拿到一个建好的 agent。这里最容易被忽略的是 权限上下文：不写 .permissionContext(...) 时，@Tool 默认 PASSTHROUGH，delete_note 会直接执行，根本不会问你。 

package com.example.notes;

import io.agentscope.core.ReActAgent;
import io.agentscope.core.permission.PermissionBehavior;
import io.agentscope.core.permission.PermissionContextState;
import io.agentscope.core.permission.PermissionMode;
import io.agentscope.core.permission.PermissionRule;
import io.agentscope.core.state.JsonFileAgentStateStore;
import io.agentscope.core.tool.Toolkit;

import java.nio.file.Path;

public final class NotesAgent {

    private NotesAgent() {
    }

    public static ReActAgent build(Path home) {
        // 1) 工具：数据目录跟着 home 走，测试时传临时目录即可
        Toolkit toolkit = new Toolkit();
        toolkit.registerTool(new NotesTools(home.resolve("notes")));

        // 2) 权限：默认模式 + 一条「delete_note 永远先问」的规则
        PermissionContextState permission = PermissionContextState.builder()
                .mode(PermissionMode.DEFAULT)
                .addAskRule("delete_note",
                        new PermissionRule("delete_note", null, PermissionBehavior.ASK, "session"))
                .build();

        // 3) Agent：模型、提示词、工具、权限、状态存储
        return ReActAgent.builder()
                .name("notes")
                .sysPrompt("""
                        你是终端里的笔记助手。
                        - 用户要记东西，调用 write_note，把原话整理成一句再写。
                        - 用户问有哪些笔记，调用 list_notes，按原样列出来。
                        - 用户要清空或删除，调用 delete_note；这一步会由用户确认，你不需要再问一遍。
                        回答保持简短；不要编造笔记内容。
                        """)
                .model("dashscope:qwen-plus")
                .toolkit(toolkit)
                .permissionContext(permission)
                .stateStore(new JsonFileAgentStateStore(home.resolve("state")))
                .maxIters(8)
                .build();
    }
}

addAskRule 的签名：PermissionContextState.java:233；stateStore 装配点：ReActAgent.java:5166；JsonFileAgentStateStore 构造器：JsonFileAgentStateStore.java:92

这行配置去掉会怎样为什么是它
.permissionContext(permission)delete_note 直接执行，永不暂停@Tool 默认 PASSTHROUGH，没有规则就没有 ASK 来源
.stateStore(...)进程一退，上下文全丢；重启后同 session 也接不上只有配上存储，AgentState 才跨进程存活
.maxIters(8)默认 10，够用；显式写出来是为了让「一轮对话最多几次推理」有据可查触顶后框架会多做一次摘要调用，不是抛异常
.model("dashscope:qwen-plus")没有模型，build() 直接失败字符串 id 由 ServiceLoader 找到 dashscope provider
sysPrompt 里的「这一步会由用户确认」模型有时会自己先问「你确定吗」，多一轮废话把「谁负责确认」写清楚，模型就不会重复问
PermissionRule 第四个参数 "session" 是什么意思

它是规则的作用域标签，跟着规则一起存进权限上下文；本章只用它做「这条规则属于本会话」的语义标注。 真正让规则长期生效的是把它放进 PermissionContextState（构建时）或通过 ConfirmResult.rules 动态加入（只在当前引擎实例里有效，换模式重建引擎就没了，08 章验证过）。

文件四：Cli.java——REPL、流式、审批，一个循环搞定

这是本章唯一有「逻辑」的文件。它只做三件事：读一行、跑一轮、如果这一轮停在 PERMISSION_ASKING 就地问人再把答案跑一轮。把它拆成三个方法看，每个方法都不超过 30 行。 

package com.example.notes;

import io.agentscope.core.ReActAgent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentResultEvent;
import io.agentscope.core.event.ConfirmResult;
import io.agentscope.core.event.RequireUserConfirmEvent;
import io.agentscope.core.event.TextBlockDeltaEvent;
import io.agentscope.core.event.ToolResultEndEvent;
import io.agentscope.core.message.GenerateReason;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.ToolCallState;
import io.agentscope.core.message.ToolUseBlock;
import io.agentscope.core.message.UserMessage;

import java.io.BufferedReader;
import java.io.IOException;
import java.io.InputStreamReader;
import java.nio.charset.StandardCharsets;
import java.nio.file.Path;
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.concurrent.atomic.AtomicReference;

public class Cli {

    /** 一轮的结果：最终消息 + 这一轮里被挂起的工具调用 */
    record Round(Msg msg, List<ToolUseBlock> asking) {
        boolean paused() {
            return msg != null && msg.getGenerateReason() == GenerateReason.PERMISSION_ASKING;
        }
    }

    public static void main(String[] args) throws Exception {
        Path home = Path.of(System.getProperty("user.home"), ".notes-agent");
        RuntimeContext ctx = RuntimeContext.builder().userId("local").sessionId("cli").build();

        try (ReActAgent agent = NotesAgent.build(home);
             BufferedReader in = new BufferedReader(
                     new InputStreamReader(System.in, StandardCharsets.UTF_8))) {

            System.out.println("笔记助手已就绪，状态目录：" + home.resolve("state"));
            System.out.println("命令：/exit 退出    /new 换新会话（旧会话留在磁盘上）");

            while (true) {
                System.out.print("\n你> ");
                String line = in.readLine();
                if (line == null || line.equals("/exit")) {
                    break;
                }
                if (line.isBlank()) {
                    continue;
                }
                if (line.equals("/new")) {
                    ctx = RuntimeContext.builder().userId("local")
                            .sessionId("cli-" + System.currentTimeMillis()).build();
                    System.out.println("已切到新会话 " + ctx.getSessionId());
                    continue;
                }
                try {
                    converse(agent, ctx, line, in);
                } catch (IllegalStateException e) {
                    System.out.println("\n这一轮没跑完：" + e.getMessage());
                    System.out.println("如果上次退出时有没答完的确认，输入 /new 换个会话再试。");
                }
            }
        }
    }

    /** 一轮对话：跑一次；若暂停，问人，再带着答案跑一次；如此往复 */
    static void converse(ReActAgent agent, RuntimeContext ctx, String input, BufferedReader in)
            throws IOException {
        List<Msg> msgs = List.of(new UserMessage(input));
        while (true) {
            Round round = runRound(agent, ctx, msgs);
            System.out.println();
            if (!round.paused()) {
                return;
            }
            msgs = List.of(ask(round.asking(), in));
        }
    }

    /** 订阅事件流：文本逐字打，工具结果打一行，顺手记下最后的消息与被挂起的工具 */
    static Round runRound(ReActAgent agent, RuntimeContext ctx, List<Msg> msgs) {
        AtomicReference<Msg> result = new AtomicReference<>();
        AtomicReference<List<ToolUseBlock>> asking = new AtomicReference<>(List.of());

        agent.streamEvents(msgs, ctx)
                .doOnNext(ev -> {
                    if (ev instanceof TextBlockDeltaEvent delta) {
                        System.out.print(delta.getDelta());
                    } else if (ev instanceof ToolResultEndEvent tool) {
                        System.out.printf("%n  [tool] %s -> %s%n",
                                tool.getToolCallName(), tool.getState());
                    } else if (ev instanceof RequireUserConfirmEvent confirm) {
                        asking.set(confirm.getToolCalls());
                    } else if (ev instanceof AgentResultEvent done) {
                        result.set(done.getResult());
                    }
                })
                .blockLast();

        Msg msg = result.get();
        List<ToolUseBlock> pending = asking.get().isEmpty() ? askingOf(msg) : asking.get();
        return new Round(msg, pending);
    }

    /** 兜底：事件流没接住时，直接从结果消息里筛 ASKING 的工具调用 */
    static List<ToolUseBlock> askingOf(Msg msg) {
        if (msg == null) {
            return List.of();
        }
        return msg.getContent().stream()
                .filter(ToolUseBlock.class::isInstance)
                .map(ToolUseBlock.class::cast)
                .filter(t -> t.getState() == ToolCallState.ASKING)
                .toList();
    }

    /** 把「允许 / 拒绝」包成 ConfirmResult，塞进下一条用户消息的 metadata */
    static Msg ask(List<ToolUseBlock> calls, BufferedReader in) throws IOException {
        List<ConfirmResult> answers = new ArrayList<>();
        for (ToolUseBlock call : calls) {
            System.out.printf("%n需要确认：%s %s%n允许吗？[y/N] ", call.getName(), call.getInput());
            String line = in.readLine();
            boolean ok = line != null && line.trim().equalsIgnoreCase("y");
            answers.add(ok
                    ? new ConfirmResult(true, call)
                    : new ConfirmResult(false, call, null, "用户拒绝，请不要重试"));
        }
        return UserMessage.builder()
                .metadata(Map.of(Msg.METADATA_CONFIRM_RESULTS, answers))
                .build();
    }
}

事件流与 call() 共用同一个核心：ReActAgent.java:1038；AgentResultEvent 在 AgentEndEvent 前发出：ReActAgent.java:1090；确认 metadata 的 key：Msg.java:77

这段代码为什么不用 call()

call() 也能跑通审批（08 章就是用 call() 写的），但它只在整轮结束后给你一个 Msg：模型吐字的过程看不到，工具执行到哪一步也不知道。命令行里这会让每次响应看起来「卡住十秒然后一次性刷屏」。 streamEvents() 把同一条生命周期拆成事件，代价是你要自己处理「流完了吗、结果在哪」——所以才需要 AgentResultEvent。

验证「跨进程记忆」只要做一件事

把上面四轮跑完，/exit，重新启动，直接问「我刚才让你记了什么？」。因为 sessionId 固定是 cli，JsonFileAgentStateStore 会把上次的消息列表读回来，模型能答出「周五交周报」。 再把 main 里的 sessionId("cli") 改成别的值跑一次——它会立刻「失忆」。这就是 (userId, sessionId) 槽位最直观的演示。

逐行解读：四个必须想明白的接缝

1. 事件流里只需要认四种事件

streamEvents 会吐十几种事件，但一个终端 UI 只需要四种。剩下的（AgentStartEvent、 ModelCallEndEvent、ToolCallStartEvent 等）不是没用，而是这个场景不需要：

事件在这里干什么不接会怎样
TextBlockDeltaEventgetDelta() 直接 print，得到打字机效果整轮静默，最后一次性出结果（如果还接了 AgentResultEvent）
ToolResultEndEvent打一行「工具名 -> 状态」，让用户知道真的动了文件模型说「已删除」但你无法判断它是在执行还是只在说话
RequireUserConfirmEvent拿到 getToolCalls()，这是要问人的那批工具不知道要确认什么；只能退而从结果消息里筛
AgentResultEventgetResult() 拿到本轮最终 Msg，判断 PERMISSION_ASKING无法判断这一轮是否暂停，审批回路直接断掉

TextBlockDeltaEvent.getDelta()：TextBlockDeltaEvent.java:59；RequireUserConfirmEvent.getToolCalls()：RequireUserConfirmEvent.java:56；AgentResultEvent.getResult()：AgentResultEvent.java:57

只监听 TextBlockDeltaEvent 的经典 bug

很多人写流式只接增量文本，然后发现「删文件时程序没反应」。实际上 agent 已经正常返回了，只是那一轮没有文本增量 （模型输出的是 ToolUseBlock），而暂停信号藏在 AgentResultEvent.getResult().getGenerateReason() 里。判断「跑没跑完」永远看 result，不要看有没有文字。

2. PERMISSION_ASKING 是「这一轮的结局」，不是异常

converse 里那个 while (true) 的退出条件只有一条：!round.paused()。 换言之，「暂停」被当成一种正常的轮次结果来处理，跟「模型说完了」是同一个层级的事件。这是 AgentScope 的 HITL 与其他框架最大的差别：没有 future、没有回调、没有线程挂起，streamEvents 正常 complete，你手里拿到一条 reason 为 PERMISSION_ASKING 的 Msg。

直觉写法（会卡住）

  • 调 call()，然后 Thread.sleep 等用户输入
  • 在工具内部弹一个对话框，阻塞等结果
  • 用 CompletableFuture 把 agent 线程挂起

框架的实际模型

  • 第一次调用正常结束，返回「暂停」这个结果
  • 进程可以退出、可以换机器、可以把确认请求丢给前端
  • 回答时带着 ConfirmResult 再调一次，同一槽位接着跑

这也解释了为什么 ask() 里拒绝时要传一句理由：拒绝不是「取消」，而是一条工具结果。 模型看到「用户拒绝，请不要重试」才会换方案；只传 new ConfirmResult(false, call)，模型常常会再试一次同样的调用， 然后又被拒，来回烧 token。

3. ConfirmResult 必须拿「原件」，不能重新造一个

框架恢复挂起调用时，靠的是 ToolUseBlock.getId() 去匹配。所以 ask() 里的 call 必须是 agent 当初发出来的那个对象（或至少是 id 完全相同的副本）。下面这些写法都会失败：

4. 「记住上次」靠的不是模型，是槽位 + 磁盘

模型本身没有记忆。第二轮能把第一轮的话接上，是因为每次 call 前框架都把 整个消息列表 从 AgentState 里取出来、拼进模型输入。而 AgentState 能不能活过进程退出，取决于 stateStore。这个案例里它的磁盘布局是： 

~/.notes-agent/state/
└── local/                        ← userId
    └── cli/                      ← sessionId
        ├── agent_state.json      ← 权限上下文、已注册规则等
        └── memory_messages.jsonl ← 一条消息一行，追加写

JsonFileAgentStateStore 的根目录由构造器决定，槽位两级目录就是 (userId, sessionId)。 名字里出现 /、中文、空格等不安全字符时，框架会做 Base64-URL 编码，所以不用担心路径炸掉。

目录规则与 safe(...)：JsonFileAgentStateStore.java:47；默认根目录 ~/.agentscope/state：JsonFileAgentStateStore.java:83

为什么这里用绝对路径 user.home

new JsonFileAgentStateStore(Path.of("state")) 是相对当前工作目录的。你在 IDE 里跑、 在项目根跑、在别的目录跑 java -jar，会得到三个不同的 state/，看起来就像「记忆时有时无」。 演示项目用 ~/.notes-agent 是为了让行为稳定；生产里更常见的是显式配置一个绝对路径或换成 Redis。

换了 sessionId，新会话看不到旧消息，但权限规则也会重置

因为 PermissionContextState 也存在 AgentState 里，跟着槽位走。所以 /new 之后如果模型又要删笔记，会重新问你一次——这不是 bug，是隔离。同理，用 ConfirmResult.rules 临时加的「本会话免问」规则，在 /new 之后同样不复存在。

1. 换成 HarnessAgent：换装配类，再改三处类型声明

第 10 章说过两者是同一颗引擎，但它们的关系不是父子类：HarnessAgent 声明的就是 implements Agent, AutoCloseableHarnessAgent.java:169， 内部持有一个 ReActAgent delegate 并转发配置。所以 NotesTools 一行不动， Cli 则必须把三处 ReActAgent 类型声明改成 HarnessAgent： try 资源声明，以及 converse / runRound 的形参。把案例拆成 NotesAgent + Cli 的价值也在这里：改动被压在三行类型上，逻辑一行没碰。 

import io.agentscope.core.permission.PermissionBehavior;
import io.agentscope.core.permission.PermissionContextState;
import io.agentscope.core.permission.PermissionMode;
import io.agentscope.core.permission.PermissionRule;
import io.agentscope.core.state.JsonFileAgentStateStore;
import io.agentscope.core.tool.Toolkit;
import io.agentscope.harness.agent.HarnessAgent;

import java.nio.file.Path;

public final class NotesAgent {

    private NotesAgent() {
    }

    public static HarnessAgent build(Path home) {
        Toolkit toolkit = new Toolkit();
        toolkit.registerTool(new NotesTools(home.resolve("notes")));

        PermissionContextState permission = PermissionContextState.builder()
                .mode(PermissionMode.DEFAULT)
                .addAskRule("delete_note",
                        new PermissionRule("delete_note", null, PermissionBehavior.ASK, "session"))
                .build();

        return HarnessAgent.builder()
                .name("notes")
                .sysPrompt("你是终端里的笔记助手。")
                .model("dashscope:qwen-plus")
                .toolkit(toolkit)
                .permissionContext(permission)
                .workspace(home.resolve("workspace"))   // ← 新增：文件工具的根
                .maxIters(8)
                .build();
    }
}

一句话记住这个案例的分层

陷阱与窍门

1. 只接了 TextBlockDeltaEvent，没有接 AgentResultEvent
你会看到
输入「把笔记清空」，模型回一句「好的」，程序直接回到提示符，磁盘上的 notes.txt 还在。
因为
那一轮模型输出的是 ToolUseBlock 而不是文本，所以 delta 流里几乎没有东西；暂停信号在 AgentResultEvent.getResult().getGenerateReason() 里，你没接就丢了。
改成
把 AgentResultEvent 当成唯一的「本轮结束」信号；TextBlockDeltaEvent 只负责显示。
2. 用 call() 却期待打字机效果
你会看到
终端安静十几秒，然后整段回答一次性刷出来；工具执行也只有一个总结果。
因为
call() 内部确实跑的是同一条 buildAgentStream，但它只把最终 Msg 交给你， 中间事件全部被消费掉了。
改成
要增量就用 streamEvents；只要最终结果、不在乎过程，就继续用 call。两者共用生命周期， onAgent 中间件不会因为换方法而跑两遍。
3. ConfirmResult 里放了一个新造的 ToolUseBlock
你会看到
IllegalStateException，信息里说引用了非 ASKING 的调用，还列出当前挂起的 id。
因为
恢复靠 getId() 匹配。新造的 block 即使工具名、参数都一样，id 也不同。
改成
只从 RequireUserConfirmEvent.getToolCalls() 或结果消息里筛 ASKING 的原件； 要改参数就重建但保留原 id（ToolUseBlock.builder().id(原 id)...）。
4. 拒绝时不写理由
你会看到
模型被拒后不死心，换个说法再调一次 delete_note，又被拒，来回好几轮。
因为
不传 reason 时，模型只看到默认文案「Permission denied by user」，它不知道你是「误操作」还是「永久禁止」。 提示词里又没写「别重试」。
改成
拒绝时传一句明确指令：new ConfirmResult(false, call, null, "用户拒绝，请不要重试")。 想永久免问就带上 ALLOW 规则（见练习 2）。
5. 上次暂停没答完就退出，重启后直接问新问题
你会看到
第一句话就抛 IllegalStateException，说还有待确认的工具调用，并贴出一段恢复代码。
因为
sessionId 还是 cli，槽位里存着上次的 ASKING。框架不允许在悬挂状态下 开启新话题，否则上下文会错乱。
改成
三个选项：把上次的 ConfirmResult 补上；用 /new 换会话；或者启动时用时间戳当 sessionId（代价是丢掉跨重启记忆）。Cli 里那个 catch 就是给这个场景兜底的。
6. stateStore 用了相对路径
你会看到
有时重启能记住、有时失忆；项目目录里冒出一个 state/，用户目录里又有一个。
因为
Path.of("state") 相对的是进程工作目录。IDE、项目根、java -jar 三处运行就有三个不同的库。
改成
用绝对路径（这个案例用 user.home），或者从配置文件读一个固定目录；多副本部署换 Redis / MySQL。

自检三问

为什么不直接看「有没有收到 RequireUserConfirmEvent」来判断暂停？

因为事件只是给 UI 的提示，不是状态本身。中间件可能把它过滤掉（09 章的坑）；DONT_ASK 模式下 本该 ASK 的调用会被降级成 DENY，也不会发这个事件。唯一权威的判据是 AgentResultEvent.getResult().getGenerateReason()。事件用来「拿要确认的工具」，reason 用来「决定要不要问」。

第二次调用时换一个新的 sessionId，会发生什么？

新槽位里没有那条 ASKING 记录，ConfirmResult 里的工具 id 匹配不上，直接抛 IllegalStateException。而且就算不抛，模型也看不到上一轮的对话，会把你当成新用户。 恢复必须用同一个 RuntimeContext。

把 runRound 换成 agent.call(msgs, ctx).block()，代码还能跑吗？要改什么？

能跑：返回的 Msg 同样带 PERMISSION_ASKING，paused() 逻辑不变。 要改两处：拿不到 TextBlockDeltaEvent / ToolResultEndEvent，流式展示退化成一次性输出； asking 只能从 msg.getContent() 里筛（也就是 askingOf 那条兜底路径变成唯一路径）。

30 分钟动手练习

  1. 加一个只读工具，验证它不会被问
    写 search_notes(keyword)，标上 @Tool(..., readOnly = true)，在 NotesTools 里用 Files.readAllLines 过滤包含关键字的行。先确认 DEFAULT 模式下它直接执行；再把 NotesAgent 里的模式改成 PermissionMode.EXPLORE，观察两件事：它仍然能跑，而 delete_note 不再是 ASK，而是直接被拒（EXPLORE 对非只读工具先 DENY）。
  2. 做一次「本会话内免问」
    在 ask() 里，用户输入 a（always）时构造 new ConfirmResult(true, call, List.of(new PermissionRule(call.getName(), null, PermissionBehavior.ALLOW, "session")))。 同一个 session 里再让它删一次，应该不再问；输入 /new 之后再删，又恢复了询问——验证规则存在槽位里。
  3. 加启动参数，一次看三种模式
    给 main 加一个 --mode 参数，把 NotesAgent.build(home, mode) 的 PermissionMode 变成可配。分别跑 DEFAULT / BYPASS / DONT_ASK，对同一句「把笔记清空」观察三种结局：问 / 直接删 / 直接被拒——尤其是 DONT_ASK，它把 ASK 降级成 DENY，不是「不问就放行」。
