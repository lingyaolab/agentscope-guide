28 · 模型接入：10 个 provider 的差异与切换

第 27 章说「10 个模型 id，6 个 artifact」。这一章把这句话拆开：同一个 Model 接口下， provider 在凭证、默认端点、formatter、结构化输出、思考参数和重试策略上并不等价。 切换模型不是改 prompt，而是换 id、换装配，必要时再换一个能兜底的 fallbackModel。

读完你能做到

  • 说清 ModelRegistry 的解析顺序，以及解析失败和创建失败分别长什么样
  • 列出 10 个 provider id、它们共用的 6 个 artifact，以及各自的标准凭证
  • 解释 OpenAI 与 OpenAI Official 为什么不是同一个东西，以及 OpenAI 兼容模块替 DeepSeek / GLM / Kimi / MiniMax 改了什么
  • 判断某个 provider 是否支持原生结构化输出，什么时候会退回工具式 fallback
  • 用 ModelCreationContext 覆盖 baseUrl、apiKey 与思考参数，并避免租户级缓存串用
  • 用 maxRetries 与 fallbackModel 做可控的重试和降级，而不是靠外层无限重试

为什么「换模型」不等于「改模型名」

AgentScope 把所有模型收在同一个 Model 接口下：一个流式 stream(...)、一个模型名， 再加上结构化输出、上下文窗口等带默认实现的能力 Model.java:22-33。 接口相同，只保证 Agent 的调用方式不变；它不保证两个 provider 对同一条请求理解一致。

最典型的是「OpenAI 兼容」：DeepSeek、GLM、Kimi、MiniMax 都走同一套 OpenAI 载荷格式，但各自的 formatter 会分别处理 strict、reasoning_content、max_tokens 与 tool_choice deepseek.md:49-53 glm.md:56-64 kimi.md:56-66 minimax.md:49-55。 所以一次真正的切换至少要核对五件事：id、artifact、凭证、端点、能力差异。少一项，问题就会在运行到工具调用或结构化输出时才暴露。

ModelRegistry：id 怎么变成一个 Model

provider 通过 ModelProvider SPI 暴露三个动作：声明 providerId、 判断 supports(modelId)、按完整 id 创建 Model ModelProvider.java:21-44。 ModelRegistry 按固定顺序查找：先看按名字注册的实例，再看解析缓存，再看用户注册的 factory（新的优先）， 最后才查 SPI provider ModelRegistry.java:98-137。

阶段发生什么失败形态

provider 创建失败例如环境变量缺失、端点非法被包装成 IllegalArgumentException，保留 causeModelRegistry.java:145-166
预检canResolve(id) 只匹配、不创建返回 false，适合启动时检查配置ModelRegistry.java:169-195

一个 artifact 里可以注册多个 provider。OpenAI 兼容模块的 SPI 文件一次列了五个实现： openai、kimi、minimax、glm、deepseek ModelProvider:1-5。 这也是第 27 章那个结论的来源：artifact 名描述的是「用哪套客户端与 formatter」，不是「只支持哪个品牌」。

先 canResolve，再发请求

启动时用 ModelRegistry.canResolve("dashscope:qwen-plus") 做一次预检，比等第一个用户请求失败更便宜。 预检只证明「有 provider 能接这个 id」，不证明凭证有效；凭证错误要等真正创建或调用时才暴露。

DeepSeek、GLM、Kimi、MiniMax 共用 OpenAI 客户端，但各自有 formatter。它们做的不是「翻译字段」这么简单， 而是在请求发出前把不兼容的参数删掉、把等价的参数改名、把历史 reasoning 内容保留或清理。

DashScope：短名、思考与结构化输出的交叉约束

DashScope 既接受 dashscope:<model>，也接受 qwen-plus 这样的短名 dashscope.md:20-34。 provider 的匹配规则是 dashscope:.+ 或 qwen.+，所以短名不是特例，而是另一条正则 DashScopeModelProvider.java:41-63。

DashScope 的 builder 还支持 search、encrypt、endpoint type 等专属选项 dashscope.md:36-48。 结构化输出有一个容易忽略的交叉约束：supportsNativeStructuredOutput() 在开启 thinking 时直接返回 false，否则才回落到父类配置 DashScopeChatModel.java:432-438。 也就是说，「用 Qwen 的思考模式」和「用原生 json_schema」不要同时假设成立。

Gemini 支持 Gemini API，也可以通过显式 builder 配置走 Vertex AI gemini.md:6-41。 Anthropic 的特殊点在鉴权：apiKey 会设置 X-Api-Key，authToken 会设置 Authorization: Bearer，两者只能配一个，同时配置会在创建模型时抛 IllegalArgumentException anthropic.md:43-59。 Ollama 则没有必填密钥，默认连本机 http://localhost:11434，适合离线或私有化部署 OllamaHttpClient.java:60 ollama.md:20-39。

重试与降级：三层预算不要叠成无限重试

AgentScope 的默认执行配置把模型调用设为 5 分钟超时、3 次尝试、指数退避（初始 2 秒、上限 30 秒、倍数 2.0）； 工具调用则是 5 分钟超时、只尝试一次 ExecutionConfig.java:34-38 ExecutionConfig.java:145-151。 HTTP 层面只有 429 与 5xx 默认算可重试，其余状态码不重试；超时与 IO 错误也会重试 ModelHttpException.java:24-43 ExecutionConfig.java:99-127。

ReActAgent 的 maxRetries 默认是 3；fallbackModel 在主模型耗尽重试后接管， 并与主模型共享同一个重试预算；failoverListener 用来观察切换 ModelConfig.java:21-36 ReActAgent.java:5192-5233。 流式调用中，主模型发出第一个错误信号时会切到 fallback ReActAgent.java:4273-4302。

    .name("assistant")
    .model("dashscope:qwen-plus")
    .maxRetries(3)
    .fallbackModel("openai:gpt-4.1-mini")

小心双重重试

如果 provider SDK 自己也在重试，外层 AgentScope 再重试一次，实际请求次数会相乘。OpenAI Official 已经显式设置 maxRetries=0，把控制权交给 AgentScope；接入其他 SDK 时也要确认这一层 openai-official.md:70。

ModelCreationContext：切换的旋钮，也是缓存的边界

ModelCreationContext 把 provider 无关的标准字段（apiKey、baseUrl、endpointPath、stream、 enableThinking）与 provider 专属的 options / components 分开 ModelCreationContext.java:22-41。 这正是「不改 Agent 代码，换端点或换租户凭据」的入口。 

Model model = ModelRegistry.resolve(
    "openai:gpt-4.1-mini",
    ModelCreationContext.builder()
        .apiKey(tenantKey)
        .baseUrl(tenantBaseUrl)
        .stream(true)
        .build());

缓存规则必须一起看：空 context 的解析结果会缓存；非空 context 默认不缓存，除非显式设置 CachePolicy.ENABLED；如果 context 里带 options / components，还必须给出稳定的 cacheId ModelRegistry.java:108-137。 如果为了省创建开销把租户凭据也塞进全局缓存，下一次请求就可能用到上一个租户的 key。

切换的三种方式：id、builder、fallback

切换模型常见且稳定的做法有三种，分别解决不同问题。把它们混用，最容易出现「配置改了但没生效」或「以为是负载均衡， 其实是故障转移」。

方式怎么做适合不解决什么
字符串 id.model("dashscope:qwen-plus") 或 ModelRegistry.resolve同一套代码切 provider不校验凭证，也不探测能力差异
显式 builderOpenAIChatModel.builder()...自定义 baseUrl、formatter、transport、thinking代码与某个 provider 绑定
fallbackModel.fallbackModel("openai:gpt-4.1-mini")主模型故障时自动接管不是轮询，也不是按成本路由

计划内切换用前两种，故障降级用第三种。切换后 Agent 的上下文、工具与权限不会自动迁移；新模型只是换了一套 formatter 与 HTTP 端点，会话状态仍由 AgentStateStore 负责。第 31 章会把这条边界接到状态存储上。

六个坑：把「兼容」当成「等价」

坑一：10 个 id 装 10 个依赖。DeepSeek、GLM、Kimi、MiniMax 都复用 OpenAI 兼容 artifact， 只有 OpenAI Official、DashScope、Gemini、Anthropic、Ollama 需要各自模块 overview.md:14-25。

坑二：以为 OpenAI 兼容就是行为一致。formatter 会移除 strict、改动 max_tokens、降级 tool_choice； 兼容的是载荷，不是模型能力 glm.md:56-64 minimax.md:49-55。

坑三：假设所有 provider 都支持原生结构化输出。OpenAI 兼容四家明确关闭，Gemini / Anthropic / Ollama 也默认不打开；不支持的路径会退回工具式 fallback ChatModelBase.java:46-60。

坑四：双重重试。SDK 自己重试，AgentScope 再重试，会把一次失败放大成多次请求；OpenAI Official 已把 SDK 重试设为 0 openai-official.md:70。

坑五：把租户凭据放进全局缓存。非空 context 默认不缓存；显式开启缓存时必须给稳定的 cacheId，否则可能跨租户复用模型实例 ModelRegistry.java:108-137。

坑六：把 fallback 当负载均衡。fallbackModel 只在主模型失败后接管，并共享重试预算； 它不会按成本或延迟轮询 ModelConfig.java:21-36。

自测：三个判断题

要接 DeepSeek，需要额外加一个 DeepSeek 专用 artifact 吗？

不需要。DeepSeek 由 agentscope-extensions-model-openai 里的 DeepSeekModelProvider 提供，加 OpenAI 兼容模块后使用 deepseek:<model> 即可 ModelProvider:1-5。

openai-official 能走 Chat Completions 吗？

目前不能。它通过 OpenAI 官方 Java SDK 只支持 Responses API，未来才考虑 Chat Completions；需要 Chat Completions 或兼容网关时用 openai: openai-official.md:6-8。

fallbackModel 是不是每次都轮询两个模型？

不是。它是故障转移：主模型耗尽重试后，fallback 才接管，并与主模型共享重试预算；不会按请求轮流分配 ModelConfig.java:21-36。

练习：做一次可解释的模型切换

目标不是「跑通一个模型」，而是能写清楚切换前后哪些能力变了。建议 45 分钟：

  1. 列能力清单
    写下你要用的三项能力：工具调用、结构化输出、思考模式；再写清楚是否要求流式。
  2. 选两个 provider
    例如 dashscope:qwen-plus 与 openai:gpt-4.1-mini，分别记录 artifact、凭证与默认端点。
  3. 先做解析预检
    用 ModelRegistry.canResolve 检查两个 id；故意写错一个前缀，记录异常文本。
  4. 跑最小对话
    用同一个 Agent 代码分别切两个 id，确认只有装配变化，Agent 代码不变。
  5. 测工具与结构化输出
    注册一个只读工具，发一个需要工具再返回 JSON 的请求；记录两家是否都调用工具、是否都返回合法结构。
  6. 加 fallback
    设置 maxRetries(3) 与 fallbackModel，用错误 key 触发一次失败，观察是否切到备用模型。
  7. 检查缓存边界
    用两个不同的 apiKey context 解析同一个 id，确认没有复用同一个模型实例。
  8. 写三行结论
    分别写「id 与 artifact」「能力差异」「失败时的降级路径」，确保每一行都能独立核对。
