05 · 模型层

第 01 章我们只验证了「"dashscope:qwen-plus" 能不能被解析」，第 02 章直接把它塞进了 builder。这一章回答的是剩下的一半问题： 这个字符串凭什么变成一个模型对象、参数在哪里调、挂了怎么重试、怎么降级、怎么让它输出一个 Java 对象而不是一段散文。

读完你能做到

  • 判断一个场景该用字符串 id 还是显式 builder，并说出各自的代价
  • 解释 maxRetries(3) 到底是「重试 3 次」还是「一共 3 次」，以及重试间隔从哪来
  • 配出一个「主模型 + 备用模型」的降级链路，并知道它在什么时刻不会生效
  • 让 agent.call(...) 直接返回一个 POJO，而不是让模型自由发挥

先说为什么：两种建模型的方式，不是「新旧」而是「场景」

框架给了两条路建模型，很多人以为显式 builder 是「高级用法」、字符串 id 是「简陋用法」，其实它们解决的是两个不同问题：

字符串 id：.model("dashscope:qwen-plus")

  • 编译期只依赖 core，代码里不出现任何厂商类
  • 换厂商 = 改一行字符串 + 换一个 Maven 依赖
  • 代价：key 只能来自环境变量，参数只能用默认值
  • 适合：教学、CLI 工具、配置驱动的多租户场景

显式 builder：.model(dashScopeModel)

  • 能设 baseUrl（反代 / 私有化端点）、formatter、defaultOptions
  • key 可以从配置中心、数据库、Vault 里取
  • 代价：编译期就要依赖具体厂商模块，换厂商要改代码
  • 适合：生产服务、需要精细控参的场景

官方文档给的判断标准很干脆：简单场景用 provider:model 格式 + 标准环境变量；需要精细控制时，优先用显式 buildermodel.md:163。换句话说，字符串 id 不是「简化版 builder」，而是一套运行时发现机制（下一节就拆它）。

最小可跑：把字符串换成完全可控的模型

第 02 章的写法是 .model("dashscope:qwen-plus")。下面这段做同一件事，但把 key、参数、formatter 全部摊开： 

import io.agentscope.core.ReActAgent;
import io.agentscope.core.model.GenerateOptions;
import io.agentscope.core.tool.Toolkit;
import io.agentscope.extensions.model.dashscope.DashScopeChatModel;
import io.agentscope.extensions.model.dashscope.formatter.DashScopeChatFormatter;

DashScopeChatModel model =
        DashScopeChatModel.builder()
                .apiKey(System.getenv("DASHSCOPE_API_KEY"))
                .modelName("qwen-plus")
                .stream(true)
                .formatter(new DashScopeChatFormatter())
                .defaultOptions(
                        GenerateOptions.builder()
                                .temperature(0.3)
                                .maxTokens(1024)
                                .build())
                .build();

ReActAgent agent =
        ReActAgent.builder()
                .name("Assistant")
                .sysPrompt("你是一个简洁的助手，回答不超过三句话。")
                .model(model)
                .toolkit(new Toolkit())
                .build();

builder 三个典型场景（流式 / 工具 / 推理）：model.md:226；defaultOptions 加载：DashScopeChatModel.java:538；agent.model(Model)：ReActAgent.java:4921

这两段代码有个隐藏差异：谁来管生命周期

用字符串 id 时，模型实例由 ModelRegistry 创建并缓存复用——同一个 id 解析两次拿到的是同一个对象； 用显式 builder 时，对象是你 new 出来的，你想复用就自己持有，想每次都新建也随你。

端到端：一个字符串怎么变成模型对象

ModelRegistry.resolve() 的查找顺序是写死在代码里的四步，顺序不能变ModelRegistry.java:99：

  • ① 具名注册
    先查 register(name, model) 直接放进去的现成实例。这一层优先级最高，可以覆盖任何厂商解析ModelRegistry.java:61
  • ② 缓存
    同样的 id 且上下文允许缓存，就直接返回上次创建的对象，不再走后面的步骤ModelRegistry.java:131
  • ③ 用户工厂
    按正则匹配你自己 registerFactory("myprov:.*", ...) 注册的工厂。这一层优先于 SPI，所以你可以「用假模型顶替真模型」做测试ModelRegistry.java:139
  • ④ SPI 发现
    扫描 classpath 上所有 META-INF/services/io.agentscope.core.model.spi.ModelProvider，逐个问 supports(id)，第一个说「支持」的负责创建ModelRegistry.java:239
两个 provider 同时说「我支持」，会悄悄用第一个

如果你同时引了两个厂商模块，而它们的 supports() 正则都覆盖了同一个 id（比如某家的短写规则很宽），注册表会打一条 Multiple ModelProvider implementations support model id ... Using the first discovered provider. 的 warn，然后继续用第一个，不报错ModelRegistry.java:256。所以看到「模型行为不对、像是别家的」时，先去日志里搜这条 warn。

失败也是分层的，这也是 01 章留下的问题在这里收口：找不到任何 provider → Cannot resolve model；找到了但创建过程抛异常 → 包一层 Failed to create model for id: ...ModelRegistry.java:163。两者都抛 IllegalArgumentException，但含义完全不同。

缓存策略：为什么带 context 就不缓存了

策略 行为 什么时候用
DEFAULT resolve(id) 按 id 缓存；resolve(id, 非空context) 不缓存 默认。单租户 / 单配置时最省事
DISABLED 永不缓存，每次都是新实例 每次调用要用不同的 key 或 endpoint
ENABLED 显式开启；建议用 cacheId(...) 表达「租户 + 配置」这一层身份 多租户网关，但每个租户内部可以复用

这条规则背后的理由很朴素：不同租户的 apiKey / baseUrl / stream 配置不一样，复用同一个模型实例等于把 A 的凭证给了 B。所以带上下文的解析默认不缓存；如果你确实要缓存，必须显式给一个 cacheId，否则遇到 option(...) / component(...) 时会直接抛 ModelCreationContext cachePolicy(ENABLED) with options or components requires an explicit cacheIdModelRegistry.java:296。

缓存 key 里 apiKey 不是明文，而是 SHA-256 摘要，避免堆转储和日志里泄露ModelRegistry.java:307

重试与降级：maxRetries 和 fallbackModel 的真实语义

这是本章最值得逐字读源码的一段，因为两个参数的直觉理解都是错的。

第一件事：maxRetries(3) 不是「重试 3 次」

ModelConfig 的注释写得很清楚：maxRetries 是「单次模型调用的重试预算」，而默认值 DEFAULT_MAX_RETRIES = 3ModelConfig.java:36。它被传给 ExecutionConfig.maxAttempts，而 maxAttempts 的语义是「包含第一次在内的总尝试次数」——maxAttempts=3 意思是 1 次初始 + 2 次重试ExecutionConfig.java:316。

重试并不只是「再试一次」这么简单，ModelConfig 只决定次数，其余参数来自 ExecutionConfig 的模型默认值：

参数 默认值 含义
timeout 5 分钟 单次尝试的超时上限
maxAttempts 3 总共最多试 3 次
initialBackoff 2 秒 第一次重试前等多久
maxBackoff 30 秒 退避上限（指数增长封顶）
backoffMultiplier 2.0 名义上按 2 倍指数增长（2s → 4s → 8s …），并叠加 0.5 抖动
retryOn RETRYABLE_ERRORS 只重试 429、5xx、超时、网络错误；400 这类参数错误不重试

全部默认值：ExecutionConfig.java:145；重试谓词的实现：ExecutionConfig.java:94

第二件事：fallbackModel 只兜「第一次就失败」

import io.agentscope.core.ReActAgent;
import io.agentscope.core.tool.Toolkit;

ReActAgent agent =
        ReActAgent.builder()
                .name("Resilient")
                .sysPrompt("你是一个简洁的助手。")
                .model("dashscope:qwen-plus")
                .maxRetries(4)
                .fallbackModel("openai:gpt-5.5")
                .failoverListener(
                        (primary, error) ->
                                System.err.println(
                                        "主模型 " + primary.getModelName() + " 失败：" + error.getMessage()))
                .toolkit(new Toolkit())
                .build();

maxRetries：ReActAgent.java:5196；fallbackModel(Model) 与 fallbackModel(String)：:5208、:5220；FailoverListener 签名：FailoverListener.java:50

降级的实现只有一个算子：switchOnFirst。

Flux<ChatResponse> primaryFlux =
        Flux.defer(() -> model.stream(messages, tools, options));
return primaryFlux.switchOnFirst(
        (signal, flux) -> {
            if (signal.isOnError()) {
                // 只有「第一个信号就是 error」时才切
                notifyFailover(failoverListener, model, error);
                return fallbackModel.stream(messages, tools, options);
            }
            return flux;
        });

完整实现：ReActAgent.java:4273

三个反直觉的结论

① 流到一半才断，不会切备用模型。只要主模型已经吐出过任何一条数据，switchOnFirst 就走 return flux 分支，后面的错误原样往上传。
② 备用模型有自己的一份重试预算。ModelConfig 的注释说 fallback 与主模型共用 maxRetries，但实际路径是主模型耗尽后再次进入 fallbackModel.stream(...)， 备用模型会重新走自己的 applyTimeoutAndRetry；maxRetries=3 时最多可发 6 次请求ModelConfig.java:22，所以总请求数上限会比只用主模型时更高。
③ 监听器自己抛异常不会影响降级。notifyFailover 会把异常吞掉只打 warnReActAgent.java:4327，所以别在监听器里做「必须成功」的业务。

还有一点容易忽略：fallbackModel 是 @JsonIgnore 的ModelConfig.java:33。它持有连接和凭证，不会随 AgentState 一起序列化，所以恢复会话时它不会自动回来——降级链是你代码里的配置，不是会话状态的一部分。

结构化输出：让模型交一个对象出来

只要最终文本、不要自由发挥时，用带 Class 的 call 重载。先定义一个普通 POJO（字段用 public 最省事）： 

public class WeatherInfo {
    public String city;
    public double temperature;
    public String unit;
}
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;
import java.util.List;

Msg msg =
        agent.call(
                        List.of(new UserMessage("上海现在天气怎么样？")),
                        WeatherInfo.class,
                        RuntimeContext.empty())
                .block();

WeatherInfo info = msg.getStructuredData(WeatherInfo.class);
System.out.println(info.city + " " + info.temperature + info.unit);

call(List, Class, RuntimeContext)：ReActAgent.java:853；取结果：Msg.java:431。结果最终挂在 metadata 的 _structured_output 上

框架内部有两条路径，你不用选，但要知道自己走在哪条上：

路径 条件 机制
Native supportsNativeStructuredOutput() = true 用 response_format + json_schema 让模型直接吐合规 JSON
Fallback（默认） 返回 false 注入一个叫 generate_response 的合成工具，模型「调工具」来交答卷

各厂商的默认行为不一样，这是接入时最容易踩的坑：

提供商 native 支持 说明
OpenAI（GPT-4o 等） 是 原生支持 json_schema
OpenAI Official（Responses API） 是 原生支持
OpenAI 兼容（DeepSeek / GLM formatter） 否 自动走 fallback
DashScope 否 原生端点只支持 json_object，不支持 json_schema，默认 fallback
Anthropic 否（默认） —

native 路径失败时（比如端点返回 400），框架会自动降级到 fallback，不需要你写 try-catch。但有一个例外要记住： DashScope 开了 enableThinking(true) 就不支持结构化输出，框架会强制走 fallbackmodel.md:394。

同时用工具 + 结构化输出，有兼容问题

部分 OpenAI 兼容 API（Kimi、DeepSeek 等）看到 response_format 后就不调工具了。解法是把 nativeStructuredOutputWithTools(false) 打开model.md:410；OpenAI 原生模型（GPT-4o 等）不需要设。

Formatter：多 agent 场景唯一需要改的一行

Formatter 负责把 List<Msg> 翻译成厂商要的请求载荷。每个厂商内置两种： ChatFormatter（默认，一条 Msg 对一条 API 消息，保留原始角色）和 MultiAgentFormatter（把连续的 agent 消息聚合，并在文本里标注发言人）。 

import io.agentscope.extensions.model.dashscope.DashScopeChatModel;
import io.agentscope.extensions.model.dashscope.formatter.DashScopeMultiAgentFormatter;

DashScopeChatModel model =
        DashScopeChatModel.builder()
                .apiKey(System.getenv("DASHSCOPE_API_KEY"))
                .modelName("qwen-plus")
                .stream(true)
                .formatter(new DashScopeMultiAgentFormatter())   // 只改这一行
                .build();

两种 formatter 的职责对比：model.md:427；六家厂商的 formatter 类名对照表：model.md:449

为什么需要它：大多数厂商的 API 只认 user / assistant / system 三种角色，而多 agent 场景下可能有五个「assistant」互相说话。不聚合的话，模型根本分不清哪句是同事说的、哪句是自己之前说的。

陷阱与窍门

1. 以为 maxRetries(3) 会打 4 次请求
你会看到
算成本、算超时的时候对不上，日志里只看到 3 次。
因为
它是总尝试次数（maxAttempts），不是「重试次数」。3 = 1 次初始 + 2 次重试。
改成
想放宽到「最多重试 3 次」就写 .maxRetries(4)。
2. 以为配了 fallbackModel 就万无一失
你会看到
流式输出到一半断了，报错直接冒到用户那里，备用模型完全没动。
因为
switchOnFirst 只检查第一个信号。已经吐过数据就不再切。
改成
这类场景要在调用层兜底：整条流加 .onErrorResume(e -> 重试或降级)；或者用更小的超时与更严格的熔断，让失败尽早发生。
3. 用字符串 id 却想改温度
你会看到
不知道在哪传 temperature；或者改了「模型」却发现别的请求也变了。
因为
字符串 id 只带 provider:model，参数只能用默认值；而且默认按 id 缓存同一个实例，改它等于改全局。
改成
要控参就用显式 builder；实在要用字符串，就在 agent 层用 .generateOptions(...) 覆盖单次调用。
4. 开了 thinking 还指望 native 结构化输出
你会看到
结构化输出能跑，但日志里没有 response_format，或者行为和你预期的不一样。
因为
DashScope 的思考模式不支持结构化输出，框架会强制走 fallback（合成工具）路径。
改成
要么关掉 thinking，要么接受 fallback；不要把「必须走 native」当成硬需求。
5. 单 agent 也套 MultiAgentFormatter
你会看到
消息角色边界变得模糊，模型偶尔「把系统提示当成用户说的」。
因为
MultiAgentFormatter 会把连续的同角色消息聚合成一条并加发言人标注，这本来是为多 agent 设计的。
改成
只有真的有两个以上 agent 在同一段历史里说话时才用它；单 agent 保持 ChatFormatter。

自检三问

maxRetries(4) 最多会发出几次模型请求？

最多 4 次（1 次初始 + 3 次重试）。而且只有 429 / 5xx / 超时 / 网络错误才会重试，400 这类参数错误一次就结束ExecutionConfig.java:139。

哪些情况下 fallbackModel 不会生效？

下面四种都不会切：

  • ① 主模型已经吐出过至少一条数据，之后才失败——switchOnFirst 已经走了正常分支，错误原样往上传ReActAgent.java:4288；
  • ② 主模型正常结束，只是回答不满意——没有 error 就没有降级；
  • ③ 主模型在构造阶段就解析失败——.fallbackModel("openai:gpt-5.5") 在 builder 里就调用 ModelRegistry.resolveReActAgent.java:5220，解析不出来直接抛 IllegalArgumentException，根本进不到运行时；
  • ④ 备用模型自己失败——降级链只有一层，fallback 没有「再 fallback」。

另外别把 retryOn 和「降级」混为一谈：重试发生在模型内部（Retry.backoff(maxAttempts - 1) + filter(retryOn)，ModelUtils.java:117），整段重试序列对 switchOnFirst 只暴露一个终态 error。所以不可重试的错误（比如 400）会 立刻以首个信号 error 触发降级——「不重试」恰恰意味着「更快切 fallback」。

为什么 DashScope 的结构化输出默认走 fallback？

因为 DashScope 原生端点只支持 json_object，不支持 json_schema， supportsNativeStructuredOutput() 返回 false，于是框架注入一个 generate_response 合成工具让模型通过 tool call 交结构化数据。

20 分钟动手练习

  1. 把两条路都跑一遍，对比对象
    分别打印 ModelRegistry.resolve("dashscope:qwen-plus").getClass().getName() 和你自己 builder() 出来的对象，再连续 resolve 两次比较 == 是否为 true。你会亲眼确认「字符串 id 走缓存」。
  2. 数一次真实的重试
    把 apiKey 设成一个格式正确但无效的值，配 .maxRetries(2)，用 doOnError 打印总耗时。观察它是「立刻失败」还是「等了 2 秒才失败」——这能帮你区分「不可重试」和「重试后仍失败」。
  3. 让模型交一个带嵌套结构的对象
