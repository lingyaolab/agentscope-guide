07 · 记忆与上下文

上一章结束时，Agent 已经能说话也能动手，但它每次 call 都像是失忆的。这一章回答一个问题： 「记住上一轮」这件事到底存在哪。答案是 AgentState —— 而 Memory、LongTermMemory 这套 1.x 的东西在 2.0.4 里已经废弃甚至移除，这是本章最容易被带偏的地方。

读完你能做到

  • 说清「无状态引擎」是什么意思，以及为什么一个 ReActAgent 实例能同时服务多个用户
  • 背出 AgentState 的 11 个字段各装什么，知道哪些是框架写的、哪些是你能读的
  • 配一次 AgentStateStore，让进程重启后对话还在，并知道三种内置实现的取舍
  • 解释同一 (userId, sessionId) 为什么会被串行化，以及并发写冲突时 ConflictPolicy 怎么选
  • 不再把「长期记忆」当成框架能力——核心已不提供实现、整包标了废弃，要用就自己接

先说为什么：无状态引擎 + 有状态槽位

新手最容易写出的架构是「每个会话 new 一个 agent，塞进 Map<sessionId, Agent>」。这在单机 Demo 里能跑，但它把配置和状态混在了同一个对象里：agent 一多，内存压不住；服务一重启，会话全丢；想扩到两台机器，Map 还不共享。

2.0 的做法是把它拆开：

agent-per-session（1.x 风格）

  • agent 对象里既有 sysPrompt，也有对话历史
  • 要自己维护 Map<sessionId, Agent> 并且管清理
  • 扩容时状态跟着 JVM 走，没法跨节点
  • 重启即失忆，除非再写一层导出/导入

无状态引擎 + AgentState（2.0）

  • agent 只持不可变配置：sysPrompt / model / toolkit / middlewares
  • 可变状态全在 AgentState 里，按 (userId, sessionId) 寻址
  • 一个实例服务所有人；不同槽位天然并行
  • 状态存在哪由 AgentStateStore 决定，可以换成 Redis

官方文档把这件事叫「无状态 Agent 引擎」：实例无状态，槽位有状态。理解了这个区分，后面所有设计（并发门、CAS、分布式恢复）都只是它的推论。

槽位来源：ReActAgent.java:397；每次调用激活槽位：:659

最小可跑：让第二次 call 记住第一次

不需要 Memory，也不需要额外配置——只要两次调用用同一个 sessionId：

import io.agentscope.core.ReActAgent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.state.JsonFileAgentStateStore;

import java.nio.file.Path;

ReActAgent agent =
        ReActAgent.builder()
                .name("Memo")
                .sysPrompt("回答简短，不要复述系统提示。")
                .model("dashscope:qwen-plus")
                .stateStore(new JsonFileAgentStateStore(Path.of("state")))
                .build();

// 同一个槽位：alice / s-001
RuntimeContext alice = RuntimeContext.builder()
        .userId("alice")
        .sessionId("s-001")
        .build();

agent.call("我叫 Alice，在做支付系统。", alice).block();
Msg second = agent.call("我在做什么项目？", alice).block();
System.out.println(second.getTextContent());   // 支付系统 ← 记得

// 换个 sessionId：同一用户，另一段对话
RuntimeContext aliceOther = RuntimeContext.builder()
        .userId("alice")
        .sessionId("s-002")
        .build();
Msg other = agent.call("我在做什么项目？", aliceOther).block();
System.out.println(other.getTextContent());    // 不知道 ← 不共享

连 store 都不配会怎样？

也记得。框架内部有一个 stateCache（Map<slot, AgentState>），同一个 agent 实例、同一个槽位的第二次调用会拿到同一份状态ReActAgent.java:684。区别是：进程一退出就没了，而且换一个 agent 实例也读不到。所以「调试时能记住、上线后失忆」几乎都是忘了配 store。

agent 实例（不可变） sysPrompt、model、toolkit、middlewares、stateStore —— 构造完就不再改，可以长期复用
槽位 (userId, sessionId) 寻址单位。user 为空时归到 __anon__ 桶；session 为空时回退到 defaultSessionId
AgentState（可变） 对话历史 + 压缩摘要 + 权限/工具/任务/PlanMode 四个子上下文 + 迭代计数

别把 RuntimeContext 和 AgentState 搞混

这两个东西名字都像「上下文」，但一个是入参，一个是状态：

RuntimeContextAgentState
生命周期一次 call，用完即弃跨 call，持久化
谁创建调用方 new框架按槽位加载
装什么userId / sessionId / 本次调用的工具配置 / 用户自定义 POJO对话历史、权限、工具组、任务、迭代计数
怎么拿到自己构造了就有rc.getAgentState()（call 期间由框架注入）
能改吗能，但只影响本次调用能改 contextMutable()，call 结束时落盘

最重要的那句：RuntimeContext 是寻址凭据 + 本次调用的旁路数据，它自己不存历史。你在里面 put 一个 POJO，只对这一次调用有效（第 06 章的参数注入用的就是它）。

call 入口把 state 注入 RuntimeContext：ReActAgent.java:754；rc.getAgentState()：RuntimeContext.java:115

端到端：一次 call 从加载到落盘

  • 调用方
    传入 RuntimeContext(uid, sid)；没传 sid 就用 defaultSessionId。
  • 寻址
    拼出槽位键 (uid 或 "__anon__") + "/" + sid，后续所有读写都围着它转ReActAgent.java:397。
  • 排队
    以槽位为 key 拿执行锁——同一槽位的 call 串行，不同槽位并行。
  • 加载
    先读 agent_state；读不到再试 1.x 老键 memory_messages + toolkit_activeGroups；都没有才新建一份空状态。
  • 注入
    ctx.setAgentState(state)——中间件和工具靠 rc.getAgentState() 拿到的就是它。
  • 推理
    主循环就地改写 contextMutable()：追加用户消息、tool_use、tool 结果、最终回复。
  • 落盘
    call 结束（或停机）时整份写回 agent_state。中途失败会先把已积累的安全状态存一次，再抛原错误。

每次调用重新加载（分布式友好）：ReActAgent.java:651；加载顺序：:421；保存：:475

不是每条消息都落盘

整份状态只在 call 结束 / 优雅停机 时写一次ReActAgent.java:359。所以：对后端吞吐很友好，但进程被 kill -9 时这一轮对话会丢。要强一致就得自己在业务层做检查点，或者依赖优雅停机（第 10 章）。

并发与隔离：为什么同一会话会被排队

框架给每个槽位分配一把锁：callSerializationKey 返回的就是槽位键ReActAgent.java:727。同一 (uid, sid) 的两次调用必须一个跑完再跑下一个，否则两个循环会同时往同一个 context 里追加消息，历史就乱了。不同槽位之间没有任何互斥，所以「一个 agent 服务一千人」在并发上是成立的。

跨进程/跨机器时锁是无效的，靠的是存储层的 CAS。框架推荐用「读版本 → 带版本写」：每个槽位缓存一个 slotVersions，保存时用 saveIfVersion；如果版本对不上，就交给 ConflictPolicy 处理：

策略行为适合
OVERWRITE（默认）无条件覆盖，后写的赢兼容 1.x 行为；单写者场景
FAIL抛 ConcurrentSessionModificationException 并跳过写入配了分布式会话门禁，宁可报错也不要脏写
APPEND_MERGE重新读最新基线，把这轮新增的消息追上去再重试普通聊天轮次；压缩/摘要轮次不能用

三种取值与取舍注释：ConflictPolicy.java:34；conflictPolicy(...)：ReActAgent.java:5176

注意一个容易误判的点：JsonFileAgentStateStore 不支持版本化，所以哪怕你写了 .conflictPolicy(FAIL)，在单机文件存储上也永远不会触发冲突——saveIfVersion 退化成普通 save。想真正测到冲突，得用 InMemoryAgentStateStore（它支持 CAS）或 Redis。 

import io.agentscope.core.state.AgentState;
import io.agentscope.core.state.AgentStateStore;
import io.agentscope.core.state.InMemoryAgentStateStore;
import io.agentscope.core.state.VersionedState;

AgentStateStore store = new InMemoryAgentStateStore();   // 支持 CAS

// 1) 一次读出「值 + 版本号」；key 不存在时 version 为 0
VersionedState<AgentState> snapshot =
        store.getVersioned("alice", "s-001", "agent_state", AgentState.class);

// 2) 带着版本写：版本对不上 → 返回 UNVERSIONED，且什么都没写
long newVersion =
        store.saveIfVersion(
                "alice", "s-001", "agent_state", snapshot.value(), snapshot.version());

if (newVersion == AgentStateStore.UNVERSIONED) {
    System.out.println("别人先改了，这一轮放弃写入");
}

getVersioned 默认实现（不支持版本化的后端直接报 UNVERSIONED）：AgentStateStore.java:104；saveIfVersion 的三种 expectedVersion 语义：:134；VersionedState 是 record：VersionedState.java:26

旁路读写：不走 agent，直接用 store

写管理后台、做数据迁移、清理脏会话时不需要经过 agent。key 只有一个约定：整份状态叫 "agent_state"。 

import io.agentscope.core.state.AgentState;
import io.agentscope.core.state.AgentStateStore;
import io.agentscope.core.state.JsonFileAgentStateStore;

import java.nio.file.Path;

AgentStateStore store = new JsonFileAgentStateStore(Path.of("state"));

// 读：key 固定是 "agent_state"，类型给 AgentState.class
AgentState state =
        store.get("alice", "s-001", "agent_state", AgentState.class).orElseThrow();

System.out.println("消息条数: " + state.getContext().size());

// 列：只列 alice 这个命名空间下的 sessionId

store 的全部方法：AgentStateStore.java:61；listSessionIds 只按用户列、没有跨用户 API：:222

读出来的是快照，改它不会自动同步

store.get(...) 返回的是独立对象：改它不会进 agent 的 stateCache；而同一个 agent 实例下一次处理该槽位时，还会用自己那份覆盖回去。所以直接改 JSON 只适合离线维护（agent 停机期间），线上会话请走 agent.getAgentState(uid, sid) 或业务接口。

「长期记忆」：还能跑，但整条路都标了废弃

这一段是本章最想省你两小时的地方。官方 1.x 的教程里满是 memory.addMessage()、LongTermMemory、StaticLongTermMemoryHook 的示例；到 2.0.4，这些类都还在、也还能跑，但 io.agentscope.core.memory 整包被标了 @Deprecated(forRemoval = true, since = "2.0.0")，连 builder 的注释都写着「will be removed in the next minor」。换句话说：能编译、能运行，但别在新项目里押注。

类型状态注释里的原话
Memory@Deprecated(forRemoval = true)对话上下文已经在 AgentState.getContext()；这个接口只为 1.x 源码兼容保留，是只写镜像
InMemoryMemory同上用 AgentState 代替
AgentStateMemoryView同上只为废弃的 1.x hook / tool 而存在
StateBackedMemory同上直接用 AgentState.getContext()
LongTermMemory / LongTermMemoryMode / LongTermMemoryTools / StaticLongTermMemoryHook同上注释写「Long-term memory is removed」，但类还在、builder 也还在接线：核心不提供实现，extensions-mem（mem0 / 百炼 / reme）仍实现这套接口

Memory.java:30、InMemoryMemory.java:32、AgentStateMemoryView.java:39、StateBackedMemory.java:33、LongTermMemory.java:66

那「记忆」到底分几层

第 1 层：对话历史（一定有） AgentState.context。全量消息，每轮全部发给模型。长了就贵、就超窗口
第 2 层：压缩摘要（配了中间件就有） AgentState.summary。由压缩中间件写入，把老消息换成一段摘要；官方 harness 叫 compaction
第 3 层：跨会话长期记忆（框架不管了） 核心不再提供实现。要么自己存一张表、按 userId 查出来拼进提示词；要么接外部记忆服务

想做第三层，现在有三条可走的路，都不需要碰废弃的 Memory：

做法怎么做适用
自己拼提示词从你自己的库按 userId 查偏好，拼进 sysPrompt，或用 RuntimeContext 注入 POJO 给工具用偏好、配置这类结构化数据，最可控
接记忆扩展agentscope-extensions-mem 里有 mem0 / 百炼 / reme 几个适配想要「自动提取 + 语义检索」
当检索用agentscope-extensions-rag（bailian / dify / ragflow / haystack）把命中片段拼进消息知识库类记忆
把「记忆」写成一个工具，比写成一个 hook 更 2.0

1.x 靠 hook 在每轮偷偷改写记忆；io.agentscope.core.hook 整包在 2.0 被标成 @Deprecated(forRemoval = true)，官方推荐改用 MiddlewareBase（第 09 章）。现在更自然的做法：给模型一个 recall_memory(query) 工具，让它自己决定什么时候查——工具属于模型，时机也属于模型。

替代写法：把记忆做成一个工具

下面这段不碰任何废弃 API：事实存在你自己的表里（示例用 Map 顶替），userId 从 RuntimeContext 拿——同一个 agent 实例服务不同用户时，记忆天然按人隔离。 

import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.tool.Tool;
import io.agentscope.core.tool.ToolParam;

import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

public class MemoryTools {

    // 真实项目换成 DB / Redis / 向量库；这里只为演示
    private final Map<String, List<String>> facts =
            new ConcurrentHashMap<>();

    @Tool(
            name = "save_memory",
            description = "记住一条关于当前用户的长期事实，例如偏好、身份、长期目标。")
    public String saveMemory(
            @ToolParam(name = "fact", description = "要记住的事实") String fact,
            RuntimeContext ctx) {
        facts.computeIfAbsent(bucket(ctx), k -> new ArrayList<>()).add(fact);
        return "已记住：" + fact;
    }

    @Tool(
            name = "recall_memory",
            description = "回忆当前用户过去告诉过你的长期事实。")
    public String recallMemory(
            @ToolParam(name = "query", description = "想回忆的主题") String query,
            RuntimeContext ctx) {
        List<String> mine = facts.getOrDefault(bucket(ctx), List.of());
        if (mine.isEmpty()) {
            return "没有关于该用户的长期记忆";
        }
        return "关于「" + query + "」我回忆到：\n" + String.join("\n", mine);
    }

    // userId 可能为 null（匿名调用），直接拿去算 key 会 NPE
    private static String bucket(RuntimeContext ctx) {
        String uid = ctx == null ? null : ctx.getUserId();
        return (uid == null || uid.isBlank()) ? "__anon__" : uid;
    }
}

无注解的 RuntimeContext 参数由框架注入：ToolMethodInvoker.java:182；ctx.getUserId()：RuntimeContext.java:106；userId 为空时按 __anon__ 归桶，和框架自己的槽位规则一致：ReActAgent.java:399

模型不会自动调用它

给了模型「什么时候查」的自由，也把责任交给了提示词。sysPrompt 里写清规则，例如「用户说『你还记得』『之前提过』时先调 recall_memory；拿到新的长期事实时调 save_memory」。否则模型往往宁可瞎猜。

陷阱与窍门

1. 不传 sessionId，以为「每个 agent 一份记忆」
你会看到
两个毫不相关的用户互相看到对方的对话；或者明明写了多用户，却总能得到同一个人的上下文。
因为
sessionId 缺省时回退到 defaultSessionId，而它默认就是 agent 的 name。所有不传 session 的调用共用一个槽位。
改成
把 sessionId 当成必传参数（业务会话 id / 对话 id）；确实需要单会话时，在 builder 里显式 .defaultSessionId("chat")。
2. 在中间件/工具里用 agent.getAgentState()
你会看到
压测时偶发「读到了别人的历史」；单线程一切正常。
因为
无参的 getAgentState() 读的是默认槽位，而且已经被标为 @Deprecated。并发下它不对应本次调用。
改成
在中间件、工具、回调里永远用 rc.getAgentState()；确实要读指定会话，用 getAgentState(uid, sid)。
3. 以为每条消息都会落盘
你会看到
进程被强制杀掉后，用户说「刚才那条消息它没记住」；明明上一轮已经回复了。
因为
整份状态只在 call 结束 / 优雅停机时写一次，没有逐条消息的写盘。
改成
关键业务在 call 返回后自己做检查点；部署上确保滚动发布走优雅停机（第 10 章）。
4. 多副本挂 JsonFile 存储
你会看到
同一个用户在 A 节点说完话，请求飘到 B 节点后 agent 失忆；或者两个 pod 同时写同一个 json 文件。
因为
JsonFileAgentStateStore 是本地磁盘实现，既不跨节点也不带 CAS。
改成
多副本必须换 Redis/MySQL 这类共享 store；单机开发才用文件。
5. 还在找 LongTermMemory / Hook 的写法
你会看到
IDE 划掉一片，编译警告一堆；官方 1.x 例子改不动。
因为
io.agentscope.core.memory 和 io.agentscope.core.hook 两个包整体标了 @Deprecated(forRemoval = true)：代码还能编、能跑，但下个小版本就可能删；官方指的方向是 MiddlewareBase + 自己存。
改成
历史用 AgentState.context，跨会话记忆自己接（拼提示词 / extensions-mem / 做成工具）。
6. 用同一个 sessionId 做并发压测
你会看到
单会话吞吐上不去，延迟约等于两次调用之和。
因为
同一槽位被设计成串行：两个循环同时写 context 会弄乱历史。
改成
压测时给每个虚拟用户一个独立 sessionId；旧代码要并发，就多建几个槽位。

自检三问

两次 call 只改 sessionId，第二次能看到第一次的对话吗？

不能。槽位是 (userId, sessionId)，换 sessionId 就是另一个槽位，状态互不可见。反过来，只要两个值都一致，哪怕换一个 agent 实例、换一台机器（共用同一个分布式 store），也能拿到同一段历史。

什么都没配（无 store），连续两次 call 会记得吗？配了 store 后进程重启还认得吗？

第一次「会记得」：内存里有 stateCache。第二次「看情况」：取决于 store 能不能活过进程——InMemoryAgentStateStore 不能，JsonFileAgentStateStore 能，Redis 能且能跨节点。所以「本地调试很顺、上线就失忆」通常是没配 store 或用了内存实现。

为什么框架要把同一 (uid, sid) 的调用串行化？

因为一次 call 是「读 state → 就地改 context → 整份写回」的读-改-写循环。两个循环并行跑同一槽位，后写的会盖掉先写的（或者历史里出现两条无头消息）。串行化是最便宜的保证；跨进程时锁失效，才需要 saveIfVersion + ConflictPolicy 兜底。

20 分钟动手练习

  1. 把状态写成文件看一遍
    用 new JsonFileAgentStateStore(Path.of("state")) 跑一轮带工具调用的对话，然后打开 state/<uid>/<sid>/agent_state.json。对着 JSON 找 context 里的 tool_use / tool_result 块，以及 tool_context 里被你激活过的工具组。这比读文档快得多。
  2. 亲手复现一次串号
    先不传 sessionId，只给 userId（alice / bob）各说一句「我是谁」。因为 userId 不同，两者在各自的槽位里，互不干扰。现在把 userId 也去掉，再问同样的问题——两个「会话」立刻变成同一个槽位，alice 的名字会被 bob 看到。这就是 __anon__ 桶 + defaultSessionId 回退叠加出来的串号。
  3. 对比 clearContext 与新建会话
    先激活一个工具组、存一条 todo，再调 agent.clearContext(uid, sid)，重跑一轮对话。检查两件事：对话是不是空的，工具组和 todo 是不是还在。再对比「换一个 sessionId」的做法，体会「同一会话清空」和「开新会话」的区别。
