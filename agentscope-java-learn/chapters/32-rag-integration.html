32 · RAG：Simple / 百炼 / Dify / Haystack / RAGFlow

第 29 章的长期记忆解决「记住用户偏好」，这一章的 RAG 解决「回答前先查资料」。两者都叫检索，但语义不同： 记忆按用户写事实，RAG 按 query 从知识库找片段。AgentScope 把 RAG 收在 Knowledge 接口下， 只有 addDocuments 与 retrieve 两个方法；和记忆一样，这条路径也从 2.0.0 起被标记弃用。

读完你能做到

  • 说清 Knowledge 的两个方法，以及 GENERIC、AGENTIC、NONE 三种模式各装了什么
  • 区分调用点 RetrieveConfig 与 provider 配置两层参数，知道哪一层真正生效
  • 按「是否自己管索引」选择 Simple、百炼、Dify、HayStack 或 RAGFlow
  • 解释为什么只有 Simple 支持 addDocuments，其余四家只读
  • 识别 2.0.4 里 RAG 包的弃用状态，以及文档里的 STATIC / metadata 两处旧说法
  • 把检索失败、空结果、阈值过高与索引未完成分开排查

RAG 的两个动作：写入与检索

Knowledge 的契约非常小：addDocuments(List<Document>) 把文档嵌入并写入知识库， retrieve(query, RetrieveConfig) 按 query 返回相关文档列表 Knowledge.java:34-57。 RAG 的效果由两段共同决定：写入时怎么切块、怎么 embedding、索引是否最新；检索时用什么 query、topK、阈值与过滤。

阶段要做的事典型故障
写入读取文档、切块、embedding、写向量库切块太大/太小、维度不匹配、索引没跑完
检索query embedding、相似度搜索、阈值过滤、排序阈值过高、topK 太小、过滤条件写错
注入把命中的文档片段交给模型片段太长挤占上下文、角色/顺序不符合预期

外部 RAG 平台（百炼、Dify、HayStack、RAGFlow）把「写入」留在平台侧，Java 只做「检索」； Simple 则把三段都交给你。选型的第一步不是比模型，而是决定「索引由谁管」。

文档与源码的分叉：整条 RAG 路径都是 legacy

官方 RAG 概览仍按 Knowledge 接口介绍五种实现，并给出 .knowledge(...) + .ragMode(...) 的接入方式 overview.md:6-25。 但 2.0.4 源码里，Knowledge、RAGMode 与 RetrieveConfig 都带 @Deprecated(forRemoval = true, since = "2.0.0")，注释写明 rag 包已移除，检索应在应用层集成 Knowledge.java:30-34 RAGMode.java:28-32 RetrieveConfig.java:28-32。

Legacy 能用，但别当新地基

五个适配器仍然实现 Knowledge，ReActAgent 也仍会在 knowledgeBases 非空时装配 Hook 或工具 ReActAgent.java:5600-5605。 新项目应把检索放在应用层，通过工具或显式上下文交给 Agent；第 32 章会同时讲清「现在怎么跑」与「以后往哪搬」。

三种模式：自动注入、主动检索、关闭

RAGMode 只有三个值：GENERIC 用 Hook 在推理前自动检索并注入， AGENTIC 注册一个 retrieve_knowledge 工具让 Agent 自己决定， NONE 什么都不装 RAGMode.java:18-55。 builder 默认是 GENERIC ReActAgent.java:4844-4851。

模式注册什么Agent 侧表现
GENERIC（默认）GenericRAGHook每次推理前自动取最后一条用户消息检索，命中就注入
AGENTICKnowledgeRetrievalToolsAgent 通过 retrieve_knowledge 工具主动检索
NONE什么都不注册知识库挂载但不参与本轮推理
文档写 STATIC，源码是 GENERIC

RAG 概览的示例注释写「或 STATIC、NONE」 overview.md:23， 但 2.0.4 的枚举只有 GENERIC、AGENTIC、NONE RAGMode.java:40-55。 照着文档写 RAGMode.STATIC 会直接编译失败。

两层参数：RetrieveConfig 与 provider 配置

RetrieveConfig 是调用点参数：limit、scoreThreshold、 vectorName 与可选的 conversationHistory；builder 默认 limit=5、 scoreThreshold=0.5，阈值必须在 0–1 RetrieveConfig.java:34-44 RetrieveConfig.java:110-136。 Agent 的默认值同样是 5 / 0.5 ReActAgent.java:4849-4851。

但 provider 配置里还有一套默认值：Dify 的 topK=10、scoreThreshold=0.0； RAGFlow 的 topK=1024、similarityThreshold=0.2；HayStack 的 topK=3。 这些值在「直接调 knowledge.retrieve(query, config)」时才可能作为 fallback；一旦走 Agent， RetrieveConfig 的 limit / threshold 会传给适配器并覆盖它们 DifyRAGConfig.java:47-53 RAGFlowConfig.java:35-47 HayStackConfig.java:35-41。

文档里的 metadata 字段不在 RetrieveConfig 里

Simple 文档的检索参数表列了 metadata simple.md:97-101， 但 2.0.4 的 RetrieveConfig 只有 limit、scoreThreshold、vectorName、conversationHistory，没有 metadata RetrieveConfig.java:34-37。 需要 metadata 过滤时，用 provider 自己的配置：Dify 的 MetadataFilter、RAGFlow 的 metadata 字段， 或 Simple 在向量库层自己做。

Simple：自己管读取、切块、embedding 与向量库

Simple 是唯一负责写入链路的实现：它自带文档 Reader、TextChunker / SplitStrategy、 四种 embedding 适配，以及 InMemory、PgVector、Milvus、Qdrant、Elasticsearch 五种向量库适配 simple.md:6 simple.md:55-91。 SimpleKnowledge 的 builder 只要求 embedding 模型与向量库两个依赖，缺一个就抛异常 SimpleKnowledge.java:85-93。 

SimpleKnowledge knowledge = SimpleKnowledge.builder()
    .embeddingModel(embeddingModel)
    .embeddingStore(InMemoryStore.builder().dimensions(1024).build())
    .build();

knowledge.addDocuments(new TikaReader().read(input).block()).block();

写入时它逐条文档生成 embedding，再批量写入向量库 SimpleKnowledge.java:97-132。 检索时它把 scoreThreshold 先置空交给向量库，再在 Java 侧按阈值过滤、按分数倒序，最后应用 limit SimpleKnowledge.java:135-173。 这也解释了为什么阈值改变会直接影响返回条数，而不是「让向量库少查一点」。

百炼：托管索引，Java 只检索

百炼适合「文档已经在控制台上传并解析完成」的团队。配置需要 AccessKey、workspaceId 与 indexId， 可选 rerank 与 rewrite；后者会基于对话历史改写 query bailian.md:6-45 bailian.md:67-80。 默认 endpoint 是 bailian.cn-beijing.aliyuncs.com BailianConfig.java:52。 

BailianConfig config = BailianConfig.builder()
    .accessKeyId(System.getenv("ALIBABA_CLOUD_ACCESS_KEY_ID"))
    .accessKeySecret(System.getenv("ALIBABA_CLOUD_ACCESS_KEY_SECRET"))
    .workspaceId("llm-xxxxxx")
    .indexId("kb-xxxxxx")
    .build();

BailianKnowledge knowledge = BailianKnowledge.builder().config(config).build();

BailianKnowledge.addDocuments 直接返回 UnsupportedOperationException， 文档管理必须走百炼控制台或平台 SDK BailianKnowledge.java:131-133。 它会把 RetrieveConfig.conversationHistory 转成百炼的 query history，供 rewrite 使用 BailianKnowledge.java:184-208。

Dify：数据集 + 四种检索模式

Dify 适合内容运营已经在 Dify 上维护知识库的团队。它支持关键词、语义、混合与全文四种检索模式，默认是 HYBRID_SEARCH；还能通过 MetadataFilter 按数据集元数据过滤 dify.md:48-57 dify.md:72-89。 base URL 默认 https://api.dify.ai/v1，自托管改 baseUrl DifyRAGConfig.java:47-53 dify.md:59-70。 

DifyRAGConfig config = DifyRAGConfig.builder()
    .apiKey(System.getenv("DIFY_RAG_API_KEY"))
    .datasetId("your-dataset-id")
    .retrievalMode(RetrievalMode.HYBRID_SEARCH)
    .enableRerank(true)
    .build();

和百炼一样，Dify 的 addDocuments 返回 UnsupportedOperationException， 文档上传与索引在 Dify 控制台完成 DifyKnowledge.java:124-131。 检索结果会按 scoreThreshold 过滤、按分数倒序、再按 limit 截断 DifyKnowledge.java:183-199。

HayStack：复用已有索引流水线

HayStack 适合已经有一整套索引流水线（分块、ChromaDB、Reranker 等）的团队。Java 侧只配置服务地址、topK 与过滤策略， 其余交给 HayStack haystack.md:6-42。 配置默认 topK 是 3、超时 30 秒、最多 3 次重试、成功码 0 HayStackConfig.java:35-41。 

HayStackConfig config = HayStackConfig.builder()
    .baseUrl("http://localhost:8080")
    .topK(10)
    .build();
HayStackKnowledge knowledge = HayStackKnowledge.builder().config(config).build();

addDocuments 抛 UnsupportedOperationException，文档更新要回到 HayStack 的 source 目录并重跑索引流水线 HayStackKnowledge.java:109-113。 检索失败会记录日志后重新抛错，不会静默返回空 HayStackKnowledge.java:209-213。

RAGFlow：复杂文档解析与可配置重排

RAGFlow 适合扫描件、复杂排版 PDF、含图片表格比例高的知识库。它调用 POST /api/v1/datasets/{dataset_id}/retrieve-chunks，支持向量相似度、topK、服务端相似度阈值、 metadata 过滤与可选 rerank ragflow.md:6-58。 配置自身默认 topK 是 1024、相似度阈值 0.2、向量权重 0.3、分页 30、超时 30 秒 RAGFlowConfig.java:35-47。 

RAGFlowConfig config = RAGFlowConfig.builder()
    .apiKey("ragflow-xxxxxxxx")
    .baseUrl("http://localhost:9380")
    .knowledgeBaseId("kb-xxxxx")
    .topK(10)
    .similarityThreshold(0.5)
    .build();

addDocuments 同样不可用；文档上传与索引走 RAGFlow 控制台或它自己的 API RAGFlowKnowledge.java:182-184。 RAGFlow 的 retrieve-chunks 接口不支持把对话历史传过去做上下文感知检索；需要时只能自己在 query 前拼指令 ragflow.md:58。

四家外部实现的 addDocuments 都返回 UnsupportedOperationException，这是刻意的「管控分离」： 避免 Java 侧与平台侧各维护一份索引状态 overview.md:45。

写入链路：Simple 要自己保证「切块与索引一致」

Simple 的 addDocuments 不做切块，它假定你传进来的 Document 已经是切好的片段； 它只负责逐条 embedding、写入向量库 SimpleKnowledge.java:97-132。 所以 Simple 的写入质量取决于三件事：

  1. 切块
    用 TextChunker / SplitStrategy 控制片段大小与重叠；块太大检索不精准，太小丢上下文。
  2. Embedding 维度
    embedding 模型维度必须与向量库 dimensions 一致；换模型要重建索引，不能只改配置。
  3. 更新语义
    文档更新是新增、覆盖还是删除旧片段，要由你的写入流程决定；addDocuments 不做去重。

外部四家的写入在平台侧，Java 侧无法保证「上传完成」与「索引完成」同时发生；检索为空时先确认平台索引状态， 而不是先调 Java 阈值。

多知识库：合并、去重、排序

ReActAgent 允许挂多个 Knowledge。多个知识库会被聚合成一个：分别检索， 按文档 id 去重（同 id 取分数更高的），再按分数倒序，最后用 RetrieveConfig.limit 截断 ReActAgent.java:5513-5551。 这意味着：

  • 不同知识库返回相同 id 的文档会被合并，不会重复占用 topK
  • 排序只按分数，不按来源权重；要加权只能在 provider 侧或拿到结果后自己做
  • limit 是合并后的总上限，不是每个知识库各取 limit

失败边界：Hook 会静默，工具会返回字符串

GENERIC 的 Hook 在检索失败时只打日志，不打断主流程 GenericRAGHook.java:161-166； AGENTIC 的工具失败时返回 "Failed to retrieve knowledge for query: ..." 字符串 KnowledgeRetrievalTools.java:162-166。 直接调 Knowledge.retrieve(...).block() 则可能收到 provider 抛出的异常（HayStack 会重新抛，Dify / Bailian 会记录后抛）。

运维：索引、阈值、延迟与权限

索引一致性是第一位。外部平台写完文档不等于索引完成；Simple 写完向量库也不等于旧文档已删除。 检索为空时先看平台索引状态或向量库条数，再调阈值。

阈值是精度与召回的直接旋钮。默认 0.5 只是起点；不同 embedding / 平台的分数分布不同， 拿一组真实问题测召回，比照搬默认值可靠。RAGFlow 自身默认阈值是 0.2，Dify 是 0.0，不能混用。

延迟与费用。百炼 rerank / rewrite、Dify rerank、RAGFlow rerank 都会增加一次远程调用； topK 越大，注入 prompt 的 token 越多。先测命中率，再开增强。

弃用之后：RAG 该往哪搬

路径怎么做适合代价
冻结 legacy保留 Knowledge 适配器，外面包一层自己的检索接口已有生产流量仍受弃用 API 约束
检索工具化把知识库检索写成 @Tool，Agent 按需调用想控制何时检索、返回多少要自己写工具与错误处理
提示注入应用层先检索，再把片段作为上下文传给 Agent固定流程、需要严格控 token检索与 Agent 解耦，需自己做编排
保留平台索引百炼 / Dify / HayStack / RAGFlow 继续管索引，只换 Java 侧接入方式内容运营在平台平台与 Agent 两套权限要打通

和记忆一样，弃用的是「Agent 内置 RAG 管线」，不是「不要做 RAG」。把检索做成应用层工具，反而更容易控制权限、阈值、 缓存与评测。

六个坑：把「检索」当成「插入 prompt」

坑一：把 RetrieveConfig 当万能过滤。它没有 metadata 字段；metadata 过滤要用 provider 配置或自己包一层 RetrieveConfig.java:34-37。

坑二：照文档写 RAGMode.STATIC。源码枚举是 GENERIC / AGENTIC / NONE RAGMode.java:40-55。

坑三：对外部平台调 addDocuments。百炼 / Dify / HayStack / RAGFlow 都只读； 写入走平台控制台或 API overview.md:45。

坑四：以为改了 provider topK 就生效。Agent 走 RetrieveConfig，limit 会覆盖 provider 默认； provider 的 10 / 1024 / 3 只在直接调用且没传 limit 时才有意义。

坑五：索引没完成就调阈值。外部平台的文档需要解析与索引时间；空结果先查平台状态。

坑六：把 RAG 当长期记忆。RAG 按 query 查文档，记忆按用户存事实；两者的写入、删除与隔离键都不同 overview.md:6。

自测：三个判断题

RAGMode 的默认值是什么？

GENERIC：用 Hook 自动检索并注入，不是 AGENTIC，也不是文档里的 STATIC ReActAgent.java:4846-4847 RAGMode.java:40-55。

百炼、Dify、HayStack、RAGFlow 都能通过 addDocuments 上传文档吗？

不能。四家都只负责检索，addDocuments 会抛 UnsupportedOperationException； 只有 Simple 支持写入 overview.md:45 HayStackKnowledge.java:109-113。

Agent 挂载知识库后，检索失败一定报错吗？

不一定。GENERIC Hook 会记日志后继续；AGENTIC 工具会返回错误字符串。 只有直接调用 Knowledge.retrieve 时，provider 才可能把异常抛给你 GenericRAGHook.java:161-166 KnowledgeRetrievalTools.java:162-166。

练习：给「内部文档问答」选一条 RAG 路径

目标不是接通一个知识库，而是能解释「索引归谁、阈值怎么定、失败时谁兜底」。建议 50 分钟：

  1. 先定索引归属
    写下文档规模、更新频率、是否需要 OCR；决定用 Simple 自建还是外部平台托管。
  2. 选一个实现
    在五个实现里选一个，记录必填参数、默认 topK / 阈值与索引更新方式。
  3. 跑 GENERIC
    用默认模式发一个能命中知识库的问题，确认注入的 <retrieved_knowledge> 出现在消息列表末尾。
  4. 切 AGENTIC
    改成工具模式，观察模型是否主动调用 retrieve_knowledge，以及 limit 参数是否被使用。
  5. 调阈值
    把 scoreThreshold 从 0.5 调到 0.2 与 0.8，记录命中条数与答案质量的变化。
  6. 制造空结果
    用平台未索引的文档提问，记录 Hook 与工具各自的返回形态。
  7. 验证写入边界
    对选中的后端调用 addDocuments，确认是支持还是 UnsupportedOperationException。
  8. 写三行结论
    分别写「索引谁管」「检索参数怎么生效」「失败谁兜底」，确保每行都能在日志或源码里找到证据。
