16 · 技能：从 SKILL.md 到治理

工具解决「能做什么」，技能解决「怎么做才对」。一个技能就是一个目录 + 一份 SKILL.md：元数据每轮进 prompt，正文和参考资料等模型真正需要时再加载。这一章从最底层的问题开始——模型怎么知道有哪些技能、凭什么相信加载的是这一个——一路走到四层合并、load_skill_through_path、files-root、skill_manage 六动作、晋升闸门、使用计数与 curator 归档。和官方文档的分歧集中在两处：默认闸门到底做了什么，以及所谓的「LLM 伞合并」其实还不存在。

读完你能做到

  • 写出一个能被正确解析的 SKILL.md，并知道 name/description/正文三者缺一个会发生什么
  • 背下四层来源的优先级顺序，并说出 skillRepository(...) 重复调用时谁覆盖谁
  • 解释 skillId = name + "_" + source 为什么必须带 source，以及同名仓库自动改名的规则
  • 画出 <available_skills> 的渲染条件，说清 <files-root> 在三种文件系统模式下的取值
  • 把 skill_manage 的六个动作、写入落点与安全扫描串起来，指出草稿为什么「看不见」
  • 说清晋升闸门的三值决策、默认 RejectAllGate 的真实行为，以及为什么官方示例里的 defaultPrompter() 永远批不下来
  • 指出 curator 的状态机、归档路径，以及「LLM 伞合并」与源码的差距

先说为什么：技能是「按需展开的程序性知识」

一段「怎么评审代码」「怎么发版」「怎么排查线上 502」的流程，动辄几千字。把它们全塞进 system prompt，成本随技能数量线性上涨，而且模型大部分轮次根本用不上。技能机制把这个成本拆成三级：

第一级：只给清单
每轮推理前，所有可见技能以 <skill> 条目进 prompt，只有 name、description、skill-id，以及可选的 files-rootSkillPromptBuilder.java:165-179。模型先判断「这事跟我有没有关系」。
第二级：加载正文
决定要用，才调 load_skill_through_path(skillId, "SKILL.md")，把完整文档取回来SkillLoadTool.java:195-201。这一步的返回内容会作为工具结果进入上下文。
第三级：按题取资料
正文里写了「详见 references/style-guide.md」，模型再发一次同一个工具，只取那一个文件；脚本则通过 shell 执行 <files-root>/scripts/...ShellPathPolicy.java:100-151。

这套「渐进披露」与第 15 章的 MEMORY.md 注入是两种思路：记忆是框架主动把文件塞进 prompt 并做预算截断；技能是模型主动决定加载哪一份，框架只负责列出候选、解析路径、守住可见性边界。

技能不是工具

工具是 Toolkit 里的可调用函数；技能是纯文本 + 资源，最终仍要靠 load_skill_through_path（读）和 execute（跑脚本）落地。所以一个没有 shell、没有文件系统工具的 agent，照样能读技能——只是跑不了技能自带的脚本。

SKILL.md 的硬约束：三个字段，一条正则

目录结构没有魔法，就三层： 

<workspace>/skills/<skill-name>/
├── SKILL.md            # 必需：YAML front matter + 正文
├── references/         # 可选：长篇资料
├── templates/          # 可选：模板
├── scripts/            # 可选：可执行脚本
└── assets/             # 可选：图片等静态资产

两个容易忽略的点：

  • 技能的身份不是 name，而是 skillId。它由 getName() + "_" + getSource() 拼成AgentSkill.java:263-269。同一个 code-reviewer 从 Git 市场来是 code-reviewer_git，从工作区来是 code-reviewer_workspace-namespaced，两者可以共存。所以调用工具时第一个参数是 skillId，不是目录名。
  • 正文里只写相对路径。绝对路径在沙箱里会失效；框架会为每个技能算出自己的 <files-root>，模型用这个前缀拼 shell 命令。

技能是怎么被「发现」的：一次 glob 加一条过滤

工作区侧的仓库实现是 WorkspaceSkillRepository。它不是遍历目录树，而是向当前文件系统视图要一次 glob：glob(ctx, "SKILL.md", "skills")，对每个命中读全文、解析成 AgentSkillWorkspaceSkillRepository.java:150-186。这里有两个关键设计：

  1. 资源不预加载
    注册时只读 SKILL.md，references/、scripts/ 全部留空，等 load_skill_through_path 时再按 resourcesFor(name, ctx) 懒加载:177-180。这样一个几百份技能的工作区也不会在启动时把磁盘读穿。
  2. 元数据子树被整棵跳过
    hasMetadataAncestor 会丢掉 skills 下第一段以 _ 或 . 开头的路径：_drafts/、.archive/、.audit/、.backups/:501-559。这就是「草稿写进去但模型看不见」的真正原因——不是权限，是枚举阶段被过滤了。
  3. 坏的 SKILL.md 只 warn，不中断
    单个技能解析抛异常会被 catch，记一条 Failed to load skill from ...，其余技能照常返回:181-184。所以「少了一个技能」通常要去看日志，而不是等一个报错。

读取资源时还有一道防穿越：sanitize 拒绝以 / 开头或包含 .. 的相对路径:642-651。别指望用 path="../../MEMORY.md" 读到技能目录外的文件。

四层合并：谁覆盖谁

build() 的第一件事是把四个来源按优先级拼成一个有序列HarnessAgentBuilderSupport.java:877-919：

优先级来源怎么开注册条件

  • 工作区共用覆盖所有市场；用户目录覆盖工作区共用。官方那张优先级表和代码一致。
  • 第 1 层目录不存在时不会报错，也不会占位——这是「配了但没生效」最常见的来源。
第 3 层依赖「宿主路径存在」

第 3 层用的是 wsManager.getSkillsDir() 返回的 Path，注册前做的是 Files.isDirectory:896-907——这是宿主 JVM 的本地文件检查。沙箱或远程文件系统模式下，如果这个目录在宿主侧不存在，第 3 层会被跳过；第 4 层走 AbstractFilesystem，不受影响。实践含义：别把「共用技能」只放在第 3 层然后指望它在所有模式下都在；要么确认宿主目录存在，要么接受第 4 层作为统一入口。

子 agent 不需要重复配置。构建子 agent 时，父级的市场列表、skillFilter、disableDefaultWorkspaceSkills、projectGlobalSkillsDir 都会被复制过去HarnessAgentBuilderSupport.java:334-405。

load_skill_through_path：四步查找与一条授权边界

工具名是常量 load_skill_through_pathSkillLoadTool.java:57，参数只有两个：skillId（必填）与 path（必填，SKILL.md 表示正文）。查找顺序固定四步:195-219：

  1. ① path 等于 SKILL.md
    直接返回完整文档：一段头部信息（skillId / name / description / source / files-root）+ 四反引号围栏里的 MarkdownSkillParser.generate(metadata, content)，也就是 front matter + 正文都给你:232-256。javadoc 写明了原因：早先只返回正文，模型拿 patch 去改 front matter 附近时总是匹配失败。
  2. ② 内存命中
    skill.getResources().get(path)。市场技能、classpath 技能、非懒加载的工作区技能都在这一层命中。
  3. ③ 懒加载兜底
    仓库实现了 LazyResourceCapable 就再试一次 lazyResources().read(path)，走的是当前调用的 RuntimeContext，所以 per-user 命名空间与沙箱路由都跟着生效。
  4. ④ 找不到时给清单，不给死路
    返回 Resource not found: '...' in skill '...'，下面列出 SKILL.md + 内存资源 + 懒加载 list() 的全部可用路径:277-311。模型下一轮能自己改对。
catalog 就是授权边界

每次调用可见的技能集合被写进 RuntimeContext（key 是 SkillCatalog.class），工具只在这个 catalog 里查 skillIdSkillRuntime.java:112-130。这意味着：某个技能即使存在于磁盘、即使别的会话能看到，只要它没在本次过滤后的 catalog 里，这次调用就加载不到。可见性过滤不是「提示词建议」，是运行时约束。

另一个细节：这个工具是未分组注册的，而且注册时会先移除同名旧工具再装自己的实例:86-110。未分组的含义是：它不受会话里持久化的「激活工具组」列表影响，老会话升级后也能立刻用。

市场技能的物化由 MarketplaceStager 负责，三个行为值得记住：

  • 按文件 SHA-256 去重：内容没变就不重写，只补变化的文件:304-345。
  • 孤儿目录有 30 分钟宽限：不在本轮白名单里的目录要「静置」超过 DEFAULT_ORPHAN_GRACE 才删:92。原因是缓存按 scope 分片共享，A 调用的「孤儿」可能正是 B 调用正在用的 files-root。
  • 补回执行位：入库时资源变成字符串，POSIX 权限丢了；stager 用「首行 shebang 或已知脚本后缀」判断，按 chmod +x 语义只给已有读权限的位加执行位:314-358。
scope 段是文档里没有的

三道过滤：可见性 → 白黑名单 → tools.json

一个技能要从「磁盘上有」走到「模型能加载」，要过三道闸，顺序固定：

① 可见性过滤（per-call）

  • 接口 SkillVisibilityFilter，先执行:275-276
  • EnvironmentFilter：sidecar 的 environments 不含当前环境就隐藏
  • CanaryFilter：对 userId × skillName 取稳定哈希，落在百分比内才可见
  • AllowListFilter：只放白名单里的名字
  • CompositeFilter：依次串联多个过滤器
  • 除 EnvironmentFilter 外都继承 AbstractAgentCreatedFilter，只约束 created_by="agent" 的技能，手写技能原样放行

② 技能白黑名单（builder）

  • SkillFilter.only(...) / except(...) / all() / none()
  • builder 级用 enableSkills、disableSkills、skillsEnabled 设置
  • 运行时可以在 RuntimeContext 放一个 overlay，由 builderFilter.overlay(ctx) 合并:325-327
  • 被这里挡掉的技能，同样进不了 catalog

第三道在 build() 的最后：tools.json 的 allow/deny 会作用到整个 Toolkit，包括 load_skill_through_path:2933-2937。这一条很多人踩过：技能清单还在 prompt 里，加载工具却被 deny 掉了，模型只能看到名字、点不开。

可见性过滤器异常 = 全部放行

内置闸门行为什么时候用
RejectAllGate（默认） 永远返回 Defer，理由写死为「promotion requires explicit HarnessAgent.promoteSkill」RejectAllGate.java:23-46 没有接审核系统，只想让业务代码手动批
LocalApprovalGate 把候选包交给 Prompter，超时（默认 30 分钟）或异常都变 Defer；默认目标环境 ["prod"]LocalApprovalGate.java:50-88 CLI / IDE 里人工确认
NotifyAndWaitGate 先推通知、立刻 Defer；真正的批准由外部回调触发再次 promoteNotifyAndWaitGate.java:34-93 IM / 工单审批
默认闸门不是「拒绝」，是「延期」

类名叫 RejectAllGate，但返回的是 Defer。差别很实际：Reject 意味着这份草稿废了，Defer 意味着它还在 _drafts/ 里等你手动批。所以「什么都没配」时，最省事的路径不是改配置，而是在业务代码里调 agent.promoteSkill(name, reviewerId, ctx)——它绕过的是「自动问闸门」，不是「安全扫描」（扫描在问闸门之前，照样跑）。

另一个坑在官方示例里：new LocalApprovalGate(LocalApprovalGate.defaultPrompter()) 看着像「本地人工确认」，但 defaultPrompter() 的实现是永远 Defer（javadoc 写的是 “never approves. Suitable for tests”）:82-88。真要用，得自己写 Prompter，或者用 stdinPrompter(in, out)。promoteSkill 的返回值也是四种：approved / rejected / deferred / invalid，其中 invalid 专门表示「前置条件不满足」（没配 promoter、草稿不存在、搬目录失败）HarnessAgent.java:306-326。

view 计数会落到另一个 key 上

把两条源码事实并排放：中间件从工具入参里取的是 skillId（形如 notes-taker_workspace-namespaced）:110-129；而晋升/写入 sidecar 时用的是纯技能名 notes-takerSkillPromoter.java:150-157。bumpView 又要求该 key 上已有 created_by 记录，否则原样返回（no-op）SkillUsageStore.java:184-200。结果是：正常链路里 view 计数不会累加，curator 判断活跃度主要靠 lastPatchedAt 与 createdAt。要自己补，就在业务侧按纯名字调 usageStore.bumpView(name)，别指望中间件。

审计侧没有这个问题：skill_manage 的每次写、promoteSkill 的每次批准都会 append 一行，带 beforeHash/afterHash，能还原「谁在什么时候把哪份内容换掉了」。queryAudit 只读某一天的文件，传 null 表示今天SkillAuditLog.java:39-52。enableSkillManageTool 没开时它返回空列表，不会报错。

打开 enableSkillCurator(config) 后，中间件会在每次 call() 完成时问一次「现在该跑吗」；该跑就丢到单线程 daemon executor，不阻塞调用方SkillCuratorMiddleware.java:32-80。默认参数：

节流有两层：.curator_state.json 里的 last_run_at 保证跨 JVM 重启也不会跑太勤；PeriodicGate 再保证多副本只有一个实例真正跑SkillCurator.java:152-185。第一次运行不会执行：它只把 last_run_at 种进去就返回 false，所以「刚部署就想看效果」得手动 runCuratorOnce()。

所谓的「LLM 伞合并」还没实现

官方文档写「可选叠加一个 LLM『伞合并』扫描（默认只 dry-run，输出报告，不实际改）」，读起来像是一次模型调用。源码里 runUmbrellaDryRunReport 的 javadoc 直接承认：prompt 与 LLM 调用被推迟到未来版本，当前实现只是把技能名按第一个 -_. 之前的段做聚类，写一份 skills/.curator_reports/<ts>/REPORT.md，内容是「前缀聚类 + 一个空的 consolidations: [] YAML 块」SkillCurator.java:248-324。没有模型、没有合并建议，只有分堆。

陷阱与窍门

1. SKILL.md 写了，模型却完全看不到
你会看到
<available_skills> 里没有这个技能，也没有任何异常；只有 DEBUG 日志里一行 Failed to load skill from ...。
因为
单个技能解析失败会被 catch 后跳过，不阻断整批:172-184。常见原因：缺 description、正文为空、文件放在了 _drafts/ 或 .archive/ 下被元数据过滤掉。
改成
先确认 front matter 三个字段齐全，再用 Files.walk 自查目录里是否存在两级以内的 SKILL.md；最后看日志。
2. 开了 curator，但它从来没跑过
你会看到
.curator_state.json 里只有 last_run_at 和一个 deferred first run 的摘要，.curator_reports/ 一直是空的。
因为
首次运行只 seed 不执行；之后还要等满足 intervalHours 并拿到 PeriodicGate 的 claim:159-185。另外 curator 嵌在 enableSkillManageTool 分支里，没开工具就根本没建:2783-2857。
改成
验证阶段直接 agent.runCuratorOnce().block()；上线后再依赖自动节流。
3. promoteSkill 永远返回 deferred
你会看到
结果里 deferred，理由固定是 “RejectAllGate: promotion requires explicit HarnessAgent.promoteSkill”。
因为
没配 enableSkillPromotionGate，build() 用了 new RejectAllGate():2831-2841。注意：调 promoteSkill 本身也要过这道闸门，它不是「绕过闸门」，只是「绕过自动询问」。
改成
要么给一个真的会 Approve 的 gate，要么自己实现 SkillPromotionGate 直接返回 Approve(reviewerId, List.of("prod"), Instant.now())。
4. 用技能名调 load_skill_through_path，一直 not found
你会看到
Resource not found 或 Unknown skillId，但技能明明就在 skills/code-reviewer/。
因为
catalog 的键是 skillId，格式 <name>_<source>AgentSkill.java:263-269。工作区来的通常是 code-reviewer_workspace-namespaced。
改成
让模型自己从 prompt 里的 <skill-id> 复制；手写调用时先 SkillCatalog.ids() 看一眼。
5. 以为 curator 会删掉没用的技能
你会看到
skills/ 下目录不见了，但 skills/.archive/ 里多了一份带时间戳的副本。
因为
删除走的是 filesystem.move，不是递归删除:272-308。要真删，得自己清 .archive/。
改成
把 .archive/ 纳入备份/清理流程；不要期待框架帮你回收磁盘。
6. patch 总是匹配不上
你会看到
报错说 old_string 不唯一或找不到，即使那段文字确实在 SKILL.md 里。
因为
load_skill_through_path 返回的是含 front matter 的完整文档，模型复述 old_string 时可能少写了 --- 或空行；patch 是在磁盘原文上做精确替换。
改成
让模型先 path="SKILL.md" 读一次、直接从返回内容里复制要替换的片段；大批修改用 edit 整篇重写更稳。
7. 改了 skills/<name>/SKILL.md，下一轮还是旧内容
你会看到
磁盘上是新文本，prompt 里的 description 还是旧的，加载出来的正文也是旧的。
因为
只有关掉动态合并（disableDynamicSkills()）才会冻结快照；默认是每轮重新读，所以更可能的原因是改了另一个仓库的同名技能（被更高优先级覆盖）或改的是一份被市场版本顶掉的副本。
改成
打印 catalog 里胜出条目的 source，确认到底是哪一层在生效；再对照四层优先级表。

自检三问

Git 市场、工作区共用目录、用户目录各有一个 code-reviewer，模型最终看到几个？

一个。mergeRepositories 按 compose 顺序写同一个 LinkedHashMap，键是技能名，后面的覆盖前面的:344-376。compose 顺序是项目全局 → 市场 → 工作区共用 → 用户目录，所以用户目录那份胜出；另外两份不会出现在 <available_skills> 里。注意「看到几个」和「磁盘上有几个」是两件事。

为什么 skill_manage(create) 写的草稿，load_skill_through_path 加载不到？

因为草稿落在 skills/_drafts/<name>/，而枚举时 hasMetadataAncestor 会跳过 skills 下第一段以 _ 或 . 开头的路径:501-559；同时 draftsRepo 不是第 4 层那个 workspace-namespaced 视图，四个合成仓库里没有任何一个扫 _drafts。所以草稿既不进 prompt，也不进 catalog——这是设计，不是权限问题。

默认闸门叫 RejectAllGate，为什么说它其实什么都不拒绝？

因为它返回的是 PromotionDecision.Defer，不是 Reject:23-46。Defer 只表示「这次不批」，草稿保留、随时可以再 promote；Reject 才带「这份不行的理由」。它的真实用途是：没有审核系统时，把「自动晋升」关掉，逼业务层显式调 promoteSkill。

20 分钟动手练习

  1. 看见 skillId 与 files-root
    建一个 skills/hello/SKILL.md（带 name/description/正文），用 LocalFilesystemSpec + 默认 shell 起一个 agent，开 DEBUG 日志，问它「有哪些技能」。从日志里抄下 <skill-id> 和 <files-root>，确认后缀是 workspace-namespaced，路径是宿主绝对路径。
  2. 验证四层覆盖
    在 workspace/skills/hello/ 与 workspace/alice/skills/hello/ 各放一份 description 不同的同名技能，用 userId=alice 调一次，确认 prompt 里只有一份、且是 alice 那份。再把 alice 那份删掉，确认回落到共用版。
  3. 走一遍「草稿 → 晋升 → 可见」
    .enableSkillManageTool(SkillManageConfig.defaults())，让模型调 skill_manage(action="create", ...)，确认文件落在 skills/_drafts/ 且下一轮 prompt 里没有它。然后手动 agent.promoteSkill(name, "me", ctx).block()，观察返回值是 deferred（默认闸门），目录仍在草稿区；再加上一个直接返回 Approve 的自定义 gate 重试，确认目录被 move 到 skills/<name>/、下一轮出现。
  4. 看 curator 真的只归档
    把 .usage.json 里某个 agent 技能的 created_at 改到 100 天前，调 runCuratorOnce()，确认返回值 archived=1、目录出现在 skills/.archive/、状态变成 archived。再检查 skills/.curator_reports/<ts>/REPORT.md，确认里面只有前缀聚类和空的 consolidations: []——没有 LLM 结论。

完成这一章之后

到这里，「能力怎么被组织、怎么被治理」就闭环了：技能负责程序性知识，工具负责原子动作，三件治理设施（闸门、计数、curator）负责不让这套东西失控。下一章回到「一次任务怎么被约束」：计划模式的只读边界、tools.json 的加载与过滤，以及 Harness 侧的 MCP 注册。
