02 · 第一个 Agent

30 行代码写一个「有记忆」的智能体：第一轮告诉它你叫什么，第二轮用同一个会话问「我叫什么」，它答得出来。 本章把 HarnessAgent.builder() 上每个链式调用拆开，并告诉你跑完之后硬盘上多出来的两棵目录 树各自是什么。

读完你能做到

  • 不看文档、自己写出一个能跑两轮且第二轮记得第一轮内容的 Java 程序
  • 说出 name / sysPrompt / model / workspace / compaction 各自在哪一步生效，以及它们的默认值
  • 解释 RuntimeContext 里的 userId 和 sessionId 是怎么变成磁盘路径的，从而能预判「换个 sessionId 会发生什么」

先说为什么：第一个例子为什么不是 ReActAgent

框架里有两个入口。ReActAgent 在 agentscope-core，是纯粹的「推理 → 调工具 → 观察 → 再推理」循环引擎；HarnessAgent 在 agentscope-harness，内部 包着一个 ReActAgent，在外面套上工作区、会话持久化、长期记忆、对话压缩、子 agent、沙箱这些工程能力。

HarnessAgent
工作区目录 + 人格文件 + 会话状态落盘 + 压缩 + 长期记忆 + 工具与技能装载。HarnessAgent.java:1196 —— Builder 里第一个字段就是 ReActAgent.Builder inner，说明它是包装而非 平行实现。
ReActAgent
推理循环本体：模型调用、工具执行、迭代控制
Model / Toolkit / Memory / Permission / Middleware
循环每一步用到的零件，04 ~ 09 章逐个拆开

官方文档同样把 HarnessAgent 定为推荐入口，理由很直接：「把工作区、长期记忆、会话持久 化、子 agent、沙箱等工程能力打包在一个 builder 里」。quickstart.md:13

那什么时候该从 ReActAgent 开始

当你只需要「把消息发给模型、模型爱调哪个工具就调哪个工具」的 API，不需要工作区、不需 要跨进程恢复状态时，agentscope-core 就够了。quickstart.md:31 第 10 章会把两者摆在一起做选型对比。本章先用 HarnessAgent，因为「第二轮记得第一轮」是 最容易让人一眼确认「框架真的在管状态」的现象。

第 3 步：主程序

下面这份文件与官方 quickstart 的例子逐字一致（包括注释），复制即可编译：quickstart.md:49 

import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.UserMessage;
import io.agentscope.harness.agent.HarnessAgent;
import io.agentscope.harness.agent.memory.compaction.CompactionConfig;
import java.nio.file.Paths;

public class FirstAgent {
    public static void main(String[] args) {
        HarnessAgent agent = HarnessAgent.builder()
                .name("note-taker")
                .sysPrompt("你是一个帮助用户做笔记的助手。")
                // 字符串形式由 ModelRegistry 解析 —— 自动读取 DASHSCOPE_API_KEY；
                // 切换其他厂商时改用 "openai:gpt-5.5"、"anthropic:claude-sonnet-4-5"、
                // "gemini:gemini-2.0-flash" 或 "ollama:llama3"。
                .model("dashscope:qwen-plus")
                .workspace(Paths.get(".agentscope/workspace"))
                .compaction(CompactionConfig.builder()
                        .triggerMessages(30)
                        .keepMessages(10)
                        .build())
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .sessionId("demo-session")
                .userId("alice")
                .build();

        // 第一轮：自我介绍 + 当天的事
        agent.call(new UserMessage("我叫天宇，今天准备一个关于 ReAct 的技术分享。"), ctx).block();

        // 第二轮：同 sessionId，自动恢复上一轮状态后回答
        agent.call(new UserMessage("我叫什么？我今天要干什么？"), ctx).block();
    }
}

官方例子不打印返回值，靠「第二轮能不能答对」来证明状态生效。想亲眼看输出，把第二轮那一行换成： 

var answer = agent.call(new UserMessage("我叫什么？我今天要干什么？"), ctx).block();
System.out.println(answer.getTextContent());
关于 getTextContent()

Msg.getTextContent() 会把消息里所有 TextBlock 的文本用换行拼接后返回（没 有文本块时返回空串）Msg.java:544。工具调用、思考块这些内容它不会给你 —— 内容的完整结构在 04 章展开；要实时看过程请用下面的 streamEvents()。

顺手能拿到的两个有用信息

拿到返回值 Msg 之后，除了正文还可以读：getGenerateReason() 告诉你这一轮是为什么停下 的（取值包括 MODEL_STOP、MAX_ITERATIONS、INTERRUPTED、 TOOL_SUSPENDED、ACTING_STOP_REQUESTED 等）Msg.java:639；getChatUsage() 给你 token 与耗时统计Msg.java:579。「回了一句莫名其妙的话」很多时候就是 MAX_ITERATIONS，先读它再改代码。06 / 10 章会分别用到这两个。注意它们不是单独序列化字段，而是放在 metadata 里，并会随状态文件一起持久化。

逐行解读：只讲容易懵的行

这一行 容易懵的点 实际上
.name("note-taker") 只是个显示名？ 没设 agentId(...) 时，它就是 agentId，直接决定状态目 录名。解析顺序：agentId > name > 兜底 "ReActAgent"HarnessAgent.java:2377
.sysPrompt("…") 和工作区里的 AGENTS.md 什么关系？ 两个都会进 system prompt：sysPrompt 是代码里写死的部分，AGENTS.md 由工作区上下文中间件在推理前拼进去。后者可被非开发角色修改，前者要重新发版。
.model("dashscope:qwen-plus") 为什么能传字符串？ model 有两个重载：model(Model):1530 与 model(String modelId):1536。 字符串走 ModelRegistry，顺手把 API key 环境变量读了；需要控超时/endpoint 时改用它负 载的那个 builder 版
.workspace(Paths.get(".agentscope/workspace")) 不写会怎样？ 会走默认解析顺序：agentscope.workspace 系统属性 → AGENTSCOPE_WORKSPACE 环境变量 → ${user.dir}/.agentscope/workspaceHarnessAgent.java:1166。注意是 user.dir（进程启动目录），不是你想象的「项目根」——IDE 里改过 working directory 就会找错地方。
.compaction(CompactionConfig.builder().triggerMessages(30).keepMessages(10).build()) 阈值 30 / 10 是必须给的吗？ 不是。默认已经是 triggerMessages=50、keepMessages=20、 triggerTokens=0（动态模式：用模型上下文窗口减去 reserved=20000 计 算）CompactionConfig.java:273。例子里调小到 30/10 只是为了让你快点看到压缩发生。

RuntimeContext：userId 与 sessionId 决定一切

这两个字符串不是装饰。它们直接拼成磁盘路径，而路径就是隔离边界：

RuntimeContext userId="alice"
sessionId="demo-session"
→
命名空间化 userId 为 null 时落到哨兵目录 __anon__JsonFile…java:72
→
磁盘路径 …/note-taker/alice/demo-session/agent_state.json

文件系统对名字有脾气，所以框架做了转义：只有匹配 ^[a-zA-Z0-9_\-.]+$ 的 id 原样当目录名，否则做无填充的 Base64-URL 编码JsonFileAgentStateStore.java:75。也就是说 sessionId 里带空格、斜杠、中文都能跑，但你在磁盘上看到的是编码后的怪名字。

并发语义（很多人踩）

同一 (userId, sessionId) 的请求会被自动串行化，不会并发写同一份状态； 不同 session 完全并行。quickstart.md:173 这就是为什么「一个 agent 实例 + 每个请求换 RuntimeContext」是正确用法，而「每个请求 new 一个 agent」是错的（工作区、模型连接都被白白重建）。

call() 与 streamEvents()

同一件事的两种拿法。call 给你最终一条 Msg（Mono<Msg>）， streamEvents 给你全过程的事件流（Flux<AgentEvent>）HarnessAgent.java:881。做 Web / CLI 界面一定要用后者，否则用户会盯着空白屏幕等 20 秒。 

import io.agentscope.core.event.AgentEventType;
import io.agentscope.core.event.TextBlockDeltaEvent;
import io.agentscope.core.event.ToolCallStartEvent;
import io.agentscope.core.message.UserMessage;

agent.streamEvents(new UserMessage("帮我把今天的关键点列三条。"), ctx)
        .doOnNext(event -> {
            if (event.getType() == AgentEventType.TEXT_BLOCK_DELTA) {
                // 模型流式返回的文本片段 —— 追加到界面或标准输出
                System.out.print(((TextBlockDeltaEvent) event).getDelta());
            } else if (event.getType() == AgentEventType.TOOL_CALL_START) {
                // agent 即将调用某个工具 —— 展示调用信息
                System.out.println("\n[tool] " + ((ToolCallStartEvent) event).getToolCallName());
            }
            // 其余事件（思考块、工具结果、回复结束……）04 章逐个讲
        })
        .blockLast();   // 等整个流跑完；GUI 程序里千万别这么写，见 03 章

仓库里的示例用的是 Java 16 的 instanceof 模式匹配写法BasicChatExample.java:89： 

agent.streamEvents(userMsg)
        .doOnNext(event -> {
            if (event instanceof TextBlockDeltaEvent e) {
                System.out.print(e.getDelta());
            }
        })
        .blockLast();
observe()：只喂上下文，不要回答

HarnessAgent 还有 observe(Msg) / observe(List<Msg>)HarnessAgent.java:927，把消息塞进记忆但不触发推理。适合「先把背景资料喂进去，等问题真正出现再让它说话」。

端到端：一次运行到底发生了什么

把上面那两行 call() 摊开成时间轴（第二轮的差别只有前面三步）：

  • 你的代码
    new UserMessage("我叫天宇，…") + RuntimeContext(alice, demo-session)
  • HarnessAgent
    拿 (alice, demo-session) 去 AgentStateStore 找 agent_state.json；找到就恢复，找不到就从空白开始
  • 工作区
    工作区上下文中间件把 AGENTS.md / MEMORY.md 等按预算（默认 maxContextTokens=8000）拼进 system prompt
  • 压缩检查
    消息数或 token 超阈值？超了就先把老对话压成摘要，原始对话另存到 session 日志（原始日志永 不压缩）
  • ReAct 循环
    推理把 system prompt + 历史 + 工具 schema 发给模型
    →
    行动模型要调工具就执行，结果作为内容块回填
    →
    观察把工具结果并入上下文
    ↻
    收敛模型不再要求调工具 → 出最终答案；最多 10 轮
  • 事件流
    过程中每一点进展都变成 AgentEvent 推给订阅者（文本片段、工具调用开始/结束……）
  • 落盘
    AgentState 写回 agent_state.json，记忆消息追加到 memory_messages.jsonl 并更新 .hash
  • 第二轮
    同 (alice, demo-session) → 读回同一份状态 → 它记得你叫什么
内存里（这次调用期间）
  • 对话上下文：Msg 列表
  • 待执行的工具调用与结果块
  • 事件流：Flux<AgentEvent>
磁盘上（跨进程活着）
  • agent_state.json：恢复上下文的前提
  • memory_messages.jsonl + .hash：追加或整体重写的判据
  • workspace/agents/<name>/sessions/：未压缩原始对话日志

陷阱与窍门

1. 换了 sessionId，agent「失忆」了
你会看到
第二轮问「我叫什么」，它一脸茫然地反问。
因为
状态的隔离粒度就是 (userId, sessionId)。换 sessionId 等于开新会话，读的是另一个目录。
改成
同一轮对话请保持同一个 sessionId；想「清空记忆」才换。userId 为空时会落到 __anon__ 目录，容易和别的匿名会话串在一起——正式一点就 always 显式给。
2. 工作区跑到了奇怪的地方
你会看到
AGENTS.md 写了却没生效；或者项目里冒出一个 .agentscope/，不是你放的那个。
因为
没调 workspace(...) 时默认解析到 ${user.dir}/.agentscope/workspace:1175，而 IDE 的 working directory 常常是模块目录甚至项目根之外；此外系统属性和环境变量优先级更高，容器里注入过就会悄悄改路径。
改成
开发期显式写 workspace(Paths.get(...))；排查时打印 System.getProperty("user.dir")，并检查 AGENTSCOPE_WORKSPACE 是否被设过。
3. 程序直接退出，什么都没打印
你会看到
命令秒退，控制台一片空白，也没有报错。
因为
你写了 agent.call(msg, ctx) 但没订阅（没 .block()）。Mono 是惰性描述，不订阅就永远不会执行。
改成
main 里 .block()；流式用 .blockLast()。想非阻塞就 .subscribe()，但要处理异常与线程。03 章把这三种写法的差异讲透。
4. Model id "dashscope:qwen-plus" 无法解析（或类似）
你会看到
启动就抛异常，提示找不到模型 / provider。
因为
模型提供商是独立模块，agentscope-harness 只带核心，不带任何厂商实现。字符串 model id 需要 ModelRegistry 找到对应扩展。
改成
加上 agentscope-extensions-model-<provider> 依赖（本章第 1 步第二个依赖）。切换厂商 = 换模块 + 换字符串 + 换环境变量，三件事一起做。
5. 以为「等很久才会压缩」，于是压根没验证过压缩
你会看到
聊十几轮，上下文一点没变短。
因为
默认阈值是 triggerMessages=50；另一种触发是动态 token 模式（triggerTokens=0 时用模型上下文窗口减 reserved=20000 计算，模型没上报窗口大小时兜底 160000）CompactionConfig.java:67。
改成
学习期就照例子调成 triggerMessages(30).keepMessages(10)，多聊几轮就能看到事实落到 workspace/memory/YYYY-MM-DD.md 并被合并进 MEMORY.md。
6. 集群里每个副本各自「记得」不同的事
你会看到
本地好好的，多副本部署后同一个用户忽而有记忆忽而没有。
因为
默认的 JsonFileAgentStateStore 是本机文件，状态在各副本本地各写一份。
改成
换成分布式 AgentStateStore（例如 Redis 实现）或用 distributedStore(...)。框架对此还会主动拦截：配了 filesystem(RemoteFilesystemSpec) 却仍用本地状态存储时，build() 直接抛 IllegalStateExceptionHarnessAgent.java:2431——把运行期的隐性错乱换成启动期的显性报错。07 章细讲。

自检三问

1. .name("note-taker") 改成 .name("note-taker-v2") 重跑，第二轮还记得吗？

不记得。没设 agentId 时 name 就是 agentId，而 agentId 是状态目录的一层HarnessAgent.java:2377。改名等于换了一个 agent 的存储根，旧状态还在原目录里，只是不再被读到。

2. 一个 HarnessAgent 实例能同时服务 100 个用户吗？需要每个用户一个实例吗？

能，也不需要。实例在调用之间无状态，每次调用传不同的 RuntimeContext 就自动隔离上下文；同一 (userId, sessionId) 的请求会被串行化，不会互相踩状态quickstart.md:173。 要留意的是存储实现必须支持多副本共享，见陷阱 6。

3. 程序重启后，工作区删了，agent 还能恢复对话上下文吗？

能——这正是状态被放在工作区之外的原因HarnessAgent.java:1134。~/.agentscope/state/<agentId>/<userId>/<sessionId>/agent_state.json 里带着恢复所需的上下文；但工作区里的 AGENTS.md / MEMORY.md 这些人格与长期记忆文件没了，system prompt 的那部分内容也就没了。

20 分钟动手练习

  1. 先证明「记忆」真的来自磁盘，不是内存
    跑完两轮后结束进程，再原样跑一次第三轮问「我叫什么」。因为 sessionId 没变、状态在文件里，它照样答得上来。如果你改成一个新的 sessionId 再跑，它就应该不知道——这一步能帮你确认隔离边界在哪。
  2. 观察 system prompt 的来源
    在工作区里写一份 AGENTS.md（例如「你只能用中文回答，回答不超过 30 字」），重跑。行为变了 → 说明工作区文件确实参与拼装。
  3. 把压缩逼出来
    保持 triggerMessages(30).keepMessages(10)，连发 35 条短消息，然后去工作区看 memory/YYYY-MM-DD.md 与 MEMORY.md 是否出现；再打开 agent_state.json 看上下文里是否只剩摘要 + 最近若干条。
  4. 故意踩一次坑
    把 .block() 删掉再跑一次，确认「秒退且无输出」的现象；然后把 call 换成 streamEvents，观察事件打印顺序。这两次对照比读十遍文档都管用。
