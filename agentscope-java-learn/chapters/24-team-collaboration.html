24 · Team 协作：Leader、成员与结果收敛

第 23 章把一台主机接进控制面；这一章把多个 Agent 组织成团队。Team 不是「同时启动所有成员」， 而是一个由 Leader 驱动的动态决策循环：Issue 给出目标，Leader 选择成员、拆出任务，成员的执行结果再回到同一个协调节点。 真正难的不是建队，而是分清 任务完成、Attempt 成功、协调节点收敛、Issue 验收是四层不同的事实。

读完你能做到

  • 说清 Team、Workflow 与单个 Agent 的分工，知道什么工作不该交给 Team
  • 按 Issue → Run → Node → AgentTask → Attempt 的顺序读懂一次协作
  • 创建 Leader 与成员，写出可验证的角色职责，而不是复制同一段宽泛指令
  • 解释九个协作策略字段的零值语义，以及创建表单为什么和零值不一样
  • 定位「Team 显示就绪但任务不派发」「成员完成但 Run 不结束」分别卡在哪一层
  • 在 Managed、Hosted、External 混合团队中，按同一套验收顺序排查问题

边界：Team 是动态决策器，不是并行加速器

Team 适合目标明确、但实现步骤需要临场决定的工作。它和 Workflow 的差别不在「有没有多个 Agent」， 而在谁决定下一步：Team 由 Leader 根据当前事实选择成员与拆分方式；Workflow 由预先声明的 DAG 决定节点何时可运行team-collaboration.md:10。 需要固定顺序、条件分支或人工关口时，应该用 Workflow，而不是在 Team 指令里写一段「必须按 1、2、3 执行」的伪流程。

Team 是持久定义；一次团队工作会创建 Run 和团队快照，由 Leader 驱动协调，而不是每次无条件并行运行所有成员 team-execution.md:10。 官方概览也把这点写得很直接：Leader 决定一项请求需要哪些成员，并不保证每次都运行整个名单； 团队配置描述的是可用能力，不是固定执行图 teams.md:34。

适合 Team

  • 目标明确，但需要先调研再决定派谁
  • 成员产出需要互相复核、追问、返工
  • 希望保留讨论、任务图与每次执行的证据

更适合 Workflow

  • 步骤顺序固定，失败要回到指定节点
  • 审批、条件、汇合规则必须可预测
  • 要把 Team 当成其中一个动态节点来调用
一句话判断

如果「下一步做什么」需要模型看上下文再决定，用 Team；如果「下一步做什么」在运行前就能画出来，用 Workflow。 Team 的动态性来自 Leader 每回合的一次评估，而不是成员越多越自动。

对象模型：Issue、Run、Node、Task、Attempt 各记什么

读 Team 排障信息时，最容易把几个状态混成一个。官方把职责拆成六行，先把这张表记住：

对象在协作中记录什么
Issue目标、负责人、讨论、交付与验收
Run / Node本次协作及协调步骤的状态
AgentTask指派给一个 Agent 的工作义务
Attempt某个后端上的一次实际执行
Comment / Artifact持久沟通与共享结果
Child Issue可独立跟踪的子目标

表源：team-execution.md:32-39。 同一 AgentTask 可以因重试产生多个 Attempt team-execution.md:41。

源码里，AgentTask 把这些关系真正落成字段：它同时带 issueId、orchestrationRunId、 runNodeId、teamId、teamRole、leaderTask、parentTaskId 与 currentAttemptId collaboration.go:257-295。 所以「谁派的、属于哪个节点、是不是 Leader 的任务、重试了第几次」都能沿字段回溯，不需要猜。

Runplanned / running / waiting / succeeded / partial_succeeded / failed一次可观察的协作实例

这里列的是 Team 视角的六类对象；更完整的会话与运行模型——direct / adaptive / declared / subrun 四种模式，以及「新 Attempt → 新 Task → 新 Run」三级重试——在官方 sessions.md 里。Team 的每个 AgentTask 最终仍落在某个会话的执行上下文里 sessions.md:16-33。

建队：一个 Leader，若干有角色的成员

创建入口在 DESIGN → Teams。先分别验证成员 Agent 能独立完成小任务，再选择统一接收任务的 Leader，添加可协作成员；需要约束委派时再展开高级协作指令 teams.md:26-32。 官方的最小复核团队是「资料助手 + 复核助手」：Leader 先整理材料，再委派复核，最后修订并交付统一结果 create-team.md:10-26。

数据模型里，Team 包含名称、描述、团队指令、状态、leaderAgentId、策略、版本与成员列表； 成员再带 agentId、role、成员指令、能力要求与运行绑定策略 collaboration.go:356-385。 角色不是装饰：它既进入 Leader 的路由上下文，也会写进派发出去的任务记录。

成员字段：角色、指令、能力要求、运行策略

官方字段表把 Team 与 Member 分开：Team 管名称、描述、Leader、团队指令与启停状态；Member 管这个 Agent 在团队里的角色、专项指令、能力要求和运行候选 team-configuration.md:12-26。 最容易被写坏的是指令：团队 Instructions 定义共同交付要求，成员 Instructions 定义专项职责 team-collaboration.md:44。

写法问题改法
五个成员复制同一段「负责分析并输出报告」Leader 无法判断该选谁，成员也无法证明自己完成了什么一个角色一个可验证产出：来源清单、能力映射、测试日志、复核结论
只在 Team 指令里写「最后汇总」成员不知道自己的边界，Leader 不知道何时算齐团队写共同验收，成员写专项交付与停止条件
把「必须按固定顺序」写进 TeamLeader 的动态决策被伪流程绑死，失败也无法回退固定顺序交给 Workflow，Team 只描述角色与协作边界

Leader 不是「权限更高的成员」。它必须具备委派、查看结果、节点完成 / 失败等协调能力； 普通成员只需要完成自己承担的角色，并非所有能进行 Chat 的 Agent 都适合当 Leader team-configuration.md:73。 成员可以混用 Managed、Hosted 与 External，但必须验证对应的任务派发与协作能力 team-collaboration.md:16。

协作上限：九个策略字段与三类零值语义

策略不是「建议值」，而是服务端在委派、提及和子 Issue 创建时真正检查的预算。零值语义并不统一， 先看官方表：

policy 字段控制内容零值语义
maxActiveTasks并发任务上限默认 32
maxHops委派跳数默认 8
maxFanout单次委派接收者数量不增加 Team 专属限制
maxChildDepth子 Issue 深度默认 4
maxChildIssues每个父 Issue 的子 Issue 数量不增加 Team 专属限制
maxTaskRetries每个任务的重试限制不增加 Team 专属限制
allowExternalDelegation是否允许委派给名单外 Agent / Teamfalse
allowMentionAll是否允许面向全体成员的委派false
requireReview按执行策略要求人工复核false

表源：team-configuration.md:28-40。 当前创建表单会写入显式值：并发 32、fanout 8、hops 8、child depth 8、child issues 64 team-configuration.md:44， 源码里也能看到这条默认组合 TeamsOverviewPage.tsx:72。

「零值」不等于「表单默认」

同样是 maxChildDepth：留空走服务端默认 4；从创建表单建队会显式写 8。两者都不是 「无限制」。而 maxFanout、maxChildIssues 与 maxTaskRetries 的零值才是「不加 Team 专属限制」。排障时先看详情页实际值，不要拿文档的零值表去解释表单建出来的 Team team-configuration.md:44。

服务端默认值写在委派守卫里：maxHops 8、maxActiveTasks 32 service.go:1084-1095； 跳数超限会以 max_hops_exceeded 阻断，自触发会以 self_trigger 阻断 service.go:1097-1107； 活跃任务达到上限则以 active_task_budget_exceeded 阻断 service.go:1109-1119。 另外三个上限有平台安全边界：maxHops ≤ 64、maxChildDepth ≤ 32、maxFanout ≤ 256 service.go:50-51。

单次提及的接收者数量在路由阶段检查，超过 maxFanout 直接失败 service.go:778-779。 子 Issue 则同时检查深度和数量 service.go:589-613。 修改 Team 时 API 用 expectedVersion 做乐观锁，版本不一致会返回冲突 team-configuration.md:63。

混合后端：Managed、Hosted、External 只在 Attempt 以下不同

同一个 Team 可以混用三种成员，但加入前要验证的东西不同：Managed 看模型、Environment / Memory / Vault 绑定； Hosted 看 Host 在线、provider 可用、定义映射与协作工具；External 看任务入口和真实完成 / 失败回报 team-configuration.md:65-71。 「能在 Chat 里回答」不等于「能作为 Team 成员完成派发」。

成员的 runtimeBindingPolicy 是可选的有序候选：每个候选包含 binding、 requiredCapabilities 与 securityConstraints，外层还有 selectionMode、fallbackMode 与可选的 retryPolicy orchestration.go:246-263。 校验要求 selectionMode=ordered、至少一个候选，fallbackMode 只能是 disabled 或 fresh service.go:66-82。

选择顺序是节点覆盖 → 成员覆盖 → Agent 策略；显式启用 fresh fallback 后，跨后端重试会从 持久 Issue、评论与 Artifact 重建上下文，不迁移原进程或私有会话 team-configuration.md:77-79。 所以混合团队的第一条验收不是「三种成员都在名单里」，而是「每个成员都能独立完成一次小任务」。

成员加入前至少验证本章前面的章节
Managed模型可用，资源绑定正确，能完成一次带工具的任务21 Managed Agent 深入
HostedHost 在线，provider 已登录，能力映射与协作 MCP / CLI 可用23 Hosted Agent 与 Runtime Host
External应用已注册，任务入口、完成 / 失败回报与 SessionBridge 正常22 External Agent

就绪度：Ready、Degraded、Unavailable 各查什么

控制台的就绪检查是「现在能不能开始有效协作」，不是「定义是否存在」。官方三态是： Ready 可做小任务验证；Degraded 有部分成员或能力不可用；Unavailable 当前无法开始有效协作，优先修 Leader 或运行时依赖 teams.md:38-43。

源码把这三态算得更具体：先默认 ready，Team 非 active 直接 unavailable； 然后逐个检查 Leader 与成员 Agent 是否在当前范围、是否 active、绑定的 Runtime 候选是否可派发。 某个成员不是 ready 时：如果它是 Leader 且状态不是 degraded，整队判为 unavailable；普通成员不可用，或 Leader 为 degraded，则降为 degraded team_detail_handler.go:73-107。

现象最可能的原因先查
整队 UnavailableTeam 被禁用，或 Leader 不可派发Team 状态、Leader 的 Runtime 绑定
整队 Degraded某个成员不可用，但 Leader 还能工作成员卡片上的原因与 Runtime 候选
成员显示可用，派发仍失败能力要求、池名或策略不匹配成员的 runtimeBindingPolicy 与目标后端
运行中才报能力错误就绪检查通过，但 Workspace 请求了 provider 不支持的能力第 23 章的能力矩阵与执行前复检

就绪检查按成员自己的运行候选走，而不是只看 Agent 是否存在 team_detail_handler.go:93-98。 这也是为什么「目录里能看到 Agent」不能替代「这个成员能接任务」。

从 Issue 启动：冻结快照，只建一个协调节点

一次协作从 Issue、Automation 或 Endpoint job 开始。控制面先冻结 Team 快照并创建 Run， 然后只创建一个协调节点和一份初始 Leader 任务，而不是给每个成员都创建一次调用 team-execution.md:12-26。 源码中的入口写得很明确：先校验 Team 是 active、范围与 Run 一致且有 Leader，再写团队快照， 最后创建 team-coordinator 节点和初始 Leader 任务 team.go:42-98。

  • 分配 人、Automation 或 Endpoint 把 Issue 交给 Team；团队定义是持久模板，不是这次运行的实时配置。
  • 冻结 序列化 Team 并写入 Run 快照，后续排障看的是当时那份名单、角色与策略，而不是今天改过的版本team.go:55-63。
  • 建节点 创建类型为 team、角色为 leader 的协调节点；同一 Run 与 NodeKey 会复用已有节点，避免重复建图team.go:64-85。
  • 建任务 给 Leader 创建一条 leader=true、带 teamId 与 teamRole=leader 的任务；已有任务则直接复用team.go:86-98。
  • 运行 自适应 Run 进入 running / waiting，Leader 的每次决策只消耗一个回合，协调节点保持 waiting 直到显式收敛。

Run 模式里 adaptive 与 declared 是两种不同编排 orchestration.go:29-34。 Team 默认是前者：拓扑可以在运行时增长；Workflow 的 team node 则把动态协作嵌进声明式外壳。

Leader 回合：评估、委派、等待、收敛

Leader 不是「一直跑到所有成员结束」的长任务。它每被唤醒一次，只处理一个协调回合：读取新增事实， 作出一次可观察的评估，然后委派、等待、升级或收敛。设计契约把评估结果分成 delegate、complete、blocked/escalate 与 no_action team-collaboration-v5.md:100-106。 这份文档标明是目标架构，具体字段仍以当前实现为准，但它解释了为什么 Leader 必须留下「看过但没有动作」的记录。

委派后，Leader 调用等待逻辑结束本回合；协调节点保持 waiting，下一条唤醒由成员结果、子 Issue 状态变化或人类评论触发 leader_wait.go:92-110。 这避免一个模型调用无限等待，也让「成员还在跑」与「Leader 卡死」在时间线上可区分。

服务端还会限制 Leader 能做什么：只有 active 的 Team Leader 任务可以创建子 Issue service.go:553； 子 Issue 的接收者必须在冻结的 Team 快照里，除非显式允许名单外委派 service.go:579-587； 深度与数量也受策略约束 service.go:589-613。

Leader 的交付长什么样

最终汇总要包含必要成员的结果、证据位置和未完成项；如果仍有必要子工作没结束，应该等待、调整计划或明确失败， 不能用「报告已生成」掩盖未完成义务 team-execution.md:49-53。

成员回合：只做被指派的事，结果必须回到协调节点

成员只收到自己的 assignment、所属 Issue / 子 Issue、触发输入和允许的工具。它可以写进度、结果与 Artifact， 但不能替 Leader 创建 Team 子任务、验收 Issue、重规划或完成协调节点 team-collaboration-v5.md:108-115。 这也是「成员回复」与「团队完成」必须分开的原因。

成员结果通过持久对象回流：评论、mention、Artifact 和子 Issue 都属于共享事实；Managed Environment、Hosted 工作目录与 External 私有文件不会因为同在一个 Team 就自动合并 team-execution.md:43-47。 评论里的本地绝对路径不是可下载文件，Leader 要打开真实 Artifact 核对 team-collaboration.md:66。

Hosted / Shell 型成员还能使用任务范围命令读写 Issue、发进度、上传产物；MCP 型成员使用对应的 collaboration 工具。 这些命令在 Host 启动的任务环境里运行，不是拿管理员令牌在普通终端模拟 team-collaboration.md:28-40。

源码层面，成员完成任务会同时完成当前的 Task / Attempt、处理输入、写结果评论，并把评论路由成 Leader 的后继输入 team-collaboration-v5.md:113-115。 这里的目标是「每个成员结果恰好形成一个 Leader 后继输入」，避免重试或重放把同一结果算两次。

任务板与邮箱：服务端 Team 和 Harness 本地 Team 不是一回事

Service 的 Team 以 Issue、AgentTask、Comment、Artifact 为持久事实；框架里的 TeamTool 则提供一套更轻的「任务板 + 邮箱」接口，用于本地或会话内的协作。两者共享词汇，但不是同一个存储。

TeamClient 的注释直接把它定义为 task board + mailbox，并列出本地 BaseStore 与 control-plane HTTP 两种实现 TeamClient.java:21-26； 本地实现明确使用 CAS，唤醒委托给 TeamWakeups LocalTeamClient.java:30-34。 本地任务状态只有 pending / in_progress / completed / failed TeamTask.java:36-44。

结果收敛：四种「完成」不能互相代替

这是整章最重要的一节。官方与设计契约都反复强调：成员回复、Attempt 成功、协调节点完成、Run 终态与 Issue 验收 分别表达不同层次 team-execution.md:49-53。 设计文档把链路写得更细： 

provider turn 结束
  ≠ ExecutionAttempt 成功
  ≠ AgentTask 语义完成
  ≠ Team coordinator 收敛
  ≠ Issue 被验收

链路来源：team-collaboration-v5.md:77-83。 注意这是设计契约对目标状态的描述，当前实现仍需逐层核对。

服务端的协调节点收敛不是「Leader 说完成就完成」。它要检查：当前 Leader 任务之外没有活跃 worker 任务； 没有未终态节点；所有子 Issue 都是 done 或 cancelled；Leader 任务必须先完成，节点才能完成 service.go:360-457。 代码注释也把顺序写死了：Run 不能在「作出决定的 Leader 义务」还活着时变成成功 service.go:465-470。

你看到的它保证什么它不保证什么
成员回复了一条结果消息已持久化，Leader 可能收到后继输入任务已完成，或结果已被采用
Attempt succeeded某后端这一次物理执行成功语义目标已完成
AgentTask completed这份定向工作义务已结束Team 已收敛，或 Issue 已验收
Coordinator node succeededTeam barrier 已满足业务验收一定通过
Run succeeded / partial_succeeded这次执行图到达终态Issue 一定 done，尤其人工验收场景

当所有节点终态后，引擎决定 Run 的终态：没有失败就是 succeeded；有失败、有成功且允许部分成功时是 partial_succeeded；其余有失败则 failed engine.go:437-443。 Run 结束后，协调总结会先写回根 Issue，再按完成策略把 Issue 留在 in_review 或自动置为 done； 失败则写 blocked 并保留已完成内容 coordinator_summary.go:52-58。

失败与重试：Attempt 失败不等于 Task 失败

Team 里最常见的误判是「一个成员报错，整队就失败」。实际分层是：物理 Attempt 失败可以重试同一份 AgentTask； 重试预算耗尽或错误不可恢复时，子 Issue 才转 blocked，并把失败事实作为普通输入交给 Leader 决策 service.go:1740-1749。 这条输入会明确列出失败码、原因、已消耗尝试次数，以及 Leader 可选的下一步 service.go:1815-1819。

场景Task / Attempt子 IssueLeader
瞬时故障，预算未耗尽新 Attempt，Task 仍可继续保持进行中继续等待，不唤醒
缺凭据 / 权限 / 能力，原样重试无意义Task failedblocked收到失败输入，决定重派、降级或求助
瞬时故障耗尽重试Task failedblocked同上
Leader 接受降级 / 部分结果失败记录保留可显式取消协调节点可收敛，Run 可能 partial_succeeded
Leader 判定目标不可恢复失败记录保留保持 blocked失败协调节点，Run failed

故障矩阵的设计意图见 team-collaboration-v5.md:147-160； 当前实现中，只有 Leader 能显式取消 blocked 子 Issue，且仍存在活跃 worker 时会被拒绝 service.go:261-295。 maxTaskRetries 的预算按重试链计数，超限返回 service.go:1062-1074。

不要用「重试」掩盖配置错误

缺 API key、凭据、权限或 provider 能力时，重试只会消耗预算并制造更多失败记录。先把失败码和证据写进 子 Issue，让 Leader 明确选择重派、换后端、请求人工，或判定目标不可恢复。

验收：Run succeeded 不等于 Issue done

Issue 的 done 需要满足验收策略，而不是只看 Run 的终态。服务端在 Issue 转 done 前会走 acceptance guard； Team 策略要求人工复核时，Leader 从任务里直接接受子 Issue 会被拒绝 service.go:117-132 service.go:238-240。

人工验收要检查最终结果、重要来源和失败说明，再决定接受还是要求修改；Run 的 succeeded / partial_succeeded 不能单独证明业务目标已达成 team-collaboration.md:50-53。 概览文档也要求：需要复核的工作保留人工验收，Team 可以用于 Issue、Automation 与 Endpoint，但更新团队后要验证新执行使用的是新成员配置 teams.md:48-50。

验收清单
  • 每个必要成员的结果都能在 Task map / 评论 / Artifact 里找到，而不是只在 Leader 的总结里出现
  • 关键结论有来源或真实工具记录；没有验证的条件明确标出
  • 失败与未完成项没有被「报告已生成」掩盖
  • 人工验收的 Issue 仍在 Inbox 里等待决定，不因 Run 成功自动通过

六个坑：先看层级，再看配置

坑一：以为建了 Team 就会并行跑所有成员。Team 是动态决策器，Leader 只选择它认为需要的成员； 团队名单描述可用能力，不是固定执行图 teams.md:34。 想每次固定运行某几个节点，应该用 Workflow。

坑二：把零值当成表单默认。零值下 maxChildDepth 是 4，创建表单却显式写 8； maxFanout 零值不限，表单写 8。排障时看详情页实际策略，不要拿文档零值表硬套 team-configuration.md:44。

坑三：让不能协调的 Agent 当 Leader。Leader 要能委派、查看结果、完成 / 失败协调节点； 只会 Chat 的 Agent 不足以承担这些动作 team-configuration.md:73。 先把 Leader 单独跑通，再加成员。

坑四：假设成员共享文件系统。Managed Environment、Hosted 工作目录与 External 私有文件不会自动合并； 共享结果必须走 Issue、评论与 Artifact team-execution.md:47。 评论里写本地路径，不等于另一个成员能读到。

坑五：把 Run succeeded 当成 Issue done。Run 只代表执行图到达终态；人工验收的 Issue 仍要 在 Inbox 接受，策略要求复核时 Leader 也不能直接接受子 Issue team-collaboration.md:50-53。

坑六：用加成员解决「太慢」。增加并发前要检查共享文件冲突、工具副作用与预算；成员越多， Leader 的路由与收敛成本越高 team-collaboration.md:46。 先确认瓶颈在成员执行、Leader 决策还是后端排队。

自测：三个判断题

Team 建好以后，一次 Issue 会并行运行全部成员吗？

不会。控制面只创建一个协调节点和一份初始 Leader 任务，Leader 根据目标选择成员并委派；成员结果回到同一个 协调节点，再触发下一轮 Leader 决策 team-execution.md:24-28。 团队名单是能力池，不是固定执行图。

maxActiveTasks 留空，是不是表示不限制并发？

不是。零值会走默认 32；只有 maxFanout、maxChildIssues 与 maxTaskRetries 的零值才是「不加 Team 专属限制」 team-configuration.md:30-40。 另外，创建表单会显式写 32，而不是留空。

Run 显示 succeeded，是否可以直接把 Issue 标成 done？

不一定。Run 成功只说明执行图到达终态；Issue 的 done 还要过验收策略。人工验收的 Issue 需要人在 Inbox 接受，requireReview 也会阻止 Leader 直接从任务里接受子 Issue service.go:238-240。

练习：让一个三人团队完成一次带返工的调研

目标不是「看到一次成功」，而是能解释每个结论来自哪个成员、哪次执行。建议 40 分钟：

  1. 先单独验证三个 Agent
    准备 Leader、Researcher、Reviewer 三个 Agent，各自完成一次小任务。Researcher 要能给出带来源的事实，Reviewer 要能指出证据缺口；此时先不要建 Team。
  2. 建队并写清角色边界
    选择 Leader，添加两个成员，分别写专项 Instructions。团队 Instructions 只写共同目标、交付格式与失败处理，不复制成员职责。
  3. 检查就绪度
    记录 Team 的 readiness 与每个成员的原因。临时禁用一个成员，确认整队变为 Degraded；恢复后再确认回到 Ready。
  4. 用一个小 Issue 启动
    创建「比较两种部署方案，给出带来源的结论」Issue，选择 Team。观察是否只创建了一个协调节点，以及 Leader 是否按需委派而不是一次叫齐所有人。
  5. 制造一次返工
    让 Reviewer 指出一个来源缺口。确认 Leader 收到结果后安排修订，而不是把 Reviewer 的评论直接当成最终交付；记录 Task map 上新增或重试的任务。
  6. 验证策略边界
    把 maxChildIssues 设成 1，尝试让 Leader 创建第二个子 Issue，确认出现预算错误；再恢复策略。记录错误来自路由、子 Issue 还是执行阶段。
  7. 验证收敛与验收
    等协调节点完成后，检查根 Issue 是否进入 in_review；在 Inbox 接受或要求修改。确认 Run 终态与 Issue 状态是两个独立事实。
  8. 可选：混合一个 Hosted 成员
    把一个成员换成 Hosted Agent，先单独验证它的任务与协作工具，再重新跑同一个小 Issue。对照第 23 章确认 Host 在线、provider 可用与能力映射。

下一章看什么

到这里，Team 的四个层次已经拆开：Issue 保存目标与验收，Run / Node 保存协作拓扑，AgentTask 表示工作义务， Attempt 表示一次真实执行。Team 的动态性来自 Leader 每回合的评估，而不是成员数量。
