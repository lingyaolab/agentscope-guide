21 · Managed Agent 深入：一个定义，四类资源，两种结果

上一章把 Agent 发布成了一条带凭据的调用契约，调用方只看见 /invoke/v1/**。但契约只能保证「调得到」， 保证不了「干得成」——真正决定它能不能读文件、跑命令、查知识、连工具的是绑在它身上的四类资源。 这一章把 Agent 定义拆开，逐个说清 Workspace、Environment、Memory、Vault 各管哪一段，以及为什么同一个 Agent 换个环境就像换了一双手。

读完你能做到

  • 分清定义里哪些字段是「职责」，哪些是「对资源的引用」，不再把 Instructions 当万能开关
  • 用一句话说清四类资源的分工，并知道绑错时分别会表现成什么故障
  • 解释 maxIters 为什么文档说 12、源码里却兜底 20
  • 说清 local 环境为什么默认关闭，以及四种 Environment 各自能不能跑 Shell
  • 用 read_only 解释「共享知识只读」，用 mergeSessionMounts 解释「省略」与「[]」为什么不是一回事

先说为什么：定义只是职责，资源才是能力

官方对 Managed Agent 的定义很克制：Service 管理 Harness、会话和模型执行，你配置的是职责、模型与资源， 不用为每个 Agent 部署独立应用managed-agent.md:10。 三样里只有「职责」是纯文本，另外两样都是外部依赖。

这解释了一个新手最常见的困惑：同一个 system 提示词，昨天让 Agent 读 inputs/report.csv 成功了，今天却报文件不存在。 提示词一个字没改，变的是它背后的执行位置或挂载。把三层分开看就清楚了：

层次存的是什么改一次影响谁
Agent 定义 名称、Instructions、模型、迭代上限、工具声明 下一次建立运行上下文时生效；已在进行中的会话仍用旧快照
四类资源 能力文件、执行环境、共享知识、工具凭据 只影响引用它的 Agent；各自有独立的生命周期与版本
会话 这一次执行实际解析到的环境、知识、凭据 只影响这一条会话；会话可以显式覆盖默认绑定
一句话分工

Workspace 定义「怎么做」，Environment 决定「在哪做」， Memory 提供「知道什么」，Vault 提供「能连什么」。 四者缺一，Agent 都还能说话，但会以不同方式「干不成活」。

官方还特意提醒：模型凭据、工具凭据和用户登录凭据用途不同，服务安装包不包含模型额度，配了 Vault 也不会自动替代模型 provider 的连接配置managed-agent.md:36。这句话几乎预告了后面所有「明明配了却不通」的故障。

定义里到底有什么：一张字段表

下表用的是 API 字段名，控制台则在 Behavior、Workspace 和 Runtime/资源设置里分别编辑它们managed-agent-configuration.md:12-27：

字段用途容易踩的地方
name / description 显示名称与职责说明 写清输入、输出和适用任务，别写成宣传语
system Instructions，拼进 Agent 指令 明确边界与验收标准；不保存 secret
model 模型注册名或 provider:model 留空用 Dataplane 默认模型
maxIters 单次推理/工具迭代上限 不是 token 预算；见下面的双默认值
workspaceId 关联共享能力定义 改变关联会发布并绑定所选草稿
workspaceBinding 版本选择、覆盖项、附加指令 与 workspaceId 是两件事
defaultEnvironmentId 新会话默认执行环境 先创建并验证环境，再绑
defaultMemoryStoreIds 新会话默认知识 Store 用 Store ID，不是显示名称
defaultVaultIds 新会话默认凭据集合 只绑该 Agent 真正需要的 Vault
tools / mcpServers / skills 工具权限、MCP 连接、技能选择 逐项加、逐项验证

源码里这份定义就是一个结构体，字段与上表一一对应managed_definition.go:41-61。注意注释里那句「Managed 与 Hosted 运行时共享这份定义」——所以别把它当成某个运行时的私有配置。

maxIters 为什么有两个默认值

文档写的是「控制台范围 1–64，未配置时表单显示 12」managed-agent-configuration.md:21；而 Go 侧落库前对 maxIters <= 0 的处理是直接赋 20managed_definition.go:91-94。两者不矛盾，但必须分清：

12 是「界面预填」

  • 控制台新建时的表单初值
  • 用户看见的是 12，提交时也带着 12
  • 它属于前端体验，不是协议默认值

20 是「后端兜底」

  • 只在你传了 0 或负数时触发
  • API 直接调用、绕过表单时就会遇到
  • 所以「不填」和「填 12」在 API 上结果不同

要写脚本创建 Agent 的话，把 maxIters 显式写上，别指望默认值——这是文档与源码之间最容易误解的一处。

定义了，就有版本

保存定义不是就地改一行。写入时会同时落一条 agent_versions 快照managed_definition.go:128-139，版本列表接口的注释说得更直接：返回的是不可变的控制面快照，新的在前managed_definition.go:210-211。官方描述同一件事：「保存 Agent 配置不等于修改正在执行的所有实例」managed-agent-execution.md:25。

改完配置，用「新」会话验证

运行上下文用的是解析后的定义快照，所以已存在的会话不会因为你改了草稿就换行为。 这也意味着「我改了但没生效」多数时候不是 bug——只是你在用旧会话看新配置。

四类资源各管一段

官方在「工作原理」里用一句话把四者并列：Workspace 保存能力定义，Environment 决定文件和命令在哪执行， Memory Store 是共享知识，Vault 在连接工具前解析凭据managed-agent-execution.md:27。展开成表更直观：

资源里面存什么决定什么绑错时的典型表现
Workspace AGENTS.md、Skills、工具声明、Subagents Agent 按什么流程干活、能发现哪些技能 Agent 说得出流程，却找不到技能文件
Environment 执行位置与连接参数 文件读写、Shell、工具在哪跑 能回复，但一碰文件就报错或路径不对
Memory 已核对的共享文档 Agent 能按需读到哪些长期知识 回答像「凭常识猜的」，引不出来源
Vault 凭据元数据与密文 工具连接时用什么身份 工具能列出，但一调用就 401

这张表最有用的不是前三列，而是最后一列：故障现象能反推是哪类资源没绑好。 第 19 章区分「模型问题 / 工具问题 / 环境问题」时用到的思路，在这里有了更细的落点。

Workspace：能力定义，以及它的版本

先把一个常见误解排掉：Workspace 是资源，不是账号的 Namespace，也不是一次执行的临时目录workspaces.md:10。它装的是可复用的「说明书 + 能力文件」：

内容用途
AGENTS.md项目操作说明与共同约束
Skills可复用任务步骤及辅助文件
Tools / MCP 配置声明外部能力连接
Subagents专项委派定义

四行来自 workspaces.md:44-51。 可长期共享的知识文档应放 Memory，密钥放 Vaultworkspaces.md:53——四类资源各归其位，别把 Vault 的活塞进 AGENTS.md。

绑定分两步，这是本章最值得记住的机制之一workspaces.md:36-42：

  • 第一步：选 Workspace 本身 在 Agent 设置里关联 Workspace，对应 workspaceId。改变这个关联会发布并绑定所选 Workspace 的草稿。
  • 第二步：选版本与覆盖 进入 Definition → Workspace，workspaceBinding 保存版本选择、覆盖项和附加指令。要选已有发布版本、调整继承范围，都在这一步。
  • 第三步：用一条可检查的约定验证 新建 Chat，要求输出必须包含「来源」和「待确认事项」，再看所选 Skill 或工具是否真的被用到。

「改草稿」和「更新绑定的发布版本」是两个动作。运行上下文用的是解析后的定义快照，所以改草稿不会立刻改变已有 Session； 多个 Agent 复用同一个 Workspace 时，还要分别确认它们绑的是哪个版本workspaces.md:42。

Workspace 不会替你装东西

Workspace 提供能力定义，Environment 提供实际文件与 Shell 执行位置；创建 Workspace 不会为 Agent 自动启动 Worker 或安装程序workspaces.md:57。Skill 描述的是流程，系统依赖得装在真正执行的那个环境里。

Environment：四种执行位置

环境回答的是「文件和命令在哪跑」。官方把它和 Workspace 的分工说得很清楚，还特意加了一句：它不是 Hosted Agent 的 Runtime Hostenvironments.md:10。四种类型的能力边界差别很大：

类型在哪执行Shell典型用途
local Dataplane 所在环境 有 本机开发、快速验证；管理员必须显式启用
sandbox E2B 云沙箱 有 需要隔离的 Shell / 文件操作
remote 共享 BaseStore 文件系统 无 只读写文件，不当远程 Shell 用
self_hosted 你自己的 Worker 有（Worker 执行） 工具必须跑在内网或自有机器时

类型表来自 environments.md:20-27。 「Docker 下 Local 指 Dataplane 容器内部，并不是宿主机的任意目录」environments.md:29——这句话能省掉很多「为什么我挂载的宿主目录看不到」的排查。

local 为什么要两道开关

第 19 章讲过 BUILDER_ALLOW_LOCAL_ENVIRONMENT 默认是 false。源码把它实现成一道硬拦截： 类型合法但 local 未启用时，直接返回 403handlers_env.go:124-132。也就是说，环境存在与否是「资源层」的事，能不能建 local 是「部署层」的事——两层都过才建得出来。

另一条容易被忽略的约束：类型创建后只读。更新接口只改名称和 Config，源码注释给的理由是「运行中的会话会从类型解析自己的 sandbox」handlers_env.go:165-166。想把 remote 改成 self_hosted，只能新建一个环境再重新绑定。

sandbox 的常用参数

字段缺省值说明
templateIdbaseE2B 模板；需要额外程序就选自定义模板
workspaceRoot/home/user沙箱工作路径
sandboxTimeoutSeconds300沙箱存活超时秒数
isolationScopeSESSIONHarness 文件系统隔离范围
persistenceModeTAR或 NATIVE_SNAPSHOT，按模板能力验证保存恢复

五行的缺省值来自 environments.md:63-75。 管理员需要先提供 BUILDER_E2B_API_KEYenvironments.md:51；在 Config 里写 packages 或网络参数不会自动装依赖、也不会落实网络限制environments.md:77。

self_hosted：Worker 只做出站连接

创建 self_hosted 环境时会生成一把 ek_ 开头的环境 key，明文只在创建和轮换的响应里返回一次， 库里存的是 SHA-256 哈希handlers_env.go:136-148handlers_env.go:245-266。这与第 20 章 Endpoint 的 asep_ key 是同一套设计：平台只回显一次，之后只说「前缀 + 哈希」。

Worker 侧启动命令不长，关键在三处参数：key、Gateway 地址、工作目录environments.md:84-94：

docker run --rm \
  --name agentscope-hands \
  -v agentscope-hands:/data \
  --entrypoint java "$SCHEDULER_IMAGE" \
  -Dloader.main=io.agentscope.builder.worker.HandsWorkerMain \
  -cp /app.jar org.springframework.boot.loader.launch.PropertiesLauncher \
  --base-url "$BASE_URL" \
  --environment-id "$ENVIRONMENT_ID" \
  --environment-key "$ENVIRONMENT_KEY" \
  --hands-root /data/hands \
  --worker-id hands-1

这个进程只向 Gateway 发起出站请求，不需要暴露端口environments.md:97。多个 Worker 用不同 worker-id；正式运行由你的进程管理器负责重启environments.md:99。

self_hosted 也改变不了模型在哪跑

官方原话是「即使使用 self_hosted，Managed 的模型推理仍在 Dataplane 中运行」environments.md:37。Worker 只负责接收工具工作并回传结果。所以「Worker 离线」表现为工具一直挂着，而不是模型没响应——这两类故障要分开查managed-agent-execution.md:33。

Memory：共享知识为什么是只读的

Memory 管的是「已核对、可复用的共享文档」，和 Chat 历史、Session 工作记忆、Issue 评论都不是一回事memory.md:10。它的使用方式和普通文件工具有个关键区别：按需读取，不整包塞进提示。

托管场景下，Dataplane 会注册四个 memory 工具ManagedMemoryTools.java:49-94：

工具作用托管挂载下的实际可用性
memory_store_list列出 Store 里的文档可用（readOnly = true）
memory_store_read读取指定路径正文可用（readOnly = true）
memory_store_write新建文档工具存在，但只读挂载会拒绝写入
memory_store_edit替换唯一匹配文本工具存在，并发修改会失败并要求重读

为什么后两个「存在却写不进去」？因为托管构建时，每个挂载的 Store 都被显式设成 read_only： 

/** Shared knowledge is read-only during execution; session files hold private working memory. */
static Map<String, String> sharedKnowledgeAccess(List<String> memoryStoreIds) {
    Map<String, String> access = new LinkedHashMap<>();
    if (memoryStoreIds != null) {
        for (String id : memoryStoreIds) {
            access.put(id, "read_only");
        }
    }
    return access;
}

同时系统提示里会追加一句明确的约束：用 memory_store_list 与 memory_store_read 访问这些只读共享库， 不要写或改共享知识，Shell 与 Worker 的文件工具也访问不到这些实时挂载HarnessAgentBuildService.java:671-678。上一节那张「只读」注释就是这段逻辑的标题HarnessAgentBuildService.java:692-700。

storeId 从哪来

工具参数写着「Mounted store ID from the system prompt」ManagedMemoryTools.java:56。也就是说，Agent 不需要你告诉它 ID，系统提示里已经列好了本次挂载的 Store。这也解释了为什么「只在 Instructions 里写 Store 名字」没用——名字不是绑定。

还有两条与「实时」有关的语义：共享文档是按需实时读取的，不是把正文固定复制进每个 Sessionmemory.md:34；更新测试事实后要重新调用读取工具才能看到新内容，已有对话里引用过的旧内容不会自动改写。资源绑定变了，用新 Session 验证memory.md:34。

维护侧的动作也有讲究：Edit 改文档，Redact 脱敏，Delete 删条目；Archive 掉 Store 后新 Session 不再挂载它，而删除整个 Store 会连同文档一起删memory.md:42。删之前先看消费者。

Vault：凭据在连工具前才被解析

Vault 存的是工具连接要用的凭据。写入后页面只展示类型、标签和目标等元数据，不再回显明文vault.md:10。四种类型的行为差别很大：

类型（API 值）怎么被用上
static_bearer Target 匹配连接名或完整 endpoint URL，解析器自动设置 Authorization: Bearer ...
mcp_oauth 内容需含 access_token，按连接需要可带刷新信息
environment_variable 只替换 MCP header、环境或 query 中明确引用的 ${VARIABLE}
api_key 通用存储类型，不会自动配置模型认证或注入工具

类型与对应 API 值见 vault.md:36， 行为表见 vault.md:24-28。 解析逻辑在 Dataplane 侧：环境变量类型按 environment_variable 或 env 命中VaultCredentialResolver.java:102，Bearer 类写入 header VaultCredentialResolver.java:119-143，OAuth 则取 access_token 拼成同样的 header VaultCredentialResolver.java:248-258。

最常见的用法是环境变量占位：

{
  "name": "reports",
  "url": "https://reports.example.com/mcp",
  "headers": {
    "Authorization": "Bearer ${REPORTS_TOKEN}"
  }
}

前提是有一条 Target 为 REPORTS_TOKEN 的 environment_variable 凭据，并且这个 Vault 已绑定到该 Agentvault.md:38-47。一个连接只选一种清晰的认证方式，避免多个凭据竞争同一目标；用 static_bearer 时 Target 直接写连接名或完整 endpoint，就不用再配同名占位符vault.md:50。

Vault 不是万能凭据池

它解析的是工具连接凭据，不会自动配置所有模型连接managed-agent-capabilities.md:47；环境变量类型也不会全局导出到 Dataplane 或任意 Shell 进程vault.md:36。另外，Vault 密文依赖部署的 master key，备份必须同时保存数据库和原密钥，单独恢复数据库不足以恢复连接vault.md:56。

会话级覆盖：省略、[] 和显式列表是三件事

普通 Chat 和 Issue 走 Agent 的资源默认值；通过 Managed Session API 建会话时，还能指定 environmentId、 memoryStoreIds 和 vaultIds。文档把语义写得非常明确：省略资源列表与显式传入空列表含义不同——省略用默认绑定，空列表表示不挂载该类默认资源managed-agent-configuration.md:49。

源码用「指针 + 是否提供」两个信息来表达这个三态。请求结构里两个字段都是指针类型，nil 才代表没传handlers_sessions.go:57-59：

请求里写成JSON 语义实际挂载
不写该字段 null / 缺失 → 指针为 nil 继承 Agent 的 defaultMemoryStoreIds / defaultVaultIds
"memoryStoreIds": [] 非 nil 的空切片 这一类资源一个都不挂，默认值被显式关掉
"memoryStoreIds": ["ms_..."] 非 nil 且有元素 只用你给的列表，默认值不参与

这段判断就是 mergeSessionMounts 的全部逻辑：环境为空才回退默认；Vault / Memory 只有在「没提供」时才用默认值，提供了（哪怕是空列表）就保留调用方的值agent_defaults.go:19-24agent_defaults.go:31-45。

为什么要设计成三态

因为「用默认值」和「明确不要」是两个业务意图。前者是「照旧」，后者是「这次任务不允许读公司知识库 / 不允许用这套凭据」。 如果 [] 也被当成「没传」，你就没办法在单次会话里做权限收窄。对应的实现细节：请求解析时先记住 memProvided / vaultProvided，再交给合并函数handlers_sessions.go:210-219。

两种结果：调用结束，和任务被接受

资源都绑对了，最后一步是「怎么算完成」。Managed 把执行结果归纳成四种意图，它描述的是任务状态，不是某轮模型回复的语气managed-harness-task-outcomes.md:12-19：

  • succeeded 有明确交付且执行可完成。下一步是检查产物并按 Issue 策略验收。
  • waiting 等待一个已存在、可追踪的依赖任务。要看依赖 ID 和它的真实状态。
  • blocked 缺少信息或条件，但保留已完成部分。补充具体输入后可沿流程继续。
  • failed 执行失败。读错误与部分结果，修复后再决定是否重试。

    • 官方在这里划了一条很硬的线：「稍后继续」「正在等待」这类普通文本不构成成功；还有未结束的后台任务或异常停止时，也不能据此判定成功managed-harness-task-outcomes.md:21。Runtime 会为续轮和等待设置预算，超限就停止自动推进——所以「一直等」不是一种可持续的状态。

    完成不等于验收

    Chat 的一轮回复结束，与 Issue 的业务验收是两件事managed-agent-execution.md:41-45。Run 或 Task 成功也不等于报告事实正确，用户要在 Inbox 对照标准检查完整结果managed-harness-task-outcomes.md:33。这与第 20 章那条 partial_succeeded → completed 的映射是同一个道理：状态机说「没整体失败」，业务说「能不能用」。

    还有一条影响排障方向的规则：子任务使用独立执行上下文，创建子 Agent 不会自动增加它没有的网络、工具或权限managed-harness-task-outcomes.md:25。子 Agent 报 403，先回头看绑定，而不是怀疑子 Agent 的实现。

    一次任务怎么把这些资源装配起来

    把前面几节按执行顺序串起来，每一步都能对应到一处可检查的配置：

    • Chat / Issue 提交工作 浏览器只提交工作和查看事件，不参与模型循环managed-agent-execution.md:10。
    • Control：解析身份与绑定 解析 Agent 定义、版本、环境及知识与凭据引用managed-agent-execution.md:14-25。会话级覆盖就在这一步生效。
    • Dataplane：构建 Harness 把定义文件准备到会话目录、构建 Harness、连接持久状态存储；模型循环在 Dataplane 里跑managed-agent-execution.md:25。
    • Dataplane：挂载共享知识 按 read_only 建 Memory 挂载并注册 memory_store_* 工具HarnessAgentBuildService.java:653-659。
    • 工具执行 → Environment Local 在 Dataplane、sandbox 用 E2B、remote 用共享存储、self_hosted 交给 Workermanaged-agent-execution.md:33。
    • Vault：连接前解析凭据 工具真正发起连接时才取凭据，替换 ${VAR} 或直接写 Bearer headermanaged-agent-execution.md:27。
    • 结果：事件、状态与交付 产出事件、状态与交付结果，最后落到 Chat 回复或 Issue 验收managed-agent-execution.md:14-20。

    第 4、5、6 步合起来解释了一个现象：模型可以正常回复，工具却接连失败。因为模型在 Dataplane，文件在 Environment，凭据在 Vault—— 三者是三条独立的链路，任何一条断了都只影响工具，不影响「说话」。

    速查：字段默认值、环境能力、结果语义

    先看几个「不填会怎样」：

    不填的字段实际行为出处
    model 用部署默认模型；部署配置的默认值是 qwen-max，由 BUILDER_MODEL_NAME 选择 managed-agent-configuration.md:33-35
    maxIters 表单预填 12；API 传 0 或负数时后端兜底 20 managed-agent-configuration.md:21managed_definition.go:91-94
    environmentId 回退到 Agent 的 defaultEnvironmentId agent_defaults.go:31-33
    memoryStoreIds / vaultIds 继承默认；传 [] 则一个都不挂 agent_defaults.go:34-39
    workspaceBinding 只绑 workspaceId 时使用所选草稿 workspaces.md:38

    再看四种环境的能力边界，一张矩阵就够：

    文件读写Shell模型在哪跑
    local有有Dataplane
    sandbox有（E2B 沙箱）有Dataplane
    remote有（共享存储）无Dataplane
    self_hosted有（Worker 工作目录）有（Worker）Dataplane

    「模型在哪跑」这一列对四行都相同，正是 self_hosted 那节的结论 environments.md:37； 文件与 Shell 能力来自类型表 environments.md:20-27。

    最后是结果四态与「该做什么」的对照：

    Outcome下一步动作别做什么
    succeeded检查产物，按 Issue 策略验收别把「跑完了」当成「合格了」
    waiting查依赖 ID 的真实状态别重复发同一份工作
    blocked补充具体输入，引用原 Issue / Task / 缺失项别用「请继续」这种空话解阻塞
    failed读错误与部分结果，修复后决定重试别在原执行上反复催促

    五个坑，每个都能从现象反推资源

    坑一：只在 Instructions 里写 Store 名称。指令里提到一个 Store 不会建立绑定 memory.md:32，Agent 也不会凭空知道路径。现象是「它答得像在猜」。 修法是去 defaultMemoryStoreIds 或会话的 memoryStoreIds 真正挂上。

    坑二：把 [] 当成「没传」。如果你为了「省事」在请求里统一写空数组，默认资源会被全部关掉 managed-agent-configuration.md:49。 现象是「同样的 Agent，为什么这个接口调起来没知识、没凭据」。

    坑三：以为改草稿会立刻影响老会话。运行上下文用解析后的定义快照，已有 Session 不会重读 workspaces.md:42。现象是「配置明明改了」。修法是新开 Chat 或新 Session 复验。

    坑四：指望 remote 跑 Shell。remote 类型只有文件系统能力，不能当远程 Shell Worker 用 environments.md:61。现象是文件工具正常、命令工具永远拿不到结果。

    坑五：把 Environment 的 ek_ key 当 Endpoint 的 key。两者都是平台凭据、都只回显一次，但用途完全不同： ek_ 是 Worker 连 Gateway 的环境凭据，asep_ 才是调用 Endpoint 的凭据。现象是 401，而且换多少次 key 都没用—— 因为你在拿错的凭据打错的接口。

    自测：三个判断题

    不填 maxIters 直接调 API，Agent 最多迭代几次？

    20 次。后端对 <= 0 一律赋 20 managed_definition.go:91-94； 控制台表单里的 12 只是界面预填值 managed-agent-configuration.md:21，不代表协议默认值。

    会话请求里写 "vaultIds": []，会发生什么？

    这一次会话不挂任何默认 Vault——提供了空列表就保留调用方的值，不再继承默认绑定 agent_defaults.go:34-39。 工具本身能列出来，但连接外部服务时没有凭据可解析，通常表现为 401。

    Agent 说「文件已读取」，能不能据此判断 Environment 配好了？

    不能。模型回复只证明模型链路通；文件与 Shell 是另一条链路。官方建议上传大文件后让 Agent 给出可核对的片段或统计， 避免只凭「已读取」的回复判断成功 managed-agent.md:42。

    练习：给一个 Agent 逐层加能力

    不要一次配完。按官方建议「一次调整一个层次」managed-agent-configuration.md:61-68，每步都用新会话验证：

    1. 先只验模型
      model 留空，问一个纯知识问题。答不出来先查 Dataplane 的 DASHSCOPE_API_KEY 与默认模型，别急着绑资源。
    2. 再加 Instructions 与迭代上限
      写清输入、输出与「缺材料时列问题」的边界；把 maxIters 显式设成一个小值（如 8），观察它何时停。
    3. 绑 Workspace 与 Environment
      放一个 AGENTS.md 约定「输出必须包含来源」，再让 Agent 读一个已知文件。读不到就查环境类型与工作目录，而不是改提示词。
    4. 加 Memory，并验证「按需读取」
      在 Store 里写一条便于核对的事实（如「本项目把 Lark 定义为周报归档任务」），提问后检查工具记录里有没有 memory_store_list / memory_store_read。
    5. 最后加 Vault
      建一条 environment_variable 凭据，在 MCP header 里用 ${VARIABLE} 引用，先执行一次只读调用。失败时依次查 Target 是否完整匹配、变量是否被明确引用、Vault 是否绑定。
