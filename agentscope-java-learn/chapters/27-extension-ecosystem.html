27 · 扩展生态总览：模型 / 记忆 / 存储 / RAG / 协议 / 渠道

前 26 章讲的是 Agent 本体、Harness 工程能力和 Service 控制面。从这一章开始，视角换成 「框架把哪些能力留成接口，由外部模块来实现」。生态不是插件市场：每个扩展都是独立的 Maven 模块， 按需引入；接口在 core / harness，实现在 extensions，装配靠 builder 或 Spring Boot starter。 先分清这两层，才不会把「加了一个依赖」误当成「换了一种运行时」。

读完你能做到

  • 用「契约 → 实现 → 装配」三层解释一个扩展从依赖到生效的完整路径
  • 分清出站能力（模型、记忆、RAG、状态、存储）与入站入口（渠道、协议、调度）
  • 说清 10 个模型 id 为什么只对应 6 个 artifact，以及 ModelRegistry 如何解析
  • 按需求选择记忆、状态存储、分布式存储、RAG、协议与渠道，而不是按品牌背模块名
  • 识别 2.0.4 里仍可用但已标记弃用的记忆 / RAG 旧路径，并知道该往哪迁移
  • 用 BOM、starter 与 mvn dependency:tree 控制版本和 classpath

为什么先看地图：生态的代价是 classpath

官方把集成扩展集中放在 agentscope-extensions/ 下，每个扩展都是独立 Maven 模块，按需引入即可 overview.md:6。 core 只保留共享契约，例如模型提供商全部迁到独立模块，core 里只留下模型接口 overview.md:12。 这带来一个和普通「配置文件开关」完全不同的后果：引入哪个模块，决定了运行时存在哪些实现。

所以生态章最容易犯的错不是「不会配」，而是「配错层」：在 prompt 里调模型行为，却没发现 provider 模块不在 classpath；以为加了 Redis 依赖就有分布式状态，却没发现状态仍落在 JSON 文件；或者同时引入两套存储，最后不知道 哪个 builder 参数生效。下面三个问题能挡住大部分误判：

  1. 它补的是哪个接口？
    Model、AgentStateStore、Knowledge、Channel 各自解决不同层的问题，接口不同就不能互相替代。
  2. 方向是出站还是入站？
    Agent 主动调用模型 / 记忆 / RAG / 存储，和外部系统主动调用 Agent，是两条相反的依赖方向。
  3. 模块怎么进 classpath？
    手写依赖、BOM 管版本、starter 自动装配，三条路最终都要落到同一组接口实现上。

三层结构：契约、实现、装配

AgentScope 的扩展不是「在 core 里加 if」，而是三层分开。第一层是 core / harness 里的接口；第二层是 agentscope-extensions-* 里的实现；第三层是 builder 参数或 Spring Boot starter。 接口定义能力边界，模块提供实现，装配决定这一次运行用哪个实现。

层在哪典型内容换掉它会怎样
契约agentscope-core / agentscope-harnessModel、AgentStateStore、Knowledge、Channel改的是 Agent 能看见的能力种类
实现agentscope-extensions-*OpenAI、Redis、Dify、飞书等适配器换的是同一能力的后端
装配builder / starter / 配置.model(...)、.stateStore(...)、.distributedStore(...)决定本次运行实际用哪一个实现

Maven 侧也一样：扩展模块依赖 core，但不重复声明版本；版本由 BOM 统一管理。根 POM 导入 agentscope-dependencies-bom 与 agentscope-bom pom.xml:134-151， 具体模块版本在 BOM 的 dependencyManagement 里 pom.xml:80-87。 以 OpenAI 扩展为例，它声明 agentscope-core 依赖时不写版本 pom.xml:29-37。

方向：谁调用谁，决定故障往哪找

同样是「接一个外部系统」，方向不同，故障位置完全不同。模型、记忆、RAG、状态存储与沙箱是 Agent 主动出站：Agent 发起请求，外部系统返回结果。渠道、协议和调度器则是 外部入站：平台把消息或任务送进来，Agent 再执行。基础设施则更像横向治理，既可能被 Agent 调用， 也可能替 Agent 做注册、发现或触发。

模型：10 个 id，6 个 artifact

模型是最典型的「一个接口，多种 provider」。core 只保留共享模型契约，provider 全部在独立模块里 overview.md:12。 Model 接口本身很小：一个流式 stream(...) 方法、一个模型名，外加结构化输出、上下文窗口等 带默认实现的 optional 能力 Model.java:22-33。

真正容易混的是 artifact 与 provider id。官方表格列了 10 个 provider id，但只落在 6 个 artifact 上： agentscope-extensions-model-openai 同时承载 OpenAI、DeepSeek、GLM、Kimi、MiniMax 五个 id overview.md:14-25。 所以「支持 DeepSeek」不等于要加一个 DeepSeek 依赖，而是加 OpenAI 兼容模块，再选 deepseek:<model>。

仓库里的 agentscope-extensions-model-e2e-tests 是测试模块，不是面向用户的集成依赖 overview.md:28-32。 第 28 章会逐个拆 provider 的凭证、formatter 与切换方式。

记忆：接口在，方向变了

官方文档把 LongTermMemory 描述成跨会话持久化用户偏好与事实的接口，并给出 Mem0、百炼、ReMe 三种实现： Mem0 适合本地或自托管、需要 metadata 过滤；百炼适合已在阿里云上；ReMe 关注工作区级轨迹摘要 overview.md:6-12 overview.md:27-30。 三者都实现同一个接口，因此 Agent 侧代码可以不变 overview.md:14。

2.0.4 的源码把这条路径标成 legacy

LongTermMemory 接口本身带 @Deprecated(forRemoval = true, since = "2.0.0")， 注释写明长期记忆已移除，会话上下文改由 AgentState 的 context 承载，跨会话持久化应在应用层集成 LongTermMemory.java:66-71。 ReActAgent 的 longTermMemory(...) 也被归入 1.x legacy 兼容 setter， 并注明会在下一个小版本移除 ReActAgent.java:5255-5265。

这不代表三个模块不能用。Mem0、百炼、ReMe 仍然实现了该接口 Mem0LongTermMemory.java:113 BailianLongTermMemory.java:77 ReMeLongTermMemory.java:66。 新代码要做的不是「找更好的 memory 后端」，而是先决定：这部分状态到底该放在会话上下文、应用数据库，还是外部记忆服务。 第 29 章会把这条差异逐项对齐。

状态：AgentStateStore 是当前主线

和记忆不同，AgentStateStore 是 2.0.4 的当前接口：它按 (userId, sessionId) 保存、读取、删除和列出 State 对象，供 Agent、Toolkit 等有状态组件跨进程恢复 AgentStateStore.java:22-38。 它还定义 UNVERSIONED = -1，用 saveIfVersion 表达乐观并发 AgentStateStore.java:63-67。

分布式存储：一个门面，四种能力

DistributedStore 是 harness 里的一站式门面：它把 Agent 状态、工作区文件系统 KV、沙箱快照和沙箱并发锁 收在同一组 getter 下 DistributedStore.java:30-73。 官方给的能力矩阵很直接：Redis 四项齐全；MySQL 四项齐全；MongoDB 四项齐全；OSS 没有 SandboxExecutionGuard，因为对象存储不适合做分布式锁 index.md:24-33。

RAG：五种知识库，一条旧接口

官方把 RAG 统一到 Knowledge 接口：Agent 通过它检索文档片段，再交给模型生成 overview.md:6。 五种实现分别是 Simple（自建 embedding + 向量库）、百炼、Dify、HayStack 与 RAGFlow overview.md:8-14。 接入方式也一样：.knowledge(...) 加 .ragMode(...)，或者包装成 KnowledgeRetrievalTools 让 Agent 自己决定是否检索 overview.md:16-33。

Knowledge 也是 legacy

Knowledge 接口在 2.0.4 里同样标了 @Deprecated(forRemoval = true, since = "2.0.0")， 注释写明 rag 包已移除，检索应在应用层集成 Knowledge.java:30-34； ReActAgent 的 knowledge(...) 也注明「legacy adapters remain functional」 ReActAgent.java:5289-5293。 五个实现仍然可用，但新项目应先判断：检索是放在 Agent 外部做成工具，还是继续走 legacy 适配器。

选型上，官方给的建议是按已有基础设施选：要自己掌控 embedding 和向量库选 Simple；已在百炼、Dify、HayStack 或 RAGFlow 上维护知识库，就选对应适配器。除 Simple 外，其余实现只负责检索，文档导入与更新走对应平台 overview.md:35-45。 第 32 章会拆接口与检索参数。

协议：三个方向，别混成一个「对外接口」

协议解决的是 Agent 与外部世界如何互操作。官方把三种协议分开：A2A 用于 Agent 之间互相调用、组成工作流； AG-UI 把 Agent 事件流标准化输出给前端 UI；Agent Protocol 提供 HTTP 标准接口，让其他系统提交任务 overview.md:6-14。 还有一个 Chat Completions Web，把 Agent 包装成 OpenAI Chat Completions 兼容接口。

渠道：入站适配器，重点在共享状态

Channel 适配器把 Agent 接进真实消息平台：钉钉走 Stream 持久 WebSocket，飞书走事件订阅回调，GitHub / GitLab 走 Webhook，企业微信走加密回调 index.md:8-14。 所有适配器遵循同一模式：入站解析成 InboundMessage，去重、防循环，再通过 Gateway 分发；出站调用平台 API 把回复投递回去 index.md:18-21。

平台差异被三个共享组件吃掉：IdempotencyStore 按消息 id 去重、BotLoopGuard 按 peer 限速防止 bot 死循环、AccessTokenStore 缓存出站 token index.md:23-27。 但它们的默认实现把状态放在 JVM 内，多副本部署时必须换成共享实现，否则平台重试会在不同副本上各处理一次 index.md:29-38。 第 34 章会拆 webhook 校验、消息路由与平台差异。

技能仓库：把 Markdown 技能放到哪

AgentSkill 用 Markdown 加资源文件描述可复用技能，AgentSkillRepository 负责把这些技能从外部存储加载进来， 再交给 Toolkit / ReActAgent 使用 overview.md:6。 官方给了 Git、MySQL、PostgreSQL 三种实现，Nacos 也提供一个技能仓库 overview.md:8-16。

选型不是看数据库品牌，而是看变更流程：想用 Git PR 管控、可读可 review，选 Git；要在管理后台动态修改、立即生效， 选 MySQL、PostgreSQL 或 Nacos overview.md:34-38。 接口本身很小：按名取、列全部、保存和删除 AgentSkillRepository.java:35-60。 第 35 章会拆三种仓库的存储布局与同步。

装配：一条依赖，三种生效方式

扩展进 classpath 只是第一步，真正生效还要经过装配。手写 builder 最直观；Spring Boot starter 把常见 bean 和配置项 预先装好；BOM 则只负责版本，不负责实例。三者职责不要混。

方式你写什么适合容易错在哪
手写 builder显式传 Model / AgentStateStore / Channel需要精细控制、非 Spring 应用忘了传，运行时用默认实现
Spring Boot starter加 starter 依赖 + 配置项Spring 应用、想少写装配代码以为 starter 会替代所有 builder 参数
BOM只导入 agentscope-bom统一版本以为 BOM 会自动引入模块

推荐的扩展节奏是「一次只加一种能力」：先让模型通，再加状态存储，再加记忆或 RAG，最后才接入渠道或协议。 每加一个模块，都用 mvn dependency:tree -Dincludes=io.agentscope 确认实际引入的 artifact， 再用一个最小任务验证。这样出问题时能立刻判断是新模块、凭证还是装配顺序。

故障边界：扩展问题通常不在 prompt 里

坑一：把 artifact 当 provider。agentscope-extensions-model-openai 同时服务 OpenAI、DeepSeek、 GLM、Kimi 与 MiniMax；加一个依赖不等于只支持一个品牌 overview.md:14-25。

自测：三个判断题

加了 agentscope-extensions-model-openai，是不是就只支持 OpenAI？

不是。这个 artifact 同时承载 OpenAI、DeepSeek、GLM、Kimi、MiniMax 五个 id；支持哪个 provider 由 id 和对应凭据决定， 不是由 artifact 名字决定 overview.md:14-25。

用了 DistributedStore，还需要理解 AgentStateStore 吗？

需要。它只是把 AgentStateStore、BaseStore、快照和锁收成一个门面，能力与优先级仍按各组件计算； aistio 托管 Store 甚至要求另备 AgentStateStore DistributedStore.java:30-73 index.md:91-108。

2.0.4 里 LongTermMemory 和 Knowledge 还是推荐入口吗？

不是。两者都标了 @Deprecated(forRemoval = true, since = "2.0.0")，适配器仍可用，但新代码应先评估应用层方案； 这也是第 29、32 章要重点拆的文档与源码差异 LongTermMemory.java:66-71 Knowledge.java:30-34。

练习：给一个真实需求选扩展

目标不是把所有模块都装一遍，而是能写出一份可解释的选型记录。建议 45 分钟：

  1. 写需求与方向
    选一个真实场景（例如「企业微信里回答内部文档问题」），标出它需要哪些出站能力和哪些入站入口。
  2. 先选接口
    把需求映射到 Model、Channel、Knowledge 或 AgentStateStore，写下为什么不是另一层。
  3. 只加一个模型模块
    导入 BOM，加一个 provider artifact，用 ModelRegistry.resolve 跑通一次最小调用；记录实际使用的 id。
  4. 换一次装配方式
    再引入对应 starter，比较手写 builder 与自动装配的差异；确认哪个参数最终生效。
  5. 检查状态落点
    确认当前用的是 JSON、内存还是远端 AgentStateStore；重启一次，看历史是否还在。
  6. 读一次弃用警告
    加一个 legacy 记忆或 RAG 适配器，观察编译警告，并把警告原文记进选型记录。
  7. 画依赖图
    用 mvn dependency:tree 画出本次引入的 artifact，标出哪些是直接依赖、哪些是传递依赖。
  8. 最后写三行结论
    分别写「接口选了什么」「后端为什么是它」「部署形态还缺什么」，确保每一行都能独立核对。
