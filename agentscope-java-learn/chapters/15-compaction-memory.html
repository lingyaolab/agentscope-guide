15 · 压缩、记忆与逐出：让上下文不爆，让事实不丢

第 14 章解决「谁去做」，这一章解决「装不下怎么办、记住了放哪」。框架里有四件经常被混为一谈的事：压缩（把前缀换成一条摘要）、结果逐出（单条工具输出太大就落盘）、记忆（把事实写进 MEMORY.md 与日流水账）、转写（每一轮都追加到会话 JSONL）。它们各自由一个中间件负责，在 HarnessAgent.build() 里按固定顺序装进同一条洋葱链；而且——这是与官方文档差得最远的一点——压缩和逐出默认就是开着的。

读完你能做到

  • 背下 CompactionConfig / PruneConfig / TruncateArgsConfig / ToolResultEvictionConfig 的全部默认值，并知道哪几个是「动态」
  • 给定模型上下文窗口，算出实际的 triggerTokens 与 keepTokens，以及 reserved 过大时会发生什么
  • 说出压缩管线的九个步骤，以及「先 prune 后判断」这个顺序带来的后果
  • 解释三处 flush 为什么不是同一份 prompt，以及 memory_save 与 MemoryFlushManager 的写入差别
  • 画出两层记忆的写者/读者关系，说清 .consolidation_state 水位线怎么控制合并范围
  • 从 build() 行号推出 onReasoning 与完成回调的真实执行顺序，并指出 MemoryMaintenanceMiddleware javadoc 与装配顺序矛盾在哪

先说为什么：三件不同的事，默认都开着

「上下文会满」是工程问题，「跨会话记住」是产品问题。官方文档把两者放进同一篇 memory.md，读起来像一个开关控制的整体；源码里它们是四条互不依赖的链路，各自有开关、各自有默认值：

压缩：改「整段上下文」
CompactionMiddleware 在每次 reasoning 前把前缀切成「摘要 + 尾巴」，用一次 LLM 调用换掉几千 token。默认 triggerMessages=50、triggerTokens 动态CompactionConfig.java:273-286。
逐出：改「单条结果」
ToolResultEvictionMiddleware 只看单个 ToolResultBlock 的文本长度：超过 80 000 字符就整段写盘，上下文里换成「首尾预览 + 路径」ToolResultEvictionConfig.java:45-52。它不调用 LLM。
记忆：改「磁盘上的文件」
MemoryFlushMiddleware 在每次调用结束后抽事实、追加到 memory/YYYY-MM-DD.md；MemoryConsolidator 周期性把它合并进 MEMORY.mdMemoryFlushManager.java:218-235。上下文里只注入 MEMORY.md。
最容易踩的认知差：默认不是「全关」

HarnessAgent.Builder 的字段初始值直接写死为 CompactionConfig.builder().build()、MemoryConfig.defaults()、ToolResultEvictionConfig.defaults()，两个 disable* 都是 falseHarnessAgent.java:1227-1231。builder 的 javadoc 也明写 “Compaction is enabled by default”“Tool result eviction is enabled by default”:1867-1908。所以「什么都不配」不等于「什么都没发生」：一个长会话跑到第 50 条消息就会自动出现一条 __compaction_summary__。

    每轮 call() 结束后都会 fire-and-forget 一次 flush；模型没啥可记时会输出 NO_REPLY，此时不写文件MemoryFlushManager.java:174-183。所以「文件存在但没有段」也是正常结果。

先用 close() 再去看文件

flush、maintenance、session 镜像都是后台任务。HarnessAgent.close() 会分别等 SessionTree 镜像与 MemoryBackgroundTasks 静止，各 5 秒上限HarnessAgent.java:453-475。测试里不等 close() 就读盘，很容易读到半份文件。

一条链路：onReasoning 上的九个步骤

CompactionMiddleware.onReasoning 只对 ReActAgent 生效；其他 Agent 实现直接放行CompactionMiddleware.java:81-83。进入之后先把首条 SYSTEM 消息摘出来——它不参与压缩，压缩完再原样拼回去:88-98。然后才是 ConversationCompactor.compactIfNeeded：

  1. ① truncateArgs（非 LLM，默认关闭）
    只改「保留窗口之前」的 ASSISTANT 消息里的 ToolUseBlock 参数值；config.getTruncateArgsConfig() 为 null 时原样返回ConversationCompactor.java:612-620。默认就是 null。
  2. ② pruneToolResults（非 LLM，默认开启）
    从后往前扫 TOOL 结果，先保护最近 protectTokens=40 000 的输出，再把更早、且单条超过 maxOutputChars=2 000 的结果换成头尾预览；可剪总量不足 minimumTokens=20 000 就整体放弃:544-557。
  3. ③ 估算 token 并判断要不要压缩
    TokenCounterUtil 用 字符数 / 2.5 向上取整，再加结构开销（消息 5、tool_call 10、tool_result 8、其他块 5）TokenCounterUtil.java:49-58。注意它是估算，不是 tokenizer。
  4. ④ 算切点：按 token 二分，或按条数
    keepTokens > 0 时二分找「尾部刚好装得下」的最早下标，并强制至少留 1 条:257-278；否则按 keepMessages 直接 size - keep。
  5. ⑤ 修正切点：不拆 ASSISTANT / TOOL 对
    如果切点落在 TOOL 上，就往前找发出这些 tool_call 的 ASSISTANT，把切点移到它之前；找不到就跳过整段 TOOL:296-338。这一步是「压缩后模型还能看懂工具调用」的关键。
  6. ⑥ 压缩前 flush（LLM）
    从待压缩前缀里剔除旧摘要消息后再 flush，避免把已经沉淀过的事实重复抽取:121-125。这一步用的 MemoryFlushManager 是 2 参构造——也就是默认 prompt，不读 MemoryConfig.flushPrompt。
  7. ⑦ offload（同步写盘）
    把整段待压缩消息（含旧摘要）经 SessionTranscriptWriter 追加到会话 JSONL，再解析出相对路径；失败只 warn，返回空串继续:155-183。
  8. ⑧ LLM 摘要
    输入是「旧摘要 + 新前缀」拼成的文本，套进 DEFAULT_SUMMARY_PROMPT 的四段式模板（SESSION INTENT / SUMMARY / ARTIFACTS / NEXT STEPS）:344-383。失败文案是 (Summarization failed: …)，空输出是 (Summary unavailable)。
  9. ⑨ 双写 + 重建输入
    新列表 = [摘要消息] + tail。它同时写进 AgentState.contextMutable() 和新的 ReasoningInputCompactionMiddleware.java:126-148——只改其中一个，后续轮次就会看到两种不同的历史。
顺序带来的两个「免费优化」

因为 prune 在判断之前跑，一次纯本地剪枝就可能把 token 压到阈值以下，于是这一轮根本不会调用摘要 LLM。同理，truncateArgs 若开启，也会先削一轮参数体量。这两步都不花钱，所以默认把 prune 打开、把 truncateArgs 留给你按需开，是很务实的选择。

压缩失败不会中断对话

compactIfNeeded 外面套了 onErrorResume：非 InterruptedException 的异常只 warn，然后 Optional.empty()，本轮按原上下文继续CompactionMiddleware.java:112-125。只有中断会向上抛。所以「摘要模型挂了」的表现是上下文继续增长，而不是报错。

阈值：动态算法与三个边界

resolveEffectiveConfig() 只在 triggerTokens == 0 或 keepTokens == -1 时才做解析；两个都写死了就原样返回CompactionMiddleware.java:155-162。解析规则如下：

情况triggerkeep结果
模型报窗口 W，且 W > reserved W - 20 000 min(8 000, max(2 000, (W-20 000) × 0.25)) 常规路径
W <= reserved max(1, W / 2) + warn 2 000（usable 为负，被下限兜住） 见下方说明
模型不报窗口（W <= 0） 160 000 0 keep 回落 keepMessages=20

逐字看两段代码更稳。trigger 的 clamp 只在 contextWindow > 0 分支里发生：effectiveTrigger <= 0 时取 Math.max(1, contextWindow / 2) 并打 warn:167-194。keep 的 -1 分支在无窗口时直接给 0:199-215，而 determineCutoffIndex 里 keepTokens > 0 不成立就走 keepMessagesConversationCompactor.java:245-254。所以「动态 keep」在无窗口模型上等价于「保留最近 20 条」，不是「保留 8 000 token」。 

// 假设 W = 32 000（很多小模型），默认配置：
//   trigger = 32 000 - 20 000 = 12 000
//   keep    = min(8 000, max(2 000, 12 000 * 0.25 = 3 000)) = 3 000
// 于是：涨到 12 000 token 触发，保留约 3 000 token 的尾巴。

// 假设 W = 16 000：
//   trigger = -4 000 → clamp 到 max(1, 8 000) = 8 000，并 warn
//   keep    = min(8 000, max(2 000, -4 000 * 0.25 = -1 000)) = min(8 000, 2 000) = 2 000
// 注意：每轮都可能在 8 000 附近反复触发，官方建议是调小 reserved。
小窗口模型上，默认 reserved=20 000 是危险的

它不会让程序崩，但会让「触发点」被 clamp 到窗口的一半，压缩变得很频繁；而 keep 会被压到下限 2 000。这段代码旁边的注释就写了 “would fire compaction on every call”，clamp 的作用是避免每轮都压:170-181。真要跑 8K/16K 窗口，请显式写 reserved(2_000) 与 triggerTokens(...)。

逐出与压缩完全独立：它不做摘要、不看对话条数，只对单个 ToolResultBlock 的文本长度做判断。默认值四项：

常量默认含义

DEFAULT_PREVIEW_CHARS2 000占位符里首尾各保留的上限（实际取 min(2 000, len/2)）

DEFAULT_EXCLUDED_TOOLSread_file、write_file、edit_file、memory_search、memory_get、session_search这些工具的结果永不逐出

execute（shell）被故意排除在豁免名单之外——源码注释直说 “command output can be very large”ToolResultEvictionConfig.java:54-73。这解释了一个常见现象：read_file 读大文件不会逐出，execute 跑 find / 会。

预处理：prune 默认开、truncateArgs 默认关

这两个常被当成一个东西，实际上触发条件、作用对象、默认值都不同：

pruneToolResults：默认开

  • 作用对象：ToolResultBlock（工具返回）
  • 保护窗口：最近 protectTokens=40 000 的 TOOL 输出不动
  • 只剪「单条超过 maxOutputChars=2 000」的结果
  • 可剪总量 < minimumTokens=20 000 时整体不动手，避免为了省一点反而破坏可读性
  • 豁免：read_file、memory_search、memory_get、session_search
  • 预览格式：head + "\n\n...(N chars pruned)...\n\n" + tail
  • 出处：CompactionConfig.java:574-580、ConversationCompactor.java:591-601

truncateArgs：默认关

  • 作用对象：ToolUseBlock（工具参数）
  • 默认值 null，必须显式配 truncateArgs(...) 才生效
  • 开启后的默认：triggerMessages=25、triggerTokens=40 000、keepMessages=20、keepTokens=0、maxArgLength=2 000
  • 只改保留窗口之前的 ASSISTANT；保留前 20 个字符 + ...(argument truncated)
  • 典型收益：write_file 这种一次几万字符的入参
  • 出处：CompactionConfig.java:472-479、:629-646

prune 与 truncateArgs 的开关判断都在方法第一行：pruneConfig == null 或 truncateConfig == null 就原样返回:510-513。所以「关掉 prune」= pruneConfig(null)，不是把阈值设成 0。

溢出兜底：只重试一次

前面都是「提前预防」，这一条是「已经报错了怎么办」。它在 HarnessAgent 的调用包装层，不在中间件里：

  1. 前提：compactionHook != null
    只有装上了 CompactionMiddleware 才挂 onErrorResumeHarnessAgent.java:958-968。如果你用 compaction(null) 关掉压缩，溢出错误会原样抛给调用方。
  2. 识别：7 个关键词
    context_length_exceeded、context length、maximum context、token limit、too many tokens、exceeds the model's maximum、reduce the length，全部对 message.toLowerCase() 做包含判断:1103-1116。所以自定义模型的报错文案要能被这七个之一覆盖。
  3. 强制配置：triggerMessages(1)
    现场 new 一个 CompactionConfig.builder().triggerMessages(1).build()，其余全是默认:1071——你在 .compaction(...) 里写的 trigger/keep/prompt 全部不参与这一次。
  4. 用主模型、读 memoryConfig 的 flushPrompt
    new MemoryFlushManager(workspaceManager, getModel(), effectiveFlushPrompt)，其中 prompt 优先取 memoryConfig.flushPrompt():1072-1078。注意这里是 getModel()，不是 compactionConfig.getModel()——配了压缩小模型也会用主模型。
  5. 压缩成功才重试，且只重试一次
    压缩结果为空 → 抛 Context overflow: emergency compaction yielded no result；成功 → delegate.call(...) 再来一次:1087-1100。第二次再溢出，错误直接冒泡（没有循环）。
紧急压缩的 keep 是「未解析」的 -1

forceConfig 没有经过 resolveEffectiveConfig()，所以 keepTokens 仍是 -1。determineCutoffIndex 里只有 >0 才走 token 路径，于是这次实际按 keepMessages=20 保留尾巴ConversationCompactor.java:245-254。如果你的会话是 20 条超长消息，这一刀可能还是装不下——第二次就真的失败了。

记忆：两层文件、两个写者、一条水位线

文件谁写怎么写谁读
memory/YYYY-MM-DD.md MemoryFlushManager（每轮 / 压缩前 / 兜底）、memory_save 只追加，段落头 ## Memory Flush — <Instant> 或 ## Memory Save — <Instant> MemoryConsolidator、memory_search
MEMORY.md MemoryConsolidator（整体重写）、memory_save（追加） LLM 输出全文覆盖；memory_save 是例外地追加 注入 system prompt；memory_search

MemoryFlushManager.writeMemoryFiles 的 javadoc 明确写了「MEMORY.md is intentionally NOT touched here」MemoryFlushManager.java:218-235——MEMORY.md 由 consolidator 独占。但 memory_save 是两处都写：先 append 到 MEMORY.md，再 append 一条带时间戳的日账，返回值是 Saved N memories to MEMORY.mdMemorySaveTool.java:71-86。这就留下一个真实副作用：下一轮 consolidation 会把这条日账当成「新条目」，可能再合并一次。

水位线是 consolidation 的「增量游标」。它默认存在 memory/.consolidation_state；如果配了分布式 store，读写优先走 store（命名空间 ["memory","consolidation"]、key watermark），写入用 CAS，最多重试 5 次MemoryConsolidator.java:65-66、 :100-102。 readDailyEntries 会跳过 .consolidation_state、archive 与非 .md 文件，只取 mtime 严格晚于水位线的日账:240-252。

为什么日账是「流」、MEMORY.md 是「文件」

默认 flush prompt 里写了两条硬规则：输出只写今天的日账，MEMORY.md 只是只读上下文、不要复述MemoryFlushManager.java:80-88。这样 flush 可以无状态、无锁地 append；去重和压缩交给 consolidation 一次性做。代价是同一事实可能在日账里出现多次——这是设计，不是 bug。

Flush：三个触发点，两份 prompt

先看三个触发点分别是谁在调、用哪份 prompt、失败怎么办：

触发点调用者prompt 来源同步性
每次 call() 结束 MemoryFlushMiddleware.onAgent → doOnComplete memoryConfig.flushPrompt()，为空则 DEFAULT_FLUSH_PROMPT（build 时已解析） fire-and-forget，走 boundedElastic
压缩前 ConversationCompactor 内部 DEFAULT_FLUSH_PROMPT 硬编码（2 参构造） 在压缩链路里同步等待
溢出兜底 HarnessAgent.forceCompactAndRetry memoryConfig.flushPrompt()，否则 DEFAULT 同步

第 2 行是本章最值得记住的细节：CompactionMiddleware.onReasoning 里写的是 new MemoryFlushManager(workspaceManager, model)CompactionMiddleware.java:106-109，而 2 参构造固定传 DEFAULT_FLUSH_PROMPTMemoryFlushManager.java:95-97。官方文档说「三处用同一份 flushPrompt」，与源码不符。

per-call flush 的调度有三个容易忽略的机制，全在 MemoryFlushMiddleware：

  1. 配额在派发时就占，不在任务里占
    MemoryBackgroundTasks.begin() 在 scheduleFlush 第一行调用。注释解释得很清楚：排队中的 flush 也必须被算作 in-flight，否则 close() 的静止检查会看到「空队列」而提前返回:162-166。
  2. 同一 key 串行，同会话新任务顶掉旧任务
    队列 key 是 memory-flush:<scope>:<id>；合并 key 是 ConversationKey(agent, userId, sessionId)。运行中若有新任务进来，就 put 到 pending 覆盖旧任务，并立刻释放被顶掉那次的配额:167-201。注释给出的正确性理由是：队列任务执行时才读 state，所以最新任务天然包含被顶掉任务会读到的一切:256-262。
  3. 三种 trigger 的判定在「任务执行时」

// ① 只关 per-call flush：压缩前与兜底仍然会 flush
.memory(MemoryConfig.builder().flushTrigger(MemoryConfig.FlushTrigger.never()).build())

陷阱与窍门

1. 以为「没配 = 没开」
你会看到
线上长会话突然出现一条 __compaction_summary__ 消息，工作区里冒出 MEMORY.md 与 memory/。
因为
三份配置在 Builder 字段上就有非空默认值，两个 disable 都是 falseHarnessAgent.java:1227-1231。
改成
要「什么都不发生」，必须显式 .compaction(null)、.toolResultEviction(null)、.disableMemoryHooks()、.disableTranscript()；只写一个不够。
2. 关掉压缩后，长会话直接抛异常
你会看到
Context overflow: no compaction configured, unable to recover，或者原始模型报错原样冒泡。
因为
onErrorResume 只在 compactionHook != null 时挂载；compaction(null) 之后 hook 为 null，兜底路径根本不存在:958-968。
改成
想「平时不压缩、溢出时救一次」，把 triggerMessages 调得极大（例如 10 000）而不是置 null——这样兜底仍然在。
3. 改了 flushPrompt，压缩前那次没变
你会看到
per-call flush 的日账段落风格变了，压缩前 flush 的段落还是老风格；同一份文件里两种口径。

自检三问

默认配置下，一个 32K 窗口的模型什么时候触发压缩、保留多少？如果窗口只有 16K 呢？

32K：trigger = 32 000 - 20 000 = 12 000，keep = min(8 000, max(2 000, 12 000 × 0.25 = 3 000)) = 3 000。16K：trigger 算出 -4 000，被 clamp 成 max(1, 8 000) = 8 000 并打 warn；keep 算出 -1 000，夹到下限 2 000CompactionMiddleware.java:167-215。注意触发条件是「条数 ≥ 50 或 token ≥ trigger」，所以短消息多的时候往往是条数先到。

压缩管线的顺序为什么是「prune → shouldCompact」，而不是反过来？

因为 prune 不花钱。compactIfNeeded 先做 truncateArgs 与 pruneToolResults，再重新估算 token、再判断ConversationCompactor.java:103-113。一次纯本地剪枝可能就把总量压到阈值以下，于是这一轮不需要调用摘要 LLM。反过来先判断，就会多付一次摘要费用。

为什么说「同一轮的 consolidation 看不到本轮 flush」？这是 bug 吗？

不是 bug，是洋葱顺序的推论。注册顺序里 MemoryFlushMiddleware（#6）在 MemoryMaintenanceMiddleware（#7）之外，流完成时内层先回，所以 maintenance 的 doOnComplete 先派发MiddlewareChain.java:55-61。两者都异步，实际完成顺序不确定；再叠加 consolidation 只读「水位线之后」的日账，就更容易漏掉刚写入的段落。要立即生效就用 memory_save。
