26 · 生产部署与运维：K8s、备份、升级、排障

第 19 章用 Docker Compose 在本机起过完整栈，那里最重要的是「能看到五个组件跑起来」。生产环境换了判据： 能不能在维护窗口内装好、能不能在数据库或卷损坏后恢复、能不能在升级失败时退回，以及出问题时能不能在十分钟内 判断该看哪个组件。这一章只讲生产差异，不重复 Compose 的首次登录流程。

读完你能做到

  • 说清生产拓扑里四个应用组件、PostgreSQL 和两个 PVC 各自负责什么，以及为什么只暴露 Gateway
  • 用 Helm 装出一套可验证的 Service，并解释 existingSecret、publicURL 与存储 values 的作用
  • 做出一份真正可恢复的备份：数据库、Workspace、Artifact 与 Vault 密钥属于同一批次
  • 在独立空库上完成恢复演练，并按验收清单确认历史、文件、凭据和新任务都正常
  • 解释升级时 Go 的启动迁移与 Java 的 Hibernate update 各自改了什么，以及为什么回退镜像不等于回退 schema
  • 用探针、日志和症状表把故障定位到具体组件，而不是盲目重启

分水岭：从「能启动」到「能恢复」

Compose 安装适合本机体验与联调；生产安装则要自己管理 PostgreSQL、持久存储、入口域名和 TLS kubernetes.md:10。 这条边界带来三个硬约束，后面所有章节都围绕它们展开。

生产拓扑：四个组件、一个数据库、两个卷

端口与暴露方式沿用 Compose 版本：Gateway 对外 8080，Control、Dataplane、Scheduler 分别监听 8081、8082、8083， PostgreSQL 在内部网络 5432 quickstart.md:54-60。 Helm Chart 用同一组端口创建四个 Deployment 和四个 Service，只有 Gateway 的 Service 类型跟随 values，其余固定为 ClusterIP planes.yaml:18 planes.yaml:151-155。

组件端口对外排障时先看什么
Gateway8080是（可经 Ingress / 反向代理）只证明入口可达，不代表模型或工具执行正常
Control8081否产品 Automation、资源、账号与编排派发
Dataplane8082否Managed 会话、模型调用与工具执行
Scheduler8083否渠道消息与 Worker 调度
PostgreSQL5432否连接、schema、备份与恢复目标

组件分工来自官方排障指南：Gateway 正常不代表模型或工具执行正常；Managed 会话看 Dataplane，渠道与 Worker 调度看 Scheduler， 产品 Automation、资源、账号和编排派发看 Control troubleshooting.md:34。

启动顺序也有依赖：Dataplane 的 initContainer 先等 Control 的 /healthz，Scheduler 再等 Dataplane 的 /actuator/health planes.yaml:61-75。 所以 Control 起不来时，看到 Dataplane 和 Scheduler 也卡在 Init 是预期现象，不要逐个 Pod 重启。

安装前置：存储、数据库与版本三件事

官方前置清单很短，但任何一项缺失都会让安装停在 Pending 或直接启动失败：Kubernetes、Helm、可达的 PostgreSQL，以及 Workspace 所需的 RWX StorageClass 或已有共享 PVC；Artifact 默认只用 RWO kubernetes.md:14。 发布包还要先用 SHA256SUMS 校验，再用应用数据库所有者在目标库执行 postgres-init.sql， 创建 cp、rt、dp 三个 schema kubernetes.md:16。

Chart 与组件镜像版本必须配套：可以用发布包里的 OCI Chart 地址加 --version 安装，也可以改用下载的 .tgz；私有仓库要先完成 Helm registry 登录 kubernetes.md:68。 发布物本身包含四个镜像：control、gateway、dataplane、scheduler，控制台随 control 镜像交付 releasing.md:14。

别把两个 Chart 叠起来

这套 Chart 运行的是 standalone HTTP 模式，不带 Kubernetes-native 控制器，也不暴露 ASDP gRPC values.yaml:23-24。 需要 CRD 或 SDK 的 ASDP 派发时，应按另一套部署模式规划，不要把两个 Chart 直接装成同一个服务 kubernetes.md:83。

Secret：密钥只进集群，不进 values

官方流程是把 kubernetes.env.example 复制到私有文件，替换全部占位值，再用 --from-env-file 创建 Secret；URI 里的密码要 URL 编码，JDBC 密码单独提供原值 kubernetes.md:20。 Secret 是运行配置，不能把明文文件或渲染结果提交到仓库 kubernetes.md:27。 

kubectl create namespace agentscope
kubectl -n agentscope create secret generic agentscope-service \
  --from-env-file=/private/path/service.env
变量约束为什么容易错
BUILDER_JWT_SECRET至少 32 字符服务启动时会直接校验，短于 32 字符拒绝启动server.go:147-150
AISTIO_BOOTSTRAP_PASSWORD12–72 字节bcrypt 上限 72 字节；配置 bootstrap 管理员时必须关闭 AISTIO_SEED_USERSbootstrap.go:30-36
BUILDER_VAULT_MASTER_KEY各组件一致，随数据备份只恢复数据库但换掉密钥，已有凭据无法解密configuration.md:23
数据库 DSN 中的密码URL 编码URI 与 JDBC 是两种解析方式，JDBC 密码要单独给原值kubernetes.md:20

Secret 只注入 Control、Dataplane 和 Scheduler；Gateway 不挂 envFrom planes.yaml:89-92。 需要排障时先确认变量落在哪个 Pod，而不是在 Gateway 上找一个根本不存在的环境变量。

values：存储、入口与资源预算

官方给了一份可直接改的起点：existingSecret 指向刚建的 Secret，allowLocalEnvironment 保持 false，publicURL 填真实外部地址，Workspace 用共享 RWX StorageClass，Artifact 用普通 RWO kubernetes.md:34-50。 

existingSecret: agentscope-service
allowLocalEnvironment: false
publicURL: https://agentscope.example.com
persistence:
  workspaces:
    storageClass: shared-rwx
    size: 20Gi
  artifacts:
    storageClass: standard
    size: 20Gi
ingress:
  enabled: true
  className: nginx
  host: agentscope.example.com
  tls:
    - hosts: [agentscope.example.com]
      secretName: agentscope-service-tls

Chart 自己的默认值更保守：Workspace 与 Artifact 都只要 10Gi，Workspace 访问模式是 ReadWriteMany，Artifact 是 ReadWriteOnce，Ingress 默认关闭，Service 默认 ClusterIP values.yaml:26-40 values.yaml:57-62。 已有 PVC 时设置 existingClaim，Chart 就不会再创建同名 PVC。

资源默认值是 requests 与 limits 的组合：Control 100m / 256Mi 起、内存上限 1Gi；Dataplane 250m / 512Mi 起、 内存上限 2Gi；Scheduler 100m / 512Mi 起、上限 1Gi；Gateway 100m / 256Mi 起、上限 1Gi values.yaml:41-56。 这些只是起点，官方要求按实际任务负载压测定容 kubernetes.md:53。

安装：一条 Helm 命令与一次用户路径验证

安装命令把 Chart 版本、镜像仓库和 values 固定在一起，--wait --timeout 10m 让 Helm 等到资源就绪或超时失败 kubernetes.md:59-66。 镜像 tag 默认取 Chart 的 appVersion，除非显式设置 imageTag values.yaml:17-18。 

helm upgrade --install service oci://REGISTRY/NAMESPACE/charts/agentscope-service \
  --version VERSION \
  --namespace agentscope \
  --set imageRepository=REGISTRY/NAMESPACE \
  -f production-values.yaml \
  --wait --timeout 10m

装完不要只看 Helm 的退出码，按下面的顺序验证：

kubectl -n agentscope get pods,pvc,svc,ingress
kubectl -n agentscope port-forward service/service-agentscope-gateway 18080:8080

确认 PVC 已 Bound、Pod Ready，再用初始管理员登录公开域名并修改密码；随后验证模型连接、执行 Environment、第一次 Chat、 Issue 交付和长连接。port-forward 只用于排障，不能替代公开回调地址的验证 kubernetes.md:72-77。

入口：只暴露 Gateway，并为 SSE 留出超时

Compose 默认把 Gateway 绑在 127.0.0.1:18080，只向用户暴露 Gateway，内部组件和数据库留在私网 quickstart.md:54-60 quickstart.md:62。 Kubernetes 下同样只有 Gateway 的 Service 类型可配置，其余固定 ClusterIP planes.yaml:151-155。

需要远程访问时，把 HTTPS 反向代理指向 Gateway，并把 BUILDER_OAUTH_PUBLIC_URL 设成真实公开 origin； OAuth 回调和渠道回调都依赖它 configuration.md:28 quickstart.md:66。 代理必须及时转发 SSE 事件、不缓存事件流，并设置足够长的读取超时；验证时要覆盖登录、长回复、刷新重连和回调， 不能只验证首页能打开 quickstart.md:68。

Ingress 的 TLS Secret 必须预先存在，或由证书控制器创建；SSE 相关的超时与缓冲行为要按实际 Ingress controller 调整 annotations kubernetes.md:31 kubernetes.md:53。 一个「能打开首页但长回复总断」的故障，通常就出在这层。

数据面：三个 schema、两个卷与一份密钥

PostgreSQL 被拆成三个 schema：cp 给控制面产品库，rt 给运行状态库，dp 给 Java 的 JDBC 连接 configuration.md:18-20。 postgres-init.sql 只做三件事：CREATE SCHEMA IF NOT EXISTS，从不删除已有数据 postgres-init.sql:1-4。

数据落在哪备份方式
产品、运行状态、Java 表PostgreSQL 的 cp / rt / dppg_dump -Fc 或数据库快照
Workspace 文件/data/workspaces，RWX PVC存储快照或卷级备份
Artifact/data/artifacts，RWO PVC与 Workspace 同批快照
Vault 凭据密文数据库内，依赖 BUILDER_VAULT_MASTER_KEY 解密备份密钥本身

Compose 版本把 PostgreSQL、共享 Workspace 和 Artifact 分别放在三个命名卷里 quickstart.md:72。 Chart 会给 Workspace 和 Artifact 各建一个 PVC，并打上 helm.sh/resource-policy: keep， 所以卸载 Chart 不会删除数据卷；重新安装时要显式指定保留的 existingClaim persistence.yaml:20-25 kubernetes.md:81。

内存存储不是生产选项

Control 的 --storage-driver 默认是 memory，只适合开发与测试，重启后会话、事件和 Team 数据都会丢； 生产必须显式使用 postgres main.go:420-423。 源码在内存模式下还会打印明确警告 main.go:520。

Java 侧默认使用 Hibernate update 自动改表，但源码注释明确写着：生产环境应使用 Flyway / Liquibase 固定 schema， 再把 BUILDER_JPA_DDL_AUTO 切到 validate application.yml:20-24。 validate 只校验已有表，不会初始化新库；只有在你自行管理 schema 时才使用 configuration.md:40。

备份：数据库、文件、密钥必须同批

一份可恢复的备份包括数据库、Workspace、Artifact，以及解密这些数据所需的密钥 operations.md:10。 Compose 的官方步骤是：安排维护窗口，先停四个应用组件、保留数据库运行，再做数据库导出和卷快照。 

docker compose stop gateway scheduler data control
mkdir -p backup && chmod 700 backup
docker compose exec -T db pg_dump -U agentscope -d agentscope -Fc > backup/database.dump

然后用卷备份工具为 workspaces、artifacts 命名卷做快照，保存 .env， 记录 SERVICE_VERSION、镜像 digest 和快照时间；备份目录要放在安装目录之外的受保护持久存储中。 确认数据库备份与文件快照属于同一维护窗口后，再启动应用 operations.md:23 operations.md:25-27。

Kubernetes 同理：数据库备份加 PVC 快照，按存储提供程序选择快照方式，并保存配置 Secret 的受保护副本 operations.md:29。 不要只备份数据库，也不要只备份卷：Vault 密文在数据库里，没有原密钥就解不开；文件路径在数据库里， 只恢复文件也无法还原归属handlers_vault.go:288-290。

恢复：先造空库，再按同一批次还原

需要回退数据时，先停止应用写入；在独立空数据库中恢复备份，恢复同一批 Workspace / Artifact 快照与原 Vault 密钥， 再用备份对应的组件版本启动。pg_restore --clean 绝不能指向仍在使用的业务数据库 operations.md:39。 

pg_restore --no-owner --no-acl --dbname="$RESTORE_DATABASE_URL" backup/database.dump

恢复到同一 PostgreSQL 实例中的新数据库后，在 Compose 的 .env 里把 POSTGRES_DB 指向恢复库，并使用原密钥和同批文件快照启动。数据库容器只在数据目录为空时初始化数据库，已有实例里的恢复库需要预先创建 operations.md:47。

恢复验收至少覆盖：管理员登录、已有 Agent 与 Session 历史、Workspace 文件、Vault 凭据解密、运行时连接， 以及一项新的小任务；Task 与 Issue 的验收状态应与备份时刻相符 operations.md:51。 只有数据库、文件和密钥都能共同恢复，备份才算通过验证 operations.md:53。

升级：先备份，再接受一次维护窗口

升级前先读新版本的迁移与兼容性说明，在测试数据库副本上演练，然后完成备份。Docker 修改 .env 里的 SERVICE_VERSION，拉取镜像并重建容器；Helm 用指定版本的 Chart 执行 upgrade operations.md:33。 由于 Chart 是单副本加 Recreate，升级期间该组件会先停后起，不能当作滚动更新 planes.yaml:28-31。

组件迁移方式升级时要看什么
Go 控制面启动时执行产品库与运行状态库迁移迁移失败会直接阻止启动server.go:162-165 factory.go:33-49
Java Dataplane / SchedulerHibernate update，默认 dp schema表结构变更不保证可逆application.yml:20-24
Chart 与镜像Chart appVersion 决定默认镜像 tag版本必须配套，不能只升一半values.yaml:17-18

Go 迁移会在 PostgreSQL advisory lock 下串行执行，已应用版本记录在 schema_migrations， 普通迁移包在事务里提交，失败会回滚 migrate.go:30-53 migrate.go:97-112。 这保证多个组件同时启动时不会重复改表，但不保证新 schema 能被旧版本读取。

回退镜像 ≠ 回退 schema

组件镜像回退不保证旧版本可以读取新 schema operations.md:35。 所以升级前的数据库备份不是「以防万一」，而是唯一的回退路径；演练时要连恢复步骤一起计时。

验收：升级与恢复都要跑同一套事实检查

官方建议用固定案例做升级回归：升级前保存样例知识与验收结果，在隔离的恢复环境里执行同一组问题。模型措辞可以不同， 但事实和持久化结果必须可核对 operations.md:59-61。

检查验收依据
知识恢复文档正文与备份一致，Agent 实际读取成功operations.md:65
文件恢复原 Artifact 可下载，内容与备份记录一致operations.md:66
新任务新 Invocation / Run 完成，引用正确来源，没有把未确认能力写成承诺operations.md:67
历史升级前的 Issue、事件与验收状态仍能查看operations.md:68
Host 与自动化在测试目标上分别运行研发与订单履约案例，检查关联记录operations.md:69

记录升级前后版本、备份批次、用例输入、执行 ID 和差异；只在需要对应集成时验证其凭据可用性 operations.md:71。 知识读取案例本身不碰外部凭据，不能证明 Vault 解密路径也已经验证 operations.md:71。

重新开放：先受控，再逐级放量

恢复或升级完成后，先保持定时规则和外部入口受控，在测试工作上验证登录、历史、文件和凭据；确认 Runtime Host 重新上线，再逐个恢复计划触发与业务流量 operations.md:57。 这一步的顺序不能反：入口先全开，故障会直接落到真实用户。

数据库快照恢复不会撤销备份之后已经发出的消息或外部写入；要对照业务系统核对幂等记录和未完成工作，再决定是否重跑 operations.md:57。 尤其注意 Workflow 的 Rerun 和 Webhook 的 Replay：它们都会产生新的执行机会，可能重复业务副作用 workflows.md:53 automation.md:73。

可观测性：探针、启动顺序与日志归属

Helm 为四个组件都配置了 startup、readiness 和 liveness 探针：Control 用 /healthz，其余用 /actuator/health；startup 每 5 秒一次、失败阈值 120，相当于最多给 600 秒启动时间 planes.yaml:113-122。 Compose 的健康检查则是 10 秒间隔、5 秒超时、30 次重试、60 秒启动宽限 compose.yaml:34-39。

Control 的健康检查是本地 HTTP 探测：/aistiod --healthcheck 请求本地 /healthz， 非 200 就退出 1 main.go:391-392 main.go:462-468。 但要看清它探测的是什么：源码里 /healthz 只返回 status: ok，真正会 Ping 存储的是 /readyz server.go:1143-1155。 而 Chart 对 Control 的 readiness 仍使用 /healthz planes.yaml:113-119。 所以数据库掉线时 Pod 可能依旧 Ready，这时要看 Control 日志和 /readyz，不能只看 Pod 状态。 

docker compose logs --tail=200 control data scheduler gateway
kubectl -n agentscope logs deployment/service-agentscope-control --tail=200
kubectl -n agentscope describe pod POD_NAME

日志默认是 JSON，本地开发可以用 --log-format=console 或 AGENTSCOPE_DEV_LOG=true 切到人类可读格式； 控制面还支持 --otel-endpoint 和 0–1 的采样率 main.go:384-386。 共享日志前先移除令牌、密码和业务敏感内容 troubleshooting.md:10。

七个坑：先分清层，再动生产

坑一：只备数据库。Workspace、Artifact 与 Vault 密钥缺任何一项，备份都不算通过 operations.md:10 operations.md:53。

坑二：用 RWO 卷当 Workspace。多个组件要跨节点挂载同一份工作目录，只有单节点可用的卷不能替代共享存储 kubernetes.md:14。

坑三：升级后只回退镜像。旧镜像不保证能读新 schema；回退前先恢复同批次的数据库备份 operations.md:35。

坑四：用 docker compose restart 应用新环境变量。restart 不会把新的环境变量注入已有容器， 要重新创建容器 configuration.md:48。

坑五：把 Gateway 健康当成执行健康。Gateway 正常只证明入口可达；模型与工具执行要看 Dataplane， 调度看 Scheduler，编排与资源看 Control troubleshooting.md:34。

坑六：把密钥写进 values。Secret 要用 existingSecret 单独创建；values 只放非敏感配置 values.yaml:21-22。

坑七：把单副本 Chart 当高可用。每个组件默认 1 副本 + Recreate，升级必然中断； 需要 HA 要先改架构并单独验证 planes.yaml:28-31 kubernetes.md:83。

自测：三个判断题

只做 pg_dump，能把一套 Service 恢复到昨天吗？

不能。可恢复备份必须同时包含数据库、Workspace、Artifact，以及解密这些数据所需的密钥； 只有三者都能共同恢复，备份才算通过验证 operations.md:10 operations.md:53。

Helm 显示安装成功、Pod 都 Ready，是否说明升级验收完成？

不是。还要验证 PVC Bound、公开域名登录、模型连接、执行 Environment、第一次 Chat、Issue 交付和长连接； port-forward 只能排障，不能替代公开回调地址验证 kubernetes.md:72-77。

把 Chart 副本数改成 2，是否就获得零停机升级？

不能这样推断。当前 Chart 使用 Recreate，注释明确说 DDL 与共享文件系统 HA 需要单独验证； 官方也不提供多副本 HA 或无停机迁移保证 planes.yaml:28-31 kubernetes.md:83。

练习：做一次可回退的生产演练

目标不是把服务跑起来，而是证明「装得上、备得全、恢复得了、退得回」。建议 60 分钟：

  1. 准备存储与 schema
    确认一个支持 RWX 的 StorageClass，并在独立 PostgreSQL 上以应用数据库所有者执行 postgres-init.sql，核对三个 schema 都存在。
  2. 创建 Secret 与 values
    复制 kubernetes.env.example，替换全部占位值并 URL 编码数据库密码；写一份 production-values，把 Workspace 指到 RWX 存储。
  3. 安装并验证用户路径
    用指定 Chart 版本安装，检查 Pod、PVC、Service、Ingress；登录后修改密码，跑一次模型请求、一次 Issue 和一次长回复。
  4. 做一次一致性备份
    停四个应用组件，导出数据库，快照两个卷，保存 Secret 受保护副本和版本 / digest / 时间；记录这批备份的批次号。
  5. 在空库上恢复
    新建空数据库，用 pg_restore --no-owner --no-acl 恢复，接入同批卷快照和原 Vault 密钥，再以备份对应版本启动。
  6. 跑恢复验收
    逐项检查管理员登录、Agent 与 Session 历史、Workspace 文件、Vault 解密、Runtime 连接和一项新任务；确认 Issue 状态与备份时刻相符。
  7. 演练一次升级
    记录当前 Chart 与镜像版本，备份后在测试环境 upgrade 到下一版本；观察 Control 启动迁移、Java 表结构变化和探针状态。
  8. 故意制造一次失败
    把镜像 tag 改成一个不存在的值，确认 Pod 停在 ImagePullBackOff 且 Gateway 不可用；改回后记录恢复时间，并写进维护手册。
  9. 最后写三行结论
    分别写「备份批次覆盖什么」「恢复验收哪几项通过」「升级回退的触发条件」，确保每一行都能独立核对，而不是用 Pod Ready 代替。
