29 · 记忆接入：Mem0 / 百炼 / ReMe

第 28 章解决「模型从哪来」，这一章解决「跨会话记住什么」。先分清三件事：会话上下文、持久化状态、语义长期记忆。 官方文档把长期记忆收在 LongTermMemory 下，给出 Mem0、百炼、ReMe 三种实现； 但 2.0.4 源码已经把这条接口标成 legacy。本章既拆它现在怎么跑，也拆它为什么不该成为新项目的长期依赖。

读完你能做到

  • 分清 AgentState 的会话上下文、AgentStateStore 的持久化状态与 LongTermMemory 的语义记忆
  • 说清 record / retrieve 的调用时机，以及 AGENT_CONTROL、STATIC_CONTROL、BOTH 各装了什么
  • 按默认值配置 Mem0、百炼、ReMe，并解释三者的隔离键、过滤规则与检索上限差异
  • 识别「接口相同但写入内容不同」：工具结果、SYSTEM 消息、压缩历史在三个后端里命运不同
  • 解释异步记录的 1 worker / 3 队列与丢任务边界，以及为什么记忆失败通常不会报错
  • 给出从 legacy 记忆迁移到应用层或 AgentStateStore 的可执行方案

先分清三种「记忆」

同一个词在 AgentScope 里至少指三样东西。混在一起，就会出现「重启后历史没了」「换了会话还记得用户偏好」「记忆库越来越大」 这类看似矛盾的需求。

层负责什么生命周期本章位置
会话上下文当前对话的消息、滚动摘要、工具与权限子上下文一次会话，可被压缩AgentState.contextAgentState.java:29-42
持久化状态把 AgentState 按 (userId, sessionId) 存取，支持重启恢复跨进程，跟会话绑定第 31 章 AgentStateStore
语义长期记忆跨会话保存用户偏好、事实、决策，并按 query 检索跨会话，跟用户 / Agent 绑定本章 LongTermMemory

三者不能互相替代：把会话历史塞进长期记忆，会得到重复、昂贵且难删除的向量库；把用户偏好只放在 AgentState 里， 换一个 sessionId 就丢了。先决定「这条信息属于哪一层」，再选后端。

文档与源码的分叉：接口还在，方向已变

官方记忆概览仍把 LongTermMemory 描述成跨会话持久化用户偏好与事实的接口，并列出 Mem0、百炼、ReMe 三种实现 overview.md:6-14。 三种实现都实现同一个接口，Agent 侧代码看起来可以完全不变 overview.md:14。

2.0.4 源码把这条路径标成 legacy

LongTermMemory 带 @Deprecated(forRemoval = true, since = "2.0.0")， 注释写明长期记忆已移除，会话上下文改由 AgentState.getContext() 承载，跨会话持久化应在应用层集成 LongTermMemory.java:66-71。 LongTermMemoryMode 也一起被弃用 LongTermMemoryMode.java:51-54， ReActAgent 的相关 setter 被归入 1.x legacy 兼容层，并注明会在下一个小版本移除 ReActAgent.java:5255-5265。

「弃用」不等于「立刻不能用」。三个模块仍然实现该接口，ReActAgent 也仍会在 longTermMemory != null 时装配工具或 Hook ReActAgent.java:5600-5602。 但新项目要把它当迁移对象，而不是新能力的地基。

接口只有两个动作：record 与 retrieve

LongTermMemory 的契约非常小：record(List<Msg>) 把消息写入记忆， retrieve(Msg) 用一条消息作为 query 检索相关记忆并返回文本 LongTermMemory.java:73-110。 它没有 delete、list、update，也没有分页；删除与合规清理必须回到后端自己的控制台或 API。

框架在两种时机调用它：Agent 推理前用最后一条用户消息检索，把结果注入上下文；Agent 回复后用当前记忆里的全部消息记录。 具体装哪一套，由 LongTermMemoryMode 决定。

这是本章最容易被忽略的差异。三个后端都叫 LongTermMemory，但 record 的过滤逻辑不同， 「切换后端」可能直接改变记忆内容。

切后端前先对齐「记什么」

从 Mem0 切到百炼，工具结果会突然不再进入记忆；从百炼切到 Mem0，SYSTEM 指令可能被当成用户事实写进去。 先定义一份消息白名单，再比较检索质量，否则你会把「内容差异」误判成「模型变笨」。

异步记录：1 个 worker，3 个排队位

默认是同步记录：Hook 在返回前调用 record，成功与否不影响主流程，但会增加这一轮延迟。 打开 longTermMemoryAsyncRecord(true) 后，记录被丢到一个专用调度器：最多 1 个并发 worker、最多 3 个排队任务， 队列满时新任务会被拒绝并记录日志 StaticLongTermMemoryHook.java:81-86 StaticLongTermMemoryHook.java:208-215。

所以「开了异步」不等于「一定记上」。高频对话、后端变慢或网络抖动时，队列会饱和，新的记录任务被丢弃； 而 Agent 的回复仍然正常返回。要判断是否丢，只能看日志或后端写入量，不能看 Agent 是否回复成功。

失败通常不报错：记忆是「静默降级」

三个后端在检索失败时都倾向返回空字符串，而不是把异常抛给 Agent：Mem0 用 onErrorReturn("") Mem0LongTermMemory.java:288-291， 百炼记录失败用 onErrorComplete、检索失败返回空 BailianLongTermMemory.java:211-214 BailianLongTermMemory.java:271-272， ReMe 检索失败也返回空 ReMeLongTermMemory.java:243。 Hook 自己也会 catch 后只打日志 StaticLongTermMemoryHook.java:191-198。

弃用之后：哪些还能用，哪些该搬走

先把边界说清楚：LongTermMemory 与 LongTermMemoryMode 从 2.0.0 起弃用， ReActAgent 的 legacy setter 会在下一个小版本移除 ReActAgent.java:5255-5265。 但三个后端模块还在，接口也还在，所以「今天能跑」与「明年还能升级」是两个问题。

资产现在建议
Mem0 / 百炼 / ReMe 后端仍实现 LongTermMemory可继续作为外部服务使用，不要绑死在 Agent 内部
ReActAgent.longTermMemory仍可装配，已标 legacy隔离到适配层，准备移除
AgentState.context当前会话主线继续用于对话上下文与压缩摘要
跨会话语义记忆无新的内置接口在应用层实现，通过工具或提示注入接入

换句话说，弃用的是「Agent 内置长期记忆」这条管线，不是「不要做记忆」。用户偏好、历史决策仍然值得存， 只是应该由应用决定存哪、怎么查、怎么删，再把结果作为工具或上下文交给 Agent。

迁移路径：三种落地方式

迁移不是把类名换掉，而是把「谁拥有记忆」重新分配。下面三条路径可以单独用，也可以组合。

路径怎么做适合代价
冻结 legacy保留现有后端，外面包一层自己的 MemoryPort 接口，Agent 只依赖这层已有生产流量，暂时不能改仍受弃用 API 约束，升级前必须再迁移
应用层记忆服务自建数据库 / 向量库，把检索暴露成 @Tool，或每轮注入一段摘要要控制删除、租户、成本与检索策略需要自己实现写入、去重、权限与评测
状态存储用 AgentStateStore 保存会话上下文，跨会话事实另存只需要重启恢复与多副本共享不提供语义检索，不能替代长期记忆

最稳的组合是「状态归状态、语义归语义」：AgentStateStore 负责会话恢复，应用层记忆服务负责用户偏好； Agent 通过工具调用后者。这样既不用依赖 legacy Hook，也不会把两套数据混在一个存储里。

运维边界：删除、重复与成本

删除不在接口里。LongTermMemory 只有 record / retrieve，没有 delete； 用户要求「忘掉我」时，必须去 Mem0 / 百炼 / ReMe 的控制台或 API 删除，再确认检索不再命中 LongTermMemory.java:91-110。

重复写入是默认风险。Hook 每轮把全量上下文交给 record；Mem0 用 infer(true) 抽取， 百炼可用 enableRewrite 合并，ReMe 按轨迹抽取，但都不是「保证去重」。上线前要用多轮对话检查后端条目数， 而不是只看回复。

token 与延迟要算在检索上。检索结果会作为一条用户消息追加到输入末尾； 百炼的 rerank / judge / rewrite 都会增加调用延迟和费用，默认关闭是有原因的。先测命中率，再开增强。

六个坑：把「接口相同」当成「行为相同」

坑一：把长期记忆当状态存储。AgentState 保存的是会话上下文，LongTermMemory 保存的是跨会话语义；重启恢复找前者，用户偏好找后者 AgentState.java:29-42。

坑二：以为三个后端写入同样内容。Mem0 会把 SYSTEM / TOOL 转成 user / assistant 文本写入， 百炼与 ReMe 直接跳过；切换后端会改变记忆内容 Mem0LongTermMemory.java:206-225 BailianLongTermMemory.java:153-186。

坑三：开了异步就以为不会丢。队列只有 3 个位置，饱和时新任务被拒绝；Agent 仍正常回复 StaticLongTermMemoryHook.java:81-86。

坑四：每轮全量记录导致重复。Hook 把 memory.getMessages() 全部交给后端， 去重是后端的责任；多轮对话后要检查条目数 StaticLongTermMemoryHook.java:221-251。

坑五：检索失败以为 Agent 会报错。三个后端大多返回空字符串，Hook 也只打日志；表现是「失忆」而不是异常 StaticLongTermMemoryHook.java:191-198。

坑六：等接口提供删除。LongTermMemory 没有 delete / list，合规删除必须去后端做 LongTermMemory.java:91-110。

自测：三个判断题

LongTermMemory 是 2.0.4 推荐的新接口吗？

不是。它从 2.0.0 起就标了 @Deprecated(forRemoval = true)，注释明确说长期记忆已移除， 会话上下文改由 AgentState.getContext() 承载；三个后端仍可用，但属于 legacy 路径 LongTermMemory.java:66-71。

BOTH 模式到底装了什么？

既注册 LongTermMemoryTools（让 Agent 主动 record / retrieve），又注册 StaticLongTermMemoryHook（每轮自动检索与记录）；它是 builder 的默认模式 ReActAgent.java:5460-5489。

Mem0 与百炼会写入同样的消息吗？

不会。Mem0 把 SYSTEM 映射成 user、TOOL 映射成 assistant；百炼只收 USER 与纯 ASSISTANT， 工具调用请求与工具结果都会被跳过。接口相同，不代表记忆内容相同 Mem0LongTermMemory.java:206-225 BailianLongTermMemory.java:153-186。

练习：给「跨会话偏好」选一条记忆路径

目标不是把 Mem0 跑通，而是能解释每条信息为什么放在这一层。建议 45 分钟：

  1. 先分三层
    列三条信息：当前对话的一句追问、用户的时区偏好、上一次任务的结论。分别归到上下文、长期记忆、状态 / 应用存储。
  2. 选一个后端
    在 Mem0 / 百炼 / ReMe 中选一个，写下隔离键、必填参数、默认 topK 与超时。
  3. 跑一轮自动记忆
    用 STATIC_CONTROL 发一条包含偏好的消息，确认后端出现记录，并在下一轮检索到。
  4. 切到工具模式
    改成 AGENT_CONTROL，观察模型是否主动调用 recordToMemory / retrieveFromMemory；记录差异。
  5. 检查注入位置
    打印发给模型的消息列表，确认记忆是 role=USER、name=long_term_memory，并追加在末尾。
  6. 制造一次失败
    把 apiKey 改错，确认 Agent 仍能回复、检索变空；记录日志里实际报了什么。
  7. 检查重复与删除
    连续三轮相近对话，观察后端条目数；再尝试从后端删除一条，确认检索不再命中。
  8. 写迁移结论
    写三行：哪些信息继续用 legacy、哪些搬到应用层、哪些交给 AgentStateStore。
