14 · 子 Agent 与团队：把「谁去做」拆成两层

第 13 章把执行关进容器，这一章回答「谁去做」。框架里其实是两件不同的事：委派——主 agent 把一个任务交给临时子 agent，拿回一段文本；协作——多个成员共享一块任务板和一个邮箱，按角色互相推进。前者靠 agent_spawn 一族工具，后者靠 team 工具；两套都接在 HarnessAgent.build() 里，但装配条件、默认值、失败方式完全不同。这一章按「来源 → 声明 → 工作区 → 运行 → 结果 → 装配 → 团队」拆开，每个结论都对到 2.0.4 的行号。

读完你能做到

  • 说出子 agent 的四个来源（内置 general-purpose、subagents/*.md、编程式声明、自定义工厂），以及各自什么时候被加载
  • 背下 SubagentDeclaration 的关键默认值，并在 build() 之前就知道哪三种组合会抛异常
  • 给定 workspaceMode 与 workspace.path，推出子 agent 的工作区落在哪、会话槽位叫什么、system prompt 从哪来
  • 解释 timeout_seconds 的三种结局：正常返回、提升为后台任务（timeout_promoted）、强制同步下硬超时（timeout）
  • 从 build() 判断实际安装的是 DynamicSubagentsMiddleware 还是静态 SubagentsMiddleware，以及这决定了哪套结果回推路径
  • 画出团队的四个零件：TeamClient、TeamContext、TeamTool、TeamsMiddleware，并说出角色是怎么裁剪工具面的

先说为什么：委派和协作是两件事

官方文档把两者放在同一篇「子 Agent」里讲，容易让人以为团队只是子 agent 的批量版。源码里它们的依赖是分开的：子 agent 依赖 AgentSpawnTool + TaskRepository；团队依赖 TeamClient + TeamContext，并且要显式打开。先建立这张三层图，后面就不会混：

调用层：让谁开始干活
agent_spawn 创建（或复用）一个子 agent 实例并可选地执行任务；agent_send 往实例追加消息；agent_list 列出当前活跃实例AgentSpawnTool.java:287-335。三者都在 AgentSpawnTool 一个类里。
结果层：干完之后结果放哪
同步调用把最终文本塞进工具结果；timeout_seconds=0 则落一条任务记录，返回 task_id，由 task_output / wait_async_results / task_list / task_cancel 管理TaskTool.java:53-63。
协作层：多个成员怎么对齐
一块共享任务板 + 一个邮箱 + 计划审批：team 一个工具 18 个 action，按 TeamContext.availableActions() 裁剪TeamTool.java:34-59。子 agent 之间默认没有这层。
最容易搞混的一对：agent_key 不是 agent_id

提示词模板专门用粗体写了这句：agent_key 是 spawn 输出里的运行时句柄（以 agent: 开头），既不是 agent_id，也不是 session_id，更不是 task_idSubagentsMiddleware.java:110。四个标识各管一段：agent_id 选「哪个 spec」，agent_key 选「哪个实例」， session_id 选「哪段状态」，task_id 选「哪次后台执行」。

最小可跑：写一个 md，主 agent 自己会用

最省事的路径是把 spec 写进 workspace/subagents/：文件名（去掉 .md）就是 agent_id，front matter 里不要再写 nameAgentSpecLoader.java:44-72。主 agent 不需要任何注册代码： 

Path workspace = Files.createTempDirectory("agentscope-subagent-demo");
Files.createDirectories(workspace.resolve("subagents"));
Files.writeString(
        workspace.resolve("subagents/reviewer.md"),

跑起来之后有三件事值得停下来确认：

  1. system prompt 里多了一段，但不是你写的 sysPrompt
    ## Subagents 段是中间件在每次 reasoning 前拼到首条 SYSTEM 消息上的， 不在 builder 的 sysPrompt 里，也不落盘SubagentsMiddleware.java:653-663。里面会列出当前可用的 agent id（每行 - `name`: description），以及 timeout_seconds 的 0/30/600 语义。
  2. 默认是「每轮重扫」，不是「构建时定死」
    Harness 默认装有 filesystem，所以安装的是 DynamicSubagentsMiddlewareHarnessAgent.java:2633-2648。它每次 reasoning 都按「filesystem 的 subagents/*.md（Layer 1）覆盖本地目录（Layer 2）」重新加载并 replaceAgentsDynamicSubagentsMiddleware.java:147-222。于是你中途新增或改写同名 md，下一个 reasoning 就能看到。
  3. agent_spawn 的返回值不只是结果
    它先给三行元信息，再给 status: ok 和 reply:（同步路径）AgentSpawnTool.java:1599-1610：agent_key、agent_id、session_id。如果这次 spawn 被允许暴露给用户，还会多一行 subagent_id 与 status: exposed。
description 才是「路由表」

可用列表只渲染 name + description:653-658，模型据此决定委派给谁。官方文档里那句「『代码评审』远不如『当用户要 review PR…』有效」是对的行为建议，不是修辞。

工作区：四种组合、一个会话槽位、两份 prompt 来源

resolveDeclaredWorkspace 的分支不多，但顺序决定结果，必须按表背：

workspaceModeworkspace.path运行根目录
ISOLATED有用你给的 path（Loader 会按主工作区解析相对路径）
ISOLATED无mainWorkspace/agents/<name>/workspace，并自动 createDirectories
SHARED有忽略 path，直接用 mainWorkspace
SHARED无mainWorkspace

出处：HarnessAgentBuilderSupport.java:709-732；相对路径解析见 AgentSpecLoader.java:360-370

会话槽位是另一条独立的规则：ISOLATED 且父上下文存在时，子 sessionId 形如 {name}[@{parentSessionId}][#{userId}]；SHARED 或父上下文缺失时退回纯 {name}:660-691。空白的 uid/sid 段会被丢掉，斜杠、空格、控制字符统一替换成下划线:698-703。这条规则解释了为什么「同一用户在不同会话里 spawn 同名子 agent 互不污染」，也解释了为什么 SHARED 子 agent 会共用父的整棵状态树。

system prompt 只有两个来源，二选一：

  • workspace.path != null：读 <path>/AGENTS.md；读不到或读失败就是空串，不会回落到正文:735-753。
  • 没有 path：用 inlineAgentsBody（工作区文件里就是 --- 之后的正文）。
  • 两者最终都会追加 SUBAGENT_CONTEXT_SECTION——那段「你是 subagent、完成任务、不要发起用户对话、不要再 spawn」的角色约束:86-129。
写了 path 又写了正文，正文会被丢掉

Loader 发现 workspace.path 与非空 body 同时存在时，会 warn 并把 body 置空，提示你把提示词放进 <path>/AGENTS.mdAgentSpecLoader.java:276-284。这不是「两者拼接」，是「path 赢，正文作废」。

工具面也有一条容易忽略的连锁反应：声明里给了 tools 白名单后，子 agent 的 ToolsConfig 会被改成 strictAllow=true、defaultToolsEnabled=false， 只保留白名单里且父级本来就允许的工具:287-305。所以「白名单」不是加法，是「先继承父级，再按白名单做交集」。

运行：超时、实例与暴露

agent_spawn 的参数只有五个：agent_id（必填）、task、 label、timeout_seconds、expose_to_user:301-335。真正复杂的全是 timeout_seconds 的分支：

  • timeout > 0
    同步等待，默认 30 秒、上限 600 秒；模型传 null 用默认，传负数当 0 处理:1498-1506。
  • timeout = 0
    立即建后台任务并返回 task_id（形如 task_<uuid>），子 agent 在后台跑:1632-1671。
  • 同步超时（默认）
    不取消、不丢结果：把还在跑的执行「提升」为 AdoptedTaskRunSpec 后台任务，返回 status: timeout_promoted + 新 task_id；提示词明确写「不要重试同一个任务」:1001-1051。
  • 同步超时（force-sync）
    硬失败：中断子 agent，返回 status: timeout，不提升为后台任务:1013-1026。

force-sync 是应用侧的旋钮，不是模型参数。当前调用的 RuntimeContext 里放 CTX_FORCE_SYNC=true 即可覆盖 LLM 的异步选择；再放 CTX_FORCE_SYNC_TIMEOUT_SECONDS 则完全覆盖 LLM 传的超时（<=0 回退 30 秒，仍受 600 秒上限约束）:1518-1545。未设置 override 时，force-sync 会把 LLM 的 0 改写成 30 秒，而不是提交后台任务。 

RuntimeContext ctx =
        RuntimeContext.builder()
                .sessionId("s-1")
                .put(AgentSpawnTool.CTX_FORCE_SYNC, true)
                .put(AgentSpawnTool.CTX_FORCE_SYNC_TIMEOUT_SECONDS, 120)
                .build();

实例寻址有两套入口：agent_send 用 agent_key（spawn 输出里的完整句柄）或 label（spawn 时自设的人类可读名），二者必须二选一；agent_spawn 本身没有 agent_key 参数。label 冲突是全局的（共享同一个 AgentSpawnTool 实例），不是按父会话隔离： Error: Label already in use: …:405-407。agent_send 与 agent_spawn 遵守同一套 force-sync 与超时规则:547-609。

expose_to_user 是四层优先级：RuntimeContext 里的 CTX_EXPOSE_TO_USER > 声明里的三态 > LLM 传参 > false:1461-1485。一旦暴露，会生成 subagentId、往父事件流发一条 SubagentExposedEvent:1570-1597，前端可以据此让用户直接和这个子 agent 对话（示例见 SubagentSendDirectlyExample 的 sendToSubagentStream(subagentId, …)）。

结果：任务记录、四个工具与两条回推路径

后台任务不是内存里的一张表。默认实现把状态写成 agents/<parentAgentId>/tasks/<sessionId>.json，是一份 taskId → TaskRecord 的 JSON map；分布式部署时这个路径会被路由到共享存储，沙箱模式下则落在宿主 工作区WorkspaceTaskRepository.java:44-54。三个维护常量值得记住：心跳 30 秒、孤儿判定 10 分钟、清扫 5 分钟:88-102。

「任务完成后会自动回到上下文」这句话在源码里有两条实现，走哪条取决于装的是哪个中间件：

默认路径：inbox + wakeup

  • 默认 messageBus 是 WorkspaceMessageBus(filesystem, ".agentscope/bus"):2504-2511，只要 filesystem 存在（默认总是存在）就会创建。
  • 子 agent 中间件把 TaskCompletionCallback 挂到仓库上：完成时 inboxPush 一条 <system-notification>，再 enqueueWakeup:2320-2354。
  • InboxMiddleware 下一轮开始前 drain，把 hint 注入上下文（以及一条 HintBlockEvent）InboxMiddleware.java:82-180。
  • 这套在 Dynamic 与静态中间件下都生效。

静态中间件额外路径：system-reminder

  • 只在 SubagentsMiddleware.onReasoning 里：findPendingDeliveries → 拼一条 role=USER、name=system、metadata.synthetic=true 的消息SubagentsMiddleware.java:413-449。
  • 最多列 10 条，其余给一句 ... and N more — call task_list():492-549。
  • markDelivered 只在 reasoning 成功完成后执行——先标后崩会永久丢消息，反过来只多推一次:450-479。
  • DynamicSubagentsMiddleware.onReasoning 不调这段，所以默认路径看不到它。

装配：build() 里的顺序与两个「隐式默认」

这一段是本章和官方文档差异最大的地方。把 build() 里与子 agent 有关的几行按顺序读一遍：

  1. 先有 messageBus，后有 InboxMiddleware
    messageBus == null && filesystem != null 时自动创建 WorkspaceMessageBusHarnessAgent.java:2507-2511；随后无条件装 InboxMiddleware:2614-2616。所以默认部署里「inbox」是开着的，不需要你配置。
  2. 团队先装，子 agent 后装
    teamsModeClient != null && teamsModeContext != null 才装 TeamsMiddleware 并注册工具:2618-2630；子 agent 分支在其后:2632-2648。两者互不替代，可以同时开。
  3. 子 agent 分支的三层条件
    外层：!leafSubagent && !disableSubagents && model != null；内层： filesystem != null && !disableDynamicSubagents 走 Dynamic，否则走静态:2633-2664。由于 resolveFilesystem 的默认分支一定会返回一个 LocalFilesystemSpecHarnessAgentBuilderSupport.java:147-168，Dynamic 才是默认；静态版要靠 disableDynamicSubagents() 主动退回。
  4. 等待工具最后装，且要能看见团队
    messageBus != null 时注册 WaitAsyncResultsTool，任务仓库从刚捕获的子 agent 中间件里取；若同时有团队，再挂一个 hasOutstandingTeamWork 探针，免得 lead 在队友还在跑时被劝「别再等了」:2670-2685。
  5. tools.json 的 allow 裁不掉这些工具
    ToolFilter 的规则是：显式 deny 永远生效；allow 只裁「目录工具」，HarnessPlatformTools 里的名字默认保留ToolFilter.java:27-43。这张平台工具表包含 agent_spawn/agent_send/agent_list、task_*、wait_async_results、 team 与 18 个别名、plan 三件套、skill_manage 等HarnessPlatformTools.java:35-78。真不想让模型用，只能显式 deny，或用 disableSubagents()/disableDynamicSubagents()。
两个「隐式默认」

① 默认就有 messageBus（因为 filesystem 默认存在），所以 wait_async_results 与 Inbox 默认都在； ② 默认装的是 Dynamic（同样因为 filesystem），所以 spec 文件是热加载的。把这两条记住，build() 里大半的「为什么会有这个工具」就不用查了。

                .model("dashscope:qwen-plus")
                .teamsMode(client, leadCtx, "team-session-1")
                .build();

团队中间件有两个「只对某种角色」的行为，值得单独记：lead 在每轮开始时刷新一次任务板摘要 boardDigest，里面会写「你还欠着哪几个任务」以及「全 settled 了，去写总结并 completeTeam」；worker 在轮次结束时把仍是 in_progress 且归自己的任务直接 failTask，理由取它最后一条 assistant 文本（截断到 4000 字符）:280-350。这是「worker 的一轮就是它的全部执行」这个模型的直接后果。

唤醒也是团队特有的：TeamsMiddleware 用两张静态表分别按 sessionId 与 team|member 查找实例，TeamWakeups 让 TeamClient 能按成员名叫醒一个会话； 唤醒时先 inboxPush 一条 source=team_event 的 hint，再 enqueueWakeup:95-99、:218-260。没绑会话时通知先缓存，下一轮再补，避免「事件早于绑定」丢失。

只给 client 不给 context，团队不会装，而且不报错

build() 的条件是「两个都非空」HarnessAgent.java:2619，没有校验、没有 warn。表现是：没有 team 工具、system prompt 里也没有团队段。排查团队「没生效」时先看这一条。

官方说了什么 vs 源码实际是什么

官方说法源码事实依据
工作区 spec 的 front matter 示例里写了 name: researcher（subagent.md:293-301） Loader 从不读 name，名字由文件名派生；未知键被 YAML 读入后直接忽略，不报错也不警告。写不写都不影响结果，但会误导你以为可以改名 AgentSpecLoader.java:217-347
「后台任务完成 → 下一轮前以 <system-reminder> 注入」（subagent.md:145-157） 这段代码在静态 SubagentsMiddleware 里；默认装的是 Dynamic，它只渲染任务摘要，不 drain delivery。默认路径的推送来自 completion callback → inbox → InboxMiddleware，文案是 <system-notification> DynamicSubagentsMiddleware.java:147-172、HarnessAgent.java:2327-2346
agent_generate「默认关闭」，示例只给了一句「拿到 builder 内部的 SubagentsMiddleware 引用」 全仓没有生产调用点：enableAgentGenerateTool 只出现在定义与 javadoc 里，build() 不调用它，builder 也没有对应方法；HarnessAgent 只暴露了 getSubagentAgentManager() 与 getTaskRepository()，拿不到中间件实例 SubagentsMiddleware.java:251-270、HarnessAgent.java:518-545

陷阱与窍门

1. 以为 subagentFactory 的 lambda 收到任务文本
你会看到
工厂里打印参数，永远是子 agent 的名字；任务文本根本传不到工厂。
因为
桥接是 (rc) -> custom.factory().apply(custom.name())HarnessAgentBuilderSupport.java:237，任务文本由 DefaultAgentManager.invokeAgent 作为 user message 传入:179-195。
改成
工厂只负责「造一个 agent」，需要按任务定制就在 agent 的 sysPrompt/工具里做；要父身份隔离，改用编程式声明。
2. 改了同名 subagents/*.md，静态模式不生效
你会看到
调了 disableDynamicSubagents() 之后，新增文件能被发现，但改已有文件的内容没反应。
因为
静态版的 loadSubagentSnapshot 只把「base 里不存在」的名字加进来，同名直接跳过:621-633；而且快照按 RuntimeContext 缓存，建一次就一直用:598-606。
改成
要么保留默认的 Dynamic（每轮 replace），要么重建 agent；不要在静态模式里期待热更新。
3. spec 文件明明在，agent_spawn 说 Unknown agent_id
你会看到
Error: Unknown agent_id: reviewer，但 subagents/reviewer.md 确实存在。
因为
三种可能，按概率排：① front matter 没写 description，Loader 直接返回 nullAgentSpecLoader.java:241-247；② 文件不在直接子级（Loader 不递归）:90-122；③ 声明是 mode: primary，被当成 PRIMARY-only 拒绝DefaultAgentManager.java:115-118。
改成
打开 debug 日志看 Loader 的 warn；确认文件层级；把 mode 改成 all 或删掉。
4. timeout_promoted 之后又 spawn 了一遍
你会看到
同一份任务跑了两遍，日志里两份结果；有时还会撞同一个 label。
因为
同步超时不是失败，执行被挂到 AdoptedTaskRunSpec 上继续跑，返回值是 status: timeout_promoted + 新 task_id:1027-1041；提示词模板也专门写了「Do NOT retry the same task」SubagentsMiddleware.java:139-140。
改成
把 timeout_promoted 当异步任务处理：等推送、task_output 或 wait_async_results(task_ids=…)。
5. 以为 tools.json 的 allow 能关掉 agent_spawn
你会看到
allow 里只写了三个文件工具，模型却还能 spawn、还能用 team。
因为
平台工具默认穿透 allow；日志会写 kept N platform tool(s) outside allowToolFilter.java:109-139。
改成
用 deny 精确列名字，或用 builder 的 disableSubagents()；团队没有 disable 开关，只能 deny 或干脆不装。
6. 团队 worker 一轮结束，任务被标成 failed
你会看到
worker 明明还在思考，板上的 in_progress 任务变成了 failed，理由是它最后一段话。
因为
TeamsMiddleware.onAgent 对非 lead 在轮次结束时执行 settleOwnedTasks，把仍归自己的 in_progress 全部 failTask:301-350。这是设计：worker 没有被再次唤醒的保证，悬着的任务会让 lead 永远等。
改成
在 worker 的提示词里要求「结束前要么 completeTask，要么 failTask 并写清原因」；长任务拆小，别让一轮装不下。

自检三问

默认配置下，装的是 Dynamic 还是静态中间件？各自的 spec 加载时机与「改名/改内容」行为是什么？

默认 Dynamic：build() 的内层条件是 filesystem != null && !disableDynamicSubagentsHarnessAgent.java:2634，而 filesystem 默认一定存在。Dynamic 每轮重新跑两层加载（filesystem 覆盖本地目录）并 replaceAgentsDynamicSubagentsMiddleware.java:147-157，所以新增和改内容都生效。静态版在 build 时扫一次本地目录，运行期只补「base 里没有的名字」，同名修改不生效SubagentsMiddleware.java:613-641。

同步 spawn 超时后发生了什么？force-sync 下有什么不同？

普通同步：超时只结束「观察」，不结束「执行」。还在跑的 CompletableFuture 被包成 AdoptedTaskRunSpec 注册进仓库，调用方拿到 status: timeout_promoted 和一个新 task_idAgentSpawnTool.java:1027-1041。force-sync：innerSub.dispose() 触发 doFinally(CANCEL) → interruptAgent，返回 status: timeout，不注册后台任务:1013-1026。

团队里 lead 和 worker 拿到的工具面为什么不同？空 availableActions 意味着什么？

TeamTool 在每次调用前检查 context.availableActions()，不在集合里的 action 直接回错误；normalize 会去掉 _/- 并转小写，另有几条兼容别名（listClaimableTasks/unclaimTask 跟着 claimTask 放行，listMessages 跟着发消息放行，failTask 跟着 completeTask 放行）TeamTool.java:644-673。空或 null 表示不裁剪，所有 action 都放行；所以「安全默认」是显式给 lead/worker 各写一份白名单，而不是留空。

20 分钟动手练习

  1. 看见「四种工作区组合」的落点
    写两个 spec：a.md 用默认（ISOLATED、无 path），b.md 写 workspace.mode: shared。 各 spawn 一次，然后看宿主目录：a 会多出 agents/a/workspace/HarnessAgentBuilderSupport.java:719-731，b 没有新目录，直接读写主工作区。再把 a.md 加上 workspace.path: ./defs/a 和一个非空正文，确认日志出现「body will be ignored」并且 ./defs/a/AGENTS.md 才是 prompt 来源。
  2. 亲手摸到任务记录文件
    用 timeout_seconds=0 spawn 一个会跑十几秒的任务，立刻去 <workspace>/agents/<name>/tasks/<sessionId>.json 看结构（taskId、status、createdAt、result）；再在同一个会话里调 task_list 与 task_output(block=false)，对比两者的输出。最后把进程杀掉重启，确认 task_list 仍能读出这条记录——这就是「压缩/迁移后仍准确」的来源:44-54。
  3. 对比两条推送路径
    同一段后台任务代码，跑两遍：默认（Dynamic）一遍，.disableDynamicSubagents() 一遍。用 streamEvents() 观察：默认应看到 InboxMiddleware 产生的 HintBlockEvent（内容含 <system-notification>）；静态版还会多一条 role=USER、name=system 的 <system-reminder> 消息进入后续上下文SubagentsMiddleware.java:413-449。这一步能把「文档写的」和「默认跑的」彻底分开。
  4. 团队最小闭环（可选，不接模型也能验证状态机）
    用 new InMemoryStore() + new LocalTeamClient(store)，直接调 createTask → claimTask → completeTask，观察 version 每次 +1；再连续两次 claimTask 同一条任务，确认第二次是幂等返回而不是冲突LocalTeamClient.java:126-175。最后给一条带 blockedBy 的任务，确认 claimableOf 在依赖完成前不返回它。
