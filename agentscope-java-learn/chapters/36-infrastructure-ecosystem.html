36 · 基础设施与生态：Nacos / Higress / Scheduler / Studio / Training

这是集成生态的最后一章。前面每一章补的是一种能力：模型、记忆、存储、RAG、协议、渠道、技能仓库。 这一章补的是「Agent 怎么进入企业已有的运行环境」：注册到控制面、通过网关拿工具、被调度器触发、在 Studio 里被看见、把线上流量喂给训练后端。 它们大多不改 Agent 的推理逻辑，改的是 Agent 的外围边界；边界没分清，接入就会变成一堆看似成功、实际不生效的配置。

想直接照着接？

本章讲清「接在哪一层、默认值是什么、哪里会坏」；真正动手时看配套的 36A 集成落地手册，那里把七条链路拆成了配置、代码、验收与失败边界。

Nacos：一个控制面，三个子模块

agentscope-extensions-nacos 不是单个 jar，而是三个可独立引入的子模块： A2A 注册发现、Prompt 配置中心、Skill 仓库 nacos.md:6-12。 三者共用 Nacos 客户端，但生命周期和失败方式完全不同，建议按需组合，而不是一次全上。

Nacos A2A：注册的是 AgentCard，不是 Agent 实例

服务端用 NacosA2aRegistry 把 A2A 的 AgentCard 与服务端点写进 Nacos； 客户端用 NacosAgentCardResolver 按名字拿到远端 AgentCard，再交给 A2aAgent 使用 nacos.md:26-53。 注册的是「这张卡 + 这些端点」，不是某个正在运行的 Java 对象；它是显式动作，不是类加载时自动完成， 新版本或新实例上线时要再调一次。 

NacosA2aRegistry registry = new NacosA2aRegistry(nacosProperties);

NacosA2aRegistryProperties props = NacosA2aRegistryProperties.builder()
    .setAsLatest(false)
    .enabledRegisterEndpoint(true)
    .build();
props.addTransport(NacosA2aRegistryTransportProperties.builder()
    .transport("HTTP")
    .host("localhost")
    .port(8080)
    .build());

registry.registerAgent(agentCard, props);

NacosAgentCardResolver resolver = new NacosAgentCardResolver(nacosProperties);
A2aAgent remote = A2aAgent.builder()
    .name("translator")
    .agentCardResolver(resolver)
    .build();

NacosA2aRegistryProperties 是一个四字段 record：isSetAsLatest、enabledRegisterEndpoint、 overwritePreferredTransport、transportProperties NacosA2aRegistryProperties.java:34-38。 用 builder 时，enabledRegisterEndpoint 默认 true，setAsLatest 默认 false，overwritePreferredTransport 默认 null NacosA2aRegistryProperties.java:83-92。

文档里的两个 Nacos A2A 构造器在源码里都不存在

文档写的是 new NacosA2aRegistryProperties() nacos.md:36-38， 但它是 record，没有无参构造器；日常走 builder()，也可以直接传四个参数。 文档又写 new NacosAgentCardResolver(props, "translator-agent") nacos.md:48-52， 而源码只有 (Properties) 和 (AiService) 两个构造器 NacosAgentCardResolver.java:75-88。 Agent 名不是构造参数，而是 A2aAgent.builder().name(...) 提供的。照文档写会直接编译失败。

解析器内部有 agentCardCaches 与 agentCardUpdaters 两张表；第一次按名取时订阅，后续命中缓存， Nacos 侧更新会通过监听器回写缓存 NacosAgentCardResolver.java:61-121。 所以「改了 AgentCard 要不要重启」的答案是：解析器会更新缓存，但你的 A2aAgent 是否重新读卡，取决于它自己的调用时机。

Nacos Prompt：缓存键只有 promptKey

NacosPromptListener 用一个 ConcurrentHashMap 保存 promptKey → Prompt； 第一次取不到时调用 aiService.subscribePrompt(...)，之后的更新由内部监听器写回同一张表 NacosPromptListener.java:37-68 NacosPromptListener.java:141-150。 这就是文档说的「下一次 getPrompt(...) 立即拿到新版本，无需重启」 nacos.md:80。 

NacosPromptListener prompts = new NacosPromptListener(aiService);

String tpl = prompts.getPrompt(
    "system-prompt",
    "1.2.0",          // version
    null,             // label，和 version 互斥
    Map.of("userName", "Alice"),
    "你是一个助手");   // 默认值
缓存只按 promptKey 命中，第二次换版本不会重新订阅

getPrompt(promptKey, version, label, args, defaultValue) 先查 prompts.get(promptKey)； 只要命中，就直接渲染，完全忽略本次传入的 version 与 label NacosPromptListener.java:112-138。 同一进程里想同时读两个版本，或想从 prod 切到 canary，不能靠再调一次 getPrompt； 需要新建一个 listener，或用不同 promptKey 隔离。文档只讲了「热更新」，没讲这个「首次绑定」语义。

另外，版本与标签是「互斥」的：源码注释明确要求 version 与 label 二选一 NacosPromptListener.java:94-109。 如果两者都传，实际行为由 Nacos 客户端决定，不要把它当成分级回退。

Nacos Skill：只读 ZIP 仓库，枚举要显式给名单

NacosSkillRepository 把 Nacos AI 模块管理的技能 ZIP 下载下来，解析成 AgentSkill nacos.md:82-105。 它是只读仓库：save / delete 只打警告返回 false，isWriteable() 恒为 false NacosSkillRepository.java:217-270。 命名空间为空时按 public 处理，source 变成 nacos@命名空间 NacosSkillRepository.java:146-149。 

Properties props = new Properties();
props.setProperty(NacosSkillRepository.SKILL_VERSION_PATH, "1.2.0");

NacosSkillRepository repo = new NacosSkillRepository(
    aiService,
    "default-namespace",
    props,
    List.of("calculator", "translator"));  // 不传就枚举不到

版本与标签的解析顺序是：构造参数 Properties → JVM -D 系统属性 → 环境变量； 两者都解析到时，版本优先，标签不参与下载 NacosSkillRepository.java:49-52 NacosSkillRepository.java:68-72。 常量分别是 agentscope.nacos.skill.version / ...label 与 AGENTSCOPE_NACOS_SKILL_VERSION / ...LABEL NacosSkillRepository.java:90-100。

不传 knownSkillNames，getAllSkills() 就是空列表

Nacos 没有「列出某个命名空间下所有技能」的接口，所以仓库只能用构造时给的名单逐个下载； 名单为空时，getAllSkillNames() / getAllSkills() 直接返回空，并打一条 warn NacosSkillRepository.java:229-258。 这意味着：显式调 getSkill("calculator") 能成功，但挂到 ReActAgent.skillRepository(...) 后， 动态技能中间件拿到的仍是空列表。Nacos 技能仓库必须配名单，或改用能枚举的 MySQL / PostgreSQL / Git 仓库。

与 Nacos 不同，Git 仓库是在本地克隆上读文件的：getAllSkills() 先做一次同步/HEAD 检查， 再读本地目录，不会为每个技能各发一次网络请求；Nacos 才是每个技能下载一个 ZIP，技能多时启动会变慢。 NacosSkillRepository.java:240-258。

Higress：工具治理留在网关，Agent 只拿 MCP 客户端

agentscope-extensions-higress 把 Higress 上以 MCP 发布的工具引入 AgentScope。 Higress 负责工具搜索、鉴权、限流、路由与可观测，Agent 侧只负责调用 higress.md:6-11。 这也是选它的主要理由：工具治理不需要在 Java 业务里重复实现。 

HigressMcpClientWrapper client = HigressMcpClientBuilder
    .create("higress")
    .streamableHttpEndpoint("http://gateway/mcp-servers/union-tools-search")
    .buildAsync()
    .block();

HigressToolkit toolkit = new HigressToolkit();
toolkit.registerMcpClient(client).block();

ReActAgent agent = ReActAgent.builder()
    .name("Assistant")
    .model(model)
    .toolkit(toolkit)
    .build();

builder 支持 SSE 与 StreamableHTTP 两种端点；默认请求超时 120 秒，初始化超时 30 秒 HigressMcpClientBuilder.java:71-82。 工具搜索默认关闭；开启后 listTools() 不再返回全部工具，而是先调 x_higress_tool_search，只返回语义相关的 Top K，默认 10 个 HigressMcpClientWrapper.java:64 HigressMcpClientWrapper.java:156-204。

文档的 .build() 也不存在：只有 buildAsync() / buildSync()

官方快速上手以 .build() 结尾 higress.md:31-34， 而 2.0.4 的 builder 只提供返回 Mono 的 buildAsync() 与阻塞式的 buildSync() HigressMcpClientBuilder.java:311 HigressMcpClientBuilder.java:357。 响应式链路用 buildAsync()，启动脚本或测试里用 buildSync()；照文档写 .build() 会编译失败。

HigressToolkit.registerMcpClient 返回 Mono<Void>；只有注册成功后才把 HigressMcpClientWrapper 缓存到 getHigressMcpClient() HigressToolkit.java:99-120。 文档里的 toolkit.registerMcpClient(client).block() higress.md:36-38 是对的；忘记 block() / subscribe() 是常见「注册了但工具不可见」的原因。

Scheduler：接口只有 schedule / cancel，没有 pause / resume

AgentScheduler 的核心契约是：注册、取消、按名取、列全部、关闭、取类型 AgentScheduler.java:77-190。 每次触发时，调度器用配置「现造」一个新的 Agent 实例，避免上一次调用的状态串到下一次 AgentScheduler.java:79-104。 这也是为什么调度配置传的是 AgentConfig，而不是一个已经创建好的 Agent。

文档把 pause / resume 当成了核心接口方法

文档写「AgentScheduler：核心接口，schedule(...) / pause(...) / resume(...) / cancel(...) / shutdown()」 scheduler.md:15-20， 示例也把返回值赋给 AgentScheduler 后直接调用 scheduler.pause(...) scheduler.md:66-73。 但 2.0.4 的接口里没有 pause / resume，只有 Quartz 实现类自己提供了这两个 public 方法 QuartzAgentScheduler.java:429-470。 照文档把变量声明成 AgentScheduler，再调 pause，会编译失败；要么声明成 QuartzAgentScheduler，要么用 ScheduleAgentTask 的 cancel()。

调度模式有四种：NONE（默认，不自动执行）、CRON、FIXED_RATE、 FIXED_DELAY ScheduleMode.java:26-37。 ScheduleConfig 的 builder 默认就是 NONE，且 NONE 不做任何时间参数校验 ScheduleConfig.java:80-105 ScheduleConfig.java:176-181。

Quartz：默认 autoStart，但默认调度模式什么也不做

QuartzAgentScheduler.builder().build() 默认 autoStart=true、schedulerId=default-scheduler QuartzAgentScheduler.java:626-629， 并在 build 时启动 Quartz QuartzAgentScheduler.java:671-689。 所有 Job 都放在 agentscope-quartz 组里，按 Agent 名做 JobKey QuartzAgentScheduler.java:224-231。 

QuartzAgentScheduler scheduler = QuartzAgentScheduler.builder()
    .autoStart(true)
    .build();

ScheduleConfig schedule = ScheduleConfig.builder()
    .scheduleMode(ScheduleMode.FIXED_RATE)
    .fixedRate(5_000L)
    .build();

scheduler.schedule(agentConfig, schedule);

// pause / resume 只在 Quartz 实现类上
scheduler.pause("DailyReportAgent");
scheduler.resume("DailyReportAgent");
scheduler.cancel("DailyReportAgent");

Quartz 把三种模式分别映射为 CronTrigger、重复的 SimpleTrigger、以及「执行完再排下一次」的固定延迟 QuartzAgentScheduler.java:246-305。 集群部署时让它共享 Quartz 数据库即可，任务本身不依赖某个 JVM 的内存。

schedule(agentConfig) 用的是 NONE，任务不会触发

便利方法 schedule(agentConfig) 内部调用的是 ScheduleConfig.builder().build()，也就是 NONE QuartzAgentScheduler.java:154-156。 在 Quartz 实现里，NONE 不会走进任何一个 scheduleJob 分支，但任务句柄仍会被放进 map 并返回 QuartzAgentScheduler.java:272-315。 表面「注册成功」，实际永远不会跑；生产上必须显式给 CRON / FIXED_RATE / FIXED_DELAY。

XXL-Job：只注册 JobHandler，调度交给控制台

XxlJobAgentScheduler 的职责不是「在 Java 里排程」，而是把 Agent 名注册成 XXL-Job 的 JobHandler； CRON、并发、路由、日志都在 XXL-Job 控制台配置 scheduler.md:101-108。 因此它只接受 ScheduleMode.NONE，传其他模式会直接抛 UnsupportedOperationException XxlJobAgentScheduler.java:148-161。 

XxlJobSpringExecutor executor = new XxlJobSpringExecutor();
executor.setAdminAddresses("http://localhost:8080/xxl-job-admin");
executor.setAppname("agentscope-demo");
executor.setAccessToken("xxxxxxxx");
executor.start();

AgentScheduler scheduler = new XxlJobAgentScheduler(executor);

// 只注册，不在这里排程
scheduler.schedule(agentConfig, ScheduleConfig.builder().build());

XXL-Job 实现不支持 cancel，调用即抛异常，提示去控制台暂停或删除 Job XxlJobAgentScheduler.java:289-304； 也没有 pause / resume，源码注释明确写了「Pause/resume operations are not directly supported」 XxlJobAgentScheduler.java:106-108。 shutdown() 会销毁 executor、清空已注册任务 XxlJobAgentScheduler.java:330-347。

Studio：初始化会自动挂 Hook，也会自动注册 Tracer

agentscope-extensions-studio 把 Agent 接入 AgentScope Studio，用于可视化调试、链路回放与 Human-in-the-Loop studio.md:6-11。 StudioManager.init() 是单例入口：先建 HTTP / WebSocket 客户端，再注册 run，最后连接 WebSocket StudioManager.java:214-245。 

StudioManager.init()
    .studioUrl("http://localhost:3000")
    .project("MyProject")
    .runName("experiment_001")
    .initialize()
    .block();

ReActAgent agent = ReActAgent.builder()
    .name("Assistant")
    .model(model)
    .build();   // 不需要再手动加 StudioMessageHook

StudioConfig 的默认值：URL 是 http://localhost:3000，项目名 UnnamedProject， runName 是 run_<时间戳>，runId 是随机 UUID，最大重试 3 次，WebSocket 重连 3 次， 重连间隔 1 秒、上限 5 秒 StudioConfig.java:149-158。 文档示例里的 8000 只是示例端口，不是默认值；不传 studioUrl 会连 3000。

initialize 已经 addSystemHook，再手动挂一次会重复推送

initialize() 成功后会调用 AgentBase.addSystemHook(new StudioMessageHook(...))， 并注册一个 TelemetryTracer StudioManager.java:246-260。 addSystemHook 是全局静态列表，所有之后创建的 Agent 都会继承 AgentBase.java:466-467。 文档第 2 步又让 .hook(new StudioMessageHook(...)) studio.md:37-42， 两条路径都生效时，同一条最终消息会被推两次。要么只调 initialize()，要么初始化后手动 AgentBase.removeSystemHook 再自己控制。

Studio 推的是 PostCall 的最终消息，不是每条 token

StudioMessageHook 只处理 PostCallEvent：取出 getFinalMessage()， 调 StudioClient.pushMessage，失败只记日志，不让 Agent 调用失败 StudioMessageHook.java:66-95。 所以文档说的「每条 user / assistant / tool 消息都被同步」 studio.md:48-52 要打个折扣：Hook 侧只负责一次调用的最终回复；工具调用与推理过程主要靠 trace / telemetry，而不是这个消息 Hook。

Studio 还提供 StudioUserAgent，它继承 AgentBase，通过 WebSocket 等 Studio 侧输入， 用于「真人扮演一个 Agent」 StudioUserAgent.java:74-82。 生产环境通常不挂这个消息 Hook，避免每次调用都写一份数据；文档建议用 Profile 或 @ConditionalOnProperty 控制 studio.md:65-75。 关闭时记得 StudioManager.shutdown()，否则 WebSocket 与 OkHttp 连接会留在进程里。

Training：采样后跑影子 Agent，不替换生产调用

agentscope-extensions-training 把生产流量按策略采样，收集 trace、计算奖励，再周期性提交给 Trinity 训练后端 training.md:6-12。 TrainingRunner.start() 把 TrainingRouter 注册成全局 system hook TrainingRunner.java:115-133。 它是全局的，不是某个 Agent 独有；同一 JVM 里所有之后创建的 Agent 都会经过路由器。 

TrainingRunner runner = TrainingRunner.builder()
    .trinityEndpoint("http://localhost:8080")
    .modelName("/path/to/model")
    .selectionStrategy(SamplingRateStrategy.of(0.1))
    .rewardCalculator(agent -> 0.0)
    .commitIntervalSeconds(300)
    .build();

runner.start();
agent.call(msg).block();
runner.stop();

命中采样后，路由器不会改动这次生产调用，而是克隆一个影子 Agent，把模型换成 TrinityModelAdapter，在异步线程池里再跑一遍；跑完用 RewardCalculator 算分，再调 feedback TrainingRouter.java:43-68 TrainingRouter.java:221-249。 这也解释了为什么它「对调用方透明」：生产响应不等影子跑完。

文档把影子流量写成了「调用替换」，奖励函数类型也写错了

文档说「命中采样 → 调用替换为 Trinity 后端」 training.md:68-74， 但源码是克隆 Agent + 换模型 + 异步执行，生产调用本身仍走原模型 TrainingRouter.java:277-298。 文档又说 rewardCalculator 是 Function<AgentBase, Double> training.md:52-58， 实际接口是 RewardCalculator，方法为 double calculate(Agent agent) RewardCalculator.java:26-34。 Lambda 能写是因为接口是函数式接口，但参数类型是 Agent，不是 AgentBase。

Chat Completions Web：核心适配器不等于 HTTP 服务

agentscope-extensions-chat-completions-web 只提供框架无关的适配器：把 Agent 的 Event 流转成 OpenAI 兼容的 ChatCompletionsChunk chat-completions-web.md:6-11。 文档也明确说「只提供核心适配器，真正的 HTTP / SSE 路由请用对应 starter 或自写 Controller」 chat-completions-web.md:23。 这句话很关键：只加核心 jar，不会自动出现 /v1/chat/completions。 

<dependency>
  <groupId>io.agentscope</groupId>
  <artifactId>agentscope-chat-completions-web-starter</artifactId>

starter 自动注册 ChatCompletionsController，默认路径来自 agentscope.chat-completions.base-path=/v1/chat/completions， enabled 默认 true ChatCompletionsProperties.java:34-41。 同一个路径同时支持普通 JSON 与 SSE；stream=true 时即使客户端没带 Accept: text/event-stream，也会自动切到流式 ChatCompletionsController.java:112-143。 流结束时补一条 data: [DONE] ChatCompletionsStreamingService.java:79-83。

适配器签名：文档的 stream(agent, request) 不存在

核心适配器不接收 ChatCompletionsRequest

文档示例是 adapter.stream(agent, request) chat-completions-web.md:33-37。 源码里只有一个 stream 重载： stream(ReActAgent agent, List<Msg> messages, String requestId, String model) ChatCompletionsStreamingAdapter.java:86-104。 OpenAI 请求到 List<Msg> 的转换由 ChatMessageConverter 完成，不是适配器内部做。 

ChatCompletionsStreamingAdapter adapter = new ChatCompletionsStreamingAdapter();
List<Msg> messages = converter.convertMessages(request.getMessages());

Flux<ChatCompletionsChunk> stream = adapter.stream(
    agent, messages, requestId, request.getModel());

适配器只订阅 REASONING 与 TOOL_RESULT 两类事件，并开启增量模式； 它还会过滤最后一个累积 REASONING 事件的文本，避免「增量 chunk + 最终全文」重复 ChatCompletionsStreamingAdapter.java:92-127。 这套去重对「边流边拼接」的客户端很重要，否则前端会看到重复文本。

工具调用是 schema-only：执行权在客户端

ChatCompletionsRequest 的 tools 字段说明写得很清楚：工具以 schema 形式注册； 当 Agent 决定调用工具时，执行会挂起，工具调用返回给客户端，由客户端执行后再把结果放回下一轮请求 ChatCompletionsRequest.java:74-81。 也就是说，这条链路不是「服务端替客户端执行工具」，而是标准的 OpenAI 工具往返。

starter 侧的自动配置假设 classpath 上已经有核心 starter，并使用它提供的 singleton ReActAgent bean；Controller 通过 ObjectProvider 取用同一个实例 ChatCompletionsWebAutoConfiguration.java:36-37 ChatCompletionsWebAutoConfiguration.java:139-148。 没有这个 bean，应用本身仍能启动；但请求走到 getObject() 时会抛 NoSuchBeanDefinitionException（通常表现为 500）。这不是「引入 starter 就自动有 Agent」。

八个坑：把「接上」当成「生效」

坑一：照文档写 Nacos A2A 构造器。 NacosA2aRegistryProperties 没有无参构造器，NacosAgentCardResolver 没有 (Properties, String) 重载 NacosA2aRegistryProperties.java:34-38 NacosAgentCardResolver.java:75-88。

坑二：以为 Prompt 缓存能按版本分开。 缓存键只有 promptKey，第一次调用决定 version / label，后续传不同值不会重新订阅 NacosPromptListener.java:112-138。

坑三：Nacos Skill 不传名单。 getAllSkills() 返回空，动态技能中间件就看不到任何技能 NacosSkillRepository.java:229-258。

坑四：在 AgentScheduler 上调 pause / resume。 接口没有这两个方法；用 Quartz 具体类型，或只保留 cancel() AgentScheduler.java:77-190。

坑五：Quartz 用默认 schedule。 NONE 不建 Trigger，任务看着注册成功，实际不会跑 QuartzAgentScheduler.java:272-315。

坑六：Studio 手动再挂一次 Hook。 initialize() 已经 addSystemHook，重复挂会让同一条最终消息推两次 StudioManager.java:246-260。

坑七：以为 Training 会替换生产调用。 它是异步影子 Agent，生产响应仍由原模型产生；只有命中采样的请求才会多跑一遍 TrainingRouter.java:221-249。

坑八：只引 Chat Completions 核心包。 核心包没有 Controller；要么引 agentscope-chat-completions-web-starter，要么自己写 @PostMapping chat-completions-web.md:23。

自测：三个判断题

Nacos A2A 的 NacosA2aRegistryProperties 可以直接 new 吗？

不能。它是 record，公开构造器需要四个参数；日常用 builder()，默认 enabledRegisterEndpoint=true、setAsLatest=false NacosA2aRegistryProperties.java:34-38。

Quartz 的 schedule(agentConfig) 会自动按某个默认周期跑吗？

不会。它用 ScheduleConfig.builder().build()，模式是 NONE； Quartz 实现不会为 NONE 建 Trigger，任务不会自动执行 QuartzAgentScheduler.java:154-156。

Chat Completions 适配器会替客户端执行工具吗？

不会。工具以 schema-only 形式注册，Agent 决定调用时执行挂起，工具调用返回客户端执行 ChatCompletionsRequest.java:74-81。

练习：把 Agent 接进一条真实外围链路

目标不是把所有扩展都装上，而是能解释「谁触发、谁治理、谁观测、失败时谁兜底」。建议 60 分钟：

  1. 画边界图
    写下请求入口、工具出口、状态存放、观测点，标出哪些在本进程、哪些在外部服务。
  2. 注册一次 A2A
    用 builder 构造 properties，把 AgentCard 注册到 Nacos，再从另一个进程解析出来。
  3. 验证 Prompt 缓存
    先按 1.0.0 取一次，再按 2.0.0 取，确认第二次仍是旧版本；换新 listener 再试。
  4. 枚举 Nacos 技能
    先不传 knownSkillNames 调 getAllSkills()，再补名单，观察差异。
  5. 接一个 Higress 工具
    用 StreamableHTTP 建客户端，注册到 HigressToolkit，确认工具出现在 Agent 的工具列表里。
  6. 跑一次 Quartz
    用 FIXED_RATE 跑 5 秒一次，再故意用默认 NONE，确认后者不触发。
  7. 观测与训练
    开 Studio 看一次最终消息；再开 Training 用 10% 采样，确认生产响应不等待影子 Agent。
  8. 写三行结论
    分别写「谁触发」「谁治理」「失败时谁兜底」，每行都要能在日志、控制台或 trace 里找到证据。
