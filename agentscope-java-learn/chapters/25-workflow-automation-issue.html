25 · Workflow、自动化与 Issue 闭环

第 24 章的 Team 把「下一步派给谁」交给 Leader 临场决定；这一章反过来，把步骤、依赖和人工关口提前写进一张图。 Workflow 负责声明式拓扑，Automation 负责「什么时候触发」，Issue 保存工作本身，Inbox 承担验收。 全章只围绕三组容易混淆的事实：草稿不等于已发布 revision、 触发被接收不等于工作已执行、Run 到终态不等于 Issue 已验收。

读完你能做到

  • 说清 Workflow、Automation、Issue、Inbox 各自保存哪一层事实，以及什么时候该用 Team
  • 从 draft 到 revision 再到 Run，解释一次 Workflow 执行究竟冻结了什么
  • 读懂八种节点、边状态、join 模式、CEL 输入映射与发布前校验
  • 区分 fail_fast、continue、partial_success，并知道 Run 终态如何回写 Issue
  • 配置 cron 与 Webhook，处理时区、幂等、跳过、排队和两种超时
  • 按验收闸门逐项排查「Run 已结束，Issue 为什么还不能 Done」

边界：四张表，四种职责

Workflow 适合有明确步骤、依赖和人工关口的工作：定义先保存为可编辑草稿，发布后生成不可变 revision， 每次执行固定一个 revision，所以后续改草稿不会改变已有运行的拓扑 workflows.md:10。 Automation 则把「何时触发」与「执行什么工作」保存成一条可复用规则，适合日报、定期检查和外部事件 automation.md:10。 Issue 保存目标、负责人、讨论、执行记录和交付物，即使执行失败或服务重启，工作本身仍然可追踪 issues.md:10。 Inbox 只汇集与你相关的更新、审批和验收，不替你做决定 inbox.md:10。

对象回答的问题不该拿它回答
Definition / Revision步骤与依赖长什么样，发布的是哪一版这次工作有没有人验收
Automation / Delivery什么时候收到触发，事件有没有被过滤工作是否已经执行成功
Run / Node本次执行走到哪一步，哪个节点失败或等待业务交付是否满足验收标准
Issue / Inbox工作目标、负责人、结果与最终验收执行图内部如何调度

Automation 与 Workflow 的分工是官方明确写出的：需要固定多步骤拓扑时用 Workflow，Automation 主要负责触发 automation.md:10。

一句话判断

如果「下一步做什么」在运行前就能画出来，用 Workflow；如果需要模型看上下文再决定，用 Team。 Automation 不改变这个判断，它只负责在某个时间点或某个事件之后把工作交出去。

定义与版本：draft 可改，revision 不可变

一个 Workflow 定义同时保存 draftSpec、draftVersion 与 version； 发布后生成独立的 OrchestrationRevision，带递增的 revision、规范化后的 spec、checksum 和发布者 orchestration.go:122-148。 发布动作会先校验草稿，再把规范化 JSON 的 SHA-256 作为校验和写入 revision service.go:87-107。 因而「修改草稿」与「发布新版本」是两个独立动作，已有 Run 也不会被悄悄换图。

  • 编辑 在设计器或 JSON 中修改 draftSpec；图形编辑与 JSON 编辑操作的是同一份定义workflows.md:47。
  • 校验 检查节点 key、必填字段、边引用、终态条件与无环性；这一步不会生成可执行版本。
  • 发布 服务端重新校验草稿并创建不可变 revision；已归档的定义不能发布service.go:87-107。
  • 启动 选择已发布 revision 启动 Run；未指定时使用最新 revision，没有发布版本则返回冲突service.go:138-152。
  • 冻结 Run 只记录 definitionRevisionId，之后所有节点都从该 revision materialize，不受草稿继续修改影响orchestration.go:150-178。

一个最小的发布定义可以写成这样，节点 key 在整张图中必须唯一：

{
  "nodes": [
    { "key": "draft", "type": "agent", "agentId": "<agent-uuid>",
      "input": { "request": "run.input.request" } },
    { "key": "approve", "type": "approval",
      "approval": { "approverRef": "<human-ref>", "prompt": "检查草稿后批准" } },
    { "key": "publish", "type": "agent", "agentId": "<agent-uuid>",
      "input": { "draft": "nodes.draft.output" } }
  ],
  "edges": [
    { "from": "draft", "to": "approve" },
    { "from": "approve", "to": "publish" }
  ]
}

节点与边字段见 spec.go:39-65； 发布成功返回 201，校验失败返回 422 orchestration_handler.go:183-202。

八种节点：谁在等，谁在选，谁在汇合

节点类型在源码里只有八个取值，每一种都对应不同的等待或收敛语义 orchestration.go:74-85。 官方节点表也按这个顺序列出用途 workflows.md:28-39。

节点引擎做什么必填或关键配置
agent为节点创建一条 Agent 任务，节点进入 waiting，任务终态后回写结果agentId 必须是合法 UUIDspec.go:174-177
team物化 Team 协调节点，由 Leader 驱动动态协作teamRef 必须是 active Team 的 UUIDspec.go:179-181
condition作为显式分支点；节点成功后由出边的 condition 选择下游，节点自身条件为假时直接 skipped条件必须返回 bool；节点级条件见 engine.go:263-279，边条件见 engine.go:180-190
join按 all / any / quorum 决定入边满足多少条才放行默认 all；quorum 必须为正且不超过入边数spec.go:191-201
approval创建 pending approval，节点 waiting；批准后成功，拒绝后失败approverRef 必填spec.go:206-208
timer记录唤醒时间，到点后节点成功at 或正的 durationSeconds 二选一spec.go:209-211

边不是「执行完就一定走」：on 只能声明终态，未声明时默认只接受 succeeded materialize.go:93-102。 普通节点要等所有入边都到达终态，再看其中有多少条被状态和条件选中；没有选中任何入边就 skipped。 join 节点则只看选中的数量是否达到 all / any / quorum 的门槛 engine.go:192-223。

发布前校验：一张图必须先能证明自己可终止

服务端把校验集中在 ParseAndValidateSpec：节点 key 非空且唯一、类型必须属于八种、每种节点的必填字段、 issueMode 只能是 inherit / child、failurePolicy 只能是三种之一、边只能引用已知节点、 on 只能是终态、整图必须无环 spec.go:150-281。 这些检查同时约束草稿创建、显式校验接口和发布动作。

检查项不通过时说明什么
节点 key / 类型拼写错误、复制粘贴后的重复 key，或用了未支持的节点类型
节点必填字段agent 缺 agentId、team 缺 teamRef、approval 缺审批人、timer 既无时间也无时长
边与终态边指向不存在的节点、自环，或把 running 之类非终态写进 on
join 门槛quorum 为 0，或大于实际入边数，永远无法满足
无环性拓扑排序没有访问完所有节点，说明图里存在环
CEL 表达式条件或 input 映射编译失败；表达式超过 4096 字节也会被拒绝

CEL 在这里是受限表达式，不是任意脚本：表达式最长 4096 字节，单次求值默认超时 50 ms，输出最大 1 MiB spec.go:32 spec.go:85-97 spec.go:113-147。 可引用的顶层变量只有 run、issue、trigger 与 nodes： 运行输入和变量在 run 下，前序节点的状态、输出与产物在 nodes 下 engine.go:665-678。

描边不等于可执行

设计器能画出来，只说明 JSON 结构可保存；发布前仍要过一次服务端校验。尤其是 join 门槛、边状态和 CEL 类型， 它们经常在运行到一半时才暴露，而发布校验本来可以提前拦住。

启动：一个 Issue、一个幂等键、一个固定 revision

启动接口要求 idempotencyKey，并且 issueId 与内联 issue 必须二选一 service.go:124-130。 幂等锁按 tenant / namespace / key 串行化，同一把键不会并发创建两个 Run service.go:110-123。 内联创建 Issue 时，服务端会用确定性的 UUID 复用同一项工作，并把负责人清空，避免 Workflow 目标与 assignee 同时存在 service.go:160-172。 

{
  "idempotencyKey": "release-2026-11-06-001",
  "issueId": "<issue-uuid>",
  "input": { "request": "整理本周发布说明" },
  "triggerType": "manual"
}

Run 创建时状态是 planned，模式固定为 declared，并绑定 revision service.go:183-205。 如果省略 triggerType，默认写 definition；它不是业务事件类型，只表示这次启动来自定义入口。 启动成功后返回 201 和 run orchestration_handler.go:216-264。

情况结果先查什么
缺少幂等键，或 Issue 来源不是恰好一个400请求体；不要靠重试绕过参数错误
定义已归档、没有已发布 revision，或 Issue 跨命名空间409是否先发布；Issue 与定义是否同租户同空间
revision 里的定义校验失败422revision 是否来自旧数据或手工改写

状态码来源：启动成功 orchestration_handler.go:259-264； 无效定义映射 422 orchestration_handler.go:688-693； 冲突映射 409 taskplane_handler.go:862-871。

调度：planned 先落图，ready 才真正开始

引擎不会在创建 Run 时就把所有节点跑起来。状态为 planned 的 Run 先执行一次可恢复的 materialization： 按 revision 校验后，用确定性 ID 建节点和边，入度为 0 的节点直接置为 ready，其余为 pending materialize.go:26-83。 写入 run.started 事件后，Run 才从 planned 进入 running materialize.go:104-110。 中途崩溃后，任何 worker 都能凭同一批确定性 ID 继续补齐，而不是重复建一套图。

状态含义下一步
plannedRun 已创建，节点与边可能尚未物化materialize 后进入 running
running至少还有 ready / running 的节点可推进继续调度，或等待外部条件
waiting只剩等待中的节点，没有可运行节点等待任务结果、审批、计时器、信号或子 Run
paused调度被显式暂停Resume 后恢复；已运行步骤仍可返回
cancelling已请求取消，正在收尾最终进入 cancelled
succeeded / partial_succeeded / failed / cancelled四种终态不再调度节点；按结果收敛 Issue

状态取值和终态判断来自模型层 orchestration.go:36-52。 每次 reconciliation 最多循环 128 轮，避免单次调用里无限推进 engine.go:61。 当还有 waiting 节点但没有 runnable 节点时，Run 进入 waiting；一旦出现可运行节点，又切回 running engine.go:454-462。

人工关口与外部事件：approval、timer、signal、subrun

approval 节点会创建一条目标为 run-node 的 pending approval，节点进入 waiting； 批准后节点成功，拒绝或取消则节点失败，失败码是 approval_rejected engine.go:344-352 engine.go:765-789。 审批通过只放行下一步；后续 Agent 要用什么工具、有没有权限，仍由它自己的运行环境决定 workflows.md:41。

timer 节点支持绝对时间 at 或相对秒数 durationSeconds； 引擎把 wakeAt 写进节点输出并进入 waiting，到点后由 sweep 推进为成功 engine.go:353-360 engine.go:811-819。 signal 节点等待名为 signalName 的运行事件，收到 run.signal.<name> 后把事件载荷写成节点输出 engine.go:361-365 engine.go:790-810。 信号接口返回 202，表示事件已接收，不表示节点已经完成 orchestration_handler.go:376-395。

subrun 节点只能引用固定 revision，且 revision 必须与父 Run 同租户同空间；子 Run 终态后， 成功或部分成功写回父节点成功，failed / cancelled 写回父节点失败 engine.go:372-389 engine.go:821-839。

等待不是失败

waiting 节点仍可能被任务结果、审批决定、计时器、信号或子 Run 推进。排障时先看节点的 waitReason，不要因为 Run 停在 waiting 就重启整个流程。

失败策略：fail_fast、continue 与 partial_success

每个节点可以声明自己的失败策略；不写时默认 fail_fast engine.go:100-108。 fail_fast 会取消所有尚未终态的节点、把失败节点的错误写到 Run 上，并让 Run 直接失败 engine.go:116-134。 continue 保留其他分支继续推进；partial_success 允许在「有失败也有成功」时把 Run 收敛为 partial_succeeded，但 Team 协调节点失败会阻止这种收敛 engine.go:437-452。

策略节点失败后发生什么Run 可能的结果
fail_fast（默认）取消其他未终态节点，立即收敛失败failed
continue继续推进其他分支，失败仍留在节点上有成功则可能成功或部分成功；全失败则 failed
partial_success允许把部分完成视为可接受结果失败与成功并存且协调节点未失败时为 partial_succeeded

失败任务是否重试由节点 retry.maxAttempts、backoffSeconds 和错误码共同决定； maxAttempts 不填时只尝试一次 engine.go:734-745。 凭据缺失、权限不足、配置错误、能力不支持、输入非法等九类错误被明确列为不可重试，重试只会重复失败 engine.go:846-860。

partial_success 不是自动验收

Run 变成 partial_succeeded 只说明执行层接受了部分结果，Issue 仍按自己的完成策略处理。业务是否接受缺项， 要由验收标准决定，不能拿 Run 状态替代。

控制与重跑：Pause、Resume、Cancel、Rerun

Pause 只阻止新节点被调度，已经在运行的步骤仍可以返回结果；Resume 恢复调度。 Cancel 会请求取消节点、任务和子运行，但不会把 Issue 自动验收，也不会删除工作记录 workflows.md:51。 这三个动作成功后返回 200 和更新后的 Run orchestration_handler.go:340-374。

Rerun 只接受终态 Run，并且固定使用原始 revision 创建一条全新的 Run，原 Run 不会被重开或改写 service.go:208-232。 新 Run 通过 rerunOfRunId 保留来源关联，输入可显式覆盖；成功返回 201 orchestration_handler.go:343-362。 但 Rerun 会产生新的执行机会，外部副作用可能重复发生，流程本身不保证补偿已经发生的副作用 workflows.md:53。

如果 Workflow 通过 Endpoint 对外提供，发布新 revision 不等于调用方已经切换；还要更新 Endpoint release， 再检查实际调用版本 workflows.md:57。 这两个「版本」不要混：Workflow revision 决定图，Endpoint release 决定外部请求落到哪个图。

Automation：触发规则与执行快照分开保存

Automation 是持久的入口规则，包含执行快照、触发器集合、动作类型与 Webhook 配置；触发配置和动作配置由控制面保存， 不交给运行时 collaboration.go:521-545。 执行快照里固定 Runbook、目标 Agent / Team、输出方式、完成策略、并发策略、两种超时和订阅者 automation.go:23-36。 触发器有稳定 ID，编辑规则不会因为光标变化就生成新身份 automation.go:38-49。

触发器适合什么实现边界
cron日报、定期检查、固定时间巡检支持时区与预览；表达式按分钟级解析
webhookCI、构建、第三方事件需要 secret 与稳定幂等键；事件可筛选
channel从消息渠道进入带执行快照的规则不支持，会返回「not implemented」service.go:183-186

执行目标只能是已注册且 active 的 Agent，或者 active Team 的 Leader；Team 在执行时会解析成 Leader Agent service.go:68-93。 规则启用时才强制校验目标可用性；停用规则可以先保存，但不能因此假设它随时可运行 service.go:144-146。

计划与积压：时区、skip、queue 与两种超时

cron 的时区留空时默认 UTC；表达式里嵌入的 TZ= 会被拒绝，必须改用独立的 timezone 字段； @every 的间隔不得小于 1 分钟 schedule.go:27-49。 预览接口一次返回接下来的 5 个触发时间，并统一转成 UTC 返回 schedule.go:51-70 automation_handler.go:373-387。 因此「页面上写 09:00」和「日志里的时间」可能相差时区，先核对 timezone 再判断有没有漏跑。

字段默认规则
outputModecreate_issue可切到 run_only，只保留自动化执行记录
completionPolicyreviewrun_only 会强制改为 automaticservice.go:105-119
concurrencyPolicyskip已有活跃运行时跳过新触发，或改为 queue 顺序排队service.go:120-125
queueTimeoutSeconds3600允许 60–604800；只限制排队阶段
runTimeoutSeconds3600允许 60–604800；只限制已经开始的执行

超时范围校验在创建时一次完成 service.go:126-134。 skip 的触发会留下一条 skipped 记录，错误码 already_active automation.go:83-99。 queue 模式下，超过排队截止仍没开始的执行会以 queue_timeout 失败；已经开始但超过运行截止的则是 execution_timeout runtime.go:366-381。 这两个阶段必须分开看：一个在执行前，一个在执行中。

规则上限还包括：名称 1–200 字符、Runbook 1–100000 字符、最多 10 个触发器、50 个事件筛选、50 个订阅者 service.go:95-103 service.go:141-143 service.go:158-160 service.go:179-182。

Webhook：Delivery 回答「收到没有」，Run 回答「做了没有」

Webhook 入口校验 X-Automation-Secret，缺失或不匹配返回 401；请求体必须是 JSON 对象或数组， 上限 256 KiB，超过返回 413 automation_handler.go:522-550 automation_handler.go:236-249。 幂等键优先读 Idempotency-Key 或 X-Idempotency-Key，没有时回退到 X-GitHub-Delivery；仍然为空则返回 400 automation_handler.go:229-235 automation_handler.go:538-548。 重传同一事件要复用同一把键和同一份内容，否则会得到冲突，而不是第二条新执行。 

curl --fail-with-body "$AUTOMATION_WEBHOOK_URL" \
  -H 'Content-Type: application/json' \
  -H "X-Automation-Secret: $AUTOMATION_SECRET" \
  -H 'Idempotency-Key: build-2026-11-06-001' \
  -H 'X-Event-Type: build.completed' \
  --data '{"project":"example","result":"passed"}'

事件类型优先取 X-GitHub-Event，其次 X-Event-Type，JSON 里的 event 字段可以覆盖它；都没有时记为 webhook.received automation_handler.go:550-564。 事件筛选留空接受全部；不匹配的 delivery 会被标成 ignored，原因 event_filtered， 不会创建 Run webhook.go:42-69。 同一幂等键重复到达时，响应里的状态会显式写成 duplicate automation_handler.go:565-579。

看哪里能回答不能回答
Deliveries事件是否收到、是否通过 secret、是否被筛选、是否重复Agent 是否真的完成了工作
Runs是否排队、是否开始、当前状态、错误码、关联 Issue事件有没有被防火墙或发送方丢在门外
Issue / Inbox交付是否满足验收标准，是否需要人决策Webhook 请求有没有通过认证

事件载荷会作为 Trigger data 附到任务说明里，但其中的地址不会自动赋予 Agent 读取能力 automation.md:67。 收到事件也不等于原来的 Team 或 Run 已恢复执行；需要恢复时要在对应工作上显式处理 automation.md:69。 Replay delivery 或 Rerun 会产生新的处理机会，可能重复业务副作用 automation.md:73。

Issue：工作状态与完成策略是两套轴

Issue 有七个状态：backlog、todo、in_progress、in_review、 blocked、done、cancelled collaboration.go:40-50。 转换不是任意跳转：例如 backlog 可直接进 todo、in_progress 或 cancelled；in_progress 可进 in_review、blocked、 done 或 cancelled；done 也允许回到 in_progress 以支持重新打开 collaboration.go:52-71。

完成策略是另一套轴：review 需要人工确认，automatic 允许按自动规则收敛， external 由外部流程管理 collaboration.go:101-107。 官方文档把这条边界写得很直接：一次 Run 成功不等于 Issue 已验收，以详情里的 Policy 和当前状态为准 issues.md:57。

Issue 也可以直接把 Workflow 作为执行目标。此时不能再同时填 assignee，目标必须是同空间的已发布 Workflow； 没有发布 revision 会返回 409 collaboration_handler.go:170-204。 创建请求会选最新 revision，并在同一次调用里启动 Run，响应同时返回 issue 和 orchestrationRun collaboration_handler.go:217-232。 官方界面说明也提醒：没有发布版本时应先发布，创建成功后要检查 Executions，而不是从「Issue 创建成功」推断 Agent 已开始工作 issues.md:26。

状态不是进度百分比

in_progress 表示工作正在推进，in_review 表示等待验收，blocked 表示缺信息、授权或依赖。 done 是完成策略满足后的结果，不是「最后一个节点跑完」的同义词。

验收闸门：Done 之前要过九道检查

把 Issue 推向 done 时，服务端会跑一组验收守卫。任何一项不满足都会返回 acceptance blocked，而不是静默改状态 service.go:136-213。 这组检查把「执行完了」与「交付可接受」分开。

闸门阻断条件
Team 复核策略Team 要求人工复核，而当前操作者不是人类
子 Issue仍有子 Issue 不处于 done 或 cancelled
待审批Issue 上仍有 pending approval
任务终态仍有 AgentTask 不在终态
任务输入输入仍处于未处理状态，未进入 processed / deferred / dead_letter / blocked
结果评论负责人是 Agent 或 Team，但没有可见的 result 评论
验收标准必填 checklist 未满足，或 artifact / approval 数量不足
结果要求显式要求 requiredResult，但没有任何可见 result 评论
活跃 Run同一根 Issue 上仍有未终态的 orchestration Run

Acceptance criteria 的结构很小：checklist、minimumArtifacts、 minimumApprovals 与 requiredResult；checklist 项默认必填，只有显式 required=false 才可跳过 service.go:319-397。 它故意保持可移植，未知字段会被保存，但不会产生额外执行语义。

审批与验收是两个独立决策：approval 决定等待中的执行继续还是失败，验收决定交付是否达到要求 inbox.md:41。 评论线程的 Resolve 只表示讨论已处理，也不会完成验收 issues.md:42。

Inbox：读到消息不等于做出决策

Inbox 的视图是 all、unread、attention 与 action， 默认每页 50 条，最大 499；非法视图或 cursor 返回 400 inbox_handler.go:28-54。 unread 只表示尚未阅读，action 才表示仍需决策；读过消息不等于处理完工作 inbox.md:24。

通知不是对所有状态变化广播。只有面向人类的工作 Issue，或者显式指派给人类的子 Issue，才进入工作 Inbox； review_request 只对 review 完成策略生成，automatic / external 不会产生人工验收请求 inbox.go:123-177。 需要动作的通知只把 needsAction 给负责人，订阅者收到的是普通更新 inbox.go:157-175。

验收动作有三个入口：accept、reject、reopen。accept 和 reject 都必须带正整数 expectedVersion，reject 还必须写原因；Issue 不在 in_review 时返回 409 collaboration_handler.go:443-506。 要求修改会把 Issue 退回 in_progress 并记录反馈，但不会自动发起下一次执行 inbox.md:35。 页面提示工作已变化时，应刷新后重新核对结果，旧版本的确认不会被静默套到新版本上 inbox.md:37。

你看到它表示下一步
Unread这条消息还没读阅读后再判断是否需要动作
Needs action仍需要负责人作决定验收、审批或补充信息
Review requestedreview 策略的 Issue 等待验收核对结果、附件与子 Issue
Archived通知已收纳历史可查；归档不删除 Issue 或 Run

闭环：Run 终态之后，Issue 还要再走一段

把一条 Workflow 从触发到验收串起来，完整链路有七个可观察点。任何一段都不能用下一段的状态反推：

  • 触发 cron、Webhook 或手工请求到达；Webhook 先写一条 delivery，状态可能是 queued、ignored 或 duplicateautomation_handler.go:565-579。
  • 执行 Automation 创建或复用 Issue，并把工作交给 Agent、Team、Workflow 或 Endpoint；Runbook 与执行快照此时已固定。
  • 建图 Workflow Run 从 planned 进入 materialize，固定 revision，创建节点与边，根节点变 readymaterialize.go:26-110。
  • 推进 节点按边状态与条件推进；agent / team 等待任务，approval / timer / signal / subrun 等待外部条件。
  • 收敛 没有活跃节点后，Run 收敛为 succeeded、partial_succeeded、failed 或 cancelledengine.go:437-452。
  • 回写 成功的根 Run 把仍在 in_progress 的 Issue 推进到 in_review；只有 automatic 策略直接推进到 doneengine.go:527-539。
  • 验收 人或其他授权方检查验收标准，accept 后 done，reject 后退回 in_progress；失败 Run 会把 Issue 树标记为 blockedengine.go:588-628。
Run 结果Issue 的预期去向还不能得出什么结论

Team 作为 Workflow 的一个节点时，协调节点还有更严格的收敛条件：Leader 任务完成并不自动等于协调节点成功， 必须等团队汇总真正收敛 engine.go:721-726。 这也是第 24 章那条边界在 Workflow 里的延续：动态协作可以被装进声明式外壳，但它的内部收敛仍按 Team 的规则走。

六个坑：先分清层，再改配置

坑一：改完草稿就以为线上流程变了。已有 Run 固定的是 revision，不是当前草稿；要让新执行使用新图， 必须先发布，再让下一次启动选中它 workflows.md:10。

坑二：把 Webhook 的 200 当成执行成功。200 只说明 delivery 被接收、可能已入队或判重； 工作是否执行要看 Run，是否验收要看 Issue automation.md:73。

坑三：用 Run succeeded 直接推断 Issue done。review 策略会停在 in_review；只有 automatic 才会由 Run 收敛直接推进到 done engine.go:527-539。

坑四：把 skip 和 run timeout 混为一谈。skip 是并发策略在触发阶段跳过；queue_timeout 是排队截止； execution_timeout 才是执行超时。三者发生在不同阶段 automation.md:46 runtime.go:366-381。

坑五：在 cron 表达式里写 TZ=。服务端会直接拒绝，必须使用独立 timezone 字段； 留空则按 UTC 解释 schedule.go:27-37。

坑六：读过 Inbox 消息就开始验收。Unread 只描述阅读状态；验收要核对结果、附件、子 Issue 和 Acceptance criteria，归档更不能代替决策 inbox.md:24 inbox.md:47。

自测：三个判断题

发布新 revision 后，正在运行的 Workflow 会自动切到新拓扑吗？

不会。每次执行固定一个 revision，发布新版本只影响后续选择该版本的启动；已有 Run 仍按原 revision 的节点和边推进 workflows.md:10。 如果外部通过 Endpoint 调用，还要单独更新 Endpoint release workflows.md:57。

Webhook 返回 200，说明 Agent 已经开始执行了吗？

不一定。200 表示请求通过了认证、写入了 delivery，并根据开关、筛选和幂等键决定是 queued、ignored 还是 duplicate；真正的执行记录在 Run 里 webhook.go:42-72。

Run 变成 partial_succeeded，Issue 就能直接 Done 吗？

不能直接推断。partial_succeeded 只说明执行层在允许部分成功时接受了结果；Issue 还要过完成策略与验收闸门。 review 策略会停在 in_review，由人核对 checklist、artifact、approval 等条件 engine.go:437-452 service.go:136-213。

练习：搭一条带人工审批的发布流水线

目标不是「点一次成功」，而是能解释每次状态变化由哪一层产生。建议 45 分钟：

  1. 先单独验证两个 Agent
    准备「草稿」和「发布准备」两个 Agent，各跑一次小任务。草稿要能读取指定输入，发布准备要能指出缺失的证据；此时先不建 Workflow。
  2. 写一张三节点图
    用 agent → approval → agent 建图，给每个节点写唯一 key 和 input 映射；先故意留一个未知边引用，确认校验失败。
  3. 发布并固定版本
    修复后发布 revision，记下 revision id；再改一次草稿但不发布，确认新启动仍可选择旧 revision。
  4. 用 Issue 启动
    创建带验收标准的 Issue，把 Workflow 设为执行目标。确认响应同时有 issue 和 orchestrationRun，且 Issue 没有额外 assignee。
  5. 走一次审批
    在 Inbox 处理 approval 节点。先拒绝一次，确认节点失败、Run 按 fail_fast 收敛；再用新幂等键 Rerun，批准后观察节点继续。
  6. 制造一次验收阻断
    在 Acceptance criteria 里要求 1 个 artifact，但先不上传。尝试 Accept，记录 blocked 原因；补齐 artifact 与 result 后再接受。
  7. 加一条 cron 自动化
    创建日报规则，时区设为 Asia/Shanghai，先保持停用并做 Test run。核对预览时间、Runbook、输出方式和完成策略，再启用。
  8. 用 Webhook 重放一次
    添加 webhook trigger，发送同一幂等键两次，确认第二次是 duplicate；再换新键并加不匹配的事件筛选，确认 delivery 为 ignored 且没有新 Run。
  9. 最后对齐三层事实
    把这次练习写成三行：delivery 状态、automation run 状态、Issue 状态。检查每一行是否能独立解释，而不是用后一层的成功掩盖前一层的失败。
