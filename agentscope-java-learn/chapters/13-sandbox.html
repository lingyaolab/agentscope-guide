13 · 沙箱与受控执行：把文件与命令关进容器

第 12 章那句「换部署模式只改一行 filesystem(...)」里，沙箱是成本最高的一个选项：它把 AbstractFilesystem 的十一个方法全部翻译成 shell 命令，在容器里跑BaseSandboxFilesystem.java:38。文件没变，命令却需要一个真实的执行环境——于是多出一整套生命周期问题：容器归谁、跨 call 怎么复用、容器丢了怎么恢复、多个副本抢同一个用户怎么办。这一章按 acquire → start → exec → release 的顺序把它拆开，每个默认值都对到 2.0.4 的行号上。

读完你能做到

  • 说出 SandboxManager.acquire 的四条优先级，以及哪两条不会过并发闸门
  • 给定 (isolationScope, userId, sessionId, agentId)，推出容器复用的粒度，并知道 USER 缺 userId 时会降级成什么
  • 解释 AbstractBaseSandbox.start() 的四分支：什么条件只补 ephemeral 条目、什么条件从快照恢复、快照不可用时怎么降级
  • 判断「容器被删掉之后工作区还在不在」——默认答案是不在，因为 DockerFilesystemSpec 挂的是 NoopSnapshotSpec
  • 排查「沙箱起不来」「execute 一直 30 秒超时」「edit_file 在容器里失败」三类问题的定位顺序

先说为什么：一个容器要管三件事

官方给沙箱的理由是三条：宿主不被污染、能跑任意命令、能力可以横向复制sandbox.md:11。但代码里为了这三条写出来的东西分属三个互不相干的关注点，混看就会晕：

能力层：一个后端能不能跑
Sandbox 接口只有 9 个方法（start / stop / shutdown / close / isRunning / getState / exec / persistWorkspace / hydrateWorkspace）Sandbox.java:42，AbstractBaseSandbox 负责「怎么把容器拉起来并把工作区摆好」，具体后端只填 5 个 do* 抽象方法。
归属层：这次调用该用哪个容器
SandboxIsolationKey 把 scope + 上下文折成一个键SandboxIsolationKey.java:67， SessionSandboxStateStore 用这个键在你配的状态后端里存一份 SandboxState JSON，SandboxExecutionGuard 负责同一个键不许两个人同时进。
内容层：容器里那堆文件从哪来
WorkspaceSpec + layout 的七种条目是声明式的「开局文件树」，宿主工作区的 AGENTS.md / skills/ 靠一条投影条目按内容哈希增量同步进去。
最容易搞混的一对：stop 与 shutdown

stop() 只把工作区打包进快照、不销毁资源；shutdown() 才销毁后端资源（容器、临时目录），而且 只对 self-managed 的沙箱调用Sandbox.java:35。 框架侧的收口在 SandboxManager.release(...)：一旦这次是「你自己传进来的沙箱」（Priority 1）就直接 return，两个都不调SandboxManager.java:197； 自管的才依次 stop() → shutdown()，各自 try/catch 只 log.warn，互不阻塞:201-211。

自检三问

stop() 和 shutdown() 谁负责写快照、谁负责删容器？框架什么时候两个都不调？

stop() 只写快照（且快照 isPersistenceEnabled() 为假时连打包都跳过），并把 workspaceRootReady 标真AbstractBaseSandbox.java:131-141；shutdown() 才 docker stop --time=30 + docker rm --forceDockerSandbox.java:107-142。两个都不调的情况是 Priority 1：沙箱是你自己传进来的（externalSandbox），release() 一进来就 returnSandboxManager.java:193-199；另外 containerOwned 为假时 shutdown() 内部也会跳过删除只打一条 debugDockerSandbox.java:113-118。

为什么容器被删掉之后，下一次 call 不会走 Branch A 把空目录当成「工作区还在」？

两道保险。第一道在 Docker 层：doEnsureContainerRunning() 发现容器查不到时，会把 workspaceRootReady 置回 false 再新建容器DockerSandbox.java:511-516，于是 start() 走进的是 C 或 DAbstractBaseSandbox.java:99-114。第二道是探测本身：万一状态说「就绪」但目录不在（例如容器复用、卷被清空），test -d 失败同样落入 B 支去恢复快照，探测异常则当作「已丢失」并 warn:197-207。默认 Noop 快照下，B 支会降级成 D：静默重建一个干净工作区，这正是「东西没了但没有任何异常」的成因。

沙箱模式下，宿主改了一个 skills/foo/SKILL.md，容器里多久能看到？

下一次 call 的 start() 末尾——前提是内容哈希变了。投影在四条分支之后无条件尝试一次AbstractBaseSandbox.java:116，哈希 = SHA-256 over「相对路径 + 0x00 + 字节」WorkspaceProjectionApplier.java:50-88；相同就跳过，不同才 tar 灌进去并重写哈希:273-282。两个例外：投影被关掉、或该文件不在默认五个根（AGENTS.md、skills、subagents、knowledge、.skills-cache）里SandboxFilesystemSpec.java:41-42。另外哈希记在 SandboxState 里SandboxState.java:43，状态没持久化时每次 call 都会重灌一遍——行为正确，只是白花时间。
