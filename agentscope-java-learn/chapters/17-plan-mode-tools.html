17 · 计划模式、工具装配与 MCP

上一章讲「模型知道什么」，这一章讲「模型能碰什么」。三件事共用同一条时间线——都在 build() 里装配，都在每次工具调用前生效：计划模式用中间件把非只读调用换成一条 DENIED 结果；tools.json 用 allow/deny 在白名单层面裁剪工具面；MCP 在构建期把外部 server 的工具注册进同一个 Toolkit。三者叠在一起，才是「这个 agent 到底能做什么」。和官方文档的分歧集中在四处：白名单是 4 个还是 9 个名字、plan_exit 的参数叫什么、子 agent 到底继不继承只读限制，以及ToolsConfig.builder() 并不存在。

读完你能做到

  • 说清 enablePlanMode() 到底装了哪三样东西，以及三个默认值分别是什么
  • 背下计划模式真正放行的两类调用：工具自带 readOnly=true 与 9 个白名单名字，并能判断任意一个工具在 plan 阶段会不会被拒
  • 解释拒绝是怎么发生的（onActing 分流 + 合成 DENIED 结果），以及为什么模型还会继续看到全部工具定义
  • 画出 plan_exit 的两段式：先 ASK，批准后才执行 exit；并指出 DONT_ASK 下为什么会卡死
  • 说清计划状态的两处存储：AgentState.PlanModeContextState（可持久化）与 plans/PLAN.md（走文件系统）
  • 把 tools.json 的加载时机、字段、失败降级讲完整，并背下 ToolFilter 的三条语义
  • 说出 MCP 三种 transport 的字段映射、注册的同步语义，以及 required 与「零工具」两种边界

先说为什么：三个开关，管的是「一次任务能碰什么」

这三个机制经常被混为一谈，其实它们作用在三个不同层面：

计划模式：运行期的阶段开关
不改变工具清单，只在执行前按名字判断一次：这个调用现在能不能跑。被拒的调用不会执行，但会留下一条结果告诉模型「为什么被拒」PlanModeMiddleware.java:168-233。它是动态的：同一份工具面，进来出去是两种权限。
tools.json：构建期的白名单裁剪
在 build() 的最后一步，把不符合 allow/deny 的工具从 Toolkit 里物理删掉ToolFilter.java:86-140。模型连工具定义都看不到，谈不上调用。它是静态的：改配置要重新 build。
MCP：构建期的能力扩充
同样是 build()，但方向相反：连上外部 server，把它们的工具加进来McpServerRegistrar.java:60-103。注册完还会被上面的 ToolFilter 再过一遍。

这个顺序很重要：先注册 MCP，再应用 allow/deny（HarnessAgent:2766-2771 对 :2935-2937）。所以 tools.json 的 deny 能一刀砍掉某个 MCP 工具；反过来，allow 非空时也可能把没列进去的 MCP 工具一起砍掉——哪怕那个 server 自己在 enableTools 里点了名。

三者的优先级

从「最不容易被绕过」到「最容易被绕过」：tools.json 删掉的工具 > 计划模式拒绝的调用 > 提示词里的建议。前两者是确定性的代码路径，第三条只是话术。所以真正想禁止某个动作，永远优先用前两个。

最小可跑：两种开启方式，三个默认值

计划模式是默认关闭的。打开它只要一个方法：

                .name("planner")
                .model(model)
                .workspace(Path.of("./workspace"))

                .enablePlanMode()                        // 装三个工具 + 中间件

                .enableTaskList()                        // 可选：注册 todo_write
                .build();
Builder 方法默认值作用点

三个计划工具：一个只读入口、一个专用写口、一个 ASK 出口

三个工具都注册在同一个 toolkit 上，共享一个 PlanModeManagerHarnessAgent.java:2736-2741。它们都是 readOnly(false) + concurrencySafe(false)——所以它们能活下来，靠的不是「只读」豁免，而是白名单：

工具参数做了什么
plan_enter 无（{"type":"object","properties":{}}） 幂等进入：置 planActive=true，若还没有计划文件路径就填默认值，返回该路径PlanModeTools.java:86-101
plan_write content（必填，完整覆盖） 经 WorkspaceManager.writeUtf8WorkspaceRelative 写文件，并把路径记回 state:135-146
plan_exit summary（可选） 先过权限 ASK；批准后才 exit，并提示用 todo_write 拆任务:180-209

为什么单独造一个 plan_write，而不是把 write_file 放进白名单？看第二个参数就懂了：plan_write 只写一个路径——当前计划文件。它不接受 path，模型无法借它去改 src/main/java/...。把通用 write_file 放进来，等于在 plan 阶段交出了整个工作区的写权限。

文档里的 rationale 是错的

官方 plan-mode.md 的工具表把 plan_exit 的参数写成 rationaleplan-mode.md:45，而源码的 input schema 里只有一个 summaryPlanModeTools.java:162-174。按文档传 rationale 不会报错，只是被 schema 校验挡住或忽略——别在业务代码里依赖它。

拦截发生在 onActing：按名字分流，再合成一条 DENIED

计划模式的执行边界不在工具内部，而在中间件的 onActingPlanModeMiddleware.java:168-233。逻辑可以拆成五步：

  1. 先看阶段
    从 RuntimeContext 解析出 AgentState；planActive=false 或这一轮没有工具调用，直接 next.apply(input) 放行——计划模式在 BUILD 阶段是零成本的。
  2. 按名字分两堆
    每个 ToolUseBlock 走 isPermitted(name)，分别进 allowed 与 denied:179-187。注意：判断依据只有名字，不看参数。
  3. 给每个被拒的调用造一条结果
    ToolResultBlock.text(DENY_MESSAGE)，带上原调用的 id/name，状态设为 ToolResultState.DENIED，然后用 ToolResultMessageBuilder 包成一条 Msg 塞进 state.contextMutable():200-209。这一步很关键：上下文里必须有这条 tool result，否则下一轮模型会看到「自己发了调用但没有结果」，直接触发协议错误。
  4. 同时补三个流式事件
    ToolResultStartEvent → ToolResultTextDeltaEvent（正文就是拒绝文案）→ ToolResultEndEvent（状态 DENIED）:210-224。所以前端看到的不是「没反应」，而是一次明确的失败结果。
  5. 顺序：先拒绝，再执行
    deniedFlux.concatWith(next.apply(new ActingInput(allowed))):229-232。全部被拒时只返回拒绝流，不调 next。这是刻意的：模型先看到「这步不让做」，再看到允许的那几个跑完。

拒绝文案不是一行短提示，而是一整段带指令的话：告诉模型「你在 PLAN 模式（只读）」「可以调查、跑只读工具、用 plan_write 记录、准备好后调 plan_exit」「在计划获批前不要改文件或跑变更命令」PlanModeMiddleware.java:72-76。这就是它「不靠报错、靠话术」的纠偏方式。

工具定义并不会被藏起来

PlanModeMiddleware 只拦执行，不改 tool schema。所以模型在 plan 阶段依然看得到 write_file、edit_file 的完整定义，也依然可能去调——只是每次都会拿到 DENIED。想让它「看不见」，得用下一节的 tools.json。

到底放行了什么：两类调用，9 个名字

isPermitted 只有三个分支PlanModeMiddleware.java:235-242：命中 ALWAYS_ALLOWED、命中 additionalAllowed（就是 allowShellInPlanMode 那个）、或者 readOnlyResolver 返回真。

readOnlyResolver 是 build 时传进去的闭包：roToolkit.getTool(name).isReadOnly()HarnessAgent.java:2750-2753。因为捕获的是 Toolkit 实例、每次调用才求值，所以后注册的工具也能被正确判定——包括 MCP 工具。而 AgentTool.isReadOnly() 默认返回 falseAgentTool.java:111-113，@Tool(readOnly=...) 的默认值也是 falseTool.java:107。所以「只读」不是猜出来的，是每个工具自己声明的。

白名单的真实内容比文档多 5 个。源码是9 个名字PlanModeMiddleware.java:60-70： 

plan_enter, plan_write, plan_exit, todo_write,
agent_spawn, agent_send, agent_list,
task_output, task_list

为什么要把子 agent 与后台任务工具也放进来？因为「调查」这件事在长任务里经常要并发：主 agent 在 plan 阶段派几个只读的子 agent 去读不同模块，比串行读快得多。而 task_output/task_list 只是取结果，不改状态。反过来说——只要子 agent 自己没被限制，它就能替父 agent 干活。这一点下一节单独讲。

todo_write 可能根本不存在

todo_write 只有在 enableTaskList() 打开时才注册ReActAgent.java:5557-5561，而 HarnessAgent 默认不装。白名单里写着它，只是「如果存在就允许」，不是「帮你装上」。

提示词侧的三段话：PLAN 横幅、额外工具、BUILD 回流

光有硬拦截不够——模型得知道自己处在哪个阶段，否则会一直撞墙。onSystemPrompt 负责补三段提示，都是追加在现有 prompt 末尾：

时机追加内容要点
planActive=true <system-reminder>PLAN MODE is active (read-only). Plan file: %s … 给出计划文件路径；明确「只调查不改状态」；要求「决定写就同一步调 plan_write，不要只说『我将写计划』」；信息不足时停下来问一个具体问题，而不是编计划:78-94

第三行是本章最容易被忽略的细节：exit 只把 planActive 置假，保留 currentPlanFilePlanModeManager.java:79-83。于是之后每一轮系统提示都会带上「计划在 plans/PLAN.md」这句话——这是抗压缩设计：对话被压掉后，模型仍能从 prompt 里知道去哪找计划。

退出：一次 ASK，两段执行

plan_exit 和其它工具最大的不同，是它重写了 checkPermissions 并且永远返回 ASKPlanModeTools.java:185-192： 

return Mono.just(
        PermissionDecision.ask(
                "The agent wants to finish planning and start executing. Approve to"
                        + " continue in BUILD mode, or reject to keep planning."));

它不读规则、不看上下文，无条件问。原因写在 javadoc 里：这是一次「刻意的交接」，必须由人确认。批准之前 callAsync 不会执行，所以 manager.exit(state) 也就不会发生——模型仍然停在 PLAN，可以继续改计划再问一次。

第一段：ASK
权限引擎弹确认。用户的决定走的是父 agent 配置的 HITL 通道（控制台回调、HTTP 接口、前端按钮都行），和普通工具确认完全同一条路。
第二段：callAsync
批准后才跑：manager.exit(state) → 返回一段话，要求「现在开始执行」「用 todo_write 把计划拆成一条条」「保持恰好一个 in_progress」:196-208。
DONT_ASK 会让 plan_exit 永远批不下来

PermissionMode.DONT_ASK 的语义是「ASK 一律降级为 DENY」PermissionMode.java:34-38。而 plan_exit 只有 ASK 一条路，所以在无人值守模式下它会稳定地被拒，agent 永远出不了 PLAN。要么这类会话别开 plan 模式，要么用程序化 API 退出（下一节）。

状态与文件：一个进 AgentState，一个进工作区

计划模式有两个「存储」，职责完全不同，别混：

PlanModeContextStateplans/PLAN.md
存什么planActive + currentPlanFile计划正文（markdown）
存在哪AgentState，跟着 AgentStateStore 走PlanModeManager.java:24-38工作区文件系统（本机 / 沙箱 / 远端都好）
谁写PlanModeManagerplan_write → WorkspaceManager.writeUtf8WorkspaceRelative

路径规则很朴素：planFileDirectory 去掉首尾斜杠后拼 /PLAN.md；空值回落 "plans"PlanModeManager.java:41-58、:112-114。注释里还有一句值得记住：所有隔离范围都用同一个逻辑路径，隔离由文件系统层面（store namespace / sandbox snapshot key）实现，而不是把 userId 编进路径:33-37。

为什么不用 PermissionMode.EXPLORE

类注释直说了：EXPLORE 在 PermissionEngine 构造时被不可变快照下来，运行期翻不动；而计划模式必须能随时开关，所以另起了一套中间件PlanModeMiddleware.java:43-57。这也解释了为什么二者不能互相替代：EXPLORE 适合「整个会话都只读」，plan 模式适合「一个阶段只读」。

程序化 API：一个入口，一个静默陷阱

不做模型驱动、而是由业务代码控制进出，用这三组方法（每组都有 RuntimeContext 与 (userId, sessionId) 两个重载）HarnessAgent.java:327-339： 

RuntimeContext ctx = RuntimeContext.builder().userId("alice").sessionId("s-1").build();

agent.enterPlanMode(ctx);        // 立即写进 state 并持久化
agent.isPlanModeActive(ctx);     // true
agent.exitPlanMode(ctx);         // 直接退出，不经过 ASK
没开 enablePlanMode() 时，这两个方法什么也不会发生

看实现：planModeManager != null 才走 manager.enter，否则直接 setPlanActive(true)HarnessAgent.java:400-408。但中间件没装，就意味着没有横幅、没有拦截——状态位是真，防护是假。isPlanModeActive() 还会返回 true，特别容易让人误以为生效了。

另外两个语义差别值得记：程序化 exitPlanMode 不触发 HITL（管理台按钮不该弹确认），而模型调 plan_exit 一定触发；两边都会持久化（delegate.saveAgentState），所以跨会话续跑时状态是一致的。

子 agent：能力下传，状态强制传播

官方文档把这里写成「已知缺口：Plan Mode 期间通过 agent_spawn 启动的子 agent 不会自动继承只读限制」plan-mode.md:151-156。2.0.4 的源码已经不是这样了，它做了两层：

  1. 构建期：把能力装到子 agent 上
    自动构造子 agent 时，configurePlanMode 会把父的 planModeEnabled/allowShellInPlanMode/planFileDir 原样传给子 builderHarnessAgentBuilderSupport.java:598-618。注释解释了为什么必须这样：PlanModeMiddleware 和 PlanModeManager 是 build() 动态装的，只拷中间件列表根本拷不过去；如果只把 planActive 置真，等于「给了状态、没给守卫」:598-606。
  2. 运行期：父在 plan，子必进 plan
    真正拉起子 agent 之前，AgentSpawnTool.propagatePlanMode 会检查父 state：planActive 为真且子是 HarnessAgent，就直接对子调 enterPlanMode(userId, sessionId)AgentSpawnTool.java:739-746。注释特别强调新建和复用都要跑——一个常驻子 agent 可能是父在 BUILD 阶段创建的，父后来才进 plan 模式:732-738。

所以现在的真实语义是：能力继承 + 状态同步。但有个边界要说清——传播的是「父当前是否在 plan」，不是「父做过什么计划」。子 agent 的 currentPlanFile 是它自己 state 里的默认值（子工作区如果是隔离的，路径前缀也不同），它不会自动去读父的 plans/PLAN.md。想让子 agent 按父的计划干活，仍然要在 task 里把计划内容或路径告诉它。

为什么这一段值得单独讲

这是「文档落后于代码」的典型：如果按文档去写防御性代码（例如给每个子 agent 再手动开一次 plan 模式），在 2.0.4 上是重复劳动；反过来，如果按文档以为「反正子 agent 不受限」而放开 agent_spawn，又会低估 plan 阶段的边界。判断依据永远以源码为准。

tools.json：在哪、谁读、读不到怎么办

配置文件是工作区根目录下的 tools.json，常量名 WorkspaceConstants.TOOLS_JSONWorkspaceConstants.java:27。读取入口是 ToolsConfigLoader.load(wsManager)，走 readManagedWorkspaceFileUtf8，也就是说它和 AGENTS.md、MEMORY.md 走同一套 overlay 读取：远端有就用远端，否则用本地模板ToolsConfigLoader.java:57-74。

三个细节决定了你能不能在生产里用得住：

  • 读之前先做环境变量替换。${VAR} 用 System.getenv 替换；未设置的变量替换成空串，并且每个变量只 warn 一次ToolsConfigLoader.java:48、:96-116。所以 "Authorization": "Bearer ${GITHUB_TOKEN}" 可以安全地留在仓库里。
  • 读失败绝不抛异常。文件缺失、空白、读不到（沙箱/远端在 build 期还没上下文）、JSON 解析失败，统统返回 Optional.empty()，agent 带着默认 toolkit 继续构建:66-88。解析失败是 warn，读不到是 debug——后者很容易在日志里被忽略。
  • 优先级：编程覆盖 > 文件。toolsConfigOverride != null 时根本不读文件；disableToolsConfig() 则连覆盖带文件一起跳过HarnessAgent.java:2757-2765、:2290-2293。
沙箱/远端可能「读不到」，而且是静默的

ToolsConfigLoader 用 RuntimeContext.empty() 去读，而沙箱后端在 build 期可能还没有可用的调用上下文，于是走进 catch、打一条 debug、返回空ToolsConfigLoader.java:62-74。结果就是：你以为 tools.json 生效了，其实它的 allow/deny 一条都没应用。沙箱/远端场景请用 builder.toolsConfig(cfg) 兜底，别只依赖文件。

ToolFilter：三条语义与一次 warn

ToolFilter 只有两个公开方法：isAllowed(name, cfg) 判单个名字，apply(toolkit, cfg) 批量删。语义写在类注释里，一共三条ToolFilter.java:31-43：

① allow 非空 → 未列出的编目工具被删
「编目工具」指 filesystem / shell / web / memory 这些产品工具。判定顺序是先 deny、再 MCP 前缀、再平台豁免、最后 allow:55-80。注意 allow 非空时，defaultToolsEnabled 那一支走不通（它额外要求 allow 为空），所以「列了 3 个就只剩 3 个」是真的。
② 平台工具永远活过 allow，但活不过 deny
HarnessPlatformTools.isPlatformTool(name) 为真时，allow 砍不掉它；但 deny 在函数最前面就返回 false 了，所以显式 deny 仍然能关掉平台工具。这是刻意留的运维逃生口。
③ 两边都空 → 不动
apply 开头就判：!allowSet && !denySet && defaultToolsEnabled 直接 return:90-96。只有 mcpServers 的 tools.json 属于这一类，工具面完全不变。

还有两个工程细节值得记：

  • 写错名字只 warn，不中止。allow/deny 里出现当前没注册的工具名，会逐条 warn「references unknown tool」然后忽略:102-107、:142-151。所以「白名单没生效」第一件事是搜这条日志，而不是怀疑框架。
  • 结果会打一条 info。removed N tool(s); M remain: [..]，平台工具被额外保留时还会单独计数:124-139。这条 INFO 是确认「过滤器到底跑没跑」的最快证据。
过滤器也在别处被复用

技能那一章的最后一步「tools.json 可以 deny loader」不是比喻：build() 计算 shellToolAvailable 时就是直接调 ToolFilter.isAllowed("execute", resolvedToolsConfig)HarnessAgent.java:2867-2873，据此决定技能的 files-root 走 noShell() 还是本地/沙箱模式。一个 allow 列表会连带改变技能注入的 XML。

mcpServers 是一个 Map<String, McpServerConfig>，键就是 server 名。字段刻意对齐标准 MCP 客户端配置，方便工作区在 AgentScope 与其它 MCP 工具之间迁移McpServerConfig.java:25-39：

注册流程：同步、逐条、失败分两级

McpServerRegistrar.register 在 build() 里被调用一次HarnessAgent.java:2766-2771，整个过程是同步阻塞的：一个 server 建好、连上、注册完，才轮到下一个McpServerRegistrar.java:44-67。单个 server 的内部顺序是：

  1. 建客户端
    McpClientBuilder.create(name) → 按 transport 配置 → 可选 timeout → buildAsync().block():176-203。注意这里是阻塞的：一个连不上的 server 会把 build() 卡到超时。
  2. 初始化 + 列工具
    wrapper.initialize().block()，然后 listTools().block() 拿全量工具名，逐个过 isToolEnabled:125-137。
  3. 零工具就关掉
    过滤后一个都不剩时，wrapper.close() 然后 return——不注册、也不报错:134-137。外层仍会发一条 SUCCESS 给监听器，因为「连上了但你没要任何工具」不算失败。
  4. 注册进 Toolkit
    toolkit.registration().mcpClient(wrapper).enableTools(selected)；prefixToolNames 为真时再 mcpToolNamePrefix(name + "__")；最后 apply():138-141。

失败分两级，这一层设计得很清楚：

required: false（默认）

  • 给监听器发 FAILED
  • 如果配了 connectionFailureHandler 就回调它
  • 打一条 warn（只记异常类名，不记消息）
  • 继续下一个 server:84-100

required: true

  • 先 toolkit.closeMcpClients() 把已经连上的全部关掉
  • 抛 McpConnectionException，build() 直接失败
  • 异常消息只有 "MCP connection failed: " + serverName，不含 endpoint 与凭据McpConnectionException.java:18-27

监听器本身是尽力而为的：onCompleted 抛异常只会被 warn 掉，不影响注册，也不影响后面的 serverMcpServerRegistrar.java:105-119。结果对象 McpServerRegistrationResult 的构造器还强制两条不变量：SUCCESS 不许带 cause，非 SUCCESS 必须有 causeMcpServerRegistrationResult.java:30-49。

谁负责关连接

HarnessAgent.close() 里有一行 ownedMcpToolkit.closeMcpClients()HarnessAgent.java:465-473。所以 stdio 拉起来的子进程会随 agent 关闭而回收——别忘了 try-with-resources 或显式 close()，否则 npx 进程会一直挂着。

MCP × allow/deny：三个交叉陷阱

MCP 工具注册完之后还要被 ToolFilter 过一遍，两者交叉出三个容易踩的点：

  1. 陷阱一：开了 allow，MCP 工具神秘消失
    isAllowed 里那条 MCP 豁免要求两个条件同时成立：!strictAllow，以及某个 server 开了 prefixToolNames 且名字以 <server>__ 开头ToolFilter.java:67-76。默认 prefixToolNames=false，工具名是裸的，于是落进「allow 非空但没列我」那一支——被删。两种解法：开前缀，或把 MCP 工具名也写进 allow。
  2. 陷阱二：deny 永远赢
    deny.contains(name) 是函数第一支，排在平台豁免和 MCP 豁免之前。所以 deny: ["mcp__danger"] 之类的前缀写法不生效——这里只做精确匹配，没有通配。要屏蔽整台 server 的工具，只能逐个列名，或者干脆把它从 mcpServers 里删掉。
  3. 陷阱三：声明式子 agent 的 tools: 更严
    子 agent 的 tools: [..] 会被转成一个新的 ToolsConfig：strictAllow=true、defaultToolsEnabled=false、allow 只保留「父也允许」的那些；deny 与 mcpServers 从父继承HarnessAgentBuilderSupport.java:287-305、:542-543。因为 strictAllow=true，平台工具不再豁免：子 agent 的 tools: 里没写 agent_spawn，它就真的没有。

装配：build() 里这四段谁先谁后

只保留与本章相关的段落，顺序是固定的：

#代码位置做了什么影响
1HarnessAgent:2735-2755若 planModeEnabled：建 PlanModeManager、注册三个工具、装 PlanModeMiddleware（带 readOnlyResolver 闭包与额外放行集合）此时 MCP 还没注册，但闭包按调用时求值，所以后面注册的工具也能判定
2HarnessAgent:2757-2771解析 ToolsConfig（override > 文件 > 无），再调 McpServerRegistrar.registerMCP 工具在此刻进入 toolkit；失败可能中止 build
3HarnessAgent:2773-2931技能四层合成、自学习设施、ShellPathPolicy、HarnessSkillMiddleware其中 shellToolAvailable 会调用 ToolFilter.isAllowed，受第 2 步的配置影响

最后一步之后再没有工具注册，所以 apply 的结果就是模型看到的结果。反过来说：任何在 build 之后动态加进 toolkit 的工具都不受 allow/deny 约束——包括你在运行时手动 registerTool 的东西。

陷阱与窍门

陷阱 1：开了 plan 模式，模型却什么都能干

两种可能：① 你只调了 agent.enterPlanMode(ctx)，却没在 builder 上 enablePlanMode()——中间件根本没装；② 你用的是 enterPlanMode 之后又手动重建了 agent（子 agent 或者新的 builder），新实例的 planActive 默认为假。先看 isPlanModeActive，再看有没有 PlanModeMiddleware。

陷阱 2：以为 plan 阶段能「先小改一下」

write_file/edit_file 在 plan 阶段一律被拒，包括改一个错别字。真要改，只能走 plan_write（只改计划文件），或者先 plan_exit 拿批准。

陷阱 3：无人值守 + plan 模式 = 卡死

PermissionMode.DONT_ASK 把 ASK 降成 DENY，而 plan_exit 只会 ASK。结果：模型反复请求退出、反复被拒、直到耗尽 maxIters。批量任务要么别让它进 plan，要么用程序化 exitPlanMode 退出。

陷阱 4：allow 白名单把 todo_write 砍了

它不在平台豁免名单里，readOnly 也是 false。表现是：plan 退出后模型说「我会拆任务」，但从来没调过工具——因为工具不存在。检查 ToolFilter 那条 INFO 日志里的 remain 列表。

陷阱 5：MCP 的 enableTools 写对了，工具还是没出现

先确认 server 名与工具名都没写错（写错只是被过滤，不会报错），再确认 defaultToolsEnabled 没被误设成 false，最后看 tools.json 的 allow 是否把它砍了（默认 prefixToolNames=false 时没有 MCP 豁免）。三步都没问题，就去看是不是 build 期根本没读到文件。

陷阱 6：一个可选 MCP server 拖慢了整个 build

注册是同步且逐条的，每个 server 都要 initialize().block() + listTools().block()。给每个条目配 timeout/initializationTimeout，并评估是否真需要放在主 agent 上（也可以用 tools.json 只给子 agent）。

陷阱 7：以为声明式子 agent 会自动继承平台工具

声明式 tools: [read_file] 会生成 strictAllow=true 的配置，平台工具不再豁免——子 agent 不能派孙 agent、不能写 todo。需要协作能力就把对应名字写进 tools:，并确保父的配置也允许它们。

自检三问

1. plan 阶段下，read_file、web_search、execute、agent_spawn 四个调用分别放行吗？

放行 / 放行 / 默认拒绝（除非 allowShellInPlanMode()）/ 放行。前两个靠 readOnly=true，第三个因为双用途且默认非只读，第四个在白名单里——而且它拉起的子 agent 会被 propagatePlanMode 同样置为 plan。

2. tools.json 写 "allow": ["read_file"]，agent_spawn 和 todo_write 还在吗？

agent_spawn 在（平台工具豁免 allow）；todo_write 不在（不在平台名单，allow 非空且未列出→被删）。同理，所有 MCP 工具默认也不在（prefixToolNames=false 时无豁免）。

3. MCP 条目写了 "transport":"stdio" 但没写 command，会发生什么？

buildClient 先校验 transport（合法），再进 configureStdio；那里发现 command 空白，抛 IllegalArgumentException("stdio MCP server 'x' requires a 'command'.")。然后看 required：为假则 warn + 继续构建，为真则关掉已连 client 并中止 build。
