10 · ReActAgent 还是 HarnessAgent：把主循环拆开看

前 9 章的每一段代码都是 ReActAgent.builder()，而官方 quickstart 一上来就是 HarnessAgent.builder()。这不是两个框架，也不是版本差异——它们是同一颗引擎的两种装配： HarnessAgent 的字段里就躺着一个 ReActAgent delegate。这一章先把 call() 一次到底怎么跑拆到行，再回头看 Harness 在哪些接缝上加东西，最后给出能落地的选型标准。

读完你能做到

  • 一句话说清两者关系：同一颗 ReAct 引擎，HarnessAgent 是外壳而不是替代品
  • 照着源码走完一次 call()：从 runLifecycle 到 reasoning、acting、下一轮，说出每个终止出口的 GenerateReason
  • 知道 maxIters 触顶后为什么是「多调一次模型做摘要」而不是抛异常，ExceedMaxItersEvent 又在哪里发
  • 分清 interrupt() 的 USER / SYSTEM 两条路，以及它跟 HITL 暂停、中间件 stop、优雅停机的区别
  • 拿到选型标准：什么项目 core 就够，什么项目直接上 harness，迁移时哪三件事不等价

先说为什么：一个引擎，两种装配

ReActAgent 回答的是「一次请求 → 推理 → 工具 → 回复」；HarnessAgent 回答的是另一组问题： 多轮怎么接上、上下文怎么不爆、多用户怎么隔离、危险操作怎么先审后跑、可复用的能力怎么沉淀。 官方把后者叫作「一层薄包装」architecture.md:7，这个说法在代码里能直接对上：HarnessAgent 的构造器以已经建好的 delegate 为首参，另接收 workspace、sandbox、skill、plan-mode、memory、distributed store 等十几项装配产物HarnessAgent.java:205-224， 而 build() 的最后一步就是 inner.build() 造出这个 delegateHarnessAgent.java:2948。

fromAgent 不是等价迁移，官方 javadoc 自己写了

如果你已经有一个 ReActAgent，想「升级」成 Harness，HarnessAgent.Builder.fromAgent(agent) 能搬过去姓名、模型、提示词、maxIters、toolkit 副本、stateStore、重试配置和中间件。但 javadoc 明说： 搬完并不行为等价——Harness 会额外装 workspace 投影、tracing、默认 skill / subagent 中间件； 而且如果原 agent 没配 stateStore，Harness 会默认补一个 JsonFileAgentStateStore，把「不落盘」变成「落盘」HarnessAgent.java:1417。迁移前先把这两条想清楚。

最小可跑：同一件事，两种写法

先别管 Harness 的那些能力。下面这个类用同一个工具、同一个提示词、同一个 session，分别建一个 ReActAgent 和一个 HarnessAgent，各问一次「现在几点」。跑完你就能直观看到：代码几乎一样， 差别在你没写的那部分。 

import io.agentscope.core.ReActAgent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.tool.Tool;
import io.agentscope.core.tool.Toolkit;
import io.agentscope.harness.agent.HarnessAgent;

import java.nio.file.Paths;

public class SameTask {

    /** 同一个工具，两边共用 */
    static class ClockTools {
        @Tool(name = "now", description = "返回当前时间")
        public String now() {
            return "2026-11-04T09:00:00+08:00";
        }
    }

    static Toolkit toolkit() {
        Toolkit toolkit = new Toolkit();
        toolkit.registerTool(new ClockTools());
        return toolkit;
    }

    /** A. 裸引擎：只给算法，持久化 / 压缩 / 工作区全由你负责 */
    static ReActAgent bare() {
        return ReActAgent.builder()
                .name("clock")
                .sysPrompt("你只回答时间问题，需要时间就调用 now。")
                .model("dashscope:qwen-plus")
                .toolkit(toolkit())
                .maxIters(5)
                .build();
    }

    /** B. Harness：同一颗引擎，外加工作区 / 持久化 / 压缩 / 文件与记忆工具 / 子 agent */
    static HarnessAgent harnessed() {
        return HarnessAgent.builder()
                .name("clock")
                .sysPrompt("你只回答时间问题，需要时间就调用 now。")
                .model("dashscope:qwen-plus")
                .toolkit(toolkit())
                .workspace(Paths.get(".agentscope/workspace"))
                .build();
    }

    public static void main(String[] args) {
        RuntimeContext ctx = RuntimeContext.builder()
                .userId("alice").sessionId("s-10").build();

        ReActAgent a = bare();
        System.out.println("[core]    " + a.call("现在几点？", ctx).block().getTextContent());

        try (HarnessAgent b = harnessed()) {
            System.out.println("[harness] " + b.call("现在几点？", ctx).block().getTextContent());
        }
    }
}

逐行解读：一次 call() 到底走了哪些路

这一节全部对着 ReActAgent 读。Harness 不在这条路上——它只是提前把东西装好，真正跑起来还是调 delegate 的这套循环。先把「外壳」和「循环」分开看，后面才不会把 onAgent、onReasoning、 acting 混成一锅。

1. 外壳：一次调用先过五道关

call() 最终都会落到 runLifecycle(msgs, doCallFn)AgentBase.java:256。它做的事可以按顺序记成五步，顺序不能换：

  1. acquire 执行许可
    Mono.using(this::acquireExecution, ...)，拿到这次调用的执行句柄，并在结束时释放。并发上限、 运行中标记都在这一层。
  2. 建 RunControl，决定「排队还是取消」
    每次调用一个 RunControlRunControl.java:28。没被外部托管时先 queue()，状态从 CREATED 变 QUEUED； 真正开跑时 start() 变 RUNNING。中断能不能生效，取决于此刻状态（见后半章）。
  3. 按 session 串行化
    callSerializationKey(rc)ReActAgent.java:727 返回 (userId, sessionId) 槽位，serializeOnKeyAgentBase.java:374 让同会话的调用排队、不同会话并行。所以同一个 session 并发发两次，是先后执行，不是一起跑。
  4. preCall → doCall → postCall
    notifyPreCall 里会 seedSystemMsg()，这也是 onSystemPrompt 中间件唯一的触发点； 然后才是 doCallFn（就是后面的 ReAct 循环）；最后 notifyPostCall 处理最终消息与存盘。
  5. 收尾：存状态、退注册
    正常结束 finish(COMPLETED)、异常 FAILED、取消 CANCELLED； 无论哪种，都会从优雅停机的注册表里退掉，并释放 session 队列槽位。
call / streamEvents同一个入口：buildAgentStream 把整次调用包成 AgentStartEvent … AgentResultEvent … AgentEndEvent
onAgent 中间件链只包一次；call 与流式共用，不会各跑一遍
runLifecycleacquire → RunControl → 同 session 串行 → preCall / doCall / postCall
ReAct 循环reasoning(iter) → acting(iter) → reasoning(iter+1) …直到某个出口

2. 循环入口：coreAgent() 与 resumeAgent()

进入循环前，doCallInner 先看一眼上一次是不是留下了「有 tool_use、没有 tool_result」的挂起调用。没有就 coreAgent() → executeIteration(0) → reasoning(0, false)；有就 resumeAgent() → acting(0)，跳过推理直接执行工具。这就是「同一 session 第二轮 还能接着上次工具跑」的底层机制，也是 07 章状态持久化的实际用途。

两个入口：ReActAgent.java:2384 / ReActAgent.java:2392；挂起判断与恢复：ReActAgent.java:1821

3. reasoning：先判触顶，再拼输入，最后决定去 acting 还是结束

reasoning(iter, ignoreMaxIters) 的第一行就是触顶检查：iter >= maxIters 直接跳 summarizing()，不再调模型做正常推理。没触顶才继续：firePreReasoning 拿输入 → 用 prependSystemMessage 拼 system → 取工具 schema → 过 onReasoning 中间件链 → 消费整条事件流 → buildFinalMessage() 得到这一轮的消息。

拿到消息后只有 四个分支，都写在 runPostReasoningPipeline 里：

gotoReasoning 能绕过 maxIters

那一行是 reasoning(iter + 1, true)：ignoreMaxIters=true。 也就是说，一个还在用 1.x Hook 的 PostReasoningEvent#gotoReasoning() 如果每次都请求重来， 这个循环可以永远不触顶。中间件没有这个入口（RequestStopEvent 只能停不能重来），所以新代码不会踩； 接老代码时要检查这里。

4. isFinished：三条判定，比想象的严格

isFinished(msg) 只有三步：消息为 null → 结束；带 ToolUseBlock → 不结束（要去 acting）；否则看有没有非空白的 TextBlock。所以「模型只输出了思考、正文为空」不算结束： 框架会补一条 synthetic 的 empty_response 提醒，然后回到 reasoning 再来一轮，直到有正文或触顶。 这个设计是为了防止推理模型把答案全写进 thinking 通道、content 为空时 agent 静默返回空串。

synthetic 提醒的构造：ReActAgent.java:4131；补提醒的位置：ReActAgent.java:2580

5. acting：先看有没有要跑的，再分三档放行

acting(iter) 上来先 extractPendingToolCalls：一条都没有，说明上一轮是纯文本回答，这时它不会直接结束， 而是检查「最近那批工具是不是全被拒了」，是就走全拒专用链，否则 executeIteration(iter + 1) 再问模型一轮。挂起调用非空才真的执行：firePreActing → 权限门 evaluatePermissions，把每个调用分成三档： ALLOWED 立即跑、ASKING 让整批暂停、DENIED 直接写一条 DENIED 结果。

跑完之后，结果按「有没有跑成」分成两组：isSuspended() 的进 pendingPairs，其余进 successPairs。接下来的分流就是主循环最后的岔路口：

「成功」与「没抛出异常」不是一回事

executeToolCalls 对工具异常是吞掉并转成 error 结果的：任何一个工具超时、抛异常， 都会变成该调用的 ToolResultBlock.error(...)，然后照常回到模型。所以一次 call() 正常返回，不代表工具成功过——要看 ToolResultBlock.getState()（SUCCESS / ERROR / DENIED / INTERRUPTED）。 只有 InterruptedException 会继续往上抛，交给中断收尾。

6. 递归就是循环：九个出口，一张表收全

源码里没有 while，下一轮就是 executeIteration(iter + 1) 再进一次 reasoning。 好处是每一轮都是同一条 Reactor 链，不会压栈；代价是调用栈展开后日志很长，排查时要靠 iter 和事件里的 replyId 对。整棵循环一共九个出口，认全了就不会再问「为什么它没停 / 为什么它返回 null」。

触顶：不是抛异常，是多调一次模型写总结

maxIters 的默认值是 10ReActAgent.java:4806，它数的是推理轮数，不是工具调用次数，也不是模型调用次数。第 iter 轮入口发现 iter >= maxIters，就进 summarizing()，做四件事：

  1. 先补挂起工具的结果
    还没执行的 tool_use 会被逐条补一条 error 结果：Tool execution cancelled because maximum iterations limit (N) was reached。 不补的话，上下文中会留下「有 use 没有 result」的非法状态，下一轮直接报错。
  2. 追加一条「请你总结」的用户消息
    prepareSummaryMessages 在现有上下文后面加一条固定英文指令：You have failed to generate response within the maximum iterations. Now respond directly by summarizing the current situation.
  3. 发 ExceedMaxItersEvent，然后调摘要模型
    事件在调模型之前发：new ExceedMaxItersEvent("", maxIters, maxIters)。注意第一个参数 replyId 传的是空串，第三个参数 currentIter 也传的 maxIters——所以 getCurrentIter() 拿到的是上限，不是真实轮次。摘要请求本身不带工具 schema， 也不再经过 onReasoning，只经过 onModelCall。
  4. 把摘要消息标成 MAX_ITERATIONS 写回上下文
    摘要失败也不抛：handleSummaryError 会造一条 SUMMARY_FAILED 元数据 + MAX_ITERATIONS 的消息作为最终回复，内容形如 Maximum iterations (N) reached. Error generating summary: ...。

summarizing()：ReActAgent.java:3862；发事件：ReActAgent.java:3892；摘要流：ReActAgent.java:3965；失败降级：ReActAgent.java:4071；事件字段：ExceedMaxItersEvent.java:43

因为不抛异常，业务代码不能靠 try/catch 发现触顶。两种可靠的判断方式： 

import io.agentscope.core.event.ExceedMaxItersEvent;
import io.agentscope.core.message.GenerateReason;
import io.agentscope.core.message.Msg;

// 方式一：非流式，看返回消息的 GenerateReason
Msg reply = agent.call("把这三个文件都改一遍", ctx).block();
if (reply != null && reply.getGenerateReason() == GenerateReason.MAX_ITERATIONS) {
    System.out.println("触顶了：这条是摘要，不是干活结果");
}

// 方式二：流式，抓事件（事件先于摘要模型调用发出）
agent.streamEvents("把这三个文件都改一遍", ctx)
        .doOnNext(ev -> {
            if (ev instanceof ExceedMaxItersEvent e) {
                System.out.printf("触顶：%d/%d%n", e.getCurrentIter(), e.getMaxIters());
            }
        })
        .blockLast();
调 maxIters 的两个经验

第一，maxIters(1) 会正常执行一次 reasoning(0)，只有需要下一轮时才进入摘要；只有 maxIters(0) 才会首次调用就跳过推理直接走摘要，你会看到一次莫名其妙的模型调用和 MAX_ITERATIONS。第二，触顶开销不是零：补工具结果 + 一次完整摘要调用都要花钱， 所以它的定位是「兜底」而不是「省 token 的手段」。真要在预算上设闸，用 09 章的中间件在 onModelCall 里计数更直接。

中断：同一个信号，两条收尾路径

中断不是杀线程。interrupt() 只是把 InterruptControl 里的标记置上，真正的检查点由循环自己埋： 每个模型 chunk 之前 concatMap(chunk -> checkInterrupted().thenReturn(chunk))，每轮开始前一次 checkInterrupted()。一旦命中就抛 InterruptedException，走统一错误处理。 这也是为什么工具执行中间中断不会立刻停：工具在自己的线程里跑，循环要等这次工具批次结束、回到流里才会看到标记。

更要紧的是 RunControl 的状态机：只有 RUNNING 才是「协作式中断」，还没开跑的 （CREATED / QUEUED）直接 cancel()，抛 CancellationException。所以「刚提交就中断」和「跑到一半中断」，调用方看到的结果不一样。 

import io.agentscope.core.ReActAgent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;

public class InterruptDemo {

    public static void main(String[] args) throws Exception {
        ReActAgent agent = ReActAgent.builder()
                .name("long-job")
                .sysPrompt("用户让你跑慢任务时，调用 slow_task 一次。")
                .model("dashscope:qwen-plus")
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("alice").sessionId("s-10-int").build();

        Thread worker = new Thread(() -> {
            Msg r = agent.call("跑一下慢任务", ctx).block();
            System.out.println("[result] " + r.getGenerateReason()
                    + " / " + r.getTextContent());
        });
        worker.start();

        Thread.sleep(1_000);
        // 只停 alice / s-10-int 这一条；同 agent 上的其他会话不受影响
        agent.interrupt(ctx, new UserMessage("User", "停一下，我要换参数"));
        worker.join();
    }
}

收尾时分两条路，取决于 InterruptSource：

InterruptSource.USER：给人看的恢复

  • 先把挂起的 tool_use 补成 error 结果（synthesizeErrorResultsForPendingToolCalls）
  • 再写一条 assistant 消息：I noticed that you have interrupted me. What can I do for you?
  • 标记 GenerateReason.INTERRUPTED，然后存盘
  • 存盘失败只 warn，不覆盖这次中断结果

InterruptSource.SYSTEM：给进程看的退出

  • 由优雅停机管理器发起，带上 SHUTDOWN_REQUEST_ID_KEY
  • 不写恢复消息，直接抛 AgentShuttingDownException
  • 中断时观察到的请求会先登记，交给停机流程统一存盘
  • 客户端重试同一句时，重复输入会被丢弃，从已保存的状态续跑

为什么你的中间件在最外层

HarnessAgent.Builder.middleware(...) 是立即把实例转给内部的 inner 的，而内置中间件要等到 build() 里才一个个加上去。大家都没改 order()（默认 1）时， List.sort 是稳定排序，先注册的排前面，而 index 0 又是最外层——所以你的中间件拿到的是「最完整的包装权」。 想插到内置链内层，才需要把 order() 调到比 1 小。

builder 的 97 个方法可以分两类记：转发型（name、model、toolkit、 maxIters、stateStore、middleware、hook……会把值同步给内部 builder）和 Harness 专有（workspace、filesystem、subagent、 skillRepository、compaction、enablePlanMode、channel……）。 遇到不确定的，先看它有没有同名方法在 ReActAgent.Builder 上：有就是转发，行为一致。

选型：什么时候 core 就够，什么时候直接上 Harness

别按「高级 / 低级」选，按谁拥有状态和资源选。ReActAgent 假设进程活着、状态由你管； HarnessAgent 假设进程会重启、会话要续、工具要能碰磁盘。

选 ReActAgent

  • 一次性的批处理 / 脚本 / 评测：跑完就退出，不需要跨进程记忆
  • 业务已经有自己的状态层、审计、文件抽象，不想被再包一层
  • 要精确控制每一次模型调用，中间件自己写、工具自己注册
  • 单元测试：不希望默认往 ~/.agentscope/ 写东西

选 HarnessAgent

  • 要做一个「能一直用」的助手：多轮、多用户、重启后还记得
  • 要让模型读写工作区文件、跑 shell、派子 agent、装技能
  • 上下文会超：需要压缩、大结果卸载、记忆沉淀
  • 要接 Channel / 网关，把同一个 agent 挂到多个入口

一句话：写库、写脚手架、写评测 → core；写产品 → harness。两者也可以混：用 Harness 管会话与工作区， 需要拿底层能力时通过 getDelegate() 拿到内部 ReActAgent（比如读 getToolkit()、 调 getAgentState(ctx)）。

从 ReActAgent 迁到 Harness，三件不等价的事

一，磁盘。原 agent 没配 stateStore 时是纯内存，Harness 会默认补 JsonFileAgentStateStore，测试之间可能串状态——单测里显式 .stateStore(new InMemoryAgentStateStore()) 盖掉。二，系统提示词。 workspace 上下文中间件会往 system prompt 里追加 AGENTS.md 等内容，模型行为会变。 三，事件数量。多出的 tracing / transcript / 记忆中间件会多出事件与模型调用，按次数断言的老测试会挂。

陷阱与窍门

1. 把 maxIters 当成「工具调用次数」
你会看到
设了 maxIters(5)，以为能跑 5 个工具，结果模型在第 5 轮就收到「请总结」，任务只做了一半。
因为
它数的是推理轮数。一轮里模型可以发多个工具调用，全算一轮；反过来，纯聊天没有工具，也在消耗轮数。
改成
按「最坏情况下要几轮推理」估，而不是工具个数；生产环境给到 20–30 很常见，靠中间件预算或业务超时兜底。
2. 想用 try/catch 抓触顶
你会看到
任务没做完，call() 却正常返回了一段「总结」，代码以为成功，把摘要写进了数据库。
因为
触顶不抛异常：summarizing() 会多调一次模型写总结，把结果标成 MAX_ITERATIONS 返回。
改成
落库前判 reply.getGenerateReason() == GenerateReason.MAX_ITERATIONS；流式场景抓 ExceedMaxItersEvent。
3. 中断后立刻用同一 session 重试，拿到 IllegalStateException
你会看到
异常信息里带着一串 xxx (id=toolu_...)，提示这些工具调用还在 ASKING 状态，需要批准。
因为
HITL 暂停时，工具被标成 ASKING 并持久化了。下一次 call 如果没带 Msg.METADATA_CONFIRM_RESULTS，框架拒绝继续。
改成
要么带 ConfirmResult 续跑；要么换新 session / 清掉持久化状态；要么显式打开 enablePendingToolRecovery(true) 让孤立调用被补成 error 结果。
4. 用无参 interrupt() 停会话
你会看到
多用户环境下，用户 A 点了「停止」，停掉的却是默认会话；或者根本没反应。
因为
无参重载固定落到 defaultSessionId 槽位，和 A 的 (userId, sessionId) 不是同一个。
改成
永远从请求里带出 RuntimeContext，用 interrupt(ctx, msg)。
5. 以为 fromAgent 是「原样升级」
你会看到
迁完之后测试目录多出 ~/.agentscope/state/，两个用例互相污染；模型回答也开始提「工作区」。
因为
Harness 默认补 JsonFileAgentStateStore，并额外装 workspace / tracing / skill / subagent 中间件。
改成
迁移时显式指定 stateStore（测试用 InMemoryAgentStateStore），并把「多了一层提示词」写进验收标准。
6. 指望 checkRunning(true) 防重入
你会看到
连着点两次提交，两个请求都开跑，会话上下文交错。
因为
ReActAgent.Builder.checkRunning(boolean) 是个空实现，参数被直接忽略；父类那个带 checkRunning 的构造器也已废弃并忽略它。
改成
同 session 串行靠框架自带的 callSerializationKey；要限并发，就用 RunControl / 业务层队列。

自检三问

maxIters(3) 最多会调几次模型？

4 次：3 次正常推理，加 1 次触顶后的摘要。如果某一轮模型直接给出非空正文（没有工具调用），会提前结束， 可能只有 1 次。注意摘要那次不带工具 schema，也不经过 onReasoning，只经过 onModelCall。

用户中断之后，call() 返回什么？

如果调用已经进入 RUNNING，返回一条 GenerateReason.INTERRUPTED 的 assistant 消息，内容是 「I noticed that you have interrupted me. What can I do for you?」，并且挂起的工具已补成 error 结果。 如果还在排队（QUEUED），则走 cancel()，抛 CancellationException，不会返回消息。

HarnessAgent 上自己加的中间件，和内置中间件谁先跑？

你的先。你的中间件在 build() 之前就转给了内部 builder，内置的在 build() 里才追加； 同 order（默认 1）时稳定排序保留注册顺序，所以你的在最外层。想反过来，只能调 order()。

30 分钟动手练习

  1. 看一次触顶的完整现场
    把 SameTask 的 maxIters 改成 2，挂一个只重写 onReasoning 的中间件打印 messages().size()，再用 streamEvents 抓 ExceedMaxItersEvent。你应该看到： 正常推理 2 次、事件 1 次、摘要调用 1 次，且摘要那次没有触发你的 onReasoning。
  2. 只停一个会话
    同一个 ReActAgent 上，用两个不同的 RuntimeContext（alice/s-1 与 bob/s-2）并发跑慢任务，1 秒后只 interrupt(aliceCtx, msg)。确认 bob 正常跑完。再换成无参 interrupt()，观察它停的是谁——这就是为什么这个方法被废弃。
  3. 把同一颗引擎换个壳
    用 HarnessAgent.Builder.fromAgent(bareAgent) 把练习 1 的 agent 迁过去，加上 .workspace(...) 跑一轮，然后对比：磁盘多了哪两棵树、系统提示词里多了什么、 streamEvents 的事件数变化。把差异记下来，下次选型就不用猜。
