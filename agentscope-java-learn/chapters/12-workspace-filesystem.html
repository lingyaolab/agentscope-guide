12 · 工作区与文件系统：agent 的手能伸到哪

第 11 章那个笔记 Agent 里，工具是自己写 Files.writeString 的——路径、权限、并发全靠你。 HarnessAgent 不这么干：它把「读文件、写文件、跑命令」收敛成一个 AbstractFilesystem 接口，然后在上面叠了三层东西——路径边界、两层合并、后端实现。 换部署模式（本机 / 共享存储 / 沙箱）只改一行 filesystem(...)，模型看到的工具名一个都不变。 这一章把这三层拆开，每个默认值都对到 2.0.4 的行号上。

读完你能做到

  • 说清 .filesystem(...) 的四种写法各自的产物是什么对象，不写的时候默认拿到哪一个
  • 判断一次 write_file("note.txt") 到底落在磁盘哪个位置：namespace 前缀、overlay 上层、PathPolicy 各管哪一段
  • 解释 overlay 的 copy-on-write：为什么读得到项目里的文件、写却永远进 workspace，删下层文件为什么会失败
  • 用 LocalFsMode + PathPolicy 把 agent 能碰的宿主目录收紧到白名单，并知道 /note.txt 这种写法为什么没出 workspace
  • 排查「AGENTS.md 没被注入」「workspace 上下文被截断」「@path 没展开」这三类问题的定位顺序

先说为什么：为什么「手」要单独做一层

官方给的理由是一句话：所有文件工具和可选的 execute 都从同一个抽象走，于是能在三种部署模式之间切换而不改 agent 代码filesystem.md:9。 但这句话背后其实有三个互相独立的关注点，混在一起写就会变成一坨 if：

工具层：模型看到的世界
read_file / write_file / edit_file / grep_files / glob_files / list_files，外加可选的 execute。它们只认 AbstractFilesystem 的 11 个方法FilesystemTool.java:111。
边界层：这只手能够到多远
LocalFsMode 决定绝对路径怎么解释，PathPolicy 是绝对路径的白名单， NamespaceFactory 决定相对路径前面加不加 alice/。PathPolicy.java:99
合并层：两份根目录怎么变成一份视图
OverlayFilesystem（workspace 盖住 project）、CompositeFilesystem（按前缀路由到 KV）、ProjectAwareOverlay（写按路径类型分流）。
后端层：字节真正存在哪
LocalFilesystem / LocalFilesystemWithShell / RemoteFilesystem（KV）/ SandboxBackedFilesystem（容器）。沙箱那一族在第 13 章。
最关键的分工：路径是「字符串」，不是「磁盘位置」

AbstractFilesystem 的每个方法第一个参数都是 RuntimeContextAbstractFilesystem.java:44，因为同一个字符串路径在不同 userId 下指向不同位置。这跟第 07 章「状态按 sessionId 分槽位」是同一个设计：身份从上下文来，不从全局字段来。所以你自己实现一个 filesystem 时，千万不要把它存成实例字段。

最小可跑：一个 workspace + 两个用户

下面这段是官方示例 WorkspaceLocalShellExample 的核心，去掉了打印部分WorkspaceLocalShellExample.java:58。它是「模式 3：本机 + shell」的显式写法： 

Path workspace = Files.createTempDirectory("agentscope-local-fs-example");

Files.writeString(
        workspace.resolve("AGENTS.md"),
        """
        # Local Shell Agent

        You are a helpful assistant that can execute shell commands.
        Keep answers concise (under two sentences).
        """);

HarnessAgent agent =
        HarnessAgent.builder()
                .name("local-shell-agent")
                .sysPrompt("You are a helpful assistant with shell access.")
                .model("dashscope:qwen-plus")
                .workspace(workspace)
                .filesystem(
                        new LocalFilesystemSpec()
                                .executeTimeoutSeconds(30)
                                .env("EXAMPLE_VAR", "hello-from-agentscope")
                                .inheritEnv(true))

  2. bob 看不见 alice 的文件，但模型不知道自己少看了什么
    list_files 会把 namespace 前缀剥掉再报给模型LocalFilesystem.java:761，所以两个用户各自看到的都是「根目录里只有我的东西」。这是特性不是 bug——提示词里不用解释「你的文件在 /bob/ 下」。

陷阱与窍门

1. workspace 目录不存在，程序照常启动
你会看到
日志里两行 warn：Workspace directory does not exist ... Please create it and add AGENTS.md.，然后 agent 表现得像没读过你的人格文件。
因为
validate() 全程只 log.warn，既不建目录也不抛异常WorkspaceManager.java:202。
改成
把 workspace 目录的准备当成部署步骤（CI 里 Files.createDirectories + 校验 AGENTS.md 存在），或者在 build() 之后自己判一次 wsManager 的 warn 是否出现。别指望框架替你 scaffold。
2. 模型写 /etc/hosts 没报错，文件却在 workspace 里
你会看到
write_file 返回成功，宿主 /etc/hosts 一点没变，<workspace>/etc/hosts 冒出来了。
因为
ROOTED 对「以 / 开头但磁盘上不存在」的路径会剥掉前导斜杠当相对路径处理LocalFilesystem.java:649。只有真实存在的越界绝对路径才抛 SecurityException。
改成
需要碰宿主目录就显式 addRoot(...)；需要「只能写 workspace」就 .mode(LocalFsMode.SANDBOXED)，那条分支对任何越界一律拒绝:609。
3. 项目里的文件删不掉（overlay 的 delete 永远失败）
你会看到
AbstractFilesystem.delete(rc, path) 返回 Cannot delete shared file: ...，但同一个文件的 edit_file 却成功了。注意内置根本没有 delete_file 这个工具，能被踩到的是宿主代码、技能脚本与其它 harness 工具直接调的 delete。
因为
overlay 的下层（project）是只读的：edit 走 copy-on-write 会在上层建副本再改OverlayFilesystem.java:175，而 delete 遇到「只有下层有」直接失败:263。
改成
想让 agent 真删项目文件：开 projectWritable(true)（换成 ProjectAwareOverlay），或者在 shell 里删。默认语义是「项目文件可以被继承和改写，不能被删除」。
4. 模式 1 起来发现没有 execute 工具
你会看到
模型说「我没有执行命令的能力」；或者你 disableShellTool() 都没调，工具列表里就是少一个。
因为
CompositeFilesystem 不实现 AbstractSandboxFilesystem，注册条件是 instanceof 检查HarnessAgent.java:2722，而它是故意不做 shell 的CompositeFilesystem.java:46。
改成
三条路：换沙箱模式（第 13 章）；用 abstractFilesystem(...) 自己拼一个带 shell 的组合；或接受「共享存储不跑命令」这个设计。不要在模式 1 里到处找开关——没有这个开关。
5. 加了 sharedLocalWorkspace(true)，多用户互相覆盖
你会看到
alice 写的 report.md 立刻被 bob 的 report.md 盖掉。
因为
这个开关在 toFilesystem 里直接把 namespaceFactory 置 nullLocalFilesystemSpec.java:323，字段 javadoc 明写「Not safe for multi-tenant workspaces」:105。
改成
它只用于「宿主应用与 agent 需要对同一个物理路径达成一致」的单进程单租户集成。多租户请保持默认，靠 workspaceFor(uid, sid) 从宿主侧读。
6. @path 和 workspace 上下文突然失效
你会看到
同一段提示词在本机模式能带上附件，切到共享存储就没了；或者 MEMORY.md 越写越长，最后被截成半句。
因为
前者是 CompositeFilesystem 分支直接关掉展开AtPathExpansionMiddleware.java:128；后者是预算只截 MEMORY.md 这一份文件WorkspaceContextMiddleware.java:233，AGENTS.md 与 knowledge 是不截的，它们把额度吃光后 MEMORY.md 就只能截。
改成
分布式模式下想让模型看文件内容，就用 read_file 而不是 @path；上下文超限就调 maxContextTokens(...) 或把知识挪进 knowledge/ 让 agent 自己去查。

自检三问

不写 .filesystem(...) 时，project 默认是什么？这会带来什么风险？

${user.dir}，即进程工作目录LocalFilesystemSpec.java:75。 风险有两层：一是 overlay 下层把整个当前目录变成只读可见（read_file 能读到你的源码、配置）， 二是 shell 的 pwd 也是它，所以 execute("ls") 看到的是项目而不是 workspace。生产部署里 user.dir 往往是 jar 所在目录，这通常不是你想暴露的东西——显式 .project(...) 收窄。

readAgentsMd(rc) 读到的内容来自 workspace 还是 project？

先 filesystem 后本地：两层读里 filesystem 优先WorkspaceManager.java:818。 默认模式的 filesystem 是 overlay，上层是 workspace、下层是 project，所以 workspace 里有 AGENTS.md 就用它，没有才退到 project。真正易错的是那个判据：它用的是「返回的字符串为空」而不是「读失败」:820， 三档真实行为各不相同：文件不存在 → read 失败 → 内容空串 → 回落本地盘；文件存在但为空或全空白 → LocalFilesystem 把内容换成一句 System reminder: File exists but has empty contents（非空！）LocalFilesystem.java:291，于是模型收到的“人格”就是这句话；KV 后端存了一个真正的空值 → 回落去读本地模板，静默换了来源。

我想让 agent 只能读写 workspace，任何宿主绝对路径都不行，最少要设什么？

.filesystem(new LocalFilesystemSpec().mode(LocalFsMode.SANDBOXED))，并把 shell 一起关掉 .disableShellTool()——只关文件工具不够，因为 execute 是宿主 sh -c，一条 cat /etc/passwd 就绕过了路径策略。注意 SANDBOXED 里绝对路径不是被拒绝而是被 重新锚定到 rootLocalFilesystem.java:616， 真要隔离命令执行，正解是第 13 章的沙箱模式。
