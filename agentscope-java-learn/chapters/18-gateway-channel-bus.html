18 · 网关、渠道与异步：把 Harness 装成一个服务

前面七章讲的是「一个 agent 怎么变强」。这一章讲「它怎么变成服务」：一条来自用户的消息，怎么找到正确的 agent、落到正确的会话、在同一会话里排队，然后——如果某个工具太慢——怎么先回一句话、事后再把结果塞回对话。这中间有五层：Channel、ChannelRouter、Gateway、MessageBus、WakeupDispatcher。和官方 channel.md 的分歧也集中在这里：文档只写了前三层，后两层（消息总线与唤醒）一个字都没提，而它们才是「后台任务结果怎么回来」的全部机制。

读完你能做到

  • 说清 agent.channel(...) 和 GatewayBootstrap 两条路各自替你做了什么、各自漏了什么
  • 把 MsgContext.canonicalKey() 的拼接规则背下来，并解释为什么「往 extra 里塞业务属性」会把用户历史聊没
  • 推出任意一条消息最终落到哪个 gw-… 会话，以及四种 DmScope 下同一句「你好」会分裂成几个会话
  • 写出 ChannelRouter 的九级优先级（1 层显式 + 7 层 binding + 2 层兜底），并说明 tier 内按什么顺序取
  • 解释 LocalSessionTurnGate 为什么是「排队」而分布式 gate 可能是「静默丢弃」
  • 画出异步工具的三段式：超时 → 占位结果 → 后台完成后进 inbox + enqueue wakeup
  • 说清 WakeupDispatcher 的三条脆弱点（丢弃、死订阅、跑错 agent），以及暴露子 agent 的四种解析路径

先说为什么：一条用户消息要穿过五层

先把全景摆出来。下面这五层各有明确分工，混在一起就会写出「消息丢了不知道在哪丢」的服务：

层类型只负责一件事出处
渠道适配 Channel / ChatUiChannel 把平台消息规范化成 InboundMessage：谁发的、在哪个会话、是不是线程回复 InboundMessage.java:63-74
路由 ChannelRouter 决定 哪个 agent 接、哪个会话键、回复投到哪（三样一起出） ChannelRouter.java:82-118
网关 HarnessGateway 把会话键换成稳定 sessionId、同会话串行、合并 RuntimeContext HarnessGateway.java:203-231
总线 MessageBus 跨轮次投递：inbox 队列、唤醒队列、会话事件回放 MessageBus.java:45-146
唤醒 WakeupDispatcher 把「闲着的会话」叫起来跑一轮：drain → 判忙 → runWakeup WakeupDispatcher.java:130-180

关键认识：前三层解决「这一轮」，后两层解决「下一轮」。用户发一句话，走前三层就够了；但后台任务跑完之后没有人再说话，就必须靠后两层把 agent 主动叫醒。很多「异步任务永远没结果」的问题，根因不在异步逻辑，而在于后两层压根没接上——这正是官方文档没讲的部分。

一个必须先分清的区分：会话 id 有两套

路由层产出的是 MsgContext.canonicalKey()（人类可读的字符串，如 chatui|r:u_1），网关再把它哈希成 gw-xxxxxxxxxxxx（12 位十六进制）。前者是稳定性来源，后者是存储键。同一份 canonicalKey 在任何机器上都得到同一个 gw-…，这是「重启后记忆还在」的前提SessionIdUtils.java:42-51。

最小可跑：两条路，两种完整度

单 agent 场景，一个方法就能接上渠道： 

HarnessAgent agent = HarnessAgent.builder()
        .name("assistant")
        .model(model)
        .build();

// 每个 peerId 一个会话；也可以 ChatUiChannel.create()（所有对话共用一个会话）
ChatUiChannel chat = agent.channel(ChatUiChannel.perPeer());

Msg reply = chat.send("user-1", "你好").block();          // 走路由
Msg again = chat.send(SendOptions.userId("user-1"), "在吗").block();  // 直给会话键

agent.channel(...) 做的事只有两件：懒创建一个内部网关、把它注入 channelHarnessAgent.java:646-650。而那个网关是这样造的： 

HarnessGateway gw = HarnessGateway.create();   // 注意：没有 ChannelManager，没有 MessageBus
gw.bindMainAgent(this);
// 之后才按需补：subagent bridge / materializer / 分布式 registry / turn gate

这就决定了它的能力边界：路由与会话串行都可用，主动投递不可用（没有 ChannelManager，deliverToSession 直接返回 falseHarnessGateway.java:335-346），网关侧唤醒不可用（没有 MessageBus，runWakeup 只剩「跑一轮」而没有事件回放）。想更完整，用第二个入口。

多 agent + 外部渠道，用 GatewayBootstrap： 

GatewayBootstrap gw = GatewayBootstrap.builder()
        .agent("sales", salesAgent)                 // 已构建的实例
        .agent("support", b -> b.name("support")     // 也可以给构建 lambda
                .model(model).sysPrompt("你是客服。"))
        .mainAgent("sales")                          // 不写就取第一个注册的
        .channel(mySlackChannel)                     // 外部渠道
        .distributedStore(redisStore)                // 可选：跨节点暴露子 agent
        .build();

ChatUiChannel chat = gw.chatUiChannel(
        ChannelConfig.builder("chatui")
                .dmScope(DmScope.PER_PEER)
                .binding(ChannelBinding.forPeer("direct:vip-1", "support"))
                .build());

gw.start();   // initAll + startAll —— build() 不会启动渠道
// ...
gw.stop();    // stopAll
build() 不启动渠道，也不建消息总线

GatewayBootstrap.build() 只做：校验 agent 非空、建 ChannelManager、HarnessGateway.create(cm)（仍然没有 bus）、注册 agent、按需装 materializer 与分布式子 agent registryGatewayBootstrap.java:264-329。渠道要你显式 start()；WakeupDispatcher 要你自己 new 出来再 start()。

Gateway：一个入口方法，五个重载，三件默认不做的事

接口本身很小。run 的五个重载是层层委托的，最终都落到参数最全的那个；runStream、runSubagent、runSubagentStream 的默认实现都是返回错误流，不是「回退成非流式」：

方法默认行为说明
run(ctx, msgs) 抽象方法 唯一必须实现的入口Gateway.java:54-55
run(ctx, msgs, outbound) 委托到四参 多一个「回复投到哪」:66-68
run(ctx, msgs, outbound, callerCtx) 委托到五参 多一份调用方的 RuntimeContext:82-88
run(..., inboundMessage) 回退到二参 run(ctx, msgs) 多一份原始信封，只给 ChannelRuntimeContextResolver 用:96-103
runStream(...) Flux.error(UnsupportedOperationException("Streaming not supported")) 自定义 Gateway 不实现就没有流式:138-145
runSubagent(...) Mono.error("Subagent routing not supported") 暴露子 agent 是可选能力:155-162

默认实现 HarnessGateway.run 的骨架值得逐行看，因为它把所有「隐式约定」都摆在这里：

  1. 会话键
    gateKey = ctx.canonicalKey()；ctx 为 null 时用 MsgContext.defaultContext()（即 "default"）HarnessGateway.java:209-210。
  2. 选 agent：看 extra["agentId"]
    唯一的路由依据是 MsgContext.extra() 里那个 key 为 "agentId" 的值，不是方法参数:212-213。这就是为什么 ChannelRouter 一定要把解析结果塞进 extra。
  3. 换 sessionId
    resolveSessionId(gateKey)："gw-" + SHA-256(gateKey) 的前 12 位十六进制:535-537，同时登记 sessionId → gateKey 反查表。
  4. 记路由
    有 outboundAddress 就写进 lastRouteBySession（可选再写 BaseStore 的 gateway/routes），供日后主动投递:222-224。
  5. 合上下文
    buildRuntimeContext(...) 造出这一轮的 RuntimeContext：sessionId + msgContext + gateKey + outboundAddress + userId。
  6. 上锁执行
    withGatedTurn(gateKey, () -> ha.call(msgs, rtc))——注意传的是 ha.call，不是 delegate，所以 HarnessAgent 自己的会话默认值、包裹逻辑都会生效。
陷阱一：路由到不存在的 agentId 不会报错

resolveAgent 的顺序是「注册表命中 → 主 agent → defaultAgentId」HarnessGateway.java:519-528。所以 binding 里写错一个 agent 名字，请求静默落到主 agent，不抛异常、不打 warn。排查「为什么 VIP 用户没有走到 support agent」时，先打印 RouteResult.matchedBy() 和 agentId()。

陷阱二：主 agent 的路由 id 不是 .agent("别名", ...) 的键

bindMainAgent 用 agent.getAgentId()（为空才退成 "main"）作为注册名:159-165、:530-533；只有非主 agent 才用你给的 key 注册GatewayBootstrap.java:289-296。所以 .mainAgent("sales") 时，binding 写 "sales" 能否命中，取决于 salesAgent.getAgentId() 是不是 "sales"；否则又会静默落回主 agent（恰好就是它，所以看起来「对」了，但换名字就错）。

会话 id：从 canonicalKey 到 gw-…

MsgContext 只有六个语义字段（外加 userId），但拼接规则决定了会话边界。源码是顺序 append，空值跳过MsgContext.java:77-103： 

channel
  + "|g:"  + group       （群 / 团队 / 账号）
  + "|r:"  + room        （房间 / peer）
  + "|t:"  + threadId    （线程）
  + "|ts:" + threadTs    （平台时间戳锚点）
  + "|x:"  + key + "=" + value   （extra，按 key 字典序，逐个拼）

举几个真实产出：chatui（MAIN 下的所有私聊）、chatui|r:u_1（PER_PEER）、slack|g:T123|r:C456|t:1699.1（guild 里的线程）、chatui|r:u_1|x:agentId=support（指定 agent 的私聊）。

最容易踩的一条：extra 参与会话键

因为 extra 被拼进了 canonicalKey，而 ChannelRouter 每次都会往里放 {"agentId": …}ChannelRouter.java:181，所以换一个 agent 就是换一个会话——这是刻意的。但如果你顺手把 tenant、traceId、requestId 也塞进 extra，那么每个请求都会得到新会话，用户上一轮说的话全部「失忆」。官方文档也提醒过这一点channel.md:112，但没说后果有多严重。业务属性请放 RuntimeContext，不要放 MsgContext.extra。

sessionId 则是纯函数：同样输入永远同样输出，与 JVM、机器无关（2^48 空间，实际不会撞）。所以「同一会话」在存储层就是同一个 gw-… 目录/键；重启、换节点、水平扩容都不会丢。若挂了 BaseStore，网关还会把 sessionId → gateKey 与 sessionId → outboundAddress 写穿到 gateway/sessions、gateway/routes 两个命名空间，缓存未命中时回查HarnessGateway.java:754-816。

同会话串行：一个公平信号量，和一种「静默丢弃」

SessionTurnGate 只有两个方法：acquire(key) 拿租约、isRunning(key) 探忙SessionTurnGate.java:26-47。默认实现是进程内的： 

private final ConcurrentHashMap<String, Semaphore> gates = new ConcurrentHashMap<>();

public TurnLease acquire(String key) throws InterruptedException {
    Semaphore semaphore = gates.computeIfAbsent(key, k -> new Semaphore(1, true)); // 公平
    semaphore.acquire();          // 阻塞等待，永不抛 TurnBusyException
    return semaphore::release;    // 租约就是一个 Runnable
}

public boolean isRunning(String key) {
    Semaphore s = gates.get(key);
    return s != null && s.availablePermits() == 0;   // 看许可数，不看线程
}

注意两个细节：公平（new Semaphore(1, true)，先到先得，不会饿死），以及它永远不抛 TurnBusyExceptionLocalSessionTurnGate.java:21-42。所以本地部署下「同一用户连发两条」是排队，第二条会等第一条跑完。

但网关的包裹逻辑对「忙」的处理是另一种画风： 

try {
    leaseRef.set(sessionTurnGate.acquire(gateKey));
} catch (TurnBusyException e) {
    log.debug("Skipping turn for {}: gate busy ({})", gateKey, e.getMessage());
    return Mono.empty();          // 整轮消失：不报错、不排队、不重试
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return Mono.error(new IllegalStateException(e));
}

Mono.empty() 意味着调用方拿到的流正常结束但没有结果HarnessGateway.java:694-720、TurnBusyException.java:18-23。本地默认实现不会走到这个分支，所以本地测不出来；一旦换成控制面托管的分布式锁（DistributedStore.sessionTurnGate()），这条路径就活了——表现是「高峰期偶发消息没回复」，日志里只有一行 debug。

gate 类型并发同会话时调用方观感代价
LocalSessionTurnGate（默认）阻塞排队慢，但有回复占用 boundedElastic 线程，线程池打满会拖垮其他会话
分布式 gate（短超时）抛 TurnBusyException空结果需要客户端区分「空」与「忙」，否则表现为丢消息

另外，整个执行都 subscribeOn(Schedulers.boundedElastic())、租约在 doFinally 里释放，所以异常、取消都不会漏锁。用分布式 gate 时官方建议把 ReActAgent 的 conflictPolicy 设为 FAIL，让并发写状态直接报错而不是互相覆盖SessionTurnGate.java:20-24。

ChannelRouter：1 层显式 + 7 层 binding + 2 层兜底

路由是这个包里最容易背错的地方。真实顺序写死在 TIERS 常量里ChannelRouter.java:124-125，resolveRoute 在其前面加了显式短路口、后面加了两级默认：

#层级命中条件matchedBy
0explicitInboundMessage.preferredAgentId() 非空白"explicit"
1peerbinding.peer == peer.key()，如 direct:u_42"peer"
2parentPeer线程消息且 binding.parentPeer == parentPeer.key()"parentPeer"
3guild + rolesguild 相同且 roles 非空且 与消息 roles 有交集"guild+roles"
4guildguild 相同且 roles 为空"guild"
5teambinding.team == msg.team"team"
6accountbinding.account == msg.accountId"account"
7channelbinding.channel == msg.channelId"channel"
8channel-defaultChannelConfig.defaultAgentId() 非空"channel-default"
9global-default兜底；构造参数为 null 时是 "main""global-default"

tier 内的规则是「按 bindings() 列表顺序，第一个命中的赢」ChannelRouter.java:144-152。所以同一 tier 里写两条重叠的规则，前面的会遮住后面的。

ChannelBinding 是 9 字段 record，但一条 binding 只属于一个 tier：「最具体的那个非空字段」决定它落在哪层ChannelBinding.java:21-40。因此 forPeer 造出来的 binding 永远不会因为 guild 匹配而生效——它只看 peer。七个静态工厂分别对应七个 tier： 

ChannelBinding.forPeer(peerKey, agentId)            // "direct:u_42"
ChannelBinding.forParentPeer(parentPeerKey, agentId)
ChannelBinding.forGuild(guild, agentId)             // roles 为空 → guild tier
ChannelBinding.forGuildRoles(guild, roles, agentId) // roles 非空 → guild+roles tier
ChannelBinding.forTeam(team, agentId)
ChannelBinding.forAccount(account, agentId)
ChannelBinding.forChannel(channel, agentId)
// 附加：binding.withSessionScope(DmScope.PER_PEER) 覆盖该条的会话粒度
显式指定 agent 时，binding 仍然会被查一次

代码里 findMatchedBinding 在显式判断之前就执行了ChannelRouter.java:89，因为即使 agent 由调用方指定，sessionScope 仍要沿用命中的 binding:105-108。换句话说：显式只覆盖 agent，不覆盖会话粒度。

DmScope：同一句「你好」会分裂成几个会话

DM 的会话粒度由 DmScope 决定，默认 MAINDmScope.java:31-40。四种取值在 buildDmContext 里各造一个 MsgContext：

scope构造出的 MsgContextcanonicalKey 形态u_1 与 u_2 两个用户
MAIN（默认） (channel, null, null, null, null) chatui 共用一个会话（适合单用户/共享助手）
PER_PEER (channel, null, peerId, null, null) chatui|r:u_1 / chatui|r:u_2 两个会话
PER_CHANNEL_PEER (channel, null, peerId, null, null) chatui|r:u_1 / chatui|r:u_2 两个会话（与上一行完全相同）
PER_ACCOUNT_CHANNEL_PEER (channel, accountId, peerId, null, null) slack|g:A1|r:u_1 两个会话，且多账号再分一层

看第三行：PER_PEER 与 PER_CHANNEL_PEER 在源码里是两个完全相同的分支ChannelRouter.java:204-210。原因不神秘：canonicalKey 的第一个片段永远是 channel，所以「把 channel 编进 key」对所有 scope 都自动成立。名字不同，行为一样——别指望靠切到 PER_CHANNEL_PEER 去解决跨渠道同名用户的问题，那件事本来就已解决。

非 DM 的三条分支也一并记住：

  • 线程：room = parentPeer.id、threadId = peer.id，即「同一父消息下的所有回复共用一个会话，不同线程彼此分开」:186-188。
  • 频道 / 群：room = peer.id、group = guild，同一频道内所有人共用一个会话:191-192。
  • userId：取 senderId，为空且是 DM 时退回 peer.id:110-113。它不进 canonicalKey，只影响 AgentState 的 (userId, sessionId) 槽位——所以「群聊里同一个会话、每个人各有一份记忆」是靠 userId 实现的，不是靠 sessionId。
群聊的默认语义容易反直觉

群聊无论 DmScope 设成什么都只有一个会话（room = peer.id），DmScope 只管 DM。想让「群里每个人各自一条私密记忆」，靠的是 userId 隔离，不是换 scope。

Channel：三个必须实现，七个已有默认

接口一共十个方法，只有 channelId()、config()、dispatch() 是抽象的；其余七个都有默认实现，且默认值都倾向「什么都不做」或「明确不支持」：

方法默认什么时候要覆盖
channelId()抽象必须与 ChannelConfig.channelId() 一致
config()抽象路由配置的唯一来源
init(Gateway)空构造时拿不到 gateway 的渠道
start() / stop()空需要接 webhook / 长轮询 / WebSocket
dispatch(InboundMessage)抽象标准三步：resolveRoute → gateway.run → 回投
dispatchStream(...)Flux.error("Streaming dispatch not supported")要做流式（SSE）就必须自己实现，或照抄 ChatUiChannel
deliver(address, msgs)空支持服务端主动推送（如子 agent 播报）
deliverWithReceipt(...)Mono.error("Provider receipts are not supported")需要平台回执（消息 id）来做「至少一次」投递

ChannelManager 是管理这些实例的小容器：register 同 id 覆盖、unregister 会先 stop、initAll / startAll / stopAll 逐个调用且吞掉单个渠道的异常（只打日志，不影响其他渠道）ChannelManager.java:60-148。主动投递时找不到渠道只 warn 一句就丢弃:163-185。

「批量启动成功」不等于「每个都起来了」

initAll / startAll 里每个 channelId 的异常都被 catch 成日志ChannelManager.java:113-135。生产上要自己核对：gw.start() 之后逐个查 channelManager().getChannel(id) 的健康状态（或你自己的探针），不要只看 start() 没抛异常。

ChatUiChannel：两种发送姿势，走两条完全不同的路

它是内核里唯一的开箱渠道实现，也是最好的「怎么写 Channel」范本。但它有两套发送 API，语义差别很大，混用就会出现「binding 明明配了却不生效」：

写法内部路径会查 binding 吗会话粒度由谁决定
send(peerId, text) ChatUiRequest.withPeer → InboundMessage.dm → dispatch → 路由 会 ChannelConfig.dmScope + binding 的 sessionScope
send(text) 同上，但 peer 固定为 "__anonymous__" 会（只是 peer 恒定） dmScope；默认 MAIN 下就是唯一会话
send(SendOptions, text) dispatchWithOptions → 直接造 MsgContext → gateway.run 不会 SendOptions.effectiveSessionKey()（sessionId 优先，否则 userId）
sendToSubagent(id, text) gateway.runSubagent 不会（绕开全部路由） 子 agent 自己的 sessionId

第三行值得展开。SendOptions 路径完全不经过 ChannelRouter，它自己拼上下文： 

String room = options.effectiveSessionKey();      // sessionId ?: userId
String agentId = options.agentId();
if (agentId == null) agentId = config.defaultAgentId();   // 只回退到渠道默认，不看 binding
Map<String, String> extra = agentId != null ? Map.of("agentId", agentId) : Map.of();
return new MsgContext(CHANNEL_ID, null, room, null, null, extra)
        .withUserId(options.userId());

出处 ChatUiChannel.java:444-457、SendOptions.java:118-121。所以 SendOptions 是「我自己知道该给谁、该落哪个会话」的低层后门；要做「按角色/群组自动分派」，还是得走 InboundMessage + binding。

其它几个实用方法：previewRoute(message) 只算路由不发送（前端可以先用它拿会话键）:161-168；pollOutbound() 把主动投递的消息从内存队列里取走（deliver 只是入队，不会真的推送）:170-193；applyRoutingConfig 在 channelId 一致时直接换 volatile 引用即可热更新:138-146。

忘了注入 gateway 的报错是明确的

ChatUiChannel.create() 造出来时 gateway 为 null；直接 send 会抛 IllegalStateException("ChatUiChannel has no gateway. Use GatewayBootstrap.chatUiChannel(), or construct with ChatUiChannel.create(gateway).")ChatUiChannel.java:459-467。要么 agent.channel(ch)，要么 gw.chatUiChannel()，别 new 完就用。完整条目：附录 B · ChatUiChannel has no gateway。

GatewayBootstrap：装配顺序，以及它会替你做的三件事

build() 的步骤是固定的，顺序本身有意义GatewayBootstrap.java:264-329：

  1. 校验 agent
    一个都没有 → IllegalStateException("At least one agent must be registered via agent(...)")；mainAgent 不在列表里 → IllegalStateException("mainAgent('x') not found in registered agents")。不写 mainAgent 时取 LinkedHashMap 的第一个，也就是第一个 .agent(...)。
  2. 建容器
    new ChannelManager() → 逐个 register(ch) → HarnessGateway.create(cm)。注意此处不建 MessageBus，也没有 WakeupDispatcher。
  3. 绑主 agent + 注册其余
    bindMainAgent(mainHa) 先做，其余按 key registerAgent(key, agent)。这一步决定了「主 agent 的路由 id 是它自己的 getAgentId()，其他 agent 的路由 id 是你给的 key」。
  4. 装子 agent 恢复链
    收集每个 agent 的 DefaultAgentManager，合成一个「挨个试」的 SubagentMaterializer；若有 distributedStore（或主 agent 自带的），换成 StoreBackedSubagentRegistry。没有 store 就停在 InMemorySubagentRegistry，暴露关系只在当前进程有效。

MessageBus：三种消费模型，四组域助手

接口只定义原语，语义分三类MessageBus.java:24-45：

模型方法语义谁在用
A · 排空队列 queuePush / queueDrain / queueDelete / queuePeek 单消费者、读到即删（ack-on-read）。读过一次就没了 inbox、唤醒队列
C · 回放日志 logAppend / logRead / logTrim 多消费者、各自游标、按 maxLen 截断。非破坏性 会话事件回放（SSE 断线重连）
D · 瞬时广播 publish / subscribe 发完就忘，只发给当前已订阅者，不保留历史 唤醒信号

在它们之上有一层「域助手」，把业务概念映射成固定的 key 约定（默认方法，不用自己实现）： 

inbox        agentscope:inbox:<sessionId>            queuePush / queueDrain
唤醒队列      agentscope:wakeups                        queuePush / queueDrain
唤醒信号      agentscope:wakeup_signal                  publish / subscribe
会话事件      agentscope:session:events:<sessionId>     logAppend(maxLen=1000) + publish

enqueueWakeup(userId, sessionId, agentId) 是「先入队、再广播一个空信号」两件事MessageBus.java:180-188；sessionPublishEvent 是「写日志 + 广播（活的副本多一个 _entry_id 当游标）」:220-229。

模型 A 没有 ack，消费方崩了就是丢消息

queueDrain 的契约是「返回的一定被删掉」。如果消费方拿到之后、处理之前进程崩了，这些条目再也回不来。异步结果依赖这条路径，所以「进程崩溃」在语义上等价于「结果丢失」——代码只能靠 AsyncToolRegistry 的 stale 检测事后补偿，而那是另一条链路（见下一节）。

WorkspaceMessageBus：文件布局、3 秒轮询，和「publish 是空实现」

默认实现把总线落在文件系统上，所以它天然跟着 workspace 走： 

{busRoot}/
  queues/{sanitizedKey}_{hash}/00000000000000000001.json   ← 模型 A，每条一个文件
  logs/{sanitizedKey}_{hash}/00000000000000000002.json     ← 模型 C，追加、按 maxLen 删旧

入口 id 是 String.format("%020d", seq.incrementAndGet())，seq 用 System.nanoTime() 初始化WorkspaceMessageBus.java:233-235。因为定长补零、目录内按路径排序，字典序就是产生顺序；重启后从 nanoTime 重新起算，所以「跨进程严格单调」并不成立——这也是官方说它「单进程」的原因之一。

queueDrain 的容错分两种，值得记住：

  • 读失败（并发被别的 drain 删了、I/O 抖动）→ continue，不删，留给下次重试:100-108。
  • JSON 坏了 → 删掉，否则每次 drain 都会卡在同一条坏数据上:115-125。
模型 D 在这里是「假的」

publish 是 Mono.empty()，subscribe 只是每 3 秒吐一个空 MapWorkspaceMessageBus.java:210-221。所以唤醒信号在这套实现里退化成轮询：延迟最多 3 秒，且与有多少节点无关（每个节点都自己 tick、自己 drain，抢到的先处理）。真正需要「毫秒级推送」时，要换 Redis/控制面实现（DistributedStore.messageBus()）。

InboxMiddleware：每个 reasoning step 开头排一次水

它是唯一的 inbox 消费者。挂在 onReasoning 上，每轮推理之前做两件并行的事，然后 zip 起来InboxMiddleware.java:82-140：

  1. 排空 inbox
    inboxDrain(sessionId, maxDrainCount)，把每条 payload 还原成 HintBlock（必须有 hint 字段，否则丢弃）。默认上限 100 条。
  2. 扫一遍僵尸异步任务
    asyncToolRegistry.findStale(sessionId, ttl)：状态还是 RUNNING 且创建时间早于 now - ttl 的记录，逐条 markTimeout，并合成一条 hint：「工具 'x' 没跑完（进程崩溃或超时），你可以重试或直接继续」。默认 TTL 10 分钟:56、:109-137。
  3. 塞进上下文 + 发事件
    有 hint 就写进 state.contextMutable()：如果最后一条是同名 assistant 消息就追加 content，否则新造一条 assistant 消息:186-209；同时为每条发一个 HintBlockEvent（前端可以实时渲染），最后 concatWith(next) 继续推理:163-178。

注册时机：只要 messageBus != null 就装，参数是 (bus, 100, asyncToolRegistry, null)HarnessAgent.java:2614-2616。而 messageBus 在「没显式设置、但有文件系统」时会自动退化成 WorkspaceMessageBus(filesystem, ".agentscope/bus"):2504-2516，而文件系统永远不为 null（默认 LocalFilesystemSpec）。结论：InboxMiddleware 默认就是开着的，你没配任何东西它也已经在排空气了。

僵尸检测是「懒」的

findStale 只在有推理步骤发生时才被调用。如果会话从此再没有人说话、也没有 wakeup，那些 RUNNING 记录会一直躺着，不会自愈。所以「进程崩了之后重启，用户不发消息就永远看不到失败通知」是预期行为，不是 bug。

AsyncToolMiddleware：超时 → 占位结果 → 后台跑完回灌

默认不装。asyncToolTimeout 字段没有初始值HarnessAgent.java:1294-1296，只有你显式 .asyncToolTimeout(Duration) 且 messageBus != null 时才注册:2666-2669。 

HarnessAgent agent = HarnessAgent.builder()
        .name("worker").model(model)
        .asyncToolTimeout(Duration.ofSeconds(30))   // 关键：不设就永远同步
        .build();

它的核心不是「多线程跑工具」，而是把一次 acting 阶段切成两段：

  1. 计时的是整个 acting 阶段
    定时器在 onActing 入口就起，等的是 next.apply(input) 整条流结束，不是单个工具AsyncToolMiddleware.java:150-169。所以「同一轮里有 3 个工具，其中 1 个慢」→ 三个工具都会拿到占位结果，而不是只处理慢的那个。
  2. 超时瞬间：登记 + 占位 + 收尾
    对 input.toolCalls() 里每个调用：往 AsyncToolRegistry 写一条 RUNNING（id 就用 toolCall.getId()）、把占位 ToolResultBlock 写进 state.contextMutable()、发 ToolResultStart/TextDelta/End 三个事件，最后 sink.complete() 让这一轮先结束:182-235。
  3. 后台不取消
    onDispose 里只有「没超时」才 sub.dispose()；超时后订阅继续跑，事件先进 backgroundBuffer 缓存而不是丢掉:105-114、:171-177。
  4. 跑完：进 inbox + 唤醒
    完成回调里把所有 ToolResultTextDeltaEvent 的 delta 拼成文本，包成 HintBlock（source="tool_output"）推进 inbox，再 enqueueWakeup(userId, sessionId, agentId):237-294。

占位文案本身也是一段提示工程：明确告诉模型「在后台跑（id=…），完成会自动通知，不要轮询、不要查询、不要等」，并给两条出路：去干别的独立任务，或者干脆回一句文本:69-75。

三条失败路径，只有一条会通知到模型

① 后台执行抛异常：只写 registry.fail(...) + 一条 warn 日志，不推 inbox、不唤醒:115-135——模型永远等不到结果，这是最坑的一条。
② 进程崩溃：记录停在 RUNNING，等下一次推理时被 stale 扫描捞出来（≥10 分钟）。
③ 没有 sessionId：deliverBackgroundResult 直接 warn 返回，结果被丢弃:239-243。裸调 agent.call(...) 不带 session 时就会这样。

另外两个细节：结果只从 ToolResultTextDeltaEvent 里取，所以不产生文本增量的工具（只返回结构化块）回灌内容是 "(no output)"；WorkspaceAsyncToolRegistry.complete(id, result) 与 fail(id, error) 都忽略第二个参数，只改状态，不存内容WorkspaceAsyncToolRegistry.java:81-94、:125-147。

RuntimeContext 合并：调用方 → resolver → 网关身份字段

三层，后一层覆盖前一层，顺序不能颠倒HarnessGateway.java:279-329：

  1. 起点：callerContext
    来自 SendOptions.runtimeContext() 或 InboundMessage.runtimeContext()，可以为 null。
  2. 替换：resolver
    配了 ChannelRuntimeContextResolver 且返回非 null，就整体替换上一步的 base（不是合并）。请求对象里带着 channelId、原始 InboundMessage、已解析的 MsgContext、OutboundAddress、callerContext，够你查租户/鉴权/工具依赖ChannelRuntimeContextRequest.java:35-40。返回 null 表示「不改」。
  3. 覆盖：网关身份字段
    sessionId、msgContext、gateKey、outboundAddress 强制写入；userId 只在非空白时写。冲突一律以网关为准——这是刻意的，否则调用方可以把 sessionId 改成别人的。

实践上分清楚两个入口：业务属性（租户、trace、工具依赖）放 RuntimeContext；会话身份（channel/group/room/thread）放 MsgContext。反过来放，前者会把会话打散，后者会让业务属性污染会话键。

端到端：一条消息的完整时序

把本章所有零件串起来。假设一个异步工具跑了 3 分钟，用户早已离开页面：

  1. ① 渠道收消息
    适配器把平台事件规范化成 InboundMessage：channelId、peer、senderId、guild、parentPeer、messages。
  2. ② 路由
    router.resolveRoute(config, msg) 产出 RouteResult{agentId, context, matchedBy, outboundAddress}——三样东西一起定下来：谁接、落哪个会话、回复投哪。
  3. ③ 网关换 id + 上锁
    gateKey → gw-…、记 lastRoute、合 RuntimeContext、acquire(gateKey)。同会话的第二条消息在本地实现下会在这里排队。
  4. ④ agent 跑一轮
    ha.call(msgs, rtc) → 中间件链 → 模型 → 工具。每次 onReasoning 开头，InboxMiddleware 都会排一次 inbox。
  5. ⑤ 工具超时
    AsyncToolMiddleware 写占位结果、登记 RUNNING、结束本轮。用户马上收到一句「正在后台处理」。
  6. ⑥ 后台完成
    结果拼成 HintBlock 推 inbox；enqueueWakeup 写唤醒队列 + 发信号。
  7. ⑦ 唤醒
    某个节点的 WakeupDispatcher（文件总线实现下最多 3 秒后）drain 到这条，判忙通过 → runWakeup(userId, sessionId) → 空输入跑一轮 → InboxMiddleware 把 hint 注入 → 模型看到结果，决定回一句话。
  8. ⑧ 主动投递
    ChannelManager.deliver(lastRoute, [reply]) → 渠道的 deliver 把消息推给平台。这一步要求网关有 ChannelManager 且会话记过 outboundAddress。
断在哪一环，症状是什么

没有 bus → ⑤ 之后彻底没有 ⑥⑦，用户只看到「正在处理」。有 bus 没 dispatcher → ⑥ 写进去了没人读，结果永远躺在队列里。有 dispatcher 没 InboxMiddleware → ⑦ 跑了但模型收到空输入。没有 ChannelManager → ⑦ 产出了回复但没人投递。四个环节，缺一个都表现为「异步没效果」，但日志完全不同。

陷阱与窍门

1. 以为 agent.channel() 就自带「主动播报」

它的网关没有 ChannelManager，deliverToSession 直接返回 false，子 agent 的 replyTo 投递也会被跳过。要主动播报，必须 GatewayBootstrap（它内部 HarnessGateway.create(cm)）。

2. 往 MsgContext.extra 里塞 traceId / tenant

extra 会被拼进 canonicalKey，于是每个请求都是新会话，用户视角就是「聊两句就失忆」。业务属性用 RuntimeContext（SendOptions.withAttribute / resolver）。

3. 以为默认是「一人一会话」

ChannelConfig.of(id) 和 ChatUiChannel.create() 都是 DmScope.MAIN：所有私聊共用一个 gw-…。上线多用户前必须显式设 PER_PEER（或走 SendOptions）。

4. 用分布式 turn gate 但没处理空结果

TurnBusyException 被转成 Mono.empty()：HTTP 层可能返回 200 + 空 body。要么客户端把空当「忙，请重试」，要么在网络层加幂等重试。

5. 后台工具失败后，模型永远不知道

超时后如果执行抛错，代码只写 registry + 日志，不推 inbox、不唤醒。要补齐，得自己包一层工具（内部 catch 并返回文本），或监听 AsyncToolRegistry 做外部告警。

6. 两条总线指向不同存储

现象：异步任务确实跑完了，但从没触发下一轮。根因几乎都是 agent 用 workspace 默认 bus、dispatcher 用手工 new 的 bus。把同一个实例显式注入两边即可。

7. 唤醒总在主 agent 上执行

runWakeup 用 resolveAgent(null)。多 agent、且各 agent 使用不同 AgentStateStore 时，被唤醒的那一轮加载的是主 agent 的会话历史，不是原 agent 的。需要严格隔离时，自己实现 WakeupTarget，按 gateKey 反查真正的 agent。

8. 把「启动无异常」当成「渠道都可用」

initAll / startAll 把单个渠道的异常吞成日志。启动后逐个确认关键渠道确实连上了，不要只看 start() 没抛。

自检三问

1. ChannelConfig.builder("chatui").dmScope(PER_PEER)，两个用户 u_1 / u_2 各发一句。它们的 gateKey 与 sessionId 分别是什么关系？

gateKey 分别为 chatui|r:u_1 与 chatui|r:u_2；sessionId 是 "gw-" + SHA-256(gateKey) 的前 12 位。两者不同，所以历史互不可见。如果把 scope 换成 PER_CHANNEL_PEER，结果完全一样（源码是同一个分支）；只有换成 PER_ACCOUNT_CHANNEL_PEER 才会多一段 |g:accountId。

2. 用户连发两条，第二条一直没回复，日志里只有一行 debug。最可能是什么？

命中了 withGatedTurn 的 TurnBusyException 分支，被转成 Mono.empty()。说明挂的是短超时的分布式 gate，而不是默认的 LocalSessionTurnGate（后者会阻塞排队）。排查方向：turn gate 实现 + 客户端对空结果的处理。

3. 异步工具超时后，用户收到了「正在后台处理」，然后什么都没有。按顺序检查哪四件事？

① asyncToolTimeout 设了吗（否则压根不卸载）；② messageBus 两侧是不是同一个（否则结果写进 A、没人读 B）；③ 有 WakeupDispatcher.start() 吗（否则队列没人消费）；④ 网关有没有 ChannelManager 且该会话记过 outboundAddress（否则回话没人投递）。若这四件都对，再看后台是否抛异常——那条路不会进 inbox。

20 分钟动手练习

  1. 看一次会话键
    用 ChatUiChannel + PER_PEER，发送前调 previewRoute(InboundMessage.dm("chatui", "u_1", msgs))，打印 context().canonicalKey()、agentId()、matchedBy()。再故意把 binding 的 agentId 写成不存在的名字，确认仍是「有结果、但落到主 agent」，且 matchedBy 仍是 peer。
  2. 验证 extra 会打散会话
    同一用户连续两轮，第二轮在 MsgContext.extra 里加一个 traceId。观察第二轮是否「失忆」（模型看不到上一轮）。再把 traceId 改放到 RuntimeContext，确认记忆恢复正常。
  3. 跑通一条异步链路
    造一个「睡 3 秒」的工具，.asyncToolTimeout(Duration.ofSeconds(1))，并把同一个 WorkspaceMessageBus 显式交给 agent 与 WakeupDispatcher。预期：第一轮立刻收到占位结果；约 3~4 秒后（文件总线 3 秒轮询）agent 自动发起第二轮，事件流里出现一条 HintBlockEvent，且其 hintSource 为 tool_output。
  4. 把异步失败那条路照亮
    让同一个工具在 2 秒后 throw new RuntimeException("boom")。观察：占位结果照旧；之后没有 HintBlock、没有唤醒，只有一条 warn 日志「Background tool execution failed after timeout」。这正好印证陷阱 5。
