19 · Service 入门：五个组件、一条命令、一个能对话的云端 Agent

前 18 章的所有 Agent 都有一个共同点：跑在你自己的进程里。你 new 一个 HarnessAgent，状态写本地 JSON，谁能调用、调用完谁付钱、会话怎么隔离，全由宿主应用决定。 Service 换了一个问题：如果 Agent 不是「库」，而是「平台上的一项服务」，需要多出哪些东西？这一章不讲代码，先把这个平台的 五个组件、三种运行方式、一条起站路径拆开，然后真的起一个站、建一个能对话的 Agent。

读完你能做到

  • 用一句话说清 Service 与 SDK 的分工：SDK 管「Agent 怎么想」，Service 管「Agent 被谁用、在哪跑、结果去哪」
  • 画出 Gateway / Control / Dataplane / Scheduler / PostgreSQL 的调用关系，并说出哪个端口对外、哪个只在内网
  • 用发布包里的 init-env.sh + docker compose 起一套本地站，健康检查通过并登录控制台
  • 创建一个 Managed Agent，在 Chat 里完成两轮对话并确认历史在刷新后仍然存在
  • 解释 BUILDER_ALLOW_LOCAL_ENVIRONMENT 为什么默认是 false，以及打开后工具到底在哪执行

先说为什么：一个库撑不起一个平台

官方对 Service 的定义很克制：面向 Agent 应用的运行、管理与编排平台，把单个 Agent 或多 Agent 协作发布成可调用、可追踪的服务index.md:10。 拆开看，它解决的是四个库解决不了的问题：

身份与权限：谁在用这个 Agent
用户、Namespace、资源归属、私有工作可见性。SDK 只认 RuntimeContext，不负责登录，也不负责「这个用户能不能看那个 Session」。access.md:20
会话与状态：对话活过这个进程
第 07 章的状态存储是「一个 Session 一个槽位」，但槽位在哪个库、多副本怎么共享、会话删了怎么回收，是部署问题。 Service 把 Chat、Session、Run、Attempt 都变成平台对象index.md:68-74。
契约：怎么被别的系统调用
Endpoint、API key、幂等键、SSE 事件流、状态查询。你自己写 Controller 也能做，但每个 Agent 都重写一遍就不叫平台了。index.md:56-62
编排与运维：多个 Agent 怎么协作、出事怎么办
Team 动态委派、Workflow 固定流程、Issue 记录工作、Inbox 验收结果；再往后是备份、升级、排障。 这些在第 14 章是中间件，在平台上是产品功能。
一句话分工

SDK 负责一次推理循环怎么跑；Service 负责这次循环由谁发起、在哪台机器上跑、结果写给谁看。 所以 Service 没有重新实现 Agent，它把第 02–18 章的那个 HarnessAgent 当成执行单元来调度。

五个组件：谁在什么时候被调用

本地安装启动的是一整套栈，不是单个 jar：Gateway、Control、Dataplane、Scheduler 和 PostgreSQLquickstart.md:10。 先记住它们的职责，后面每个「为什么连不上」都能对号入座。

组件容器端口管什么关键事实
Gateway 8080（宿主默认 18080） 唯一公开入口：控制台静态页、管理 API、会话事件、Endpoint 调用都从这里进 纯路径路由，没有数据库、没有自己的鉴权；JWT 与内部令牌由目标组件校验GatewayApp.java:24-26
Control 8081 Agent / Team / Workflow 目录、工作记录、发布、账号与 Namespace Go 写的 aistiod，同时提供控制台 SPA；连 PostgreSQL 的 cp / rt schemacompose.yaml:57-76
Dataplane 8082 Managed Agent 的模型循环、单轮会话执行、SSE 事件、worker HTTP API 会话 turn 的路由目标是它，不是 Controlapplication.yml:37-54
Scheduler 8083 调度与执行协调、外发消息、IM 渠道回调 /api/outbound/** 与飞书/企微/GitHub/GitLab 回调都路由到这里application.yml:65-75
PostgreSQL 5432 一套库、多套 schema：控制面产品库、运行状态库、Java 侧 dp 官方没有为每个组件配独立数据库，恢复时要整体备份configuration.md:18-20

对外只暴露 Gatewayquickstart.md:62。 容器编排里的端口映射是 127.0.0.1:18080 → gateway:8080compose.yaml:120，所以「18080」是宿主端口，「8080」是容器内端口，两个数字都对，只是站在不同网络里。

三种 Agent 运行方式：同一个目录，不同的执行者

Service 不要求所有 Agent 都用它托管。目录里可以同时存在三种运行方式，它们在控制台上看起来一样，区别是模型循环跑在哪index.md:32-48：

方式你负责Service 负责适合
Managed 在控制台填职责、模型、知识与工具 启动 Agent、跑模型与工具循环、保存会话状态 零代码应用、想最快看到效果
External 用 AgentScope 写应用、部署进程、管依赖 登记身份、会话与能力，需要时派发任务 已有代码、要保留框架控制权
Hosted 在主机上安装并登录 Codex / Claude Code / Qoder 等 provider 把工作调度到这台主机，管理任务与交付 复用现成 Coding Agent 的执行能力

这一章只碰 Managed，因为它是唯一「装完站就能用」的路径；External 与 Hosted 留给后面的章节。

最小可跑：一条 compose 命令起整站

官方推荐的本地路径不是从源码构建，而是下载 Release 里的 compose 包quickstart.md:16。解压后目录里有一个 init-env.sh 和一份 compose.yaml；前者生成密钥，后者定义五个服务。 

tar -xzf agentscope-service-VERSION-compose.tar.gz
cd agentscope-service
./init-env.sh VERSION REGISTRY/NAMESPACE
docker compose pull
docker compose up -d --wait --wait-timeout 600

这五行里有两个容易忽略的细节。第一，init-env.sh 会先 umask 077 再写 .envinit-env.sh:13， 所以文件权限是 600，里面是数据库密码、JWT 密钥、内部令牌、Vault 主密钥和初始管理员密码。第二，脚本发现 .env 已存在就直接退出，不覆盖、不重置密码、也不改版本init-env.sh:4-6——升级时想换版本，得自己改 SERVICE_VERSION。

起完之后按顺序验三件事，不要只看容器是不是 Up：

docker compose ps
curl -fsS http://localhost:18080/actuator/health
# 浏览器打开 http://localhost:18080，用 admin 与 .env 里的 AISTIO_BOOTSTRAP_PASSWORD 登录

健康检查走的是 Gateway 的 /actuator/health，暴露的是 health、info 与 gateway 三类端点application.yml:120-127。登录账号 admin 与密码来自 AISTIO_BOOTSTRAP_ADMIN / AISTIO_BOOTSTRAP_PASSWORD，而且只在用户库为空时创建quickstart.md:37；重启不会把密码重置回 .env 里的值，忘了密码只能走管理员重置流程。

本地工具默认是关的，这不是 bug

Managed Agent 要用本机文件系统或 shell，必须先设置 BUILDER_ALLOW_LOCAL_ENVIRONMENT=truequickstart.md:44。它的默认值是 false，而且是双重默认：compose 里写的是 ${BUILDER_ALLOW_LOCAL_ENVIRONMENT:-false}compose.yaml:76，Go 控制面自己的 flag 默认值也是 false，注释写着「只应在可信的开发环境打开」main.go:411-412。

第一个云端 Agent：从「资料助手」到两轮对话

官方快速开始用「整理会议待办」串起整条链路，第一步只有三个动作first-session.md:16-25：

  1. DESIGN → Agents → 新建
    名字填「资料助手」，Runtime 选 AgentScope Managed，Model 留空——留空表示使用管理员在部署里配置的默认模型，不是「没有模型」。
  2. 写 Instructions，选 Environment
    把职责写成可验收的句子，例如「列出任务、负责人、期限与待确认事项；缺少资料时明确说明，不虚构来源」。Advanced settings 里选一个可用 Environment，再保存。
  3. WORK → Chat → New chat
    选择「资料助手」，粘贴一段会议记录，检查回复是否包含负责人、期限和「评审时间待确认」；再追问「还缺少哪些信息？」， 刷新页面重新打开这个 Chat，两轮历史都应该在first-session.md:29-36。

这一段验证的其实是三件不同的事：Agent 定义存进了 Control 的目录库；Session 由 Dataplane 执行并把事件写进会话日志；账号与权限由 Control 的 JWT 链路负责。三件事任何一件没配好， 表现都是「发出去没回复」，但排查位置完全不同。

你在控制台看到的

  • Agent 列表里出现「资料助手」
  • Chat 里能看到流式回复
  • 刷新后历史还在

平台里实际发生的

  • Control 写入 Agent 定义与版本
  • Dataplane 建 Session、跑模型循环、写事件
  • Gateway 把 SSE 原样转给浏览器

端到端：一条消息在五个组件之间怎么走

把「在 Chat 里发一句话」摊开成时间轴，就能看出每个组件的边界。下面这条路径对应 Gateway 的默认路由表application.yml:94-108：

  • 浏览器 打开 http://localhost:18080，请求控制台静态页；Gateway 落到 control-spa 路由。
  • Gateway → Control 登录、读 Agent 列表、建 Session 的元数据都走 /api/**；Control 校验 JWT 并读写 PostgreSQL。
  • Gateway → Dataplane 发送消息走 /api/sessions/{id}/events/**，这类 turn 流量被单独路由到 Dataplaneapplication.yml:37-42。
  • Dataplane → 模型 Dataplane 里跑的是第 02 章那个 HarnessAgent 循环：组装上下文、调模型、执行工具、产出事件。
  • Dataplane → Gateway → 浏览器 事件以 SSE 回传。Gateway 把响应超时放宽到 1 小时，专门为长连接让路application.yml:13-15。
  • Scheduler（异步时） 外发消息、IM 回调、定时任务走 Scheduler；它不参与这条同步对话的主链路，但没有它，自动化与渠道都不工作。
SSE 是这套架构的「压力测试点」

官方在安装文档里专门提醒：反向代理必须支持 SSE——及时转发、不缓存事件流、读取超时足够长quickstart.md:68。因为浏览器看到的「打字机效果」不是前端轮询，而是一条被 Gateway 转发了一个小时的长连接。代理一缓冲，页面就变成 「转圈很久，然后一次性出全文」。

配置速查：改哪里、怎么确认生效

Compose 下所有配置都在 .env；Kubernetes 下敏感项放 Secret，其余走 Chart valuesconfiguration.md:10。最常改的是这几项：

变量作用默认 / 约束
BIND_ADDRESS / GATEWAY_PORT 宿主监听地址与端口 127.0.0.1 / 18080；改了要同步公开 URLconfiguration.md:15
BUILDER_JWT_SECRET 用户令牌签名 至少 32 字符，相关组件保持一致configuration.md:21
BUILDER_INTERNAL_TOKEN 组件间认证 至少 32 字符，不用于用户登录configuration.md:22
BUILDER_VAULT_MASTER_KEY Vault 凭据加密 各组件一致，必须随数据一起备份configuration.md:23
AISTIO_BOOTSTRAP_PASSWORD 初始管理员密码 12–72 字节，只在空用户库生效configuration.md:24
BUILDER_ALLOW_LOCAL_ENVIRONMENT 是否允许 Local Environment 默认 falseconfiguration.md:27；打开后 shell 在 Dataplane 容器里执行，宿主文件不会自动挂进来quickstart.md:48
BUILDER_OAUTH_PUBLIC_URL 用户可访问的公开 origin 必须与 OAuth 回调一致configuration.md:28
DASHSCOPE_API_KEY 默认 DashScope 模型凭据 只在使用该模型路径时需要configuration.md:29

改完之后怎么确认生效，官方给了一张按「修改位置」区分的表，摘要成三步：

  1. Compose 改 .env：重新创建容器
    docker compose up -d --wait。仅 restart 不会把新的环境变量注入已有容器configuration.md:48。
  2. 改 Agent Instructions：保存并发布 revision
    控制台里的草稿不会自动生效；要绑到目标 revision，再新建工作验证configuration.md:50。
  3. 改 Memory 正文：让 Agent 再读一次
    旧回复不会因为知识库更新而自动改写configuration.md:52。

陷阱与窍门

1. 装完站、建了 Agent，一用工具就「没有可用环境」
你会看到
Managed Agent 创建或运行时提示环境不可用，或者工具列表是空的；日志里没有模型错误。
因为
BUILDER_ALLOW_LOCAL_ENVIRONMENT 默认 false，compose 与 Go 控制面双重默认compose.yaml:76main.go:411-412。没有打开时，Local Environment 根本不会出现在可选列表里。
改成
只在可信的本地开发环境把它设成 true，并重新创建容器；同时明白它的边界：shell 在 Dataplane 容器里执行，宿主目录不会自动出现quickstart.md:48。生产环境不要为了省事打开它。
2. 改了 .env，docker compose restart 后配置没生效
你会看到
端口、密钥或开关明明改了，行为还是旧的。
因为
环境变量是在创建容器时注入的，restart 只重启进程，不会重新读 .envconfiguration.md:48。
改成
用 docker compose up -d --wait --wait-timeout 600 重建；改端口时同步改 BUILDER_OAUTH_PUBLIC_URL，否则 OAuth 与渠道回调会回错地址quickstart.md:66-68。
3. 一条 docker compose down -v 把数据卷删了
你会看到
重新起站后账号、Agent、会话全没了；.env 还在，但数据库空了。
因为
三个命名卷分别保存 PostgreSQL、共享 Workspace 和 Artifactquickstart.md:72，-v 会连卷一起删quickstart.md:91。
改成
日常停止只用 docker compose down；要做「干净重来」之前先确认不需要里面的数据，并把 Vault 主密钥和备份放在一起。
4. 照抄示例 .env，版本号是旧的
你会看到
拉镜像时提示版本不存在，或者拉到的不是你要的版本。
因为
仓库里的 .env.example 示例值仍是 2.0.3-rc.1.env.example:17，它只是格式示例，不是当前版本。
改成
以 Release 的 release-manifest.json 为准，把 SERVICE_VERSION 写成发布说明里的准确值；init-env.sh 会用正则校验版本格式，但不会替你判断新旧init-env.sh:8。

自检三问

Gateway 没有数据库、也没有自己的鉴权，为什么不怕被绕过？

因为它只做路径转发，真正的校验在目标组件：用户 API 校验 JWT，组件之间校验内部令牌GatewayApp.java:24-26。同时 Gateway 会把客户端伪造的内部头（X-Builder-Internal-Token 等）剥掉application.yml:16-19，并且把 /api/internal/** 直接 404application.yml:24-30。

把 BUILDER_ALLOW_LOCAL_ENVIRONMENT 改成 true 之后，Agent 的文件和命令在哪里执行？

在 Dataplane 容器里，不是在你的宿主机上。官方安装文档写得很直接：Local 工具运行在 Dataplane 容器内， 主机的文件不会自动挂载quickstart.md:48。 要访问宿主目录，得显式配挂载，并保证容器用户 65532:65532 有权限quickstart.md:74。

同事把 GATEWAY_PORT 从 18080 改成 18081，为什么登录后的 OAuth 回调还是回到 18080？

因为 GATEWAY_PORT 只改宿主端口映射，公开 origin 由 BUILDER_OAUTH_PUBLIC_URL 单独决定.env.example:26-28。两者不一致时，浏览器会被重定向回旧地址。改端口要同时改公开 URL，并重新创建容器。

20 分钟动手练习

目标：亲手验证「端口映射」和「重建才生效」这两件最容易记错的事。

  1. 起站并确认健康
    按本章命令起站，docker compose ps 应该看到 db/control/data/scheduler/gateway 五个服务；curl http://localhost:18080/actuator/health 返回 {"status":"UP"}。
  2. 确认宿主端口与容器端口
    docker compose port gateway 8080 应返回 127.0.0.1:18080。这一步证明你访问的 18080 是映射出来的，容器里的 Gateway 仍监听 8080。
  3. 只 restart，验证配置没变
    把 .env 的 GATEWAY_PORT 改成 18081，执行 docker compose restart gateway，再访问 18081——应该连不上，18080 仍可用。
  4. 重建，验证配置生效
    执行 docker compose up -d --wait，这次 18081 可用、18080 失效。改回 18080 再重建一次收尾。
练习的验收标准

你能不看文档解释：为什么 restart 不生效、为什么容器端口和宿主端口可以不同、为什么改端口还要动 BUILDER_OAUTH_PUBLIC_URL。三个都答上来，这一章就算过关。
