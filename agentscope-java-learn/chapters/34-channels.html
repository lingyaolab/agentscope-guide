34 · 渠道：钉钉 / 飞书 / 企微 / GitHub / GitLab

第 33 章的协议是「标准接口」，这一章的渠道是「平台适配」。钉钉、飞书、企微、GitHub、GitLab 各有自己的认证、 签名、事件格式、去重键与回复 API；Channel 的职责就是把这些差异吃掉，让 Agent 只看到统一的入站消息与出站回复。 真正容易出事的不是模型调用，而是 webhook 验签、重复投递和多副本下的 JVM 内状态。

读完你能做到

  • 说清 Channel 的入站 / 出站管线，以及平台差异由哪一层吸收
  • 解释 IdempotencyStore、BotLoopGuard、AccessTokenStore 三个共享组件各防什么
  • 按平台选择 Stream 还是 HTTP 回调，并配置签名、加密与回调路径
  • 识别 GitHub / GitLab 的评论事件过滤与 bot 自身过滤，避免自激循环
  • 说清多副本下默认 JVM 内去重 / token 缓存的失效边界，以及怎么注入共享实现
  • 按症状判断是验签失败、事件被过滤、重复投递还是 token 刷新问题

渠道不是「另一个 HTTP 入口」

官方把 Channel 定义为「把 Agent 接入真实消息平台」的适配器：每个适配器负责平台特有的认证、webhook 签名校验、 消息解析和回复投递，Agent 代码不需要感知平台差异 index.md:6。 这和 A2A / Agent Protocol 的区别在于：协议定义「怎么互操作」，渠道定义「某个平台的消息怎么进、回复怎么出」。

平台入站方式回复方式主要差异
钉钉Stream WebSocket（默认）或加签 HTTPOpenAPI batchSendStream 无需公网入口；HTTP 模式有重放风险
飞书事件订阅 v2 HTTP 回调IM API 发消息可选 AES 加密；当前仅文本消息
企微加密 HTTP 回调应用消息 / 群聊 API所有回调都加密；文本消息
GitHubWebhook（issue / PR 评论）新建 issue commentHMAC-SHA256；bot 自身评论过滤
GitLabNote hook新建 noteSecret token 可选；bot 自身 note 过滤

入站管线：解析、去重、防循环、交给 Gateway

所有适配器遵循同一模式：入站从平台接收消息（webhook、WebSocket 等），解析成统一的 InboundMessage， 去重、防循环，再通过 Gateway 分发；出站调用平台发送 API 把回复投递回去 index.md:18-21。

平台事件Webhook / Stream

→
去重 / 防循环共享组件
→
GatewayAgent 执行

这条管线里，Agent 只收到「一条已经通过认证与去重的入站消息」；平台签名、加密、事件 id、回复地址都在适配器内解决。 所以排障时先问「消息有没有过验签和去重」，再问「Agent 为什么没回」。

三个共享组件：去重、防循环、token 缓存

所有适配器共享 agentscope-extensions-channel-common 的三个组件：IdempotencyStore 按消息 id 去重，BotLoopGuard 按 peer 限速防止 bot 之间死循环，AccessTokenStore 缓存出站调用平台 API 的 access token index.md:23-27。

组件默认实现 / 默认值状态在哪 IdempotencyStoreTTL 5 分钟、最多 10,000 条JVM 堆IdempotencyStore.java:40-43 BotLoopGuard20 条 / 60 秒窗口，触发后冷却 60 秒JVM 堆BotLoopGuard.java:23-49 AccessTokenStoreInMemoryAccessTokenStore，一个实例只服务一个凭据JVM 堆AccessTokenStore.java:18-37

AccessTokenStore 的约束要特别注意：它不按 key 分组，一个实例只保存一个凭据的 token； 把同一个 store 实例共享给不同凭据的 provider，会静默混用 token AccessTokenStore.java:21-31。 多实例部署时，应该用按 channel id 分 key 的共享存储实现，并通过 channel 工厂注入。

安全边界：签名、加密与重放

五家平台的认证方式不同，但共同点是：webhook 请求必须先在适配器内通过验签或解密，才会进入 Gateway。 不要自己写「先解析 JSON 再验签」的中间件，那等于把未认证输入交给解析器。

平台认证 / 加密失败时
钉钉 HTTPtimestamp / sign 头做 HMAC-SHA256；可选 aesKey 解密签名错或时间戳过期拒绝
飞书X-Lark-Signature + 可选 AES-256-CBC 解密验签失败拒绝
企微token + timestamp + nonce + 加密体解密 / 验签失败拒绝
GitHubX-Hub-Signature-256 对 body 做 HMAC-SHA256签名不匹配拒绝
GitLabSecret token（本适配器必填，平台侧可留空）不匹配拒绝
钉钉 HTTP 回调：不加密就有重放窗口

钉钉文档明确提醒：请求签名只认证 timestamp 请求头；不开启消息体加密时，被截获的签名对在有效时间窗口内仍可重放 dingtalk.md:78。 面向公网的 HTTP 回调应开启 aesKey，或者优先用 Stream 模式。

钉钉：Stream 默认，HTTP 可选

钉钉适配器支持两种接收模式：Stream 是默认的持久 WebSocket，不需要公网 webhook；HTTP 回调由钉钉以 App Secret 加签后 POST 到你的 Spring 应用 dingtalk.md:6。 Stream 断线后以指数退避重连，间隔从 1 秒增长到 60 秒上限 dingtalk.md:88-90。 

DingTalkChannel channel = DingTalkChannel.fromProperties(
    "my-dingtalk",
    ChannelConfig.of("my-dingtalk", "main"),
    Map.of(
        "appKey", "your-app-key",
        "appSecret", "your-app-secret",
        "robotCode", "your-robot-code"
    ));

HTTP 模式需要额外设置 "mode": "http"，开启消息体加密时还要 43 位 base64 的 aesKey； 回调地址是 /api/channels/dingtalk/{channelId}/callback dingtalk.md:51-76。 回复走 OpenAPI 的 batchSend（单聊）或 groupMessages/send（群聊），不通过 HTTP 响应返回 dingtalk.md:84-86。

飞书：事件订阅 v2 + 可选加密

飞书通过事件订阅 v2 回调接入，FeishuCallbackController 自动注册在 /api/channels/feishu/{channelId}/callback，并自动处理 URL 验证握手 feishu.md:6 feishu.md:50。 必填只有 appId 与 appSecret；encryptKey 与 verificationToken 可选 feishu.md:52-61。 

FeishuChannel channel = FeishuChannel.fromProperties(
    "my-feishu",
    ChannelConfig.of("my-feishu", "main"),
    Map.of(
        "appId", "cli_xxxxx",
        "appSecret", "your-app-secret"
    ));

配置 encryptKey 后，回调 body 以 {"encrypt":"<base64>"} 到达，适配器自动解密并校验 X-Lark-Signature feishu.md:63-65。 入站按 event_id 去重，当前只支持文本消息；出站用 tenant access token，token 缓存并在约 80% TTL 时主动刷新 feishu.md:67-71。

企业微信：所有回调都加密

企微通过加密回调接入，控制器注册在 /api/channels/wecom/{channelId}/callback； 必填 corpId、agentId、secret、token、encodingAesKey wecom.md:6 wecom.md:52-62。 它用 WeComCrypto 按企微规范处理解密与签名校验，没有「明文回调」模式 wecom.md:64-66。 

WeComChannel channel = WeComChannel.fromProperties(
    "my-wecom",
    ChannelConfig.of("my-wecom", "main"),
    Map.of(
        "corpId", "your-corp-id",
        "agentId", "1000002",
        "secret", "your-secret",
        "token", "your-callback-token",
        "encodingAesKey", "your-encoding-aes-key"
    ));

入站先做 URL 验证（echostr），再解密、按 MsgId 去重、映射文本消息、防循环，最后交给 Gateway wecom.md:68-70。 出站走 /cgi-bin/message/send（单聊）或 /cgi-bin/appchat/send（群聊）。

GitHub：评论线程 + 自激过滤

GitHub 适配器响应 issue / PR 评论，Agent 以新评论形式回复。它要求 PAT 具备 issues:write 与 pull_requests:write，webhook 需要 Secret 用于 X-Hub-Signature-256 校验 github.md:6-30。 

GitHubChannel channel = GitHubChannel.fromProperties(
    "my-github",
    ChannelConfig.of("my-github", "main"),
    Map.of(
        "token", "ghp_xxxxxxxxxxxx",
        "webhookSecret", "your-webhook-secret"
    ));

入站管线是：HMAC 验签 → 事件类型过滤（只收 issue_comment 与 pull_request_review_comment）→ comment.id 去重 → bot 自身评论过滤 → 只处理 action=created → 防循环 → Gateway github.md:65-69。 启动时通过 GET /user 解析 bot 用户 id；来自该 id 的评论会被静默丢弃 github.md:61-63。

每个 issue / PR 线程建模为 THREAD peer，id 形如 owner/repo#number， 因此同一线程共享一个 session，Agent 能看到线程内的历史 github.md:71-73。

GitLab：Note hook + bot 自身过滤

GitLab 适配器响应 issue / merge request 评论（Note），Agent 以新 note 回复。PAT 需要 api 权限， webhook 勾选 Note events；GitLab 平台侧的 Secret token 可留空，但本适配器构造时必须配置 webhookToken gitlab.md:6-29。 

GitLabChannel channel = GitLabChannel.fromProperties(
    "my-gitlab",
    ChannelConfig.of("my-gitlab", "main"),
    Map.of("token", "glpat-xxxxxxxxxxxx",
           "webhookToken", "your-webhook-token"));

入站管线是：note.id 去重 → bot 自身 note 过滤 → 映射 → 防循环 → Gateway gitlab.md:61-65。 启动时通过 GET /api/v4/user 解析 bot 用户 id，来自该 id 的 note 会被丢弃 gitlab.md:57-59。 生产环境应配置 Secret token；文档标注它是可选的，但不配就等于少一层来源校验。

路由：channelId、agentId 与 peer

每个渠道用 ChannelConfig.of(channelId, defaultAgentId) 指定路由， GatewayBootstrap 再把 agent 与 channel 组装起来 dingtalk.md:33-48。 不同平台的 peer 模型不同：GitHub 把 issue / PR 线程当 THREAD peer；其他平台按用户 / 会话 / 群组划分。

peer 决定 session

Agent 是否「记得上一句」取决于 peer 如何映射到 session。GitHub 的线程共享 session； 如果你把每个评论都当独立 peer，就会得到「每句都失忆」的行为。排障时先看 peer id，而不是先改提示词。

多副本：默认状态只在 JVM 里

三个共享组件默认都把状态放在 JVM 内：IdempotencyStore、InMemoryAccessTokenStore， 以及 BotLoopGuard。单进程没问题；多副本负载均衡后，平台重试可能落到不同 Pod， 每个 Pod 都认为「第一次见」，于是重复处理 index.md:29-38.

适配器工厂提供了注入入口：传共享 InboundEventDeduplicator 让所有副本识别同一事件， 传共享 AccessTokenStore 让一个副本的刷新服务整个部署 FeishuChannel.java:142-147 GitHubChannel.java:106-110。

BotLoopGuard 没有共享注入入口

当前工厂方法里 BotLoopGuard 是直接 new 的，它防的是单进程内的失控循环，不是跨副本总速率。 多副本要限制总流量，得在网关 / 平台侧另做，或自己包装 channel 层。

部署：回调路径、公网与多副本

所有 HTTP 渠道都要求你的应用可达平台回调地址：钉钉 /api/channels/dingtalk/{channelId}/callback、 飞书 /api/channels/feishu/{channelId}/callback、企微 /api/channels/wecom/{channelId}/callback、 GitHub /api/channels/github/{channelId}/webhook、GitLab /api/channels/gitlab/{channelId}/webhook。路径要完整保留 {channelId}，否则控制器无法路由。

多副本时，负载均衡只保证「有一个副本收到」，不保证「只有一个副本处理」；共享去重与 token 缓存是生产必选项。 钉钉 Stream 则要确认每个副本的 WebSocket 连接都被平台正确分配消息，避免重复消费。

六个坑：把渠道当普通 Controller

坑一：先解析 JSON 再验签。验签应使用平台约定的原始请求字节；先反序列化再重新序列化通常会改变字节， GitHub 的 HMAC 会直接失败。

坑二：多副本用默认去重。IdempotencyStore 只在 JVM 内有效；平台重试落到另一个 Pod 就会重复处理 index.md:29-38。

坑三：多个凭据共用一个 token store。AccessTokenStore 不按 key 分组，会混用 token AccessTokenStore.java:21-31。

坑四：飞书 / 企微期待图片和卡片。当前映射只覆盖文本；其他类型需要自己下载与转换。

坑五：GitHub / GitLab 不配 bot 过滤。bot 自己的评论会再次触发自己，形成自激循环；适配器会解析 bot 用户 id 并丢弃 github.md:61-63 gitlab.md:57-59。

坑六：钉钉 HTTP 只验签不加密。签名对在有效时间窗口内可重放；公网回调应开 aesKey dingtalk.md:78。

自测：三个判断题

飞书和企微适配器会把图片、文件、卡片都转成文本给 Agent 吗？

不会转换成可读内容。飞书与企微会把媒体消息映射为占位文本并保留 ChannelMediaMetadata， 图片、文件、卡片仍需自己下载与转换 feishu.md:69 wecom.md:70。

多副本部署时，默认的 IdempotencyStore 能跨 Pod 去重吗？

不能。它把状态放在 JVM 堆，只在单进程内生效；多副本要注入共享 InboundEventDeduplicator IdempotencyStore.java:31-33。

GitHub 的回复是通过 webhook 请求的 HTTP 响应返回吗？

不是。入站 webhook 只负责收消息；回复通过 GitHub REST API 新建一条 issue comment github.md:69。

练习：接一个「评论即回复」的 GitHub 渠道

目标不是让 webhook 返回 200，而是能证明「验签、去重、bot 过滤、回复、多副本」五段都成立。建议 50 分钟：

  1. 准备 PAT 与 webhook
    创建具备 issues:write / pull_requests:write 的 PAT，配置 webhook Secret 与评论事件。
  2. 启动 channel
    用 GitHubChannel.fromProperties 启动，确认日志里解析出了 bot login。
  3. 发一条评论
    在 issue 里评论，观察 webhook 验签、comment.id 去重与 Agent 回复。
  4. 制造重复投递
    用相同 comment.id 重放 webhook，确认第二次被去重，不产生第二条回复。
  5. 制造自激
    让 bot 回复后再触发一次评论事件，确认 bot 自身评论被过滤，不会无限循环。
  6. 换一个 peer
    在另一个 PR 线程评论，确认 peer id 为 owner/repo#number 且 session 独立。
  7. 模拟多副本
    启动两个实例，用共享去重存储替换默认 IdempotencyStore，再重放一次事件。
  8. 写三行结论
    分别写「谁验签」「谁去重」「回复走哪个 API」，确保每行都能在日志或源码里找到证据。
