08 · 权限与人机交互

第 07 章结尾留了个伏笔：AgentState 里有个 permissionContext 一直没展开。这一章回答 「模型说要用工具，谁有权说不」。答案是五步判定加一条会话级模式，而「问人」不是回调—— 它会让 call 提前返回，等你第二次带着 ConfirmResult 回来。

读完你能做到

  • 背出权限判定的先后顺序，说清为什么 allow 规则排在第 4 位而不是第 1 位
  • 选对 5 种模式，知道 EXPLORE / ACCEPT_EDITS 只认 isReadOnly()
  • 写出完整 HITL 回路：PERMISSION_ASKING → 取出 ASKING 的 ToolUseBlock → ConfirmResult → 第二次 call
  • 知道哪类工具压根不走权限系统（不继承 ToolBase 的 AgentTool）
  • 识别 2.0.4 里三处「文档说有、代码没接线」的能力，不把时间浪费在调不通的 API 上

先说为什么：模型的手比嘴危险

sysPrompt 只能影响模型想做什么，管不住它能做什么。一段被污染的网页、一个恶意 MCP server、一次「帮我把这个目录清空」的误判，都可能让它去读 .env、覆盖配置、执行 rm -rf。权限系统就是工具执行前的最后一道闸。

只靠 sysPrompt（不要这么做）

  • 「不要删除重要文件」——模型可以不听
  • 提示注入可以覆盖任何口头约定
  • 出了问题没有审计点，只能看日志猜
  • 所有工具一视同仁，读和写没有区别

权限引擎（2.0）

  • 三道闸：静态规则 + 模式 + 工具自检
  • DENY 写死在代码里，模型再会说也过不去
  • ASK 会把控制权交回你的 UI，由人拍板
  • 每次决策都有 PermissionDecision，可记可审计

三者分工：模式是全局默认（这个会话是探索还是放行），规则是按工具名的例外 （这个工具永远拒），工具自检是运行时的动态判断（这条命令里带了 rm -rf 吗）。 下面先跑通一条最完整的链路。

权限包入口：PermissionEngine.java:47；AgentState 里的权限子状态：AgentState.java:207

最小可跑：一次 ASK，一次人工放行

这段是本章唯一必须亲手跑通的代码。它展示了 HITL 的全部四个动作：暂停 → 取单 → 回复 → 继续。

注意两次 call 用的是同一个 RuntimeContext——换成别的就是另一个槽位， 找不到挂起的那批工具调用。 

import io.agentscope.core.ReActAgent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.ConfirmResult;
import io.agentscope.core.message.GenerateReason;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.ToolCallState;
import io.agentscope.core.message.ToolUseBlock;
import io.agentscope.core.message.UserMessage;
import io.agentscope.core.permission.PermissionBehavior;
import io.agentscope.core.permission.PermissionContextState;
import io.agentscope.core.permission.PermissionMode;
import io.agentscope.core.permission.PermissionRule;
import io.agentscope.core.tool.Tool;
import io.agentscope.core.tool.ToolParam;
import io.agentscope.core.tool.Toolkit;

import java.util.List;
import java.util.Map;

public class HitlDemo {

    public static class FileTools {
        @Tool(name = "delete_file", description = "永久删除一个文件，无法撤销。")
        public String delete(
                @ToolParam(name = "path", description = "要删除的文件路径") String path) {
            return "deleted: " + path;
        }
    }

    public static void main(String[] args) {
        Toolkit toolkit = new Toolkit();
        toolkit.registerTool(new FileTools());

        // 1) 声明规则：delete_file 每次都要问
        PermissionContextState perm =
                PermissionContextState.builder()
                        .mode(PermissionMode.DEFAULT)
                        .addAskRule(
                                "delete_file",
                                new PermissionRule(
                                        "delete_file", null, PermissionBehavior.ASK, "session"))
                        .build();

        ReActAgent agent =
                ReActAgent.builder()
                        .name("Guarded")
                        .sysPrompt("你是文件助手，按用户要求调用工具。")
                        .model("dashscope:qwen-plus")
                        .toolkit(toolkit)
                        .permissionContext(perm)
                        .build();

        RuntimeContext ctx =
                RuntimeContext.builder().userId("alice").sessionId("s-001").build();

        // 2) 第一次 call：命中了 ASK，agent 暂停，不会真的删
        Msg first = new UserMessage("user", "删掉 /tmp/a.txt");
        Msg paused = agent.call(List.of(first), ctx).block();
        if (paused == null
                || paused.getGenerateReason() != GenerateReason.PERMISSION_ASKING) {
            System.out.println("模型没有调用工具，或规则没命中：" + paused);
            return;
        }

        // 3) 从返回的 Msg 里取出状态为 ASKING 的工具调用
        List<ToolUseBlock> asking =
                paused.getContent().stream()
                        .filter(b -> b instanceof ToolUseBlock)
                        .map(ToolUseBlock.class::cast)
                        .filter(t -> t.getState() == ToolCallState.ASKING)
                        .toList();
        asking.forEach(t -> System.out.println("待确认: " + t.getName() + " " + t.getInput()));

        // 4) 用户点了「允许」；把 ConfirmResult 塞进下一条消息的 metadata
        List<ConfirmResult> results =
                asking.stream().map(t -> new ConfirmResult(true, t)).toList();
        Msg resumeMsg =
                UserMessage.builder()
                        .metadata(Map.of(Msg.METADATA_CONFIRM_RESULTS, results))
                        .build();
        Msg resumed = agent.call(List.of(resumeMsg), ctx).block();

        System.out.println(resumed.getTextContent());
    }
}

可编译参考：PermissionHITLExample.java:159；metadata key：Msg.java:77

四个动作，一个都不能少

暂停靠 getGenerateReason() == PERMISSION_ASKING 识别；取单必须筛 getState() == ASKING（同一批里可能有已被规则自动拒绝的）；回复靠第二次 call 携带 ConfirmResult；继续是框架在新一轮里自动执行那些被放行的工具。没有回调、没有 wait—— agent 是「返回了」，不是「卡住了」。

暂停后不带确认再 call，会直接抛异常

只要上下文里还有 ASKING 的工具调用，下一次 call 必须带 ConfirmResult，否则抛 IllegalStateException，错误信息里会列出待确认的 工具名和 id，并直接给你一段可复制的恢复代码ReActAgent.java:1960。所以「忘了回确认、直接问下一句」是 HITL 里最常见的崩溃点。

逐行解读：五种模式、四种行为、六步判定

1. 五种模式，差别比名字大

模式实际行为（按代码）什么时候用
DEFAULT规则不命中就 ASK；工具自检可以先拒或先放默认值，人在场的交互式应用
ACCEPT_EDITS只放行 isReadOnly()==true 的工具，其余继续走规则 → 默认仍然是 ASK想减少只读确认的编码场景（别指望它自动允许写入）
EXPLOREisReadOnly()==true → 放行；否则直接 DENY，连 allow 规则都不看代码探索、只读分析
BYPASS规则与工具自检之后仍然没有结论时，一律放行完全可信的沙箱；不是「关掉权限系统」
DONT_ASK只把默认 ASK 降级成 DENY；显式 addAskRule(...) 命中的 ASK 与工具自检的 safety ASK 仍会暂停无人值守、CI、定时任务

五个取值与注释：PermissionMode.java:33；EXPLORE 的只读判定：PermissionEngine.java:229

2. 四种行为，PASSTHROUGH 是「我不管」

行为含义工具自检返回它时
ALLOW放行立即放行，跳过后续 allow 规则与 BYPASS 判定
DENY拒绝立即拒绝，BYPASS 也救不回来
ASK问人只有当 decisionReason 含 "safety" 时立即暂停；否则继续走 allow 规则
PASSTHROUGH交给引擎继续走 allow 规则 → BYPASS → 默认 ASK

四个取值：PermissionBehavior.java:32；ToolBase 默认返回 PASSTHROUGH：ToolBase.java:235

3. 六步判定：allow 规则为什么排在后面

  • 第 1 步
    deny 规则。命中即拒绝，最高优先级，任何模式都盖不住。
  • 第 2 步
    ask 规则。命中即暂停——ask 比 allow 更强势，同一个工具身上两者共存时，问。
  • 第 3 步
    工具自检。先看 EXPLORE/ACCEPT_EDITS 的只读判定，再调 tool.checkPermissions()。
  • 第 4 步
    allow 规则。到这里才轮到「无条件放行」。前面任何一步给出 DENY/ASK，都到不了这。
  • 第 5 步
    BYPASS 兜底放行。
  • 第 6 步
    默认 ASK；DONT_ASK 下改为 DENY。

checkPermission 的六段代码：PermissionEngine.java:139；allow 规则在 continueAfterToolCheck 里：:180

这个顺序意味着：allow 规则不是「白名单」。它挡不住工具自检的 DENY，也压不过 ask 规则； 反过来，工具自检返回 ALLOW 时，你连 allow 规则都不需要写。想把「这个工具永远放行」写在配置里，就得保证 工具自检没先拒它。

4. 一个隐藏开关：isTrivial() 决定走不走引擎

PermissionContextState 有一个 isTrivial()：模式是 DEFAULT、没有工作目录、 三张规则表全空时为 true。此时 agent 不走完整的 PermissionEngine，而是退回轻量路径—— 只调工具的 checkPermissions()，返回 ASK 或 DENY 都会拦，只有 PASSTHROUGH/ALLOW 直接放行ReActAgent.java:3336。

「没配权限」不等于「没有权限检查」

轻量路径下，注解式 @Tool 默认返回 PASSTHROUGH → 直接执行；但非只读的 MCP 工具 自检返回 ASK → 仍然会暂停问你。反过来，只要你设了 .mode(EXPLORE)， isTrivial() 立刻变成 false，完整引擎上线，判定规则全变。所以「加了个 mode， 行为突然不一样了」不是 bug。

isTrivial 的五个条件：PermissionContextState.java:107；轻量路径：ReActAgent.java:3378

HITL 完整回路：从暂停到继续

阻塞式 call 是入门写法；Web 后端更常见的是事件流：把 agent 的每一步推给前端，前端渲染成 「这张卡片要不要批准」。两者内核一样，只是拿 ToolUseBlock 的位置不同。

1. 事件流版本：监听 RequireUserConfirmEvent

import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.RequireUserConfirmEvent;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.UserMessage;

import java.util.List;
import java.util.Map;
import java.util.concurrent.atomic.AtomicReference;

RuntimeContext ctx =
        RuntimeContext.builder().userId("alice").sessionId("s-001").build();

// 1) 跑一轮，把「要确认」的事件捡出来
AtomicReference<RequireUserConfirmEvent> pending = new AtomicReference<>();
agent.streamEvents(new UserMessage("user", "删掉 /tmp/a.txt"), ctx)
        .doOnNext(
                event -> {
                    if (event instanceof RequireUserConfirmEvent confirm) {
                        pending.set(confirm);
                    }
                })
        .blockLast();

RequireUserConfirmEvent confirm = pending.get();
if (confirm == null) {
    return;   // 这一轮没有工具需要确认
}

// 2) 事件里直接带出了 ToolUseBlock 列表
List<ConfirmResult> results =
        confirm.getToolCalls().stream().map(t -> new ConfirmResult(true, t)).toList();

// 3) 用同一个 ctx 恢复（换了 ctx = 换了槽位，找不到挂起的调用）
Msg resumeMsg =
        UserMessage.builder()
                .metadata(Map.of(Msg.METADATA_CONFIRM_RESULTS, results))
                .build();
Msg resumed = agent.call(List.of(resumeMsg), ctx).block();

事件流可编译参考：PlanModeAutoExample.java:140；事件类：RequireUserConfirmEvent.java:26

事件流的额外好处：RequireUserConfirmEvent 同时带 replyId，你可以用它把「问」和「答」 配对（多轮并行确认时尤其重要）。

2. ConfirmResult 的四个字段，每个都有用

字段作用注意
confirmedtrue 放行，false 拒绝没有任何默认值，必须显式给
toolCall要确认的那个调用id 必须与 ASKING 的一致；可以传一个改过参数的副本
rules顺手加几条规则，下次免问只在 confirmed=true 时注册进引擎
reason拒绝的理由会成为模型看到的工具结果文本，不写就是默认文案

「用户改了参数再放行」是常见需求，把 toolCall 换成一个同 id 的新块就行：

ToolUseBlock edited =
        ToolUseBlock.builder()
                .id(t.getId())        // id 必须原样，否则对不上 ASKING
                .name(t.getName())
                .input(Map.of("path", "/tmp/b.txt"))
                .build();

ConfirmResult result = new ConfirmResult(true, edited);   // 执行的是改过的参数

ConfirmResult 四个字段与三个构造器：ConfirmResult.java:35；确认后改为 ALLOWED 并注册规则：ReActAgent.java:2098

3. 拒绝之后，模型看到什么

谁拒的写回 context 的文本模型接下来会
人在 HITL 里点「拒绝」且没填理由Permission denied by user看到拒绝，换一种做法或解释原因
人在 HITL 里填了 reason你填的那句话根据理由调整（「换个目录」之类）
命中 deny 规则Permission denied by rules同上，但连问都不会问

两句默认文案：ReActAgent.java:1707；reason 的优先级：:2108

被拒不是「报错」，是一轮正常的工具结果

拒绝会生成一条 ToolResultBlock，状态是 DENIED，带完整的 ToolResultStart / TextDelta / End 事件链。模型拿到它，就像拿到 「这个工具返回了错误」一样继续推理。所以拒绝之后 agent 不会崩，它会换个办法——除非你用中间件把 它停下来。

4. ToolCallState 与 ToolResultState 别搞混

枚举取值用在哪
ToolCallStatePENDING / ASKING / ALLOWED / SUBMITTED / FINISHED工具调用本身的状态；没有 DENIED
ToolResultState包含 DENIED 等工具结果的状态；拒绝体现在这里

所以「筛待确认」只能筛 ASKING；被拒的调用已经不在 ASKING 里了，它对应一条 DENIED 的结果。

AllToolsDeniedEvent 不会自动停

当一轮里所有工具调用都被拒，框架会发一个 AllToolsDeniedEvent，但它只是个通知：没有中间件 响应的话，agent 会继续下一轮推理（这是为了兼容旧行为）。想「一拒就停」，得由中间件看到它之后发 RequestStopEvent，并把停止原因写成 GenerateReason.ALL_TOOLS_DENIED——这部分在第 09 章。

2.0.4 里「文档写着、代码没接线」的四件事

这一节是本章最省钱的部分。下面四项能力在文档、注释里都描述得像现成的，翻实现却会发现它们只是数据或 字段，没有真正的执行代码。先知道边界，再决定要不要自己补。

看起来能用2.0.4 的实际情况你该怎么做
「建议规则」一键免问suggestedRules 只生成、没人读自己塞 PermissionRule 进 ConfirmResult.rules
ACCEPT_EDITS 自动放行工作目录内的编辑引擎从不读 workingDirectories只当「只读放行」用；要目录白名单就自己写规则
.stopOnReject(true) 拒绝即终止只存进 ReactConfig，无消费点用中间件监听 AllToolsDeniedEvent
内置危险路径保护常量和 isDangerousPath 只有单测在调自己继承 ToolBase 在自检里调用

1) suggestedRules：生成了，但没人接

PermissionDecision 有一个 suggestedRules 字段，引擎在「ask 规则命中」和「默认 ASK」两个 分支里都会调用 tool.generateSuggestions(input) 把它填上PermissionEngine.java:152。但全仓找不到一处 getSuggestedRules() 的调用：RequireUserConfirmEvent 只带 List<ToolUseBlock>，而 ToolUseBlock 根本没有这个字段。文档里的 ConfirmResult.acceptedRules 和 toolCall.getSuggestedRules() 都不存在， 照抄会编译不过。

自己实现「不再问」很简单——把默认建议等价写成一条工具级 ALLOW 规则： 

PermissionRule remember =
        new PermissionRule(t.getName(), null, PermissionBehavior.ALLOW, "suggested");

ConfirmResult result = new ConfirmResult(true, t, List.of(remember));

没有被消费的 getter：PermissionDecision.java:93；默认建议的内容：ToolBase.java:253

2) workingDirectories：存了，但引擎不读

PermissionContextState 用一整张表存工作目录，AdditionalWorkingDirectory 的注释也写着它 「驱动 ACCEPT_EDITS 的自动放行」。但 PermissionEngine 全文只读 getMode() 和三张规则表，getWorkingDirectories() 一次都没被调用PermissionEngine.java:210。ACCEPT_EDITS 的实际行为只有一条：isReadOnly() 为真的工具放行，其余继续走规则。

官方示例自己的注释也承认了这一点：「EXPLORE mode auto-denies non-readOnly tools before allow rules are checked, so it should only be used with ToolBase tools that set readOnly(true)」PermissionContextExample.java:99。

3) stopOnReject：设了，但没人读

ReactConfig 的注释说它控制「拒绝是否终止循环」，ReActAgent.builder().stopOnReject(true) 也能设ReActAgent.java:5241。但整个 core 里除了赋值和 getter，没有任何代码读它。实际行为恒定为：拒绝结果写回 context，模型下一轮继续。 要「一拒就停」，还是得靠中间件。

4) 危险路径：常量很全，但只有单测在用

ToolDangerousPathConstants 列了 22 个敏感文件（.env*、.ssh/config、 .npmrc……）、4 个敏感目录（.git / .vscode / .idea / .ssh）和 11 条高危命令；ToolBase.isDangerousPath() 还实现了符号链接解析ToolDangerousPathConstants.java:37。但生产代码里没有任何调用点，内置的 view_text_file / write_text_file / list_directory 又都是注解工具（不是 ToolBase 子类），压根用不上它。下一节给出补法。

自己补上缺口：三招够用

上一节那四项「没接线」的能力，其实都能在自己的代码里补回来。只需要三招：标 readOnly、 写 ToolBase 子类、运行时换模式。

第 1 招：先让模式认识你的工具

EXPLORE / ACCEPT_EDITS 的唯一依据就是工具自报的 isReadOnly()，而 @Tool 注解的 readOnly 默认是 false。不标它，一个纯粹的查询工具在探索模式下也会被拒。 

// 只读：在 EXPLORE / ACCEPT_EDITS 下自动放行
@Tool(name = "search_docs", description = "在文档库里检索", readOnly = true)
public String search(
        @ToolParam(name = "query", description = "检索词") String query) {
    return "命中 3 条：...";
}

// 会改状态：不要标 readOnly，否则 EXPLORE 会错误放行
@Tool(name = "publish_doc", description = "发布文档")
public String publish(
        @ToolParam(name = "id", description = "文档 id") String id) {
    return "published: " + id;
}

@Tool.readOnly() 默认为 false：Tool.java:107；ToolBase.isReadOnly() 是 final，只能从 builder 传：ToolBase.java:173

内置文件工具没标 readOnly

自带的 view_text_file / list_directory / write_text_file 都是注解工具， 一个都没标 readOnly = true。所以在 EXPLORE 下，连「读文件」都会被拒。想在只读模式里用内置读工具， 只能自己包一层 readOnly = true 的工具，或者干脆不配 EXPLORE、改用 deny 规则挡写工具。

第 2 招：继承 ToolBase，把安全检查写进工具里

这一步同时补上「危险路径」和「工具自检」两件事：isDangerousPath() 自带 22 个敏感文件名、4 个敏感目录和符号链接解析， 你要做的只是在合适的时机调它。 

import io.agentscope.core.message.TextBlock;
import io.agentscope.core.message.ToolResultBlock;
import io.agentscope.core.permission.PermissionBehavior;
import io.agentscope.core.permission.PermissionContextState;
import io.agentscope.core.permission.PermissionDecision;
import io.agentscope.core.tool.ToolBase;
import io.agentscope.core.tool.ToolCallParam;
import io.agentscope.core.tool.ToolDangerousPathConstants;

import java.util.List;
import java.util.Locale;
import java.util.Map;
import reactor.core.publisher.Mono;

public class SafeDeleteTool extends ToolBase {

    public SafeDeleteTool() {
        super(
                ToolBase.builder()
                        .name("safe_delete")
                        .description("删除文件；敏感路径直接拒绝")
                        .inputSchema(
                                Map.of(
                                        "type",
                                        "object",
                                        "properties",
                                        Map.of(
                                                "path",
                                                Map.of("type", "string", "description", "文件路径")),
                                        "required",
                                        List.of("path")))
                        .readOnly(false));
    }

    @Override
    public Mono<ToolResultBlock> callAsync(ToolCallParam param) {
        String path = String.valueOf(param.getInput().get("path"));
        return Mono.just(
                new ToolResultBlock(
                        param.getToolUseBlock().getId(),
                        getName(),
                        List.of(TextBlock.builder().text("deleted: " + path).build())));
    }

    @Override
    public Mono<PermissionDecision> checkPermissions(
            Map<String, Object> input, PermissionContextState context) {
        String path = String.valueOf(input.getOrDefault("path", ""));
        String lower = path.toLowerCase(Locale.ROOT);

        // 1) 敏感路径：直接 DENY，BYPASS 也放不过去
        if (isDangerousPath(path)) {
            return Mono.just(PermissionDecision.deny("拒绝操作敏感路径: " + path));
        }

        // 2) 参数里出现高危片段：要问人，decisionReason 必须带 safety
        boolean risky =
                ToolDangerousPathConstants.DANGEROUS_COMMANDS.stream()
                        .anyMatch(cmd -> lower.contains(cmd.toLowerCase(Locale.ROOT)));
        if (risky) {
            return Mono.just(
                    PermissionDecision.builder()
                            .behavior(PermissionBehavior.ASK)
                            .message("参数含高危命令片段：" + path)
                            .decisionReason("safety: dangerous command fragment")
                            .build());
        }

        // 3) 其余交给引擎按规则 / 模式评估
        return Mono.just(PermissionDecision.passthrough(getName()));
    }
}

完整可编译的 ToolBase 子类：ToolBaseExample.java:135；isDangerousPath 与符号链接解析：ToolBase.java:263；常量表：ToolDangerousPathConstants.java:67

两个细节：decisionReason 与 contains 的粗糙

第一，PermissionDecision.ask("safety: ...") 不会触发「立即暂停」——静态工厂只设 message， decisionReason 是 null，引擎查不到 "safety" 就继续走 allow 规则。必须用 builder() 显式写 decisionReason。第二，contains 匹配很粗：DANGEROUS_COMMANDS 里有 "dd"， /tmp/add.txt 这种路径也会命中。真做命令工具时换成前缀匹配或词边界匹配。

还有一处：PermissionRule.ruleContent 要靠工具的 matchRule() 解释，而 ToolBase 的默认实现 只认 null——非空模式一律不匹配。想让「按路径」的规则生效，得自己重写： 

@Override
public boolean matchRule(String ruleContent, Map<String, Object> input) {
    // 规则写成 "path:/tmp/" 时按前缀命中；其余交给默认实现
    if (ruleContent != null && ruleContent.startsWith("path:")) {
        String prefix = ruleContent.substring("path:".length());
        return String.valueOf(input.get("path")).startsWith(prefix);
    }
    return super.matchRule(ruleContent, input);
}

默认只匹配 null：ToolBase.java:244；引擎怎么用它：PermissionEngine.java:310

第 3 招：运行时换模式，而不是重启 agent

模式和规则都存在槽位里，属于会话状态，可以随时改。改完立刻生效，而且只影响这一个 (userId, sessionId)。 

RuntimeContext ctx =
        RuntimeContext.builder().userId("alice").sessionId("s-001").build();

// 临时切成只读：后面的 call 全部按 EXPLORE 判定
agent.setPermissionMode(ctx, PermissionMode.EXPLORE);
doSomething(agent, ctx);

// 用完切回（规则全保留，withMode 只换模式）
agent.setPermissionMode(ctx, PermissionMode.DEFAULT);

// 想改规则：整体替换上下文，改完会重建该槽位的引擎并落盘
PermissionContextState cur =
        agent.getAgentState("alice", "s-001").getPermissionContext();
PermissionContextState next =
        PermissionContextState.builder()
                .mode(cur.getMode())
                .addAllowRule(
                        "safe_delete",
                        new PermissionRule(
                                "safe_delete", null, PermissionBehavior.ALLOW, "session"))
                .build();
agent.replacePermissionContext("alice", "s-001", next);

setPermissionMode 两个重载：ReActAgent.java:4608；replacePermissionContext：ReActAgent.java:4626；withMode 保留全部规则：PermissionContextState.java:148

replacePermissionContext 是整体替换，不是追加

上面那段用 builder() 从零建了一个新上下文，老规则全丢了。要保留就得自己把 cur.getAllowRules() / getDenyRules() / getAskRules() 三张表逐条搬过去；只换模式请用 withMode()，它会把目录和三张表一起复制。

确认时附带的 rules 只活在内存里

ConfirmResult.rules 走的是 permissionEngine.addRule(rule)——只加进这个槽位当前的引擎实例， 不写回 AgentState.permissionContext。所以：进程重启就没了，切一次模式（引擎按上下文重建）也没了。 要「永久免问」，得像上面那样写进 permissionContext。

陷阱与窍门

1. 配了 EXPLORE，结果连读文件都被拒
你会看到
切到只读模式后，模型说「没有权限读取文件」，而它调的正是 view_text_file。
因为
EXPLORE 只看 isReadOnly()，而内置的注解式文件工具都没标 readOnly = true，默认是 false → 一律 DENY。
改成
自己包一层 readOnly = true 的读工具；或者不用 EXPLORE，改用 deny 规则单独封掉写工具。
2. 把 allow 规则当白名单
你会看到
明明给工具加了 ALLOW 规则，它还是弹确认框；或者开了 BYPASS，某个工具依然被拒。
因为
判定顺序是 deny → ask → 工具自检 → allow → BYPASS。ask 规则在 allow 前面，工具自检的 DENY 更在前面。
改成
先确认没有同名的 ask/deny 规则，且工具自检没先拒；要绝对免问，就得同时拿下这两关。
3. 暂停了，直接追问下一句
你会看到
一次普通的 call 直接抛 IllegalStateException，说「有工具处于 ASKING 状态，需要你的批准」。
因为
上下文里还挂着 ASKING 的工具调用，新一次 call 却没带 ConfirmResult。框架宁可报错也不替你猜。
改成
先处理暂停：要么带 ConfirmResult 恢复，要么另开一个 sessionId。错误信息里直接给了可复制的恢复代码。
4. 两次 call 用的不是同一个 RuntimeContext
你会看到
带着 ConfirmResult 恢复，却报「引用了非 ASKING 的调用」；或者干脆看不到暂停，直接把原始请求重跑了一遍。
因为
挂起的调用存在槽位里。第二次 call 没传 ctx（用了 call(String) 这类便捷重载）或换了 sessionId，就是另一个槽位。
改成
把第一次 call 用的 RuntimeContext 存起来，两次都用它；别在恢复时用不带 ctx 的重载。
5. 自己写的工具没继承 ToolBase，权限完全失效
你会看到
为一个工具配了 deny 规则，它照样执行；工具自检也从来不进。
因为
evaluateOne 里只有 instanceof ToolBase 才进引擎，其余 AgentTool 一律按 ALLOW 直接放走。内置的 ShellCommandTool、SubAgentTool 就是这种——它们自带白名单 / 回调，不归权限引擎管。
改成
要受管就继承 ToolBase；不改的，就在自己工具里做检查，别忘了它们完全绕过了这套闸。
6. PermissionDecision.ask("safety: ...") 没生效
你会看到
工具自检返回了 ASK，文案里还写着 safety，但 agent 没暂停——尤其在 BYPASS 下直接执行了。
因为
静态工厂只设 message，decisionReason 是 null；引擎只查 decisionReason.toLowerCase().contains("safety")，查不到就继续走 allow 规则和 BYPASS。
改成
用 PermissionDecision.builder().behavior(ASK).message(...).decisionReason("safety: ...").build()。

自检三问

同一个工具同时有 ALLOW 和 ASK 两条规则，会发生什么？

问人。判定顺序是 deny → ask → 工具自检 → allow，ask 在 allow 前面。规则表按工具名分桶，所以两条规则都存在，但只有 ask 能被看到。反过来，如果有 DENY 规则，连问都不会问。

一轮里 3 个工具都停在 ASKING，我只想确认其中 1 个，剩下两个不理——行吗？

行，但至少要给一条。校验只要求：id 不能重复，且必须是当前 ASKING 里的 id；只确认子集是合法的（源码注释原话："Confirmations may cover a subset of ASKING calls"）。没被覆盖的两个继续保持 ASKING，这一轮不会执行、也不会被当成拒绝，下次恢复时你仍然得处理它们；而一条 ConfirmResult 都不给，直接抛 IllegalStateException。

一个自己写的工具只 implements AgentTool，我给它配了一条 DENY 规则，能拦住吗？

拦不住。evaluateOne 开头就是 if (!(tool instanceof ToolBase tb)) return ALLOW，连引擎都不会进。自定义工具想受管就必须继承 ToolBase；内置的 ShellCommandTool、SubAgentTool 属于前者，它们各自用自己的白名单 / 回调做保护。

20 分钟动手练习

  1. 把最小例子跑一遍，然后换成拒绝
    先按 HitlDemo 跑通一次放行。再把 new ConfirmResult(true, t) 改成 new ConfirmResult(false, t, null, "我不想删 /tmp/a.txt，换个目录")，观察两件事：agent 不会崩，它会根据理由回句话或换一个方案。这就是「拒绝是一条正常工具结果」的直观证据。
  2. 给一次确认加上「以后不再问」
    确认时传 new ConfirmResult(true, t, List.of(rule))，rule 是 new PermissionRule(t.getName(), null, ALLOW, "suggested")。再发一句会触发同一个工具的请求，确认它不再暂停。然后把 agent.setPermissionMode(ctx, PermissionMode.DEFAULT) 调一次（模式没变也会重建引擎），再试——规则没了。这就验证了「确认时带的规则只在内存里」。
  3. 用 ToolBase 验证三种模式
    把 SafeDeleteTool 注册进去，分别用 DEFAULT / EXPLORE / BYPASS 各跑一次，看同一句「删掉 /tmp/.env」会发生什么： DEFAULT 下工具自检直接 DENY；EXPLORE 下因为 readOnly=false 连自检都没到就被拒；BYPASS 下依然是 DENY——因为工具自检的 DENY 排在 BYPASS 之前。
