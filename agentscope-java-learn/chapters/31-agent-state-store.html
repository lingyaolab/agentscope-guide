31 · Agent 状态存储：Redis / MySQL / OSS

第 30 章解决「组件落在哪」，这一章把镜头拉近到 AgentStateStore 本身。 它保存的不是一份聊天记录，而是 Agent 恢复一次会话所需的完整状态：上下文、摘要、权限、工具组、任务与 Plan Mode。 多副本下真正的难点也不是「连上 Redis」，而是 (userId, sessionId) 怎么寻址、版本怎么比较、冲突时覆盖还是失败。

读完你能做到

  • 说清 AgentState 的字段与 JSON 形态，知道恢复会话为什么不能只存消息列表
  • 列出 AgentStateStore 的方法边界：单值、列表、会话删除、按 key 删除、按用户列会话
  • 看懂 Redis / JDBC / MongoDB / OSS / JSON 五套 key 或表结构，并能按落点排障
  • 解释 UNVERSIONED、saveIfVersion 的三种 expectedVersion 语义，以及为什么列表没有版本
  • 在 OVERWRITE、FAIL、APPEND_MERGE 之间做出有依据的选择
  • 把 SessionTurnGate、CAS 与多副本部署组合成一条可解释的一致性方案

状态不是聊天记录

AgentState 是「单个 Agent 恢复一次会话所需的运行时状态」：对话缓冲区、滚动摘要、当前回复 id、迭代计数、 权限上下文、工具上下文、任务上下文与 Plan Mode 上下文 AgentState.java:29-42。 只存 messages，恢复后会丢掉工具组激活状态、权限规则与任务进度。

字段JSON 名恢复时为什么需要
会话 / 用户session_id / user_id定位槽位，避免串会话
摘要summary压缩后的历史不能被丢掉
上下文context消息、工具调用与结果
回复与迭代reply_id / cur_iter中断恢复与轮次判断

context 对外通过 getContext() 返回防御性副本，通过 contextMutable() 提供可变句柄； 存储层可以整体替换 AgentState，也可以原地改内部集合 AgentState.java:36-39 AgentState.java:170-177。 JSON 里的字段名是 snake_case，排障时直接看存储里的 agent_state 就能对上 AgentState.java:95-107。

契约：一个槽位，几种操作

AgentStateStore 用 (userId, sessionId) 寻址：sessionId 必须非空， userId 可空，空表示匿名 / 单租户调用方 AgentStateStore.java:22-38。 方法分成四组：

组方法边界
单值save / get / getVersioned / saveIfVersion主要存 agent_state；支持版本化的后端才有 CAS
列表save(List) / getList按 key 存列表；实现决定增量 append 还是整体重写
会话exists / delete / listSessionIds只能按单个用户列会话，没有跨用户列表 API
清理delete(userId, sessionId, key) / close按 key 删除默认是 no-op，不是每个后端都覆盖

按 key 删除的默认实现是空操作 AgentStateStore.java:201-210； listSessionIds(null) 只列匿名会话，列某个用户要传具体 userId，跨用户统计是管理端的职责 AgentStateStore.java:212-222。 不要假设「接口有 delete(key)」就等于「所有后端真的删了」。

落点：同一个槽位，五种排法

Agent 层只传 (userId, sessionId)，具体怎么拼 key 由后端决定。排障时第一件事就是找到这个槽位的实际落点。

后端槽位单值 / 列表索引 / 版本
Redis{user}/{session}（匿名 __anon__）{prefix}{slot}:{key}；列表加 :list列表 hash；_keys Set 记录该会话所有 keyredis.md:98-109
JDBC__anon__:session(session_id, state_key, item_index) 行；单值 item_index=0新 JDBC 表有 version 列SessionStateDialect.java:21-26
MongoDB复合 _id {user, session}states.<key>；列表是 BSON 数组versions.<key> / hashes.<key>MongoAgentStateStore.java:62-69

Redis 的实际槽位是 normalizeUser(userId) + "/" + sessionId，匿名用户固定为 __anon__ RedisAgentStateStore.java:439-450； JDBC 则是 __anon__:session JdbcAgentStateStore.java:571-582。 MongoDB 特意用结构化 _id，避免 userId 或 sessionId 里出现分隔符时跨租户碰撞 MongoAgentStateStore.java:563-573。

一次调用：先读 agent_state，再按版本写回

ReActAgent 启动一次调用时，先读 agent_state。读到就用它和它的版本；读不到就尝试旧版 key memory_messages + toolkit_activeGroups，再读不到才创建新状态 ReActAgent.java:414-445。 旧格式没有版本，迁移时按「create-if-absent」的版本 0 处理 ReActAgent.java:437-445。

调用结束时，把当前 AgentState 写回同一个槽位；如果后端支持版本化，会带上本轮加载时观察到的版本做 CAS ReActAgent.java:475-495。 Agent 进程内还会按槽位缓存状态与版本，避免每次调用都重新反序列化 ReActAgent.java:286-293。

列表状态走另一条路

单值有 getVersioned / saveIfVersion，列表没有。列表保存靠实现里的 hash + 计数判断 「增量 append 还是整体重写」；Redis、JDBC、Mongo、OSS、JSON 各有自己的 hash 字段或列 AgentStateStore.java:140-157。 所以「单值 CAS 成功」不代表「同一会话里的列表也原子」。

版本：UNVERSIONED、0 与 expectedVersion

AgentStateStore 用 UNVERSIONED = -1 表示「这个后端不支持乐观并发」， 也用于「CAS 冲突且什么都没写」。默认 supportsVersioning() 返回 false， saveIfVersion 会退化成无条件 save AgentStateStore.java:63-67 AgentStateStore.java:81-138。

expectedVersion语义返回
0create-if-absent；已有 version 0 的旧行也允许写入成功返回新版本；已有非零版本则冲突
UNVERSIONED（-1）无条件覆盖，等同于 save支持版本的后端返回本次写入的版本
其他正整数只有当前版本等于它才写成功返回新版本；冲突返回 UNVERSIONED 且不写

当前实现里，InMemory、Redis、JDBC、MongoDB 都提供版本化；JSON 文件与 OSS 在文档里仍按 last-writer-wins 描述 index.md:103-106 InMemoryAgentStateStore.java:61 JdbcAgentStateStore.java:200 MongoAgentStateStore.java:160。 选后端时，如果同一会话会被多个副本并发写，版本化不是可选项。

冲突：覆盖、失败还是合并

默认 conflictPolicy 是 OVERWRITE，保留旧的 last-writer-wins 行为 ReActAgent.java:347-348。 但 CAS 冲突发生在轮次末尾，回复可能已经流式输出、工具副作用可能已经发生，所以「冲突」不是可以静默忽略的小事 ConflictPolicy.java:22-31。

策略冲突时做什么适合风险
OVERWRITE（默认）无条件再写一次单副本、可接受最后写入者静默丢掉另一轮的状态
FAIL抛 ConcurrentSessionModificationException，跳过写启用了分布式 SessionTurnGate调用方必须处理异常
APPEND_MERGE重读最新基线，追加本轮新增消息，再重试 CAS普通聊天轮次压缩 / 摘要轮会重写历史，不安全

FAIL 的异常会带 userId、sessionId、key 与 expectedVersion，方便定位是哪一轮撞了 ConcurrentSessionModificationException.java:22-61。 APPEND_MERGE 的合并逻辑只把 loadedContextSize 之后的新消息追加到最新基线， 再保留本轮的权限上下文，然后重试 CAS ReActAgent.java:607-639。

SessionTurnGate：先把同一会话的轮次排队

SessionTurnGate 是按 key 的互斥：同一个会话同一时间只允许一个 turn， 本地实现是进程内公平信号量，分布式实现由控制面托管 SessionTurnGate.java:18-24。 它和 CAS 解决的不是同一个问题：gate 减少并发轮次，CAS 负责在写入时发现版本不一致。

使用分布式 gate 时，官方建议把 conflictPolicy 设为 FAIL，让并发写以错误暴露， 而不是被 OVERWRITE 静默吞掉 ConflictPolicy.java:26-31 ReActAgent.java:5172-5177。 DistributedStore.sessionTurnGate() 默认返回 null，此时回退到本地 gate DistributedStore.java:152-167。

Redis：key 结构清楚，CAS 用 Lua

Redis 状态存储支持 Jedis、Lettuce、Redisson 三类客户端，也可注入自定义 RedisClientAdapter redis.md:15 redis.md:45-85。 单值存 String，列表存 List，列表另有 hash key；_keys Set 记录该会话下所有 stateKey，删除和存在性判断都不用扫全库 redis.md:98-109。 

AgentStateStore stateStore = RedisAgentStateStore.builder()
    .jedisClient(new JedisPooled("redis://localhost:6379"))
    .keyPrefix("myapp:session:")
    .build();

ReActAgent agent = ReActAgent.builder()
    .name("assistant")

RedisAgentStateStore 的版本化由 RedisStateVersionSupport 配合 Lua 脚本完成； 单值有版本 key，saveIfVersion 通过 Lua 脚本原子比较再写；列表只用 hash 做增量判断，不走版本化 RedisAgentStateStore.java:226-291。 默认前缀是 agentscope:session:，多项目共享 Redis 时要改。

JDBC：当前是 JdbcAgentStateStore，不是旧 Mysql 那张表

这里有三层容易混：MysqlDistributedStore 已标记未来移除（第 30 章）， MysqlAgentStateStore 是旧 MySQL 实现， 新统一路径是 agentscope-extensions-jdbc 的 JdbcAgentStateStore，支持 MySQL / PostgreSQL / H2 / SQLite JdbcDistributedStore.java:31-42。

表结构也有文档差异。分布式 MySQL 页写的是 user_id、state_value、state_type mysql.md:52； 旧 MysqlAgentStateStore 源码实际建的是 session_id、state_key、item_index、state_data（外加 version） MysqlAgentStateStore.java:42-56 MysqlAgentStateStore.java:240-247 MysqlAgentStateStore.java:197-203； 新 JDBC 同样按 (session_id, state_key, item_index) 存，单值 item_index=0 SessionStateDialect.java:21-26。 不要按旧文档的列名写 SQL 报表。

以源码的 item_index 模型为准

当前两代实现都是「一行一个 item」：单值一行 item_index=0，列表每项一行； hash 另存一行做增量判断。新 JDBC 多一个 version 列支持 CAS SessionStateDialect.java:69-96。 列名对不上时，先怀疑文档版本，而不是数据库坏了。

MongoDB：结构化 _id + versions 子文档

MongoDB 每个会话一个文档，复合 _id 是 {user, session}； 状态在 states.<key>，版本在 versions.<key>，列表 hash 在 hashes.<key> MongoAgentStateStore.java:62-69。 结构化 _id 的好处是 userId / sessionId 里出现分隔符也不会串租户 MongoAgentStateStore.java:563-573。

状态 key 会作为字段名写进 states 子文档，所以必须匹配 ^[a-zA-Z_][a-zA-Z0-9_]*$：不能有点、美元符号或 Unicode MongoAgentStateStore.java:84-98 MongoAgentStateStore.java:575-593。 会话 TTL 默认关闭，只有显式 ttlDays(n) 才创建 TTL 索引 MongoAgentStateStore.java:688-703。 

AgentStateStore stateStore = MongoAgentStateStore.builder()

    .databaseName("agentscope")
    .collectionName("agentscope_sessions")

OSS：对象布局简单，但没有版本化

OSS 把单值写成 {key}.json、列表写成 {key}.list.json、hash 写成 {key}.list.hash， 路径前缀是 {prefix}{user}/{session}/ OssAgentStateStore.java:45-47 OssAgentStateStore.java:243-259。 它没有覆盖 supportsVersioning()，走默认 false，因此 saveIfVersion 会退化成无条件写； 文档也把 OSS 列为 last-writer-wins index.md:103-106。 

AgentStateStore stateStore = OssAgentStateStore.builder()

    .bucketName("my-bucket")

OSS 更适合「状态写不频繁、容量大、可接受 last-writer-wins」的场景；高并发写同一会话时， 应选 Redis / JDBC / Mongo，或至少用 SessionTurnGate 把同一会话串起来。

本地实现：JSON 与 InMemory 的边界

JsonFileAgentStateStore 是 HarnessAgent 的默认状态存储，根目录默认在 ~/.agentscope/state，HarnessAgent 实际按 ~/.agentscope/state/<agentId>/<user>/<session>/ 落盘；直接 new 的 store 才按 __anon__/<session> 或 <user>/<session> 分目录； 它支持列表的 hash 增量 append，但不支持版本化 JsonFileAgentStateStore.java:47-84。 InMemoryAgentStateStore 只用于测试，但它反而实现了版本化与 CAS InMemoryAgentStateStore.java:61-95。

多副本配方：共享存储 + 轮次闸门 + 明确冲突策略

把第 30 章和前文的结论合成一条可执行链路：

  1. 选版本化状态存储
    Redis / JDBC / MongoDB 三选一；OSS 只用于低频写，JSON 只用于单机。
  2. 接 RemoteFilesystemSpec
    文件走 BaseStore，状态走 AgentStateStore；两者来自同一个 DistributedStore 最省心。
  3. 开分布式 SessionTurnGate
    用控制面托管 gate 或自己实现按会话互斥；没有 gate 时本地 gate 只在一个进程内有效。
  4. 把 conflictPolicy 设为 FAIL
    让并发写显式失败，而不是 OVERWRITE 静默覆盖；调用方要能处理 ConcurrentSessionModificationException。
  5. 确认 TTL 与备份
    Mongo 要显式 ttlDays，OSS 要配生命周期，Redis / JDBC 要自建清理；备份要覆盖状态存储本身。

六个坑：状态存储不是「把 JSON 丢进去」

坑一：只存消息。AgentState 还带摘要、权限、工具组、任务与 Plan； 只存 messages，恢复后工具与权限状态会丢 AgentState.java:59-69。

坑二：以为所有后端都有 CAS。JSON 与 OSS 默认不版本化；saveIfVersion 会退化成无条件写 AgentStateStore.java:81-138。

坑三：对压缩轮用 APPEND_MERGE。它只追加本轮新消息，压缩 / 摘要轮会重写历史，合并会破坏语义 ConflictPolicy.java:41-44。

坑四：假设 delete(key) 一定生效。接口默认是 no-op；按 key 清理前先确认后端实现 AgentStateStore.java:201-210。

坑五：RemoteFilesystemSpec 配 JSON 状态。Harness 会直接拒绝；多副本必须用远端状态存储 HarnessAgent.java:2431-2438。

坑六：按旧文档的 MySQL 列名写查询。源码是 session_id / state_key / item_index / state_data， 不是 user_id / state_value / state_type MysqlAgentStateStore.java:42-56。

自测：三个判断题

列表状态的保存也有 saveIfVersion 吗？

没有。版本化方法只覆盖单值；列表保存是 save(List)，靠 hash 判断增量 append 还是整体重写， 不受单值 CAS 保护 AgentStateStore.java:140-181。

conflictPolicy 默认是 FAIL 吗？

不是。默认是 OVERWRITE，保留旧的 last-writer-wins；官方建议在启用分布式 SessionTurnGate 时改成 FAIL ReActAgent.java:347-348 ConflictPolicy.java:26-31。

JSON 文件存储支持 CAS 吗？

不支持。它没有覆盖默认的 supportsVersioning()，仍是 last-writer-wins；需要 CAS 时换 InMemory、Redis、JDBC 或 Mongo AgentStateStore.java:81-89 JsonFileAgentStateStore.java:45-69。

练习：看清一次状态写入

目标不是「换一个 store」，而是能追踪一个 agent_state 从加载到写回的全过程。建议 50 分钟：

  1. 先看 JSON 形态
    用 JsonFileAgentStateStore 跑一轮，打开 agent_state.json，对照字段表确认 summary / context / tool_context。
  2. 换 Redis
    切到 RedisAgentStateStore，跑同一轮，找到 agentscope:session:<user>/<session>:agent_state 与 _keys。
  3. 观察版本
    连续跑两轮，记录 agent_state 的版本变化；确认第二轮拿着第一轮的版本做 CAS。
  4. 制造冲突
    两个线程同时写同一 session，先用 OVERWRITE，再用 FAIL，记录日志与异常文本。
  5. 试 APPEND_MERGE
    普通聊天轮用 APPEND_MERGE，确认新消息被追加；再想一遍压缩轮为什么不能用。
  6. 测删除
    对 Redis 调 delete(user, session, key)，再对 Mongo 调一次，比较是否真的删除。
  7. 测会话列表
    分别用 listSessionIds(null) 与具体 userId，确认匿名与具名会话不会混在一起。
  8. 写三行结论
    分别写「槽位怎么拼」「版本怎么变」「冲突怎么处理」，确保每行都能在存储里找到证据。
