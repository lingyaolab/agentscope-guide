01 · 环境与依赖

这一章只解决两件事：编译不过和能写出第一行能跑的验证代码。看完你会明白为什么框架要拆成 core / harness / extensions-model-* 三层，以及每一个 ClassNotFoundException 该改哪一行 pom.xml。

读完你能做到

  • 在自己的 Maven 工程里写出正确的三段依赖，并用 mvn -q compile 编译通过
  • 说清 agentscope-core、agentscope-harness、agentscope-extensions-model-dashscope 各自提供什么，以及什么时候不需要 harness
  • 看到 Cannot resolve model: "..." 或 Failed to create model for id: ... 时，能直接判断是 「模块没引」还是「环境变量没设」

先说为什么：装依赖就是给框架「插能力」

把 AgentScope 想成一台模块化的咖啡机：机身（agentscope-core）负责「把豆子磨了、冲了」这个 循环本身；水箱、奶泡器、豆仓是可选配件，你买哪台机器就装哪个配件。配件不装并不是「配置错了」，而是整台机器 不认识那个名字——同理，你没引 dashscope 模块时，框架连 "dashscope:qwen-plus" 这个字符串都解析不了。

agentscope-harness（可选，官方推荐入口）
工作区、会话落盘、长期记忆、对话压缩、子 agent、沙箱。它本身是包在 core 外面的一层，不是另一套 引擎。agentscope-harness/pom.xml:36
agentscope-core（必需）
ReActAgent 推理循环、Msg、事件、工具系统、权限、状态接口。自带 Reactor、Jackson、MCP SDK、OkHttp 等基础设施。agentscope-core/pom.xml:55
agentscope-extensions-model-*（按厂商选）
DashScope / OpenAI / Anthropic / Gemini / Ollama 各一个模块，通过 ServiceLoader 在 运行时被发现。代码里永远只出现字符串，不出现厂商类。
为什么厂商要单独一个模块，而不是全塞进 core

官方文档给的理由很直接：特定提供商的 Chat Model 与 formatter 位于独立的 agentscope-extensions-model-* 模块中quickstart.md:31。落到工程上就是：不用的厂商不进你的 classpath，也就不会带来它的 SDK、传递依赖和漏洞面。

最小可跑：三段依赖 + 两个验证程序

第 1 步：三段依赖

新建一个空 Maven 工程，pom.xml 里只留这三段（版本号来自仓库根 pom.xml:30 的 2.0.4）： 

<properties>
  <maven.compiler.source>17</maven.compiler.source>
  <maven.compiler.target>17</maven.compiler.target>
  <agentscope.version>2.0.4</agentscope.version>
</properties>

<dependencies>
  <!-- ① 入口：想要工作区 / 状态落盘 / 压缩 / 长期记忆就引它（会顺带拉进 core） -->
  <dependency>
    <groupId>io.agentscope</groupId>
    <artifactId>agentscope-harness</artifactId>
    <version>${agentscope.version}</version>
  </dependency>

  <!-- ② 只想用裸 ReActAgent 时，用这个替换 ①，别两个都引 -->
  <!--
  <dependency>
    <groupId>io.agentscope</groupId>
    <artifactId>agentscope-core</artifactId>
    <version>${agentscope.version}</version>
  </dependency>
  -->

  <!-- ③ 模型厂商：用哪个引哪个。不引 = "dashscope:xxx" 解析不出来 -->
  <dependency>
    <groupId>io.agentscope</groupId>
    <artifactId>agentscope-extensions-model-dashscope</artifactId>
    <version>${agentscope.version}</version>
  </dependency>
</dependencies>

harness 的坐标与「会带进 core」：quickstart.md:16； 模型扩展的坐标：quickstart.md:36；JDK 17 是硬要求：pom.xml:33

不要再去找一个叫 agentscope-bom 的东西来管版本

仓库里确实有个 agentscope-dependencies-bom，但它管的是第三方依赖（Reactor、Jackson、 OkHttp 这些的版本对齐），里面没有 io.agentscope 自己的构件。所以版本号请老老实实写死或 用属性，不要指望 <scope>import</scope> 能替你管 harness 的版本。

第 2 步：验证「模块真的在 classpath 上」

先别急着调模型。用 ModelRegistry.canResolve() 检查字符串能不能被解析——它只查注册表，不创建实例、 不读 keyModelRegistry.java:173： 

import io.agentscope.core.model.ModelRegistry;

public class CheckEnv {
    public static void main(String[] args) {
        System.out.println("dashscope:qwen-plus → " + ModelRegistry.canResolve("dashscope:qwen-plus"));
        System.out.println("qwen-plus（短写）   → " + ModelRegistry.canResolve("qwen-plus"));
        System.out.println("openai:gpt-5.5      → " + ModelRegistry.canResolve("openai:gpt-5.5"));
        System.out.println("DASHSCOPE_API_KEY   → " + (System.getenv("DASHSCOPE_API_KEY") != null));
    }
}

引了 dashscope 模块但没引 openai 模块时，你会看到第 1、2 行为 true，第 3 行为 false。这就是「模块决定能不能解析」的最直观证明。

第 3 步：真正创建一次模型

import io.agentscope.core.model.Model;
import io.agentscope.core.model.ModelRegistry;

public class ResolveModel {
    public static void main(String[] args) {
        Model model = ModelRegistry.resolve("dashscope:qwen-plus");
        System.out.println(model.getClass().getName());
    }
}

resolve 比 canResolve 多做一步：它会让 provider 真的把模型对象造出来ModelRegistry.java:104，所以这一步会检查 DASHSCOPE_API_KEY。设好环境变量后再跑，应该打印出 DashScope 模型类的全名。 

$env:DASHSCOPE_API_KEY = "sk-你的key"
mvn -q compile exec:java -Dexec.mainClass=ResolveModel
export DASHSCOPE_API_KEY=sk-你的key
mvn -q compile exec:java -Dexec.mainClass=ResolveModel

第 4 步：确认依赖树没有打歪

mvn -q dependency:tree -Dincludes=io.agentscope

期望看到三行 io.agentscope:agentscope-*:jar:2.0.4。如果 harness 那行后面没有跟着 core，说明你引的不是 harness 而是别的 artifactId（拼写错误在 IDE 里往往只报「找不到符号」，很难第一眼归因）。

逐行解读：容易懵的地方

这一行 容易懵的点 实际上
<groupId>io.agentscope</groupId> 和包名 io.agentscope.core 什么关系？ groupId 与 Java 包名只共享前缀，不是同一件事；但所有官方模块都用这个 groupId，包括扩展。
只引 agentscope-core 那 HarnessAgent 为什么编译不过？ HarnessAgent 在 agentscope-harness 里，而 harness 依赖 core（反向不成立）。 依赖方向是 harness → core，不是互相依赖。
agentscope-extensions-model-dashscope 为什么代码里完全看不到这个包名？ 它通过 ServiceLoader 自动注册：模块里有一份 META-INF/services/io.agentscope.core.model.spi.ModelProvider，里面写着实现类全名。 ModelRegistry.java:367
"dashscope:qwen-plus" 能不能只写 "qwen-plus"？ 能。DashScope 的 provider 同时接受 dashscope:模型名 和以 qwen 开头的短写DashScopeModelProvider.java:59；带前缀时会把前缀剥掉再当模型名用DashScopeModelProvider.java:75。为了可读性，仍然推荐带前缀。
DASHSCOPE_API_KEY 为什么不是写在代码里？ provider 的取值顺序是「显式传入的 key → 环境变量」DashScopeModelProvider.java:77；两个都没有就抛错。所以用字符串 model id 时，key 只能来自环境变量。
maven.compiler.source/target=17 我用 JDK 21 编译行不行？ 行。框架要求的是最低 17，用 21 编译、把 target 设成 17 都能跑。

端到端：从字符串到模型实例，中间发生了什么

这一节把「写一个字符串」到「真的拿到模型对象」的链路摊开，后面 05 章会在此基础上加参数、换厂商、加重试。

  • 编译期
    Maven 把 harness（连带 core）与 dashscope 扩展打进 classpath；此时框架还不知道有哪些厂商
  • 首次解析
    你调用 ModelRegistry.resolve("dashscope:qwen-plus")，注册表按顺序查：具名模型 → 缓存 → 你注册的工厂 → SPI 提供者ModelRegistry.java:99
  • SPI 发现
    扫描 classpath 上所有 META-INF/services/io.agentscope.core.model.spi.ModelProvider，把 provider 实例收集起来 ModelRegistry.java:365
  • 匹配
    逐个问 provider「你支持这个 id 吗」；DashScope 用两条正则判断：dashscope:.+ 或 qwen.+
  • 创建
    provider 取 key（显式 → DASHSCOPE_API_KEY），构造 DashScopeChatModel，默认开流式（stream=true）DashScopeModelProvider.java:84
  • 回填缓存
    命中的模型实例进缓存，同一 id 再解析不再重建ModelRegistry.java:159
两个失败点，报错长什么样

① 模块没引：IllegalArgumentException: Cannot resolve model: "dashscope:qwen-plus"，后面跟一整段 Possible causes 提示ModelRegistry.java:402；② key 没设：provider 抛的 IllegalStateException 会被包一层再抛出，所以你看到的是 Failed to create model for id: dashscope:qwen-plus: Environment variable DASHSCOPE_API_KEY is required...ModelRegistry.java:163。看到 Failed to create 就该想到「模块已经到了，是创建过程失败」。

依赖选择速查

你的场景 引什么 不引会怎样
要工作区 / 状态落盘 / 压缩 / 长期记忆 agentscope-harness + 模型扩展 编译期就找不到 HarnessAgent
只要「把消息发给模型 + 让它调工具」 agentscope-core + 模型扩展 多引 harness 只会让 classpath 变胖，功能不受影响
用通义千问 / DashScope agentscope-extensions-model-dashscope Cannot resolve model
用 OpenAI / Anthropic / Gemini 对应 agentscope-extensions-model-openai 等 同上，且提示信息会点名缺哪个模块
想完全本地、不花钱 agentscope-extensions-model-ollama 没有默认 key 可读，但默认连 http://localhost:11434
要用 MCP 工具 官方 MCP SDK 已经在 agentscope-core 的依赖里了agentscope-core/pom.xml:96；示例工程另有写法可参考 agentscope-examples/documentation/pom.xml —

官方安装说明原文：quickstart.md:9； MCP 相关提示：quickstart.md:43

陷阱与窍门

1. Cannot resolve model: "dashscope:qwen-plus"
你会看到
启动即抛 IllegalArgumentException，消息里夹着 7~8 行 Possible causes。
因为
classpath 上没有任何 provider 认领这个 id：要么模型扩展没引，要么 id 拼错（比如写成 dashscope:qwen_plus）。
改成
先跑第 2 步的 canResolve 打印 false 就说明是依赖问题；依赖没问题再核对 id 大小写与连字符。
延伸
同一张错在 附录 B · Cannot resolve model 有更完整的原因清单。
2. Failed to create model for id: ...: Environment variable DASHSCOPE_API_KEY is required
你会看到
报错说缺环境变量，但你「明明已经设了」。
因为
环境变量是进程级的：IDEA 的 Run Configuration 有自己的一份环境变量，Windows 上「改完系统变量不重开 终端/IDE」也不会生效。
改成
在 Run Configuration 的 Environment variables 里加一条；或者干脆用显式 key 的模型 builder（05 章），绕开环境变量。
3. UnsupportedClassVersionError
你会看到
class file version 61.0 ... this version of the Java Runtime only recognizes ... 55.0 一类信息。
因为
框架用 JDK 17（class file 61）编译，你的运行环境是 JDK 11（55）。
改成
换 JDK 17+ 运行；同时把 maven.compiler.source/target 设成 17，避免自己代码编译目标不一致。
延伸
附录 B · UnsupportedClassVersionError。
4. 引了 harness，但代码里 import io.agentscope.core.* 全红
你会看到
IDE 里 io.agentscope.core 下的类全部无法解析。
因为
多半是 artifactId 拼错成了 agentscope-harness-core 这类不存在的名字，Maven 其实下载失败，只是 IDE 没提示。
改成
跑一次 mvn -q dependency:tree -Dincludes=io.agentscope，看真实解析到了什么。
5. 想省钱：先用 Ollama 把流程跑通
你会看到
没有付费 key，不敢试任何例子。
因为
不是所有 provider 都必须有 key：Ollama 的默认地址是 http://localhost:11434，只需本地跑着 Ollama。
改成
引 agentscope-extensions-model-ollama，.model("ollama:llama3")；注意 Ollama 的模型能力弱， 工具调用一类例子未必稳定，见 06 章的说明。

自检三问

只引 agentscope-harness 不引 agentscope-core，能编译通过吗？

能。harness 以 compile 作用域依赖 coreagentscope-harness/pom.xml:36， Maven 会把 core 作为传递依赖带进来。反过来只引 core 就不行——core 里没有 HarnessAgent。

canResolve 返回 true，是不是就一定不会报错了？

不是。它只证明「有人认领这个 id」ModelRegistry.java:169，不创建实例、不读 key、不联网。key 缺失、模型名不存在、网络不通都会在真正调用时才暴露。

为什么模型的 key 不放在 pom.xml 或代码里？

因为用字符串 model id 时，provider 只会从「显式传入的 key」和「环境变量」两处取DashScopeModelProvider.java:77，配置文件不在取值路径上。这是刻意的：密钥不该进 git。

20 分钟动手练习

  1. 把 openai 模块也引进来，观察 canResolve 的变化
    加 agentscope-extensions-model-openai 依赖后重跑第 2 步，第 3 行会从 false 变成 true——即使你没有 OPENAI_API_KEY。
  2. 故意写错模型名
    把 id 改成 "dashscope:qwen-not-exist"，观察 canResolve 仍是 true（因为正则匹配 dashscope:.+），但真正调用时会收到服务端的「模型不存在」。结论：解析层只做前缀匹配，模型是否存在由服务端判定。
  3. 不设 key 跑 ResolveModel
    把环境变量去掉再跑，确认报错是 两层嵌套：外层 Failed to create model for id，内层才是 Environment variable ... is required。以后见到外层消息就知道该往下看 getCause()。
