20 · Endpoint 与 SSE：把 Agent 发布成一条带凭据的调用契约

第 19 章结束时，你在控制台里有了一个能对话的 Agent。但「人坐在浏览器前点按钮」和「另一个系统自动调它」是两件事：后者需要固定地址、可轮换的凭据、输入输出约定、 幂等重试、以及一条能把过程播出来的事件流。这一章把 Agent 发布成 Endpoint， 然后像第三方系统那样，用 curl 把它完整跑一遍。

读完你能做到

  • 说清 Endpoint 到底「包装」了什么：为什么它必须是一个与运行时地址解耦的稳定契约
  • 在 conversation 与 job 之间做正确选择，并知道 Team / Workflow 为什么只能走 job
  • 发布一个 Endpoint，拿到 asep_ 开头的 key，并解释它为什么还能被找回
  • 用 curl 提交一个 job，从 eventsUrl 读 SSE，从 statusUrl 取结果
  • 解释三个高频故障：为什么 X-Builder-Environment-Key 调不通、为什么断线不等于失败、为什么重试要复用同一个 key

先说为什么：控制台能聊，不等于系统能调

官方对 Endpoint 的定义只有一句话，但每个词都是约束：把 Agent、Team 或已发布的 Workflow revision 包装成具有认证、输入输出 schema 和调用记录的服务，调用方无需了解内部调度和运行时地址endpoints.md:10。源码里的注释把这句话补全了：Endpoint 是「稳定公开的 API 契约」，运行时绑定与物理实例在调用时才解析， 永远不会变成公开地址的一部分agent_endpoint.go:51-53。

把「控制台里的一次对话」和「一条 Endpoint 调用」并排看，差别立刻出来：

控制台里点「发送」

  • 身份是登录用户的 JWT
  • 地址是 SPA 拼出来的 /api/sessions/...
  • 目标 Agent 是本次会话里选中的那个实例
  • 重发一次，就是多说一句话

应用调用 Endpoint

  • 身份是 Endpoint 自己的 key 或平台令牌
  • 地址是 /invoke/v1/endpoints/{slug}/...，与部署无关
  • 目标由发布的 release 决定，调用方看不见
  • 重发一次，可能命中幂等、也可能报冲突
一句话分工

控制台是「给人用的客户端」，Endpoint 是「给系统用的契约」。前者可以依赖登录态和内部路由，后者不行—— 所以 Endpoint 必须自己带认证、自己定 schema、自己记调用记录，并且把「调度到哪台机器」藏起来。

两种契约：conversation 与 job

发布时要先选调用形式，只有两种endpoints.md:14-21：

形式请求入口语义结果怎么拿
conversation /invoke/v1/endpoints/{slug}/conversations 多轮交互；下一轮发到 /invoke/v1/conversations/{conversationId}/turns 订阅 eventsUrl，用 invocationId 判断这一轮何时结束
job /invoke/v1/endpoints/{slug}/jobs 一次可跟踪的工作；Agent、Team、Workflow 都能用 轮询 statusUrl 取 invocation.result，文件走 artifacts 接口

源码里这两条不是「建议」而是硬校验。发布时，conversation 只允许 targetType=agentagent_endpoint_handler.go:292-294；调用时还会再看一次，模式不对直接 409agent_endpoint_handler.go:1183-1186。Team 与 Workflow revision 则明确只支持 job，Readiness 会给出 incompatibleagent_endpoint_handler.go:615-640。

别把「能对话的 Agent」套在 Team 上

官方原话是「不要强行将只支持 job 的 Team / Workflow 作为会话目标」endpoints.md:21。原因不神秘：conversation 绑定的是一个 session 的多轮，而 Team 的产物是一次 Run 的编排结果， 两者根本不是一个形状。

请求体也完全不同。conversation 只认 {"message":"..."}，空消息直接 400agent_endpoint_handler.go:1213-1223；job 认 title、description 和 input，title 缺省时会被填成 Endpoint jobagent_endpoint_handler.go:1434-1460。

发布：slug、schema、认证，以及先看 Readiness

在目标详情的 Endpoint 发布区域创建入口，设置 slug、模式、schema、认证、超时和请求大小限制； 发布前看 Readiness，处理目标缺失或能力不匹配endpoints.md:21。创建接口的校验顺序值得记住，因为报错文本就是按这个顺序出的：

字段约束不满足时
name / slug / targetRef 都不能为空；slug 只允许小写字母、数字与单个连字符分隔 name, slug and targetRef are required
slug 正则 ^[a-z0-9]+(?:-[a-z0-9]+)*$ slug must contain lowercase letters, numbers, and single hyphen separators
invocationMode 只能是 conversation 或 job invocationMode must be conversation or job
timeoutSeconds / maxPayloadBytes 不能为负数 timeoutSeconds and maxPayloadBytes cannot be negative
rateLimit 给了就必须 requests 与 windowSeconds 都为正 rateLimit requires positive requests and windowSeconds

以上五行全部来自同一个函数 agent_endpoint_handler.go:282-311； slug 正则定义在文件头部 agent_endpoint_handler.go:56。

另一个容易忽略的默认值：不写 authPolicy 就等于 api_key，而且创建响应里 会直接带出一个默认凭据的明文 keyagent_endpoint_handler.go:354-365agent_endpoint_handler.go:386-399。也就是说，「先建一个试试」也可能已经产生了一把可用的钥匙——建完要立刻决定是保管还是撤销。

创建成功只是 draft，Draft 不接收正式调用endpoints.md:25。Publish 时请求体必须带 version，Readiness 不兼容就 409 并把原因一起返回agent_endpoint_handler.go:682-693；首次发布会自动写一条 release，理由是 initial publicationagent_endpoint_handler.go:694-701。之后的版本切换、回滚都不是改 Endpoint 本身，而是追加 release——slug 与契约保持稳定，目标历史保留下来agent_endpoint.go:80-93。

Readiness 的六种状态值得先认全

ready、unavailable（目标 Agent 不活跃）、inactive / unbound（没有可用实例或绑定）、incompatible（模式与目标类型不匹配）、 disabled（已归档）agent_endpoint_handler.go:571-649。发布被 409 挡住时，先看返回里的 readiness.reason，比翻日志快。

凭据：asep_ 前缀、两种认证、三条轮换规则

选 api_key 时创建调用凭据，并以 X-API-Key 发送；选 platform 时使用 Authorization: Bearer，两种凭据用途不能互换endpoints.md:25。源码生成的 key 长这样：asep_ 加 32 字节随机数的 base64url 编码agent_endpoint_handler.go:66-75。

库里存的是三样东西，不是明文
前缀（用于查行）、SHA-256 哈希（用于常量时间比对）、AES-GCM 密文（用于授权后「再看一眼」）。所以凭据列表里 只能看到前缀，reveal 才能拿回完整 keyagent_endpoint.go:103-120。
轮换后 principal 不变
新 key 的 rotatedFrom 指回根凭据，认证时用它算 principalagent_endpoint_handler.go:1136-1143。所以轮换不会让同一个人「变成另一个人」，历史 job 仍归他。
每次都记 LastUsedAt，签发时可设过期
认证成功会更新使用时间；过期时间一到，即使 key 没被撤销也会判无效agent_endpoint_handler.go:1124-1138。轮换与撤销都是新增状态，不是删行。

还有一个藏在实现里的宽容：api_key 模式下先读 X-API-Key，读不到会退回 Authorization: Beareragent_endpoint_handler.go:1120-1123。这不是「两种认证可以互换」——policy 仍然决定走哪条分支；它只是让不支持自定义头的 HTTP 客户端也能带上 key。

X-Builder-Environment-Key 不是 Endpoint 凭据

API 参考里它是Worker 工具执行协议的头，和 Endpoint API key 分属两行api-reference.md:12-21。更关键的是：Gateway 在 /invoke/v1/** 这条路由上会主动移除它，连同 X-Builder-Internal-Token 与 X-Builder-Internal-Userapplication.yml:80-88。所以拿它调 Endpoint，结果只能是 401，而不是「权限更大」。

限流也是 Endpoint 自己的属性：配置了 rateLimit 就按 principal 计数，超了返回 429 与 Retry-Afteragent_endpoint_handler.go:1147-1169。这也是「为不同调用方建不同凭据」的实际收益：限流与审计能分开算endpoints.md:27。

最小可跑：提交一个 job，然后拿到它的结果

假设已发布一个 slug 为 report 的 job Endpoint，且 input schema 允许 request 字段。 把 BASE_URL 设为 Gateway 的公开 origin（末尾不带斜杠），ENDPOINT_TOKEN 设为该入口的凭据endpoints.md:31-41： 

curl --fail-with-body "$BASE_URL/invoke/v1/endpoints/report/jobs" \
  -H "X-API-Key: $ENDPOINT_TOKEN" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: report-order-001' \
  --data '{"title":"Prepare report","description":"Summarize the supplied material","input":{"request":"List the open questions"}}'

响应是 202，带四个必须保存的东西：invocationId、status、statusUrl、 eventsUrlagent_endpoint_handler.go:1770-1782。如果这次 job 已经物化出 Issue 与 Run，响应里还会多 issueId、runId。 

{
  "invocationId": "9f1c...",
  "status": "running",
  "statusUrl": "/invoke/v1/jobs/9f1c...",
  "eventsUrl": "/invoke/v1/jobs/9f1c.../events",
  "issueId": "3a77...",
  "runId": "d2e0..."
}

官方提醒得很直接：保存返回的 URL，用它查询状态或订阅事件，不要自行拼接假定的内部 Run 地址endpoints.md:43。然后先查一次状态： 

curl --fail-with-body "$BASE_URL$STATUS_PATH" -H "X-API-Key: $ENDPOINT_TOKEN"

状态响应是三个对象的合体：invocation 本身，加上 issue 与 run 的摘要agent_endpoint_handler.go:1860-1866。终态时 invocation.result 才承载结果，按该 Endpoint 的 output schema 读endpoints.md:50。要文件就走 artifacts 列表，再用返回的 downloadUrl 和同一凭据下载sse-events.md:106-108。

job 背后真的有一个 Issue

实现里，job 会先创建一个 IssueKindEndpointJob 的 Issue，完成策略是自动，来源标记为 endpoint，然后把 Agent 或 Team 指为 assigneeagent_endpoint_handler.go:1483-1522。所以控制台的 Issue 列表里能看到它——这也是排查「job 卡住」时最有用的一处现场。

SSE：帧格式、心跳、游标与续传

订阅只要三件事：同一个凭据、GET 到 eventsUrl、Accept: text/event-streamsse-events.md:12-17。每条业务事件包含 id、event 与 JSON data，以空行结束sse-events.md:21-30： 

id: 1
event: run.started
data: {"id":"...","runId":"...","sequence":1,"type":"run.started","actor":{"type":"system","ref":"endpoint:example"},"occurredAt":"..."}

服务端就是按这个格式逐帧写出的：id: %d event: %s data: %s agent_endpoint_handler.go:1962-1965。响应头四项也都写死：text/event-stream、no-cache, no-transform、 keep-alive、X-Accel-Buffering: no——最后一项专门用来关掉 Nginx 一类代理的缓冲agent_endpoint_handler.go:2001-2005。

你会看到它是什么怎么处理
id: 该流的顺序游标，不是调用 ID 处理成功后保存，断线续传用它
event: 事件类型 按类型分派，遇到未知类型要容忍
data: 一个 JSON 事件对象 Conversation 与 Job 的结构不同，分别解析
: heartbeat 空事件的注释行，服务端 15 秒没新事件就发一次 忽略，不当成 JSON，也不当成进展

心跳不是协议要求，是实现的等待策略：服务端最多等 15 秒新事件，超时就写一行 : heartbeat\n\n 再继续agent_endpoint_handler.go:1981-1995。它也解释了为什么长时间没内容时连接不会立刻断——但这也意味着「连着」不等于「在跑」。

续传靠游标，不靠重连碰运气。两个入口都接受 after 查询参数与 Last-Event-ID 头，同时给出时取较大的有效数值sse-events.md:84-93，源码里就是一次比较agent_endpoint_handler.go:1951-1954：

curl -N --fail-with-body "$BASE_URL$EVENTS_PATH" \
  -H "X-API-Key: $ENDPOINT_TOKEN" \
  -H 'Accept: text/event-stream' \
  -H "Last-Event-ID: $LAST_EVENT_ID"

conversation 与 job 的事件不是同一种事件，字段名都不一样：

ConversationJob
事件来源运行时 Session 事件Run 编排事件
SSE id 对应seqsequence
类型字段eventTypetype
关联标识sessionFk，可能带 frameworkMetarunId，可选 nodeId / attemptId
常用内容role、content、toolNameactor、payload、occurredAt

表格来自 sse-events.md:48-59。 实现上的差别也能对上：job 的 eventsUrl 读的是 Run 的事件表agent_endpoint_handler.go:1957-1966，conversation 读的是 Session 事件agent_endpoint_handler.go:1660-1670。

从 0 订阅 conversation，可能收到「上一轮」

conversation 的 eventsUrl 带一个 invocationId 查询参数，它只用来判断当前这轮何时结束， 不会把 Session 历史过滤成只剩这一轮；从游标 0 开始订阅，可能先收到早先的会话事件sse-events.md:70。实现里也确认了这一点：返回的 URL 就长这样agent_endpoint_handler.go:1309-1314。所以客户端要按 turnId 等关联信息区分轮次，别把历史当新回复重复显示。

最后一条边界：这里用的是标准 SSE 封装，业务事件是 Service 的会话或编排事件， 不要假设 data 是某个模型厂商的 token 增量协议，也不要依赖固定的 [DONE] 标记sse-events.md:46。流结束的唯一可靠信号，是状态查询说它到了终态。

状态与幂等：哪些状态算完成，重发会发生什么

调用状态一共八个，源码里是一组常量agent_endpoint.go:122-133：

  • accepted 请求已受理，还没开始派发。不是完成。
  • dispatching 正在物化目标（建 Issue / 建 Run / 派 AgentTask）。不是完成。
  • running Run 已启动、正在执行。不是完成。
  • waiting 等待人工审批或外部条件。不是完成，但通常需要人。
  • completed 成功终态。结果在 invocation.result。
  • failed / cancelled / timed_out 三种不成功的终态，分别对应执行失败、主动取消、超过 timeoutSeconds。

    • 「终态」在代码里就是一个四值判断agent_endpoint_handler.go:2008-2011；SSE 循环也只在「Run 终态」或「invocation 终态」时才关流agent_endpoint_handler.go:1970-1977。所以断线本身不携带任何「成功/失败」信息。

    partial success 也会映射成 completed

    Run 结束时按状态映射：succeeded 与 partial_succeeded 都映射为 completed，只有 cancelled 映射为取消，其余算失败agent_endpoint_handler.go:1829-1843。官方也写了「单个节点成功不代表整个 Run 成功；部分成功是否足够由业务决定」sse-events.md:110。也就是说：completed 是「调用结束且没整体失败」，不等于「业务验收通过」。

    幂等键不是可选优化，是必填项。job 与 conversation 都在第一步就校验它，缺了直接 400 Idempotency-Key is requiredagent_endpoint_handler.go:1429-1433agent_endpoint_handler.go:1232-1236。同一个 key 再来一次，只有两种结局：

    重发的请求结果为什么
    同 key + 同内容 返回原来那次 invocation（202），不会重复执行 先按 key 找到记录，内容一致就直接复用agent_endpoint_handler.go:1472-1479
    同 key + 不同内容 409 Idempotency-Key was already used with different input 内容不一致说明这是另一个业务请求，却复用了旧号agent_endpoint_handler.go:1473-1475

    「内容一致」的判断比字符串相等聪明一点：它先把 JSON 解析再重新序列化，忽略对象 key 顺序，同时保留数字精度agent_endpoint_handler.go:171-189。所以你重试时字段顺序变了不算「不同内容」，但改了一个值就一定算。job 还会把这个 key 与 Endpoint ID 拼起来，作为 Run 的幂等键agent_endpoint_handler.go:1523-1548——两层幂等，任一层挡住都不会重复建 Run。

    超时也是状态机的一部分：配了 timeoutSeconds 且已过期，读取状态时会被就地改成 timed_out、错误码 endpoint_timeout；job 还会顺带取消 Runagent_endpoint_handler.go:1751-1767。这就是为什么「查状态」不只是读，它可能推进状态。

    端到端：一条 job 请求在平台里走了哪些门

    把前面几节串成时间轴，每一步都对应截图上能验证的一行：

    • 应用 → Gateway 请求进 /invoke/v1/**，Gateway 用一条独立路由转发到 Control，并剥掉客户端伪造的环境头与内部头application.yml:77-88。
    • Gateway → Control aistiod 从 slug 取 Endpoint，校验是否已发布、认证策略、限流，再校验请求体与 input schemaagent_endpoint_handler.go:1413-1467。
    • Control：幂等 用 Idempotency-Key 预留 invocation。命中旧的且内容相同就原地返回；内容不同就 409agent_endpoint_handler.go:1463-1479。
    • Control：物化 建一个来源为 endpoint 的 Issue，把 Agent / Team 设为 assignee；Agent 走 direct Run，Team 走 adaptive Run，Workflow 则从已发布 revision 启动agent_endpoint_handler.go:1483-1549。
    • Control → Dataplane 派发排队中的 AgentTask；Managed Agent 的模型循环在 Dataplane 里跑，产出 run 事件agent_endpoint_handler.go:1555-1560。
    • 应用 ← eventsUrl SSE 从 Run 事件表按 sequence 顺序吐出；15 秒无新事件发心跳；Run 到终态关流agent_endpoint_handler.go:1957-1996。
    • 应用 ← statusUrl 最后再查一次状态：completed 读 invocation.result，否则按 errorCode 处理；同时能看到 issue 与 run 的摘要agent_endpoint_handler.go:1815-1867。

    把这张时间轴与第 19 章的组件表叠起来看，会发现 Endpoint 的入口与编排决策都在 Control 里： Gateway 只转发，Dataplane 只执行模型循环与工具，Scheduler 不参与这条同步链路。这也解释了为什么「Endpoint 报错」和「Agent 回复慢」 要查完全不同的地方。

    速查：路径、错误码、三个必存变量

    调用侧只有 10 条路由，全部挂在 Gateway 上server.go:387-396：

    用途方法与路径
    开启 conversationPOST /invoke/v1/endpoints/{slug}/conversations
    继续一轮POST /invoke/v1/conversations/{conversationId}/turns
    conversation 状态GET /invoke/v1/conversations/{conversationId}
    conversation 事件GET /invoke/v1/conversations/{conversationId}/events
    提交 jobPOST /invoke/v1/endpoints/{slug}/jobs
    job 状态GET /invoke/v1/jobs/{invocationId}
    job 事件GET /invoke/v1/jobs/{invocationId}/events
    job 交付文件列表GET /invoke/v1/jobs/{invocationId}/artifacts
    下载单个交付文件GET /invoke/v1/jobs/{invocationId}/artifacts/{artifactId}
    取消 jobPOST /invoke/v1/jobs/{invocationId}/cancel

    错误码按「谁的问题」记，比背文案有用：

    响应典型原因下一步
    400缺 Idempotency-Key、空 message、input 不符合 schema、payload 超限先修请求，不要换 key
    401key 错误/过期/已撤销，或把环境头当成了凭据核对认证类型与凭据
    404slug 不存在、Endpoint 未发布或已归档、job 不属于当前 principal先确认是「没有」还是「不是你的」
    409模式不匹配、幂等键内容冲突、Readiness 不兼容读响应里的原因，别盲目重试
    413超过 maxPayloadBytes压缩或拆分输入
    429超过 rateLimit按 Retry-After 退避，保留同一个 key
    503限流器不可用或派发失败先查状态，再决定重试

    错误语义与官方错误表一致 api-reference.md:74-84； 具体状态码来自实现里的分支，例如 413 agent_endpoint_handler.go:1443-1446、 409 模式不匹配 agent_endpoint_handler.go:1425-1428、 404 归属校验 agent_endpoint_handler.go:1808-1812。

    应用侧只需要存三个变量

    BASE_URL（Gateway 公开 origin）、ENDPOINT_TOKEN（凭据，放后端 secret 配置）、 LAST_EVENT_ID（按流分别保存的游标）。不要存内部 Run 地址、不要存 slug 之外的拼装路径，也不要把 key 塞进前端页面endpoints.md:27。

    陷阱与窍门

    1. 用 X-Builder-Environment-Key 调 Endpoint，一直 401
    你会看到
    请求带着「看起来更内部」的头，但返回 invalid endpoint credential。
    因为
    它是 Worker 工具执行协议的头，不是 Endpoint 凭据api-reference.md:20；而且 Gateway 在 /invoke/v1/** 上会主动把它删掉application.yml:80-88，根本到不了校验逻辑。
    改成
    按 policy 二选一：X-API-Key 或 Authorization: Bearer。想「绕过用户权限」的念头也要打消：平台管理员不等于能读所有私有工作access.md:28。
    2. SSE 连接断了，就判定「任务失败」并重新提交
    你会看到
    网络抖动后 curl 退出，界面上任务还显示执行中——或者反过来，任务其实成功了，却因为重提又跑了一遍。
    因为
    SSE 只是事件传输方式，接到一个事件或连接关闭都不能单独作为成功依据sse-events.md:19。重连不会重新提交工作，重提才会sse-events.md:95。
    改成
    断了先查 statusUrl；还要看事件就用同一凭据带 Last-Event-ID 重新订阅。只有确实要重试提交时，才复用原 Idempotency-Key。
    3. 重试时换了新的 Idempotency-Key，结果多出两条 job
    你会看到
    业务上只应有一次报告生成，Issue 列表里却有两个 endpoint job，各带一个 Run。
    因为
    幂等只在「同一个 key」内生效；新 key 就是新的业务请求endpoints.md:56-58。而且 job 会真实创建 Issue 与 Run，副作用是可见的。
    改成
    把 key 的生成放在「业务请求」这一层：一次用户操作生成一次，重传沿用；用户明确发起新工作才换 key。
    4. 把 Team 发布成 conversation，卡在 Readiness
    你会看到
    发布时报 endpoint target is incompatible，或调用时 409 endpoint does not accept conversations。
    因为
    conversation 在发布与调用两处都要求 targetType=agentagent_endpoint_handler.go:286-294；Team 与 Workflow revision 只支持 jobagent_endpoint_handler.go:615-640。
    改成
    要「多轮聊」就发布 Agent；要「跑一次团队任务、拿结果」就发布 Team 的 job。两者可以并存，共用同一个 slug 命名空间要另起名字。
    5. 看到 completed 就当成业务验收通过
    你会看到
    调用成功、result 也有内容，但交付物缺了一部分。
    因为
    partial_succeeded 也会映射成 completedagent_endpoint_handler.go:1832-1843；官方明确说部分成功是否足够由业务决定sse-events.md:110。
    改成
    把 completed 当「调用结束」，再按 output schema 与业务标准校验 result；必要时结合 issue 摘要与 artifacts 列表确认。

    自检三问

    为什么 SSE 的 id 不能用 data 里那个 JSON id 来做续传？

    因为两者不是一回事：SSE id 是这条流的顺序游标（Conversation 对应 seq，Job 对应 sequence），而 JSON 里的 id 是存储记录标识sse-events.md:32-35。官方还专门写了一句：Conversation JSON 的 id 不能用于续传，Job JSON 的 id 也不能代替 sequencesse-events.md:59。

    同一个 Idempotency-Key 再发一次，服务端会做哪些判断？

    先按 key 找已有 invocation：找不到就新建；找到且内容一致，直接返回原来那次（202），不重复执行；内容不一致则 409agent_endpoint_handler.go:1463-1479。判断「一致」时会规范化 JSON 的 key 顺序agent_endpoint_handler.go:171-189，所以字段顺序变了不算冲突。

    为什么查询别人的 job 得到的是 404，而不是 403？

    因为读取 job 时会先认证 Endpoint，再把 invocation.PrincipalRef 与当前 principal 比对， 不一致直接返回 job is unavailableagent_endpoint_handler.go:1805-1812。这是一种「不泄露存在性」的做法：你无法通过状态码判断这个 invocationId 到底存不存在。

    20 分钟动手练习

    目标：把「提交、订阅、断线、续传、查结果」这五步亲手走一遍，中间故意断一次线。

    1. 发布一个 job Endpoint
      选第 19 章那个「资料助手」，创建一个 slug 为 report 的 job Endpoint， timeoutSeconds 设为 120，认证保持默认的 api_key。发布前先看 Readiness， 应该是 ready；发布后把返回的 key 存进环境变量。
    2. 提交并保存四个值
      用本章的 curl 提交，带上 Idempotency-Key: report-001。把响应里的 invocationId、 statusUrl、eventsUrl 抄下来——后面每一步都只靠这三个值。
    3. 订阅事件，读到终态
      curl -N 打开 eventsUrl，观察 id: / event: / data: 三行一组。如果中途出现 : heartbeat，确认它没有 JSON。
    4. 中途 Ctrl+C，再续传
      记住最后一条成功处理的事件 id，Ctrl+C 断开；然后带 Last-Event-ID: <那个 id> 重新订阅，确认不会从头重播。
    5. 同一个 key 再提交一次
      原样重发第 2 步的 curl，应该拿回同一个 invocationId；然后把 input 里的值改一个字再发， 应该得到 409。最后查一次 statusUrl，把 invocation.status 与 result 记下来。
    练习的验收标准

    你能不看文档说出：这条 job 的 Issue 在哪、为什么断线不需要重新提交、续传用的是哪个数字、以及 completed 之后还要检查什么。四个都答上来，这一章就算过关。
