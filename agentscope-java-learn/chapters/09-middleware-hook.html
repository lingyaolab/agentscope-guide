09 · 中间件与 Hook：在循环里插手

第 08 章结尾留了一个「不会自动停」的 AllToolsDeniedEvent。这一章就解决这类需求：不修改框架、 也不塞进工具，却要在循环的特定位置插一手。2.0 给出的答案是 MiddlewareBase—— 5 个 hook，4 个洋葱 + 1 条管道。至于 1.x 的 Hook 体系，整包已经标了 @Deprecated(forRemoval = true)，但代码还在 fire，别慌也别新写。

读完你能做到

  • 说清 5 个 hook 谁包谁、各自的「一次」到底指什么，不再把 onActing 当成「每个工具一次」
  • 用 order() 排出想要的嵌套顺序，并知道 GracefulShutdownMiddleware 为什么永远在最外层
  • 在 onReasoning / onActing / onModelCall 里改输入、滤事件，用 RequestStopEvent 叫停
  • 认出框架会自动挂的中间件，知道 enableTaskList(true) 悄悄加了什么
  • 分清 MiddlewareBase（2.0，推荐）与 io.agentscope.core.hook（废弃但仍可用），不做无用迁移也不新写旧 API

先说为什么：横切的事，塞哪儿都别扭

有三类需求天生不属于「工具」也不属于「业务代码」：可观测（每轮花了多少 token、工具跑了多久）、 治理（超过预算就停、敏感操作先审计）、上下文加工（每轮补一条任务清单、只把最终答案推给前端）。 塞进工具里，工具看不到模型调用；塞进业务代码里，每次 call 前后都要抄一遍。中间件就是给这些事准备的接缝。

1.x 的 Hook（接 legacy 代码时会遇到）

  • 一个 onEvent(HookEvent) 收所有事件，自己 instanceof 分流
  • 只能改事件对象：Pre/PostReasoning、Pre/PostActing 等有 setter
  • 换不了模型实例、改不了工具 schema、发不了「停」的信号
  • 整包 @Deprecated(forRemoval = true, since = "2.0.0")

2.0 的 Middleware（新代码写这个）

  • 5 个方法各管一段，只重写你关心的，其余默认直通
  • 拿到的 input 是 record，换一个新的就能改下游输入
  • 能换 Model、能发 RequestStopEvent 叫停整个循环
  • order() 控制洋葱层次，可组合、可嵌套

接口与 5 个 hook：MiddlewareBase.java:59；洋葱链的构建：MiddlewareChain.java:46；Hook 的废弃声明：Hook.java:121

官方文档这两处，抄下来会踩坑

第一，文档把 onSystemPrompt 画在 onReasoning 里面、说它「在每次组装 system prompt 时触发」。 实际是 AgentBase.notifyPreCall() 里调一次 seedSystemMsg()AgentBase.java:744，每次 call 只跑一次，不在每轮 reasoning 里。第二，文档的 TimingMiddleware、DynamicContextMiddleware 示例少了 RuntimeContext ctx 参数，签名和 2.0.4 对不上，直接编译不过。本章的代码都按源码签名写。

最小可跑：一个审计中间件，三处下手

这段是本章的主干：一个类同时重写 onSystemPrompt（改提示词）、onReasoning（记一轮的开始与耗时）、 onActing（记这一批工具和每个结果）。跑一次带工具的对话，控制台就能看到三处都在工作。 

import io.agentscope.core.ReActAgent;
import io.agentscope.core.agent.Agent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentEvent;
import io.agentscope.core.event.ToolResultEndEvent;
import io.agentscope.core.middleware.ActingInput;
import io.agentscope.core.middleware.MiddlewareBase;
import io.agentscope.core.middleware.ReasoningInput;
import io.agentscope.core.tool.Tool;
import io.agentscope.core.tool.ToolParam;
import io.agentscope.core.tool.Toolkit;

import java.util.List;
import java.util.function.Function;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

public class AuditDemo {

    static class AuditMiddleware implements MiddlewareBase {

        // 1) 管道：每次 call 组装 system prompt 时跑一次
        @Override
        public Mono<String> onSystemPrompt(
                Agent agent, RuntimeContext ctx, String currentPrompt) {
            return Mono.just(currentPrompt + "\n\n## 会话\n当前用户：" + ctx.getUserId());
        }

        // 2) 洋葱：每一轮推理前后
        @Override
        public Flux<AgentEvent> onReasoning(
                Agent agent, RuntimeContext ctx, ReasoningInput input,
                Function<ReasoningInput, Flux<AgentEvent>> next) {
            System.out.printf("[reason] msgs=%d tools=%d%n",
                    input.messages().size(), input.tools().size());
            long start = System.nanoTime();
            return next.apply(input)
                    .doOnComplete(() -> System.out.printf(
                            "[reason] done in %d ms%n",
                            (System.nanoTime() - start) / 1_000_000));
        }

        // 3) 洋葱：每一批工具调用前后（注意是「一批」）
        @Override
        public Flux<AgentEvent> onActing(
                Agent agent, RuntimeContext ctx, ActingInput input,
                Function<ActingInput, Flux<AgentEvent>> next) {
            System.out.println("[act] batch = "
                    + input.toolCalls().stream().map(t -> t.getName()).toList());
            return next.apply(input)
                    .doOnNext(ev -> {
                        if (ev instanceof ToolResultEndEvent end) {
                            System.out.println("[act] " + end.getToolCallName()
                                    + " -> " + end.getState());
                        }
                    });
        }
    }

    static class FileTools {
        @Tool(name = "read_file", description = "读一个文本文件")
        public String read(@ToolParam(name = "path", description = "文件路径") String path) {
            return "content of " + path;
        }
    }

    public static void main(String[] args) {
        Toolkit toolkit = new Toolkit();
        toolkit.registerTool(new FileTools());

        ReActAgent agent = ReActAgent.builder()
                .name("Audited")
                .sysPrompt("你是文件助手，按用户要求调用工具。")
                .model("dashscope:qwen-plus")
                .toolkit(toolkit)
                .middleware(new AuditMiddleware())
                .build();

        RuntimeContext ctx = RuntimeContext.builder()
                .userId("alice").sessionId("s-09").build();
        System.out.println(agent.call("读一下 /tmp/notes.txt", ctx).block().getTextContent());
    }
}

一个实例，会被很多请求复用

AuditMiddleware 里没有可变字段，所以安全。一旦你要「记第几次模型调用」「累计 token」这类 请求级状态，别放实例字段——放进 RuntimeContext（ctx.put/get）。 否则同一个 agent 上的两个会话会互相串数。

逐行解读：5 个 hook、3 种顺序

1. 五个 hook：谁包谁，各跑几次

hook类型「一次」指什么input典型用途
onAgent洋葱一次 call（call 与 streamEvents 共用，只跑一次）AgentInput(msgs)整次调用的计时、trace、入口鉴权
onReasoning洋葱每一轮推理ReasoningInput(messages, tools, options)补临时消息、滤中间轮文本、按轮限流
onModelCall洋葱每一次模型 API 调用ModelCallInput(messages, tools, options, model)换模型、改 delta 文本、统计 token
onActing洋葱每一批工具调用（一批可含多个）ActingInput(toolCalls)工具审计、全拒即停
onSystemPrompt管道每次 call 组装提示词时一次String注入时间、租户、任务说明
onAgent整个 ReAct 循环，最外层；call 和 streamEvents 走同一条链，不会重复触发
onReasoning每一轮：组装输入 → onModelCall → 解析输出
onModelCall最贴近模型，能拿到 Model 实例和工具 schema
onActing每一批工具：内部还会过权限引擎，然后才真正执行
onSystemPrompt不在这棵树里：call 开始前单独跑一条串行管道

四处挂链的位置：ReActAgent.java:1096（onAgent）、:2464（onReasoning）、:2624（onModelCall）、:2884（onActing）

2. order()：数字越大越靠外，但系统中间件插队

四个洋葱 hook 共用同一份中间件列表，顺序只由 order() 决定：数值越大越靠外；相同 order 保持注册顺序（List.sort 是稳定排序）。 

public class Outer implements MiddlewareBase {
    @Override public int order() { return 10; }   // 比默认 1 大 → 更外层
}

public class Inner implements MiddlewareBase {
    // 不重写 order() → 1
}

ReActAgent agent = ReActAgent.builder()
        .name("Ordered")
        .model("dashscope:qwen-plus")
        .middleware(new Inner())    // 先注册
        .middleware(new Outer())    // 后注册
        .build();
// 实际链条：onAgent/onReasoning/... 都是
//   Outer 前 → Inner 前 → 核心 → Inner 后 → Outer 后

排序发生在 build()：ReActAgent.java:5621；链按「后往前」构建、index 0 最外层：MiddlewareChain.java:56

GracefulShutdownMiddleware 永远在最外层

它不参与排序：build() 排完序后，构造函数又把 new GracefulShutdownMiddleware(...) 插到列表第 0 位ReActAgent.java:341。所以你把 order() 写成 100，也只能在「用户中间件」里最靠外，仍然在它里面。它的作用是让 reasoning / acting 各自跑完再检查停机，属于框架自己的生命周期，不该被业务包住。

3. 事件方向：外层的「前」先跑，内层的「看到」先跑

洋葱的「前逻辑」从外往里，事件流却从里往外冒泡。所以同一个事件，内层中间件先看到；这也解释了为什么 doOnNext 里的日志顺序，和 next.apply 之前的日志顺序是相反的。

  • Outer.pre
    最先执行，此时内层还没开始
  • Inner.pre
    随后执行，再往下就是核心逻辑
  • 事件冒泡
    核心产生 TextBlockDeltaEvent → Inner 的 doOnNext 先看到 → 才轮到 Outer
  • Inner.post / Outer.post
    doOnComplete 从里往外依次触发

    4. onSystemPrompt 是管道：按 order 降序接力

    它不是洋葱，没有 next。框架把上一个中间件的输出喂给下一个，按 order() 降序串行执行 （相同 order 才退回注册顺序）。排序作用于同一份 middlewares 列表，四个洋葱 hook 与这条管道共用。

for (MiddlewareBase mw : middlewares) {          // 已按 order 降序排序的列表

return result;

    6. onReasoning 与 onActing：一个包「一轮思考」，一个包「一批动作」

    onReasoning 能改的是「这一轮发给模型的消息、工具、参数」——补一条临时消息最方便，因为 ReasoningInput 的 messages 就在手里。注意 record 不可变，要构造新对象： 

    @Override
public Flux<AgentEvent> onReasoning(
        Agent agent, RuntimeContext ctx, ReasoningInput input,
        Function<ReasoningInput, Flux<AgentEvent>> next) {
    List<Msg> messages = new ArrayList<>(input.messages());
    messages.add(new UserMessage("system",
            "<system-reminder>别忘了先读 README</system-reminder>"));
    return next.apply(new ReasoningInput(messages, input.tools(), input.options()));
}

    onActing 的 input.toolCalls() 是整批工具调用。想知道单个工具的结果， 不要去数调用次数，订阅 ToolResultEndEvent：它带 toolCallName 与 state（success / error / denied / interrupted）。

    临时消息别写进 AgentState

    上面这条 UserMessage 只存在于本次 next 的输入里，不会落库、不会被压缩、也不会出现在下一轮。 想「每轮都提醒」，就每轮在这里补（内置的 TaskReminderMiddleware 正是这么干的）；想「永久记住」， 应该写进 AgentState 或长期存储，而不是靠中间件。

    叫停：RequestStopEvent 的三个消费点

    中间件不能靠 throw 来停（那会变成一次错误），也不能直接 return 一个 Msg——它返回的是事件流。 2.0 的约定是：往流里发一个 RequestStopEvent，框架把当前阶段跑完再收尾。

    你从哪发谁接住收尾动作
    onReasoning（含更深层的 onModelCall） reasoning 链外层的 doOnNext 等这次模型调用跑完；buildFinalMessage() 非空才写入上下文并打上 generateReason，随后跳过 postReasoning
    onActing acting 链外层的 doOnNext 等这一批工具都执行完；PERMISSION_ASKING 特判返回上一条 assistant，否则用 buildStopMsg(results, reason) 带着已产出的工具结果返回
    onActing（全拒专用链） emitAllToolsDeniedThroughMiddleware 发了 stop → 最后一条 assistant 打上 reason（缺省 ALL_TOOLS_DENIED）；没发 → 继续下一轮

    reasoning 的捕获与收尾：ReActAgent.java:2476；acting 的：:2891；全拒专用链：:4150；buildStopMsg：:3484

    最常用的是「预算守卫」：允许到第 N 次模型调用为止，第 N 次正常返回，然后在流尾追加一次停止请求。 

    import io.agentscope.core.agent.Agent;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentEvent;
import io.agentscope.core.event.RequestStopEvent;
import io.agentscope.core.middleware.MiddlewareBase;
import io.agentscope.core.middleware.ModelCallInput;

import java.util.function.Function;
import reactor.core.publisher.Flux;

public class BudgetGuardMiddleware implements MiddlewareBase {

    private static final String KEY = "model_calls";
    private final int maxCalls;

    public BudgetGuardMiddleware(int maxCalls) {
        this.maxCalls = maxCalls;
    }

    @Override
    public Flux<AgentEvent> onModelCall(
            Agent agent, RuntimeContext ctx, ModelCallInput input,
            Function<ModelCallInput, Flux<AgentEvent>> next) {
        Integer prev = ctx.get(KEY);
        int n = (prev == null ? 0 : prev) + 1;
        ctx.put(KEY, n);                       // 请求级状态放 ctx，不放实例字段

        Flux<AgentEvent> call = next.apply(input);
        if (n < maxCalls) {
            return call;
        }
        // 第 maxCalls 次照常完成，然后在流尾追加停止请求
        return call.concatWith(Flux.just(
                new RequestStopEvent("模型调用达到上限 " + maxCalls)));
    }
}

    两个公开构造器：RequestStopEvent.java:64；默认 reason 就是 MIDDLEWARE_STOP_REQUESTED：GenerateReason.java:70

    只发 stop、不调 next，等于白停

    reasoning 路径上，框架要先 context.buildFinalMessage() 拿到这一轮的最终消息，才会把 generateReason 打上去（源码里的条件是 rs != null && finalMsg != null）。你没调 next 就没有模型调用、也就没有 finalMsg，这次 stop 会被直接丢掉，call() 返回 null——不报错、不停止，最难查。正确写法永远是 next.apply(input).concatWith(...)。

    第二个高频场景就是 08 章留下的尾巴：全拒之后要不要停。默认不停（向后兼容），想停就观察 AllToolsDeniedEvent 并追加停止： 

    import io.agentscope.core.event.AllToolsDeniedEvent;
import io.agentscope.core.event.RequestStopEvent;
import io.agentscope.core.message.GenerateReason;

public class StopOnAllDeniedMiddleware implements MiddlewareBase {

    @Override
    public Flux<AgentEvent> onActing(
            Agent agent, RuntimeContext ctx, ActingInput input,
            Function<ActingInput, Flux<AgentEvent>> next) {
        return next.apply(input).concatMap(ev ->
                ev instanceof AllToolsDeniedEvent
                        ? Flux.just(ev, new RequestStopEvent(
                                "本轮工具全部被拒绝", GenerateReason.ALL_TOOLS_DENIED))
                        : Flux.just(ev));
    }
}
    用 concatMap，别用 flatMap

    这里要先保留原事件、再追加 stop，顺序有意义。flatMap 会把两个事件重新交错，concatMap 保证 AllToolsDeniedEvent 先被下游看到，再看到停止请求。官方文档的示例用的是 flatMap， 能跑，但顺序不保证。

    停下来之后，返回的 Msg 会带着对应的 GenerateReason。照例按它分流：

    GenerateReason谁打的你该做什么
    MIDDLEWARE_STOP_REQUESTEDRequestStopEvent 的默认值展示「已暂停」，需要时再 call 续跑
    ALL_TOOLS_DENIED必须显式传入：RequestStopEvent 的构造器会把 null 兜成 MIDDLEWARE_STOP_REQUESTED告诉用户「都拒了」，别再自动重试
    PERMISSION_ASKING框架内部（HITL 暂停）别自己发，走 08 章的 ConfirmResult
    REASONING_STOP_REQUESTED / ACTING_STOP_REQUESTED旧 Hook 的 stopAgent()维护老代码时才会见到
    INTERRUPTED / MAX_ITERATIONS中断 / 触顶与中间件无关，但会从同一个出口返回

    续跑很轻：挂起状态已经持久化在 AgentState 里，用同一个 RuntimeContext 再 call 一次即可—— agent.call(List.of(), ctx)；只有一个默认会话时，agent.call() 也行。注意摘要阶段也走 onModelCall，但那条路径不捕获 RequestStopEvent，别指望在摘要里把 agent 叫停。

    内置中间件：只有两个在 middleware 包里，其余在别的包

    搜 implements MiddlewareBase 会得到 5 个实现：2 个在 middleware 包（可直接用）， 3 个在别处（其中 2 个由框架自动挂）。先认清谁是谁，再决定要不要自己写。

    类重写了什么谁挂上去干什么 / 代价
    TaskReminderMiddleware onSystemPrompt + onReasoning enableTaskList(true) 自动 system prompt 里加一段 todo_write 用法；每轮把任务清单渲染成 <system-reminder> 临时注入，带 METADATA_SYNTHETIC，不落库、不被压缩
    FinalAnswerFilterMiddleware onReasoning 手动 middleware(...) 缓冲文本事件；一旦本轮出现 ToolCallStartEvent 就整轮丢弃，只放行最后一轮。代价：首字要等到本轮模型调用结束才出现
    OtelTracingMiddleware onAgent / onModelCall / onActing 手动 invoke_agent / chat / execute_tool 三层 span；没配 OTel SDK 时近零开销
    GracefulShutdownMiddleware onReasoning / onActing 自动，插在列表第 0 位 每个阶段跑完检查是否在停机；在安全点打 checkpoint，不浪费已生成的 token
    DynamicSkillMiddleware onSystemPrompt 配了 skillRepositories 且开启动态技能时自动加 每次 call 重新解析技能仓库，把可用技能清单拼进 system prompt

    两个可直接用的：TaskReminderMiddleware.java:54、FinalAnswerFilterMiddleware.java:44；追踪：OtelTracingMiddleware.java:77；停机：GracefulShutdownMiddleware.java:53

    Hook：整包废弃，但代码还在 fire

    io.agentscope.core.hook 下 19 个类全部标了 @Deprecated(forRemoval = true, since = "2.0.0")，javadoc 的原话是 middleware 「replaces this entire hook system」。但它没有被拆掉：AgentBase 仍然在 PreCall / PostCall 阶段 fire，ReActAgent 仍然通过 LegacyHookDispatcher fire 推理、行动、摘要的各阶段事件， builder.hooks(...) 也还在。技能功能内部自己也在用 SkillHook。

    Hook 事件对应的 middleware 位置差别
    PreCallEvent / PostCallEventonAgent（改提示词用 onSystemPrompt）Hook 能改最终返回的 Msg，middleware 的 onAgent 只能看事件流
    PreReasoningEvent / PostReasoningEventonReasoningHook 改事件对象，middleware 换 ReasoningInput
    ReasoningChunkEventonModelCall 的事件流一个按 chunk 回调，一个是流
    PreActingEvent / PostActingEventonActingHook 的 PostActing 是单个工具一次；middleware 的 onActing 是整批一次
    PreSummaryEvent / PostSummaryEvent无对应摘要阶段只经过 onModelCall，没有 onReasoning

    废弃声明：Hook.java:121；仍在 fire 的 Pre/PostCall：AgentBase.java:726；摘要走 onModelCall：ReActAgent.java:3965

    三条实用结论

    一，新代码不要再写 Hook，用 middleware；二，老代码能跑就先别动，forRemoval 指的是 「下个小版本可能删」，不是「今天就坏」；三，两者可以共存，但同一件事别写两遍——双重日志事小，双重改写输入事大。

    public Mono<String> onSystemPrompt(
            Agent agent, RuntimeContext ctx, String currentPrompt) {
        String tenant = ctx.get("tenant");        // 调用方放进 RuntimeContext 的属性
        if (tenant == null) {
            return Mono.just(currentPrompt);      // 没有就原样返回，别返回 empty
        }
        return Mono.just(currentPrompt
                + "\n\n## 租户规则\n当前租户：" + tenant
                + "\n只能访问该租户自己的数据。");

}

    配方 2：整次调用记账（token / 模型调用次数）

    public class UsageMiddleware implements MiddlewareBase {

    @Override
    public Flux<AgentEvent> onAgent(
            Agent agent, RuntimeContext ctx, AgentInput input,
            Function<AgentInput, Flux<AgentEvent>> next) {
        int[] calls = {0};
        int[] in = {0};
        int[] out = {0};
        return next.apply(input)
                .doOnNext(ev -> {
                    if (ev instanceof ModelCallEndEvent end && end.getUsage() != null) {
                        calls[0]++;
                        in[0] += end.getUsage().getInputTokens();
                        out[0] += end.getUsage().getOutputTokens();
                    }
                })
                .doFinally(sig -> System.out.printf(
                        "[usage] calls=%d in=%d out=%d%n", calls[0], in[0], out[0]));
    }
}

    用 doFinally 而不是 doOnComplete：取消和报错也要把数字打出来。这里数到的是整次 call 的模型调用，包含触顶后的摘要那次；只想数推理轮次，就把同样的代码挪到 onReasoning。

    陷阱与窍门

    1. 发了 RequestStopEvent，call() 却返回 null
    你会看到
    中间件里明确发了停止，程序不报错，但返回的 Msg 是 null，后续按钮全部 NPE。
    因为
    你直接 return Flux.just(new RequestStopEvent(...))，没调 next。没有模型调用 → buildFinalMessage() 为 null → 源码里的 rs != null && finalMsg != null 不成立，stop 被丢弃。
    改成
    永远 next.apply(input).concatWith(Flux.just(stop))；要「不调模型就拒绝」，别用 stop，直接在业务层拦住这次 call。
    2. 把请求状态放在中间件实例字段里
    你会看到
    并发跑两个会话，A 的 token 计数跑到 B 头上；或者「只提醒一次」变成了全局只提醒一次。
    因为
    一个中间件实例会被同一个 agent 上的所有 (userId, sessionId) 共用，实例字段就是全局变量。
    改成
    请求级状态放 RuntimeContext：ctx.put("k", v) / ctx.get("k")；它在一次 call 内是线程安全的，也随 ctx 天然隔离。
    3. 以为 onSystemPrompt 每轮都跑
    你会看到
    把「当前时间」「本轮任务」写进 onSystemPrompt，结果整轮对话里时间一直不变。
    因为
    它在 PreCall 阶段由 seedSystemMsg() 调一次，每次 call 只跑一次；管道按 order() 降序执行（同序才按注册顺序）。
    改成
    要「每轮变」的内容放 onReasoning，往 messages 里补一条临时消息；onSystemPrompt 只放整次 call 不变的东西。
    4. 把 onActing 当成「每个工具一次」
    你会看到
    一轮里模型调了 3 个工具，你的日志只打了一行；或者想给每个工具单独计时，发现拿不到。
    因为
    onActing 包的是一整批，ActingInput.toolCalls() 是列表。单个工具的粒度在事件流里。
    改成
    用 next.apply(input) 的流，按 ToolResultEndEvent.getToolCallName() 拆；要改参数则在工具内部或权限层做。
    5. 在 onActing 里吞掉了 RequestStopEvent
    你会看到
    配上自己的 onActing 过滤器后，08 章的权限确认不再暂停了：本来该出 PERMISSION_ASKING，现在直接跑下去。
    因为
    HITL 的暂停信号也是以 RequestStopEvent("permission asking", PERMISSION_ASKING) 的形式从 acting 流里发出的。你过滤事件时把它一起丢了。
    改成
    过滤只针对你要处理的类型；遇到 RequestStopEvent、RequireUserConfirmEvent、AllToolsDeniedEvent 一律原样放行。
    6. 在 onModelCall 里调两次 next 做重试
    你会看到
    账单翻倍；日志里一次失败后紧跟两次成功；超时时间也不对。
    因为
    next.apply(input) 就是一次真实模型调用，你在 onErrorResume 里再调一次就是两次请求，而且绕过了框架的退避与超时配置。
    改成
    重试交给 modelExecutionConfig(...) / maxRetries(...)；中间件只负责换模型或改输入。

    自检三问

    A 的 order() 是 2、B 是 1，A 先注册。谁先看到 TextBlockDeltaEvent？

    B 先看到。A 更靠外，所以 A 的「前逻辑」先执行、B 的后逻辑先执行；但事件是从内层往外冒的，B 比 A 先拿到每个事件。order 只决定嵌套层次，不决定事件到达顺序。

    一个 onSystemPrompt 返回了 Mono.empty()，会发生什么？

    整条管道断掉：applySystemPromptMiddlewares 用 flatMap 串联，遇到空序列就结束，后面的中间件全不执行；最终 seedSystemMsg 拿到空字符串，再被 filter(prompt -> !prompt.isEmpty()) 滤掉，于是这次 call 没有 system message。想不改就返回 Mono.just(currentPrompt)。

    在 onActing 里发了 stop，这一批剩下的工具还会执行吗？

    会——只要你的中间件把 next 的流接上。框架是「把当前阶段跑完再停」：它继续消费完整的 acting 流，所以这批工具都会执行（或走完权限判定），然后才把 RequestStopEvent 收尾成 buildStopMsg(results, reason)，已产出的结果都会保留。想让某个工具根本不跑，得在权限引擎或工具入口拦。

    20 分钟动手练习

    1. 给审计中间件加一层「总账」
      在 AuditDemo 上再加一个 order() = 10 的中间件，只重写 onAgent：用 doFinally 打印整次 call 的毫秒数，并数出 ModelCallEndEvent 的个数。把 maxIters 调成 1，让它触顶并走摘要，观察模型调用次数是不是比你预期的多一次。
    2. 跑一次预算守卫，再跑一次续跑
      用 BudgetGuardMiddleware(2) 问一个需要多轮工具的问题，确认返回的 getGenerateReason() 是 MIDDLEWARE_STOP_REQUESTED；再用同一个 RuntimeContext 调 agent.call(List.of(), ctx)，观察请求一开始就又停了——因为计数还在 ctx 里。想重置就 ctx.put("model_calls", null)（传 null 会删 key）或换一个 ctx。
    3. 把 08 章的「全拒」变成「一拒就停」
      挂上 StopOnAllDeniedMiddleware，重跑 08 章的全拒场景：返回的 Msg 应该带 ALL_TOOLS_DENIED，而不是继续下一轮。然后再试「只拒一部分」：AllToolsDeniedEvent 不会触发，agent 会继续。这个对比能让你记住事件名里的 All 不是形容词。
