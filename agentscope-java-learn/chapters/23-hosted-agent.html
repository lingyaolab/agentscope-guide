23 · Hosted Agent 与 Runtime Host

第 22 章把一个应用注册进目录；这一章把一台已经装好 Coding Agent 的机器接进来。 Hosted 既不运行你的 Agent 代码，也不替你管理模型账号——它把「工作派发」做成一个 Host 主动 claim 的循环： 控制面记录工作与调度，Runtime Host 在你的电脑或服务器上启动 provider，provider 用你本机已登录的账号执行。 难点不在 connect 那一行，而在分清 Host 在线、provider 可探测、Agent 可派发是三个不同的检查点。

读完你能做到

  • 说清 Managed、External、Hosted 三者分别「谁在运行 Agent」，以及 Hosted 为什么是拉取而不是推送
  • 安装三个 CLI 可执行文件，用交互登录、enrollment token 或已有 Host 凭据完成连接
  • 解释 Host / Runtime Profile / Agent 三层配置各自负责什么，模型覆盖按什么顺序生效
  • 对照五类 provider 的能力矩阵，判断指令、技能、MCP、工具策略、子 Agent 与会话恢复是否可用
  • 读懂 claim 的准入条件、容量与租约，定位「Host 在线但任务不来」到底卡在哪一项
  • 按「目录 → claim → 工作目录 → provider → 审批 / 恢复」的顺序做验收与排障

边界：Service 安排工作，主机执行工作

Hosted 的定义可以压成一句：Service 负责工作、调度和协作记录；Runtime Host 在本机启动 provider 并回传结果； 模型、工具和 provider 账号由你管理hosted-agent.md:10。所以 Hosted 的重点不是「Agent 定义存在哪」，而是「执行进程运行在哪台机器、用谁的账号登录」。

方式谁运行 Agent工作怎么到达你主要维护什么
Managed Service 的 Harness 与 Dataplane 控制面内部调度 定义、Instructions、绑定的资源
External 你自己的应用进程 注册 + 会话合约；任务能力另走 ASDP 进程、框架、模型与工具凭据、任务实现
Hosted 本机 Coding Agent provider Host 主动 claim ExecutionAttempt 主机在线、provider 登录、Profile / Pool / 容量

这三条路径共享工作入口，但执行责任不同。官方特别提醒：Host 在线不等于 provider 已登录，也不等于所有工具权限都可用hosted-agent.md:31。排查时先问「缺的是哪一层」，不要把所有失败都归因成「Agent 没创建好」。

一句话边界

Managed 把 Agent 交给 Service 跑；External 把身份和会话交给 Service，进程仍归你；Hosted 把一台已登录 provider 的主机交给 Service 调度。 Runtime Host 不是托管 Agent 的 Hands Worker，它管理的是 provider 进程与任务工作目录runtime-host.md:53。

三层结构：控制面、Host 守护进程、provider

把 Hosted 拆开看，稳定只有三层，故障也基本落在这三层里：

控制面：记录与调度
Agent 目录、Runtime Profile / Pool、ExecutionAttempt、租约、工具审批、Issue / Team 记录。 它决定「这活该给哪个池、哪个 Host、哪个 provider」，但不执行模型循环hosted-agent-execution.md:10。
Runtime Host：领取、准备、拉起、回传
注册稳定身份与能力，按容量 claim 工作，准备任务目录，把可移植定义投影成 provider 能读的格式， 启动 provider 子进程，上报事件、checkpoint 和最终状态hosted-agent-execution.md:12-19。
Provider：真正跑模型与工具
Codex、Claude Code、Qoder、QwenPaw、OpenClaw 等本机 CLI。模型、登录态、工具权限都在这一层； 适配器只负责把平台事件翻译成 provider 的原生协议hosted-agent-providers.md:10。

和 External 最大的结构差别是方向：External 的 ExecutionAttempt 由控制面通过 ASDP 长连接推给应用； Hosted 的 Host 则按 poll-interval 主动 POST 到 claim 端点，拿到一条 Attempt 后才开始执行engine.go:109-128。因此控制面不需要回连 Host 守护进程；它只需要 Host 能出站访问 Service。

claim 的响应不是一个空壳：它同时带回冻结的 Runtime Profile、Agent 定义、任务上下文，以及 attempt token 与 task tokenclient.go:169-193。Host 不需要在派发时再拼一次配置；它执行的是控制面在入队时冻结的那份快照。

执行者与平台协作也走两层：MCP 可用的 provider 优先用 agentscope-collaboration； 只能跑 Shell 的 provider 用任务范围 CLI 读写 Issue、发进度、上传 Artifactruntime-host-cli.md:80-98。这两条通道都需要任务范围凭据，而不是主机凭据。

安装：三个可执行文件，provider 不算在内

从同一 Service Release 下载对应操作系统与 CPU 架构的 agentscope-cli-VERSION-OS-ARCH.tar.gz， 包里有 agentscope、别名 aistioctl 和 aistio-runtime-host。 三个文件必须放在同一个 PATH 目录中runtime-host.md:14。provider 本体需要另行安装、登录并确认可运行runtime-host.md:16。 

mkdir -p agentscope-cli "$HOME/.local/bin"
tar -xzf agentscope-cli-VERSION-OS-ARCH.tar.gz -C agentscope-cli
install -m 0755 agentscope-cli/agentscope agentscope-cli/aistioctl \
  agentscope-cli/aistio-runtime-host "$HOME/.local/bin/"
export PATH="$HOME/.local/bin:$PATH"

包名按 linux/darwin 与 amd64/arm64 组合； 不确定平台时先用 uname -sm 看runtime-host.md:20-27。如果是从源码构建，仓库里也提供了 make install-runtime-cli PREFIX=... 的入口runtime-host-cli.md:6-13。

升级时先检查活跃任务，再替换配套二进制并重新启动；config.json、state/host.id 与 workspaces/ 这些持久状态要保留runtime-host.md:77。把它们删掉不会「清理环境」，只会让这台机器换一个身份。

连接：先登录 provider，再让 Host 拿到身份

正确顺序是先在目标主机安装并登录 provider，用本机完成一个简单请求，确认模型与授权可用； 再连接 Runtime Hosthosted-agent.md:23。连接成功后，status 看守护进程，probe 看 provider 探测： 

agentscope connect https://agentscope.example.com
agentscope runtime status
agentscope runtime probe

不传 URL 时，CLI 会依次探测 http://127.0.0.1:18080、:8080、:8081 的 /healthz，每个候选 800ms；都探不到就要求显式传入 Service 地址connect.go:208-229。这对本地 Compose 很方便，也意味着「连不上」时先确认地址，而不是先怀疑 token。

身份有四种来源，选一种即可，不能把两种凭据混着传：

方式你提供什么换取什么
交互登录 控制台用户名与密码，走 /api/auth/login 平台 token，再换成本机范围的 asrh_ 凭据connect.go:241-299
Enrollment token 操作者生成的短期 asre_ token，放进 AGENTSCOPE_ENROLLMENT_TOKEN 绑定本机 host key 与 token 范围的 asrh_ 凭据service-v5-api-contract.md:86-92

enrollment token 是给无人值守服务器用的：操作者先执行 agentscope runtime enrollment-token create， 在目标主机设置环境变量后再 connect；服务端只接受 asre_ bearer 加本地 hostKey， 换出绑定三者的 asrh_ 凭据service-v5-api-contract.md:88-91。不要把 enrollment token 或 config.json 放进共享脚本runtime-host.md:63。

重复 connect 不是「只加一个参数」

命令会先读已有配置，只覆盖显式传入的 URL、provider、pool、capacity、workspace 与 state 根目录； 如果旧守护进程在跑，它会先停掉旧进程，再保存配置并启动新进程connect.go:55-60。所以「补一个 --capacity」会顺带重启 Host，正在执行的任务要提前检查。

非前台启动会等 state/daemon.ready，最长 15 秒；超时会停掉子进程并回显最后几行日志local_runtime_process.go:241。看到这个超时，先看日志里是注册失败、provider 探测失败，还是控制面不可达，不要反复 connect 刷屏。

配置：Host、Profile、Agent 三层，不要混着改

Hosted 有三层配置：Host 的连接与容量、Runtime Profile 的 provider 参数、Agent 的职责与模型覆盖hosted-agent-configuration.md:10。排障时先确认改的是哪一层，否则很容易「在 Agent 里改了模型，却以为是主机容量问题」。

层谁维护关键字段典型问题
Host 运维 / 主机所有者 pool、capacity、providers、两个根目录 池名不匹配、容量满、provider 未发现
Runtime Profile 管理员 provider、configuration、requirements 沙箱 / 权限参数不适配，requirements 与主机能力不符
Agent Agent 作者 Instructions、model、Workspace、skills / subagents、执行覆盖 模型覆盖写错、请求了 provider 不支持的能力

模型覆盖的顺序

Agent 的 model 非空时优先于 Profile 的 model；两者都为空时使用 provider 自己的默认配置hosted-agent-configuration.md:41。源码里的 DefinitionModel(request, fallback) 也是这个顺序：先看 Agent 定义，再退回 Profile 配置provider.go:169-174。

Agent 绑定还可以带执行覆盖：reasoningEffort、serviceTier、 providerConfiguration 与 customArgs。这些值在派发时解析并冻结到本次 Attempt， 不会修改共享的 Runtime Profileagent_catalog.go:94-134。自定义参数最多 64 条、单条最长 1024 字符agent_catalog.go:104-121；按 argv token 传递、不经过 Shell，并拒绝 Runtime Host 保留参数provider.go:130-146；工作目录、模型、沙箱、协议、resume、MCP 与权限相关的保留参数不能覆盖hosted-agent-configuration.md:63。

五类 provider：先看能力，再看模型名

当前 Runtime Host 包含五类适配器；runtime probe 只验证可执行文件可探测，实际工作还需要 provider 登录、模型与工具可用hosted-agent-providers.md:10。

自动探测会按顺序找 PATH 上的 codex、claude、qodercli、qwenpaw、 openclaw，也接受 AISTIO_CODEX_BINARY 等五个环境变量覆盖，以及 ~/.local/bin 下的同名文件local_runtime_discovery.go:37-57。每个候选的 --version 只等 4 秒，超时或报错就跳过local_runtime_discovery.go:81-86。

指定 --providers codex,qoder 时不会「能装几个算几个」：只要列表里有一个已知 provider 没找到，connect 就直接失败； 写了未知名字也会报不支持local_runtime_discovery.go:91-106。这能避免「以为启用了 Qoder，实际上只注册了 Codex」。

还有第二道探测：守护进程启动时会再对所有已配置 provider 执行一次 Detect，任何一个失败都会让 Host 注册失败engine.go:139-146。connect 之后卸载了某个 CLI，现象就是守护进程起不来，而不是「少一个 provider 继续跑」。

官方矩阵把可移植定义拆成指令、技能、MCP、Managed 风格工具策略、子 Agent 与会话恢复六列hosted-agent-providers.md:26-32。下面把「审批」也单列出来，因为它是 Tool 权限里最容易误解的一列：

「支持」只表示适配器有对应集成，仍需要目标 CLI 版本与账户能力。Codex 原生子 Agent 映射要求 0.153.4+， Qoder 要求 1.0.37+，且当前映射要求共享工作区hosted-agent-providers.md:34。源码还会拒绝两类声明：Codex 子 Agent 不能带 tools 或 maxIters； Qoder 子 Agent 的工具名必须能映射到原生工具名subagents.go:93-114。

Claude Code 的权限通过其 CLI 配置控制，不能承诺与 Codex / Qoder / QwenPaw 相同的控制面确认流程； OpenClaw 使用支持 Shell 的任务 CLI 完成协作，但不支持本适配器的 MCP 注入hosted-agent-providers.md:36。同一 Team 可以混用不同 provider，但要先逐个验证成员的独立任务与协作工具，再检查 Leader 的委派与汇总hosted-agent-providers.md:42。

创建 Hosted Agent：选 Runtime，不是选 Managed

在 DESIGN → Agents 新建 Agent 时，Runtime 要选择已发现的 Coding Agent provider，而不是 AgentScope Managed； 填写职责、可选模型覆盖和 Workspacehosted-agent.md:35。页面会展示 runtime 的指令、工具、技能、子 Agent 等能力映射，按实际支持范围配置hosted-agent.md:35。

Hosted 绑定在数据模型里同时需要 runtimeProfileId 与 runtimePoolId，缺一个就验证失败types.go:182-185。日常使用通常是在控制台选择一个已发现的 Runtime，由它带入 Profile 与 Pool；管理员再维护 Profile 和池hosted-agent-configuration.md:43。

Workspace 可以提供可移植的指令、技能和工具定义，适配器把支持的内容映射到 provider；但安装额外 CLI、登录第三方系统与工具权限仍需在目标主机完成。 不能只修改 Instructions 就获得主机未安装的程序hosted-agent.md:47。执行前会先做能力校验，请求了 provider 不支持的能力会直接拒绝，而不是「先跑起来再说」compatibility.go:86-94。

不要把某台机器的路径写成所有 Host 的路径

Pool 用来聚合可承载执行的主机，Profile 决定 provider 参数，Agent 只声明自己要什么。把 /Users/alice/repo 这类本机路径写进共享 Workspace，换一台 Host 就会失败；任务目录由 Host 自己管理hosted-agent.md:37。

派发：一次 claim 要过多少道门

把一次 Hosted 执行按时间排开，路径是这样的：

  • 工作入队 Issue / Team / 支持的 Chat 产生 AgentTask，控制面冻结 Runtime 绑定、Profile 配置与能力要求，生成 queued 的 ExecutionAttempthosted-agent-execution.md:14。
  • Host 轮询 守护进程每 2 秒按自身容量 claim；没有工作就收到 204，不报错engine.go:67-69。
  • 准入匹配 数据库在一条语句里检查池名、online 状态、generation、容量、required capabilities、provider 与 hostSelector，然后 SKIP LOCKED 取一条execution_attempts.go:216-245。
  • prepare Host 上报 preparing，按 session / task 计算工作目录键，准备目录与仓库，然后把可移植定义写入 .agentscope/definitionengine.go:218-249。
  • 能力复检 确认 Profile 存在、provider 已安装，并用该适配器的 Descriptor 再校验一次 Workspace 能力；不通过就以明确 failure code 结束engine.go:252-271。
  • start 与租约 上报 running，启动 provider 子进程；同时每 LeaseTTL / 3 续租，默认 60 秒租约即 20 秒续一次engine.go:553-584。
  • 事件与 checkpoint 适配器把 provider 事件交给 Host；Host 写本地 journal、发布到控制面，并在 provider session 变化时提交 checkpointengine.go:300-329。
  • 收尾 成功提交 result 与 checkpoint；失败提交 failure code；取消走 cancelled。终态一旦被控制面确认，时间线封闭，仍在跑的进程会被要求停下engine.go:330-363。

最容易卡住的是第三步。把 claim 的准入条件拆成表，就能按顺序排除「Host 明明在线，为什么没有任务」：

准入条件怎么满足不满足时的现象
h.state = onlineHost 心跳正常；draining 不接新活Host 列表在线状态不对，或已 drain
h.lease_generation 匹配用当前注册返回的 generation claim旧进程 claim / heartbeat 报冲突
e.runtime_pool_name = h.pool_nameAgent 绑定与 Host 用同一个池名池里没有能领这条 Attempt 的 Host
h.active < h.capacity提高容量，或等当前执行结束任务一直 queued
required capabilities 是 Host 能力的子集Host 真实探测到对应 provider能力不匹配，永远不选它
Profile provider 在 Host 的 providers 里安装并让 Host 探测到该 CLIHost 在线，但这条 Profile 无主机可去
Pool 的 hostSelector 是 Host labels 的子集标签与池选择器一致同池但被选择器排除
preferredHostId 为空或等于本机恢复时优先原 Host；不可用则清空恢复被路由到别的主机或退回 fresh

claim 端点在没有可领工作时返回 204 No Content，这是正常状态，不是错误taskplane_handler.go:522-525。如果一直 204，按上表从下往上查：先看池与 generation，再看容量与能力，最后才看 Agent 定义。

Host 的并发由自己控制：循环里先比较 active 与注册 / 心跳返回的有效容量，再决定是否 claim； 注册与心跳响应里的容量会覆盖本地配置engine.go:109-116。所以控制台调低容量不会杀掉正在跑的执行，只会让 Host 在占用降到容量以下之前不再领新任务。

工作目录：Host 管的目录，不是你的 checkout

任务工作目录由 Host 管理，默认位于其状态目录下；不要把它当成你已打开的本地 Git checkout。 仓库内容和分支必须按任务的工作区配置准备hosted-agent.md:43。Host 也不会默认切到你正在编辑的仓库hosted-agent-execution.md:30。

目录键由 Host 计算，规则只有两种：

  • 普通任务：<workspaceRoot>/<tenant>/<taskId>，任务之间隔离workspace.go:70-76。
  • Hosted Conversation：<tenant>/<namespace>/conversations/<agent>/<sessionId>，同一会话的后续轮次复用同一目录workspace.go:71-74。

复用目录不是「省事」，而是某些 provider 的原生 session 索引按工作目录划分；目录一变，旧会话可能就找不到了workspace.go:52-57。传入的 workspaceKey 还会做路径校验，绝对路径、.. 和越界前缀都会被拒绝workspace.go:133-143。

如果任务上下文带仓库地址，Host 只在目录为空时 git clone；已经存在 .git 就跳过； 目录非空且不是 Git 仓库则直接报错workspace.go:159-178。这条规则能防止把上一次的残留文件当成干净仓库继续改。

可移植 Workspace 文件不会散落在仓库根目录，而是投影到 .agentscope/definition： 每次执行先清空再写入，路径不允许逃逸，.agentscope 本身不能是符号链接execution_environment.go:29-69。provider 再按自己的能力把 skills / subagents 映射到原生目录，例如 Codex 的 .agents/skills、 Claude 的 .claude/skills。

任务范围身份通过环境注入：Host 只给 provider 子进程任务 token、控制面地址和 task / issue / agent / team / run 标识； AGENTSCOPE_API_TOKEN、AGENTSCOPE_RUNTIME_TOKEN、内部 token 等主机 / 人类凭据会被移除provider.go:250-306。MCP 配置写成 0600 的临时文件，token 放请求头而不是 argv，避免进程列表泄露provider.go:309-342。

协作入口有两条：MCP 可用的 provider 得到 agentscope-collaboration； Shell 可用的 provider 还能调用 agentscope task context、issue current、 task progress、artifact upload 等任务范围命令runtime-host-cli.md:86-98。如果 Team Leader 既没有 MCP 也没有 CLI，执行会直接失败，而不是静默地「只做一半」engine.go:439-446。守护进程启动时找不到 agentscope 会告警，Shell-only provider 的协作能力也会随之缺失main.go:109-112。

provider 能把文件留在 Host 磁盘上，不等于其他协作者能访问；需要共享的结果应上传为 Artifacthosted-agent-execution.md:32。

工具审批：三种 provider 接控制面，两种走原生权限

Codex、Qoder 与 QwenPaw 适配器提供控制面工具确认接入；Claude Code 的权限通过 CLI 配置控制， OpenClaw 也不走本适配器的控制面确认流程hosted-agent-providers.md:36。源码里的断言也很直接：Codex 的 Approval 目标是 item/*/requestApprovalcodex/adapter.go:62，Qoder 是 control_request/can_use_toolqoder/adapter.go:73，QwenPaw 是 session/request_permissionqwenpaw/adapter.go:64。

  • provider 请求 适配器把 provider 的原生审批请求转成 ToolApprovalRequest：工具 ID、名称、输入预览、输入 SHA-256、过期时间provider.go:48-63。
  • 创建审批 Host 用任务 token 调 POST /api/v1/agent-tasks/{id}/runtime-approvals，kind 为 tool_confirmationclient.go:273-288。
  • 轮询决定 GET decision；202 表示还没决定，等 1 秒再查；拿到决定后带 decisionVersion 回 ackclient.go:290-325。
  • 幂等重试 创建与 ack 对同一 tool-use / decisionVersion 幂等；短暂控制面故障按 250ms 起步、最多 2 秒退避重试，总预算 1 分钟client.go:327-356。

这意味着控制台里的「允许 / 拒绝」不是装饰：拒绝消息会回传给 provider；审批记录绑定工具输入哈希，避免审批后输入被替换。 但不要把这条流程套到 Claude Code 上——它的权限语义由 CLI 自己解释，平台不能承诺同样的 Inbox 确认体验。

恢复：resume 有条件，重试是新 Attempt

适配器把 provider 事件转换成平台执行记录；Host 保留日志、provider session 标识和 checkpoint，用于支持的恢复路径。 重启时保留状态目录与 Host 身份，但「声明 Resume 支持」不等于任意中断都能恢复：目标 provider 的会话仍需存在且可访问； OpenClaw 当前不提供 Session resumehosted-agent-execution.md:38。

场景发生什么会话会复用吗
取消 取消请求传到执行链路，Host 取消 provider 上下文并确认 cancelled；控制面给 30 秒确认宽限，超时强制取消runtime_control_sweeper.go:190-205 不适用；这是一次执行的终点
重试 产生新的 ExecutionAttempt；只有符合恢复条件时才使用原 provider 会话hosted-agent-execution.md:42 有条件，见下

六个坑：先看方向，再看代码

坑一：probe 成功，就以为能派发。probe 只是重新扫描 PATHlocal_runtime_process.go:156-171；守护进程用的是保存下来的 provider 列表，启动时还会逐个 Detect，任何一个缺失都会注册失败engine.go:139-146。正确顺序是：provider 能本机跑 → probe 能看到 → Host 注册成功 → Profile / Pool 匹配 → Agent 可派发。

坑二：只加 capacity，不改 Profile / Pool。容量只决定「同时能跑几个」，不决定「这条任务能不能来」。 claim 还会检查池名、provider 能力、requirements、hostSelector 与 generationexecution_attempts.go:226-238。容量也不是模型额度，增加 Host 并发不会让 provider 账号多出配额hosted-agent-configuration.md:43。

坑三：把本地 checkout 当任务目录。Host 为每个任务 / 会话准备自己的目录，不会切到你正在编辑的仓库hosted-agent-execution.md:30。目录非空且不是 Git 仓库会直接报错，而不是「就地覆盖」workspace.go:163-168。

坑四：复制或删除 state/。Host 身份是状态目录里的持久 UUID，不是主机名；删掉会换一个新身份，复制到另一台机器会造成身份冲突identity.go:32-49。官方也要求保留 Host 身份与状态文件，避免把已有主机错误地注册为新实例runtime-host.md:49。

坑五：把 config.json 当模板，或用命令行传 secret。配置里有 credential， 文件权限是 0600；正常路径是环境变量传给守护进程，而不是进程参数runtime-host-cli.md:38-42。connect 还会把平台 token 从守护进程环境里移除，只保留 Host 范围凭据local_runtime_process.go:322-326；把 config 复制进共享脚本，等于把主机身份也共享了。

坑六：请求 provider 根本没有的能力。Codex 不支持 Managed 内置工具策略，需要改用 sandbox / 审批compatibility.go:73-75；OpenClaw 不支持 MCP 注入，也不提供 Session resumeopenclaw/adapter.go:62-65；Claude Code 当前适配器没有声明控制面 Approval，不能指望与 Codex 相同的确认流程anthropiccli/adapter.go:52-65。这些都会在执行前被拒绝，属于「设计上不支持」，不是重试能解决的。

自测：三个判断题

runtime probe 能看到 Qoder，创建 Agent 时却选不到对应 Runtime，先查什么？

先查守护进程实际配置的 provider 列表，而不是 probe 的输出。probe 固定用 auto 重新扫描 PATHlocal_runtime_process.go:156-171；如果 connect 时只选了 Codex，配置里就没有 Qoder，Host 注册的能力里也不会出现它。其次再看 Host 是否 online、 池名与 Profile 是否匹配、容量是否已满。

Host 重启后，旧进程还在发心跳，为什么会得到 409？

重新注册会递增 lease_generationcontrolplane_registry.go:317-327；心跳要求请求里的 generation 与当前记录一致，否则返回冲突controlplane_registry.go:363-372。这是 fencing：旧进程不能再代表这台主机领任务或续租。

一次执行报 heartbeat_timeout 后重试，一定会回到原来的 provider 会话吗？

不一定。重试会产生新的 Attempt；只有同一会话里存在成功的 checkpoint，且原 Host 仍 online、池名、Profile 能力与 Pool 选择器都匹配时， 才保留 provider session 与 workspace key，否则退回 freshservice.go:433-455。跨后端时只能靠 Issue、评论与 Artifact 重建上下文，进程内记忆不会跟着搬hosted-agent-execution.md:42。

练习：接通一台 Host，再故意让它接不到任务

目标不是「看到绿色」，而是能独立判断每一层坏在哪。建议 35 分钟，按顺序做，每步留证据：

  1. 先证明 provider 自己能跑
    在目标主机安装并登录一个 provider，直接用它的 CLI 完成一次只读请求。记录版本号与登录账号；此时还不需要 connect。
  2. 连接并核对身份
    执行 agentscope connect URL --providers codex --capacity 1，再跑 status 与 probe。记录 Host ID、Host key、Pool、配置路径；确认 config.json 是 0600。
  3. 创建一个只读 Agent
    在 DESIGN → Agents 选择刚发现的 Runtime，Instructions 写明只读，Model 留空跟随 Profile / CLI。保存后检查 Runtime 就绪状态。
  4. 派一个小 Issue
    创建「读取示例仓库 README，输出三条改进建议，不修改文件」的 Issue。检查 Execution 时间线、provider 事件与最终评论；如果产生文件，再上传为 Artifact 验证共享路径。
  5. 制造一次离线
    停止 Host，观察控制面在 45 秒后把主机标为 offline；再启动，确认 Host key 不变、generation 变化。期间提交的 Issue 应保持 queued，而不是消失。
  6. 用容量和 drain 各挡一次
    把容量降到 1 并同时提交两个任务，确认第二个排队；再 drain 主机，确认没有新任务被领取。resume 后恢复。记录 400 / 409 各触发一次的条件。
  7. 触发一次能力拒绝
    给 Codex Agent 加一条 Managed 风格内置工具策略，或在 OpenClaw Agent 上请求 MCP，提交任务，确认在 provider 启动前就以能力错误结束。把 failure code 与证据写进排障笔记。
  8. 可选：验证恢复边界
    如果有第二个 Host，把原 Host 停掉后重试同一会话，观察是 fresh fallback 还是路由到新 Host；对照 runtime diagnose 的输出确认判断。

下一章看什么

到这里，Hosted 的三层边界已经拆完：控制面负责记录与准入，Runtime Host 负责领取 / 准备 / 拉起 / 回传，provider 负责真正的模型与工具。 它和 External 最大的差别不是「谁更聪明」，而是工作怎么到达执行者：External 靠应用注册与会话合约，Hosted 靠主机 claim 与租约。

下一章看 Team 协作：Leader、成员与结果收敛。Hosted 已经能作为 Team 里的实施者：同一 Team 可以混用不同 provider， 但每个成员要先独立跑通，再检查 Leader 的委派、等待、重试与汇总。那会把本章的「单任务派发」扩展成「多任务收敛」。
