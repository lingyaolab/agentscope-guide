30 · 分布式存储：Redis / MySQL / MongoDB / OSS

单机跑 Agent 时，状态写本地 JSON、文件写本地目录、沙箱快照不存，一切都能工作。一旦变成多副本， 同一会话可能落到不同进程：状态会互相覆盖，文件会「这台有、那台没有」，沙箱会在两个节点同时启动。 DistributedStore 就是把这些组件收成一个门面的地方，但它不替你选文件系统，也不保证每个后端能力相同。

读完你能做到

  • 说清 DistributedStore 的九个 getter 中，哪两个必填、哪些有默认值、哪些可以留空
  • 解释 HarnessAgent 的装配优先级，以及为什么 RemoteFilesystemSpec 配本地状态存储会直接报错
  • 按能力矩阵选择 Redis、JDBC、MongoDB、OSS，而不是按品牌背模块名
  • 用混合后端解决「对象存储不能做锁」「MongoDB 快照很大」「MySQL 已有基础设施」三类冲突
  • 区分 USER、SESSION、AGENT、GLOBAL 四种隔离范围，以及并发时的真实语义
  • 识别 CAS 不是每个后端都有，并解释 aistio 托管 Store 为什么仍要求自备 AgentStateStore

单机默认与多副本现实

不开分布式存储时，Harness 会退回本地实现：状态用 JsonFileAgentStateStore，工作区用本地文件系统， 沙箱快照默认 NoopSnapshotSpec，并发锁默认 no-op HarnessAgent.java:2426-2429 DistributedStore.java:90-112。 这些默认值在单进程里很合理，在多副本里就是数据竞争。

问题单机默认多副本后果
会话状态本地 JSON 文件同一 sessionId 落到不同 Pod，互相看不到；并发写最后写入者覆盖
工作区文件本地目录换节点后文件消失；RemoteFilesystemSpec 直接拒绝本地状态
沙箱快照不保存下次调用拿不到上一次的工作区
并发锁不限制USER / AGENT / GLOBAL 范围下两个沙箱同时改同一份状态

DistributedStore 的设计目标就是「一次配置，覆盖这些组件」。但它只提供存储组件， 文件系统模式仍要你显式选：注释写得很清楚，distributed store 提供 storage，filesystem mode 是用户的选择 HarnessAgent.java:2381-2384。

契约：九个 getter，两个必填

官方文档常把它讲成「四件套」，但 2.0.4 的接口实际有九个 getter：状态、基础 KV、快照、并发锁，外加消息总线、 异步工具注册表、任务仓库、会话轮次闸门和 Team 客户端 DistributedStore.java:74-179。

builder 的校验很简单：agentStateStore 与 baseStore 必须非空，快照与锁为空就换成 no-op， 其余五个直接传 null DistributedStore.java:303-321。 所以「混合后端」不是高级技巧，而是 builder 的默认能力。 

DistributedStore store = DistributedStore.builder()

    .baseStore(redisStore.baseStore())

装配：显式 builder > distributedStore > 本地默认

HarnessAgent 的优先级是固定的：显式 builder 方法最高，其次是 distributedStore 自动注入， 最后才是 workspace 默认 HarnessAgent.java:2381-2407。 自动注入覆盖：状态、远程文件 KV、沙箱快照、沙箱锁、消息总线、异步工具注册表；任务仓库与会话闸门在上层按需使用。

远程文件 + 本地状态 = 启动失败

如果用了 RemoteFilesystemSpec，但最终生效的 AgentStateStore 仍是 JsonFileAgentStateStore 或 InMemoryAgentStateStore，Harness 会直接抛 IllegalStateException，提示你配置分布式状态存储或改用 .distributedStore(...) HarnessAgent.java:2431-2438。 这不是配置警告，而是设计上的拒绝：远程文件系统不能配一个进程内的状态存储。

这也是本章与第 31 章的分界：本章讲「怎么把组件接上」，第 31 章讲「状态存储内部怎么序列化、怎么做 CAS」。

Redis 是文档里的多副本首选，也是能力矩阵里四项核心组件齐全的后端 redis.md:6 index.md:24-33。 RedisDistributedStore.fromJedis(jedis) 会把默认前缀 agentscope: 拆成 agentscope:session:、agentscope:store:、agentscope:snapshot:、 agentscope:guard: 四组 key RedisDistributedStore.java:56-108。

JDBC：当前推荐路径，不是旧的 MysqlDistributedStore

这一页文档与源码有一个重要差异：官方 MySQL 文档仍用 MysqlDistributedStore.create(dataSource) mysql.md:20-33， 但 2.0.4 源码已经把 MysqlDistributedStore 标成 @Deprecated(since = "2.1", forRemoval = true)， 并明确建议改用 agentscope-extensions-jdbc 的 JdbcDistributedStore MysqlDistributedStore.java:54-60。

新实现会自动检测数据库方言，再组装四个组件：JdbcAgentStateStore、JdbcStore、 JdbcSnapshotSpec、JdbcSandboxExecutionGuard，支持 MySQL、PostgreSQL、H2 与 SQLite JdbcDistributedStore.java:31-42。 组件是懒加载的，第一次访问才建表，之后复用，避免每次 getter 都跑一遍 DDL JdbcDistributedStore.java:65-78。 

DistributedStore store = JdbcDistributedStore.create(dataSource);

新 JDBC 实现的状态表可自动创建，库名 / 表名限定 [A-Za-z_][A-Za-z0-9_]*（不允许连字符）且长度 ≤ 64；旧 MysqlAgentStateStore 才允许连字符，迁移时需改名。JdbcStore 的 putIfVersion 通过单语句 CAS 实现；在 MySQL 方言下，JdbcSandboxExecutionGuard 走 GET_LOCK() / RELEASE_LOCK()，锁名超过 64 字符会自动 hash， 且 named lock 是 server 级别，共享实例时要用唯一前缀 mysql.md:52 mysql.md:76 mysql.md:93-106。

新项目直接用 JdbcDistributedStore

旧类不是不能用，而是它只覆盖 MySQL，且已被标成未来移除。新项目用 JdbcDistributedStore， 同一套代码可以跑 MySQL、PostgreSQL、H2 与 SQLite；迁移时只需换工厂，组件接口不变。

MongoDB：文档型状态 + GridFS 快照

MongoDB 用复合 _id 组织会话，状态键放在 states 子文档、版本放在 versions 子文档 mongodb.md:48-64。 MongoDistributedStore.create(mongoClient) 默认库名是 agentscope，四个集合分别是 agentscope_sessions、agentscope_base、agentscope_snapshots、 agentscope_sandbox_locks MongoConstants.java:26-44。

DistributedStore store = MongoDistributedStore.create(mongoClient);

这里也有一个文档与源码的差异。文档写会话 TTL 30 天、快照上限 15MB；源码写的是： 会话 TTL 默认关闭，要显式 ttlDays(n) 才创建 TTL 索引； 快照走 GridFS，按 255KB 分块，单文件上限 16GB，并且快照没有独立 TTL MongoAgentStateStore.java:84-98 MongoRemoteSnapshotClient.java:40-50。 文档的 30 天 / 15MB 不能作为容量与保留策略依据 mongodb.md:64 mongodb.md:89。

OSS：大快照首选，但不做锁

OSS 提供状态、基础 KV 与快照三件，不提供 SandboxExecutionGuard： 对象存储不适合做分布式锁 oss.md:80-93。 OssDistributedStore.create(ossClient, bucket, "agentscope/") 会把前缀拆成 state/、store/、snapshot/ 三组对象 OssDistributedStore.java:39-84。 

DistributedStore oss = OssDistributedStore.create(ossClient, "my-bucket", "agentscope/");
DistributedStore mixed = DistributedStore.builder()
    .agentStateStore(oss.agentStateStore())
    .baseStore(oss.baseStore())
    .sandboxSnapshotSpec(oss.sandboxSnapshotSpec())

OSS 的运维重点不在接口，而在凭据与生命周期：生产建议用 RAM Role + STS 临时凭证，不要硬编码 AK/SK； 给快照 bucket 配生命周期规则（文档举例 7 天），避免存储成本失控 oss.md:104-107。

混合后端：把「必须在一起」拆开

混合后端的规则很简单：状态和基础 KV 必填，快照与锁可以来自另一套后端，后五个可选组件也可以单独接。 最常见的组合有三种：

组合解决什么代价
JDBC 状态 + 文件，Redis 快照 + 锁已有 MySQL，但想要 Redis 的低延迟锁两套基础设施、两套备份
MongoDB 状态 + 锁，OSS 快照快照超过 Mongo 单文档时代的容量假设，或想用对象存储生命周期状态与快照不在同一后端，恢复要同批协调
OSS 状态 + 文件 + 快照，Redis 锁阿里云生态、大快照、仍需要并发控制OSS 的 CAS / 延迟不适合高频状态写

builder 只要求状态与基础 KV，其余为空时用 no-op 或 null；这意味着「只补一个能力」是合法的， 不需要为了锁引入一整套新后端 DistributedStore.java:303-321。

隔离范围：同一 scope 不等于同一个活沙箱

IsolationScope 同时决定状态键与 store 命名空间：USER 按用户共享（默认，缺 userId 回退 SESSION），SESSION 按会话隔离，AGENT 按 Agent 名共享，GLOBAL 在同一 workspace / store 实例内全局共享 IsolationScope.java:30-51。

这是顺序复用，不是活实例共享

源码注释特别说明：沙箱模式下，同一 scope 的并发调用各自拿到自己的容器，结束时收敛到最后一个持久化快照； 它不是「多个调用共享同一个正在运行的容器」 IsolationScope.java:49-51。 所以 USER / AGENT / GLOBAL 范围才需要 SandboxExecutionGuard 来串行化 SandboxExecutionGuard.java:27-31。

一致性：CAS 不是每个后端都有

BaseStore.putIfVersion 的默认实现直接返回 false，注释要求支持分布式的后端自己覆盖成服务端原子检查 BaseStore.java:47-77。 AgentStateStore 也一样：默认 supportsVersioning() 为 false，saveIfVersion 会退化成无条件 save，返回 UNVERSIONED = -1 AgentStateStore.java:63-67 AgentStateStore.java:81-138。

因此「用了分布式存储」不等于「解决了并发」。还要确认后端是否实现版本化：Redis 用 Lua、JDBC 用 SQL CAS、MongoDB 用 versions 子文档；OSS 在文档里被列为 last-writer-wins index.md:103-106。 高并发写同一会话时，优先选支持 CAS 的后端。

ControlPlaneStores cp = ControlPlaneStores.fromEnv();
DistributedStore store = cp.withAgentStateStore(redisStore.agentStateStore());

fromEnv() 要求 AISTIO_CONTROL_PLANE_HTTP、BUILDER_INTERNAL_TOKEN、 AISTIO_AGENT_NAME，命名空间默认 default ControlPlaneStores.java:57-67。 托管组件是否可达由 GET /api/v1/dp/healthz 探测；不可达时部分可选组件返回 null，回退到 workspace 实现 ControlPlaneStores.java:182-189。

六个坑：把「接上」当成「接对」

坑一：以为 DistributedStore 会自动切文件系统。它只提供存储组件，文件系统仍要显式 RemoteFilesystemSpec 或 Sandbox 模式 HarnessAgent.java:2381-2384。

坑二：远程文件配本地状态。Harness 会直接拒绝；这不是可以忽略的警告 HarnessAgent.java:2431-2438。

坑三：用 OSS 做锁。对象存储没有 guard；需要并发控制时混入 Redis / JDBC / Mongo oss.md:80-93。

坑四：沿用 MongoDB 旧文档的 TTL / 15MB。源码是 TTL 默认关闭、GridFS 16GB；容量与保留策略要按源码重算 MongoAgentStateStore.java:84-98。

坑五：以为 putIfVersion 一定有效。BaseStore 默认返回 false，AgentStateStore 默认 UNVERSIONED； 要选实现了 CAS 的后端 BaseStore.java:64-77。

坑六：继续用 MysqlDistributedStore。它已标记未来移除；新代码用 JdbcDistributedStore MysqlDistributedStore.java:54-60。

自测：三个判断题

传了 distributedStore，文件系统就自动变成分布式了吗？

不会。它只提供 BaseStore 等存储组件；文件系统模式仍要显式选 RemoteFilesystemSpec 或 Sandbox 模式，源码注释明确区分 storage 与 filesystem mode HarnessAgent.java:2381-2384。

OSS 能不能同时提供沙箱并发锁？

不能。OSS 提供状态、基础 KV 与快照，但不提供 SandboxExecutionGuard； 需要锁时混入 Redis / JDBC / Mongo oss.md:80-93。

MongoDB 快照还有 15MB 上限、会话 30 天自动过期吗？

2.0.4 源码不是这样：快照走 GridFS，单文件上限 16GB；会话 TTL 默认关闭，要显式 ttlDays(n) 才创建 TTL 索引。旧文档的 15MB / 30 天不能直接作为当前依据 MongoAgentStateStore.java:84-98 MongoRemoteSnapshotClient.java:40-50。

练习：给多副本部署选一套存储

目标不是装齐四个后端，而是能写清楚为什么每个组件落在那里。建议 50 分钟：

  1. 画四个组件
    写下状态、文件 KV、快照、锁，分别标出当前单机默认与多副本需求。
  2. 先排除缺能力
    如果要用 OSS 做快照，先把锁从 OSS 方案里排除，补一个 Redis / JDBC / Mongo 锁。
  3. 配 Redis 一键
    用 RedisDistributedStore.fromJedis 配 RemoteFilesystemSpec，启动并跑一轮对话。
  4. 看 key 前缀
    在 Redis 里确认 session / store / snapshot / guard 四组 key，记录默认前缀与实际写入。
  5. 换 JDBC 一键
    用 JdbcDistributedStore.create(dataSource) 跑同一轮，比较表结构与启动日志。
  6. 做一次混合
    用 MongoDB 或 JDBC 管状态和文件，OSS 管快照，Redis 管锁；确认 builder 只要求状态与基础 KV。
  7. 测 CAS
    对同一个 key 连续两次 putIfVersion，第一次成功、第二次失败；换 OSS 看行为差异。
  8. 写三行结论
    分别写「状态落在哪」「快照为什么在那」「锁为什么不能省」，确保每行都能独立核对。
