04 · 消息与事件

上一章我们知道了「流里流着东西」，这一章拆开看流里到底是什么。框架把「一句话」和「正在说这句话的过程」拆成了两套类型：Msg 体系负责结果（会进历史、会落盘、会喂给下一个模型），AgentEvent 体系负责过程（只在传输途中有意义）。搞混这两者，是做流式界面时最常见的返工原因。

读完你能做到

  • 说清 Msg 的 7 个字段各管什么，以及 9 种 ContentBlock 分别该塞给谁
  • 看到 replyId / blockId / toolCallId 时，能判断这三个 id 各自把什么关在一起
  • 用 streamEvents() 自己拼出完整回答，并知道为什么「不该这么做」

先说为什么：消息是包裹，事件是物流轨迹

把 Msg 想成已经签收的包裹：里面有东西（内容块）、有寄件人（name）、有面单号（id）、有签收时间（timestamp）。包裹可以堆在仓库里，下次还能拿出来看——这就是「对话历史」。

而 AgentEvent 是物流轨迹：「已揽收」→「运输中」→「派送中」→「已签收」。轨迹只在运输期间不断产生，你不会把轨迹存进仓库当包裹用，但你可以盯着轨迹做实时播报（这正是流式界面干的事）。

Msg：结果

  • 一次性拿到，可序列化、可落盘、可回放
  • 是模型的输入（历史就是 List<Msg>）
  • 内部是 List<ContentBlock>，一条消息可以同时有文字和图片

AgentEvent：过程

  • 几十上百条，只在该次调用期间存在
  • 是界面的输入（打字机、工具进度条、思考折叠块）
  • 靠 replyId 归到同一条消息，靠 blockId 归到同一个块

两者是同一件事的两个视角，所以框架内部只有一套执行路径：call() 也是跑同一条事件流，只是它把 AgentResultEvent 里的最终 Msg 挑出来返回ReActAgent.java:1012。这一点在 05 章不重复，但你要记住：流式不是另一种调用方式，阻塞式只是流式的一个消费者。

最小可跑：造一条消息 + 数一遍事件

第 1 步：造一条同时含文字和图片的消息

import io.agentscope.core.message.ImageBlock;
import io.agentscope.core.message.Msg;
import io.agentscope.core.message.TextBlock;
import io.agentscope.core.message.URLSource;
import io.agentscope.core.message.UserMessage;
import java.util.List;

public class InspectMessage {
    public static void main(String[] args) {
        Msg msg = new UserMessage(List.of(
                TextBlock.builder().text("这张图里有几只猫？").build(),
                ImageBlock.builder()
                        .source(URLSource.builder()
                                .url("https://example.com/cats.png")
                                .mimeType("image/png")
                                .build())
                        .build()));

        System.out.println("role   = " + msg.getRole());      // USER
        System.out.println("blocks = " + msg.getContent().size());  // 2
        System.out.println("text   = " + msg.getTextContent());     // 只有文字那半句
        System.out.println("image  = " + msg.hasContentBlocks(ImageBlock.class)); // true

        ImageBlock img = msg.getFirstContentBlock(ImageBlock.class);
        System.out.println("url    = " + ((URLSource) img.getSource()).getUrl());
    }
}

UserMessage(List<ContentBlock>) 构造：UserMessage.java:69；getTextContent()：Msg.java:544；三个按类型取块的方法：Msg.java:346、:359、:386

getTextContent() 不是「消息转字符串」

它的实现是「筛出所有 TextBlock，把 getText() 用换行拼起来」Msg.java:545。所以一条纯图片消息调用它会得到空字符串，而一条「文字 + 图片」消息只能拿到文字那半句。想拿全部内容必须遍历 getContent()。

第 2 步：数一遍一次回答产生多少事件

import io.agentscope.core.event.AgentEvent;
import io.agentscope.core.message.UserMessage;
import java.util.Map;

Map<String, Integer> counter = new TreeMap<>();

agent.streamEvents(new UserMessage("用一句话介绍你自己"))

counter.forEach((type, n) -> System.out.printf("%-28s %d%n", type, n));

逐行解读：Msg 的字段与 9 种内容块

Msg 的 7 个字段

字段 取法 它解决什么问题
id getId() 消息的唯一标识。构造时不给就随机生成 UUID；事件里的 replyId 最终指的就是它。
name getName() 「谁说的」。单 agent 时可空；多 agent 场景（辩论、主管-工人）靠它区分发言人，formatter 会把它写进请求载荷。
role getRole() 只有 4 个值：USER / ASSISTANT / SYSTEM / TOOL。
content getContent() List<ContentBlock>，一条消息可以混合多种块。返回的是不可变列表。
metadata getMetadata() 框架偷偷塞东西的地方：生成原因、token 用量、结构化输出都在这。
timestamp getTimestamp() 格式固定为 yyyy-MM-dd HH:mm:ss.SSS 的字符串，不是 Instant。
usage getUsage() / getChatUsage() 这次生成消耗的 token 与耗时。注意两个取法：getUsage() 只看字段，getChatUsage() 会回退到 metadata 里的 _chat_usage 并顺手反序列化Msg.java:579。
角色和内容块有白名单，塞错了直接抛异常

Msg 构造时会跑一遍 validateRoleContentMsg.java:181：USER 只能是 text / data / image / audio / video 五种；SYSTEM 只能是 text；ASSISTANT 与 TOOL 不限制。所以「往 UserMessage 里塞一个 ToolUseBlock」会在 构造那一刻抛 IllegalArgumentException: USER message may only contain ...，而不是等到调模型才报错。

9 种内容块

ContentBlock 是一个 sealed 类，permits 明确列出 9 个子类ContentBlock.java:58。sealed 带来的好处很实在：你在自己代码里 switch 它时，编译器能检查你有没有漏分支。

块类型 JSON type 承载什么 通常出现在
TextBlock text 纯文本 所有角色
ThinkingBlock thinking 模型的思维链（推理过程） ASSISTANT（开了 thinking 的模型）
ToolUseBlock tool_use 「我要调这个工具，参数是这些」 ASSISTANT
ToolResultBlock tool_result 工具执行结果 TOOL
DataBlock data 通用二进制（图片/音频/视频/文件都行） USER / ASSISTANT
ImageBlock image 图片（遗留类型，兼容保留） USER
AudioBlock audio 音频（遗留类型） USER
VideoBlock video 视频（遗留类型） USER

新代码该用 DataBlock 还是 ImageBlock？

源码注释写得很直接：ImageBlock / AudioBlock / VideoBlock 是为了向后兼容而保留的遗留类型，DataBlock 才是「面向未来」的统一容器，新代码应优先用它DataBlock.java:24。两者都能放进 USER 消息（白名单里都放行了），所以升级不会破坏旧管道。

至于底层是「URL 引用」还是「base64 内联」，不写在块上，而是写在块里的 Source 上：URLSource 走链接（适合大文件、CDN），Base64Source 走内联（适合小图、离线）。URLSource 还支持一个 mimeType 提示，专门对付「没有扩展名的签名 URL」URLSource.java:40。

key 常量 内容

端到端：一次带工具的回答，事件是怎么排队的

事件的骨架永远是 start → delta(×N) → end。但一次回答里可能有多轮「推理→执行」，所以下面这个序列会循环出现：

  • 开场
    AgentStartEvent：带 replyId、sessionId、agent 名称与角色。后面所有事件都归到这个 replyId 上
  • 第 1 轮推理
    ModelCallStartEvent → 文本块 / 思考块的生命周期 → ModelCallEndEvent（带 input/output token）
  • 模型要调工具
    ToolCallStartEvent → ToolCallDeltaEvent（JSON 参数一片片到达）→ ToolCallEndEvent，全程靠 toolCallId 关联
  • 框架执行工具
    ToolResultStartEvent → ToolResultTextDeltaEvent / ToolResultDataDeltaEvent → ToolResultEndEvent（带 ToolResultState）
  • 第 2 轮推理
    拿着工具结果再问一次模型，于是又一轮 ModelCallStart / TextBlock* / ModelCallEnd。这就是「ReAct 循环」在事件流里的样子
  • 收尾
    AgentResultEvent（携带最终 Msg）→ AgentEndEvent
三个关联 id 的分工
  • replyId：把「这一次回答」里的所有事件关在一起。一次 call() 一个 replyId。
  • blockId：把「同一个内容块」的 start/delta/end 关在一起。文本块、思考块、数据块用它。
  • toolCallId：把「同一次工具调用」的 call 与 result 关在一起。跨轮次配对也靠它。
最容易踩的假设
  • blockId 只保证在一个 reply 内唯一，不是全局 UUID，别拿它当数据库主键。
  • 一次 reply 里 ModelCallStart 可能出现多次，因为工具调用会带来第二轮推理。
  • 不要假设「文本块只有一块」——模型可能先输出一段思考、再输出一段正文。

事件公共方法（getId / getCreatedAt / getType / getSource / getMetadata）：AgentEvent.java:115；AgentStartEvent 的四个 getter：AgentStartEvent.java:58

getSource() 是给「子 agent」用的

顶层 agent 发出的事件 getSource() 为 null；子 agent 的事件会带斜杠路径（如 "main/researcher"）。你在做多 agent 的界面时，靠这个字段把不同 agent 的输出分栏显示——不需要自己维护映射表。

从事件流重建消息：能做，但通常别做

只想要纯文本：拼 delta

import io.agentscope.core.event.TextBlockDeltaEvent;
import io.agentscope.core.message.UserMessage;

StringBuilder text = new StringBuilder();

agent.streamEvents(new UserMessage("用三句话解释什么是 ReAct"))
        .filter(e -> e instanceof TextBlockDeltaEvent)
        .cast(TextBlockDeltaEvent.class)
        .doOnNext(e -> text.append(e.getDelta()))
        .blockLast();

System.out.println(text);

这就是所有「打字机效果」的全部原理：把 delta 一片片接到同一个 StringBuilder 上。没有魔法。

想要完整的工具调用记录：自己配对 toolCallId

import io.agentscope.core.event.ToolCallDeltaEvent;
import io.agentscope.core.event.ToolCallStartEvent;
import io.agentscope.core.event.ToolResultEndEvent;
import io.agentscope.core.message.UserMessage;
import java.util.LinkedHashMap;
import java.util.Map;

Map<String, StringBuilder> args = new LinkedHashMap<>();

agent.streamEvents(new UserMessage("北京现在天气怎么样？"))
        .doOnNext(e -> {
            if (e instanceof ToolCallStartEvent s) {
                args.put(s.getToolCallId(), new StringBuilder());
                System.out.println("开始调工具：" + s.getToolCallName());
            } else if (e instanceof ToolCallDeltaEvent d) {
                args.get(d.getToolCallId()).append(d.getDelta());
            } else if (e instanceof ToolResultEndEvent r) {
                System.out.println("工具结束 state=" + r.getState()
                        + " args=" + args.get(r.getToolCallId()));
            }
        })
        .blockLast();

ToolCallStartEvent.getToolCallId()：ToolCallStartEvent.java:55；ToolCallDeltaEvent.getDelta()：ToolCallDeltaEvent.java:71；ToolResultEndEvent.getState()：ToolResultEndEvent.java:85

想要一条真正的 Msg：用 call()

上面两个例子都是「重建」，而重建是有代价的：你要自己处理思考块、多轮工具、错误状态、token 统计。框架内部的 call() 之所以能返回一个完整 Msg，是因为它在同一条事件流上做了三件事——过滤出 AgentResultEvent、取出里面的 getResult()、取最后一个ReActAgent.java:1014。 

// 要过程 → 订阅事件，自己做增量渲染
agent.streamEvents(userMsg).doOnNext(...).blockLast();

// 要结果 → 让框架把事件收成一个 Msg 再给你
Msg reply = agent.call(List.of(userMsg), RuntimeContext.empty()).block();
什么时候才真的需要自己重建？

三种情况：① 你要把事件转发给浏览器做 SSE，前端自己拼；② 你要在 不结束调用 的前提下显示「到目前为止的内容」（比如超过 N 秒就先把已生成部分展示出来）；③ 你在做可视化调试器，要看到每个块的边界。除此之外，用 call() 更省事也更不容易错。

陷阱与窍门

1. 以为 getTextContent() 能拿到全部内容
你会看到
用户发了一张图 + 一句话，你把消息转成字符串存库，结果图「消失」了；纯图片消息甚至存成空串。
因为
它只筛 TextBlock 并用换行拼接，非文本块一律忽略。
改成
要完整内容就遍历 getContent()，按块的运行时类型分支处理；只做日志摘要时才用 getTextContent()。
2. 试图直接改 getContent() 返回的列表
你会看到
UnsupportedOperationException。
因为
构造时用的是 content.stream().filter(...).toList()，得到的是不可变列表Msg.java:151，而 getter 直接把它返回出去。
改成
用 msg.withContent(newList) 造一条新消息；Msg 是不可变对象，所有「修改」都是返回副本。
3. 把 blockId 当全局唯一 ID 存进数据库
你会看到
不同会话、不同请求的记录互相覆盖；或者重启后对不上。
因为
blockId 只承诺在一个 replyId 作用域内唯一，实现甚至可以用固定类型标识（比如文本块统一用一个常量）当 blockId。
改成
落库主键用 Msg.getId()；需要关联块时用「replyId + blockId」组合。
4. 假设一次回复只有一轮模型调用
你会看到
界面上工具结果出来了，后面又冒出一段文字，但你的代码只处理第一条 TEXT_BLOCK_START，第二段丢了。
因为
模型调工具后会带着工具结果再次推理，所以 MODEL_CALL_START 与 TEXT_BLOCK_START 都可能出现多次。
改成
用 blockId 作 key 维护多个缓冲区，或者干脆每次 TEXT_BLOCK_START 都新开一个段落。
5. 把事件流当历史存下来
你会看到
会话恢复后模型「不记得」之前聊了什么，或者上下文里混进了重复内容。
因为
历史是 List<Msg>，不是事件集合。事件只是同一条消息的施工过程，存了也不能直接喂回模型。
改成
要持久化就存 Msg（框架的 AgentStateStore 就是这么做的，见 07 章）；要回放界面才存事件。

自检三问

一条纯图片消息调用 getTextContent() 返回什么？为什么？

返回空字符串。因为它的实现只保留 TextBlock 并拼接 getText()Msg.java:545，图片块在 filter 阶段就被排除了。

replyId、blockId、toolCallId 各自把什么关在一起？

replyId 关「一次回答的全部事件」；blockId 关「一个内容块的 start/delta/end」；toolCallId 关「一次工具调用的 call 与 result」。三者是包含关系：一个 reply 里有多个 block，一个 block 可能对应一个 tool call。

既然 streamEvents() 的信息更全，为什么还要用 call()？

因为 call() 在内部跑的是同一条流，只是帮你把 AgentResultEvent 里的 Msg 取出来ReActAgent.java:1015。它省掉了你处理思考块、多轮工具、错误状态、token 统计的全部工作。只有需要「边生成边展示」时才值得自己消费事件。

20 分钟动手练习

  1. 给事件做一次「类型普查」
    跑 CountEvents，然后把问题换成需要工具的（比如「现在几点？请用工具查」），再跑一次。对比两次的 MODEL_CALL_START 数量——你会亲眼看到「一轮变两轮」。
  2. 手搓打字机 + 首字延迟
    在 doOnNext 里记录第一次收到 TextBlockDeltaEvent 的时刻，和请求发起时刻相减，打印「首字延迟 xxx ms」。这个数字就是用户感知的「卡不卡」。
  3. 故意制造一个白名单错误
    试着 new UserMessage(List.of(ToolUseBlock.builder().id("x").name("t").input(Map.of()).build()))，把异常信息完整读一遍。以后再看到这条报错，你就不用猜了。
