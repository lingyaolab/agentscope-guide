22 · External Agent：把已有应用注册进目录

前两章都在讲「Service 怎么替你跑」：第 20 章把 Managed Agent 发布成 Endpoint，第 21 章拆开它的定义与四类资源。 这一章换一边——应用仍然跑在你自己的 JVM 里，模型、工具、部署方式都不变，Service 只拿走三样东西： 目录身份、会话视图、可选的派发权。难点不在注册那一行代码，而在分清这三样各自走哪条通道。

读完你能做到

  • 判断一个应用该用 External、Managed 还是 Hosted，并说清三者各自「谁在运行」
  • 用六个环境变量把 Java 应用注册进目录，知道每个值填错时会出现什么现象
  • 解释 HTTP contract 与 ASDP 的分工：为什么注册成功、会话能读，却仍然接不到 Issue
  • 读懂 /agentscope/* 的读写路由、401 / 409 / 501 的语义，以及 500 条会话截断
  • 用 AgentTaskStarter 接一次派发，并按 succeeded / waiting / blocked / failed 回报
  • 按「身份 → 会话 → 派发」三层顺序做验收，而不是看到目录里有卡片就宣布接入完成

先说边界：Service 托管，还是你的进程在跑

External 的定义只有一句，但每个短句都是约束：保留你的应用进程、框架和部署方式，同时接入统一目录、会话诊断与工作协作； 它不是由 Service 启动的 Managed Agent，也不要求改造成 Runtime Host providerexternal-agent.md:10。换句话说，Service 拿到的是「这个 Agent 存在、它能做什么、它的会话长什么样」，不是「这台机器归 Service 调度」。

把三种运行方式并排放在一张表里，边界立刻清楚AGENTS.md:30-36：

方式谁运行 AgentService 负责什么你要负责什么
Managed Service 的 Harness 与 Dataplane 模型循环、会话、执行环境、资源装配 定义、Instructions、绑定的资源
Hosted 你电脑或服务器上的 Coding Agent provider Runtime Host 注册、发现、派发与恢复 安装并登录 provider，保持主机在线
External 你自己的应用进程 目录身份、会话视图、可选的派发与租约 进程、框架、模型与工具凭据、任务实现

这里最容易被忽略的是最后一行：External 应用不会因为注册成功就被 Service 接管external-agent-execution.md:10。模型额度、工具密钥、数据库连接仍然在你的应用里；Service 不会替你读 Managed Vaultexternal-agent-configuration.md:48。所以「注册完还是 401」通常不是注册问题，而是应用自己的凭据问题。

一句话分工

Managed 是「把 Agent 交给 Service 跑」，Hosted 是「把一台已登录的主机交给 Service 调度」， External 是「把身份和会话视图交给 Service，进程仍归你」。三者共享工作入口，但能力边界不同AGENTS.md:36。

两条接入路径，三层验收

官方把 External 的接入拆成两条路径，差别不在语言，而在是否需要 ASDP 长连接external-agent.md:22-27：

路径网络前提拿到的能力
Java HTTP contract 应用能访问注册 API；控制面能回连应用的合约地址 注册、合约查询、会话命令、以及适配器实现的命令
ASDP 框架接入 上述 HTTP 连通性，再加上可达的 ASDP gRPC listener 实时事件上报，以及适配器实现的 ExecutionAttempt 派发

标准 Service Compose / Helm 跑的是 standalone HTTP，不提供 ASDP listener；Python instrument() 的自动注册又和 ASDP 初始化绑定， 不能靠 start_grpc=False 把它变成完整的 HTTP 注册方案external-agent.md:27。这不是配置开关的问题，而是部署形态的问题：开关打开，不会让 Gateway 凭空长出一个 gRPC listenerexternal-agent-configuration.md:42。

选完路径，还要按三个层次分别验收，因为它们的证据完全不同external-agent-execution.md:23-27：

  • 第一层 · 目录身份 逻辑 Agent、运行绑定与实例注册成功；范围、副本身份、generation 正确。证据是目录里的卡片与实例列表。
  • 第二层 · 会话能力 应用运行会话后，bridge 能提供它声明的上下文、消息与命令。证据是一次真实对话加一次历史读取。
  • 第三层 · 工作执行 具备任务入口的适配器接受 Attempt，执行并回报状态。证据是一次成功、一次失败、一次取消。

    • 只有第二层的应用仍然有用：可以观察独立应用的运行情况。但平台会根据真实 capability 判断 Chat、命令和派发是否可用， 不会因为目录里有一张卡片就全部点亮external-agent-execution.md:29。

    两个入口的差别，比名字大

    instrument 对已经 build 完的 Agent 也能用：会话快照、有效上下文、历史与命令都能读到， 但它不会产生 Level-2 事件，因为 ReActAgent 的 middleware 列表在构造时就固定了，事后加不进去Aistio.java:46-48。要事件流，必须在 build 时把 adapter.middleware() 挂上。

    Java 内置适配器的识别条件很窄：target instanceof AgentAgentScopeAdapter.java:158-160。包了一层自定义对象、或者传进去的是框架的 Session 而不是 Agent，都会在 attach 阶段直接抛 IllegalArgumentExceptionSessionBridge.java:148-157，不会「注册到一半」。

    六个环境变量，逐条对号

    官方最小示例只用了六个变量，刚好覆盖「注册到哪、以谁的身份、哪个副本、控制面怎么回连」四件事first-session.md:107-115：

    变量填什么填错时的典型现象
    AISTIO_CONTROL_HTTP 应用可访问的 Service HTTP 注册地址，带 scheme，例如 http://aistio:8081 启动日志反复出现 register failed (will retry)，目录里始终没有卡片
    AISTIO_BOOTSTRAP_TOKEN 管理员交付的受信任 workload / bootstrap 凭据 401 或注册被拒；换成 Endpoint 的 asep_ key 也不会通
    AISTIO_TENANT 目标租户；未设置时 SDK 按 default 处理 卡片出现在错误的租户下，控制台当前范围看不到
    AISTIO_NAMESPACE 目标命名空间；未设置时 SDK 按 default 处理 同租户但跨 namespace，目录与权限都对不上
    AISTIO_INSTANCE_KEY 当前副本的稳定标识；不同副本必须不同，同一副本重启保持不变 多副本互相顶掉；或每次重启都变成新实例，历史会话找不到原实例

    localhost 只指它自己

    如果 publicBaseUrl 留空，bridge 会推导出 http://localhost:<实际端口>SessionBridge.java:317-327。这在控制面与应用同机时能用；一旦应用进了容器，localhost 只指容器自己，控制面永远回连不到。官方把这条列为常见接入问题external-agent-configuration.md:39。

    还有两个变量不在「六个」里，但排障时经常遇到：AISTIO_CONTROL_GRPC 是 ASDP 的 host:port， 不带 HTTP scheme，也不是 Gateway URLexternal-agent.md:97；BUILDER_INTERNAL_TOKEN 则是示例代码里另一种写法，语义与 AISTIO_BOOTSTRAP_TOKEN 相同，别同时填两套互相矛盾的值。

    注册是一次事务，不是一次心跳

    第一次注册不是「往目录里插一行」，而是一次事务：用受信任的 bootstrap / workload 身份声明 (tenant, namespace, agentKey)，控制面创建一个 active Agent、一个 External binding、一条默认 runtime policy、一个实例、一份注册凭据； 明文凭据只返回一次，库里只存哈希。后续副本必须用这份凭据或匹配的 workload 身份，bootstrap token 本身不能重新认领已有 keyadr-0002-service-v5-agent-identity.md:29。官方契约同样写明「plaintext registration credential exactly once」service-v5-api-contract.md:18。

    入口是 POST /api/v1/agent-registrations，它不在控制台 JWT 路由组里，而是自带机器身份信任边界：首次收 bootstrap，后续收 registration credentialserver.go:377-381。请求体字段如下agent_catalog_handler.go:62-79：

    字段必填作用
    tenant / namespace否注册范围；空则分别回落 default 与默认 namespace
    agentKey是逻辑 Agent 身份
    instanceKey是副本身份
    displayName / description否目录展示信息
    framework / frameworkVersion否框架与版本，用于目录展示
    sdkVersion否SDK 版本标识
    capabilities否能力列表，决定控制台按钮与派发资格
    routingKey否应用合约地址；SDK 把 publicBaseUrl 放在这里
    capacity否容量提示
    credentialTtlSeconds否注册凭据有效期；不填则不过期

    SDK 实际发出的 body 比表更窄：tenant、agentKey、namespace、instanceKey、routingKey、 framework、sdkVersion、capacity=1、capabilitiesHttpSelfRegistration.java:195-205。bootstrap token 走 X-Builder-Internal-Token，registration credential 走 X-Agent-Registration-CredentialHttpSelfRegistration.java:207-214。

    成功响应固定包含 agent、binding、instance 三段身份，外加明文 registrationCredential 与脱敏的 credential，HTTP 状态是 201agent_catalog_handler.go:160-165。SDK 会再校验一遍：agent.id、binding.id、instance.id 都不能空，generation 必须大于 0，凭据不能空； 缺任何一项都当作注册失败并重试HttpSelfRegistration.java:219-233。这条校验很实用：它保证「目录里出现卡片」时，三件套身份一定齐全。

    注册成功后，bridge 每 15 秒发一次心跳：POST /api/v1/dataplanes/{instanceId}/heartbeat，body 带当前 generationHttpSelfRegistration.java:105。心跳返回 404 时不会「继续等」，而是把状态置回未注册并重新走注册HttpSelfRegistration.java:180-183；网络异常同样触发重注册HttpSelfRegistration.java:184-193。所以日志里偶尔出现一次失败并不可怕，连续失败才是。

    SessionBridge：启动顺序与五个定时器

    start() 的顺序是固定的：先起合约 HTTP 服务，再发注册，再开 ASDP，最后才排定周期性任务SessionBridge.java:183-229。顺序有意义：启用合约服务时，先监听再注册，注册上报的 routingKey 才指向一个已经能接受连接的端口；反过来，控制面可能刚拿到地址就来拉，拿到的是连接拒绝。

    注册本身还有一道「静默跳过」：startHttpRegister=true 但 bootstrap token 与 registration credential 都为空时， bridge 只打一条 warning，然后跳过注册SessionBridge.java:203-210。应用照常启动、/agentscope/health 也照常 200，只是目录里永远没有它——这是「本地看着一切正常，控制台就是看不到」的头号原因。

    五个定时器决定了「多久能看到变化」，它们都写在类常量里SessionBridge.java:88-95：

    周期做什么影响
    10 s上报 Level-1 会话快照控制台会话列表的刷新粒度
    5 s刷事件 outbox，每批最多 20 条，等 ACK 最多 15 s事件流延迟与重发窗口
    30 s上下文推送冷却同一会话不会每轮都重推上下文
    30 s刷新 Subagent / Workspace 目录首次连接立即推一次，之后变慢
    15 sAttempt 租约心跳任务执行期间保活，超时会被控制面重试

    适配器调用另有 10 秒超时：handleCommand、extractContext、listMessages、listTasks 等都在 block(Duration.ofSeconds(10)) 上等SessionBridge.java:95。你的适配器如果做远程查询，要自己控制在这之内，否则控制台看到的是 500，而不是「慢」。

    会话有五个 phase，不是「运行/停止」两态：active、idle、compressing、archived、terminatedSessionBridge.java:81-86。控制面的运维语义更细：active 时禁止压缩、新 turn 进行中；idle 才允许压缩与新 turn；archived 需要 restore 回 idle；terminated 只用于显式硬销毁，数据面失踪不等于终止contract.md:221-227。所以「会话不见了」和「会话被终止了」是两种完全不同的结论。

    能力列表由三部分拼成：bridge 固定提供 session-reporting 与 context-reporting； 只有事件 journal 真的建起来时才加 event-reporting；其余全部来自 adapter 的 capabilities()SessionBridge.java:366-375。journal 的创建条件是 enableEvents && startGrpcSessionBridge.java:128-143，所以「只开 HTTP、却期待事件上报」在源码层就不成立。

    close() 的顺序也值得记：先停调度器，再关 gRPC，再注销实例，再关合约 HTTP，最后 detach adapterSessionBridge.java:330-362。先注销再关 HTTP，是为了让控制面在实例消失前还能完成最后一次状态确认。

    事件流：为什么 middleware 必须在 build 时挂

    Level-2 事件不是「读出来的」，是应用主动推的。Java 的做法是在构建 Agent 时把 AgentScopeAdapter 的 middleware 放进链里， 再把同一个 adapter 传给 Aistio.instrumentAistio.java:23-44。源码注释说得很直白：ReActAgent 的 middleware 列表在构造时固定，事后没有入口再加Aistio.java:46-48。

    middleware 采集的粒度也比「一轮问答」细：tool call 的参数在 onActing 里读，因为 ToolCallEndEvent 只带名字和 id； tool 输出则从 delta 事件重新拼起来，因为框架只在那里增量暴露输出AistioObserverMiddleware.java:49-52。这解释了为什么「事件里有工具名但没有参数」通常不是采集器坏了，而是挂错了阶段。

    事件先写本地 journal，再按批推给控制面。journal 是一个 crash-safe 的 outbox：每条记录带长度前缀、追加后 force(true) 落盘， 确认后再从 pending 里移除EventJournal.java:86-103。目录默认在 ~/.agentscope/aistio/event-journal，文件名由 tenant + namespace + agentKey + instanceKey 的 SHA-256 决定EventJournal.java:60-79。容器里不挂持久卷，重启就会换一份空 journal；这不是「事件丢了」，而是 outbox 本来就没保住。

    journal 不是业务状态库

    官方明确区分：事件 journal 帮助断线恢复，但不保存所有业务状态，也不代替框架自己的 Session storeexternal-agent-execution.md:37。应用仍需保留自己的数据、工具连接和任务幂等处理。把 journal 当数据库用，恢复出来的只会是「说过什么」，不是「做到哪」。

    任务派发：信封、Starter 与四种结尾

    这是整章最硬的一条边界：任务派发不走 HTTP 合约。合约服务里没有任何一条「提交任务」的路由； ExecutionAttempt 只从 ASDP 的 onExecutionAttempt 进来SessionBridge.java:702-747。所以 startGrpc(false) 的应用可以注册、可以被读会话、可以接命令，但永远不会收到 Issue/Team 的派发。

    派发信封一共 12 个字段，都是不可变值AgentTaskAssignment.java:24-36：

    字段用途
    attemptId / agentTaskId这一次执行与它所属的持久任务
    runId / nodeId所属 Run 与编排节点
    generation派发时的实例代次，用于拒绝过期执行
    command执行或取消
    contextUrl任务范围上下文的读取地址
    taskToken / attemptToken任务范围与执行范围凭据
    sessionId从 runtime binding 里解析出的会话；没有则为空
    payload任务输入，防御性拷贝
    timestamp派发时间

    bridge 收到后的动作顺序是固定的：先 ack，如果是 cancel 就直接回报 cancelled 并返回，不进入业务； 否则回报 start，启动 15 秒心跳，再交给 adapter.handleAgentTask(assignment)SessionBridge.java:704-747。适配器返回的 Mono 结束时，心跳才被取消。这个顺序保证了「取消」不会先跑一半业务再停。

    Java 侧的任务入口只有一个方法：AgentTaskStarter.start(AgentTaskAssignment)，返回 Mono<Void>AgentTaskStarter.java:26-30。但「有这个接口」不等于「声明了能力」：AgentScopeAdapter 只有在 agentTaskStarter != null 时才把 agent-task 加进 capability； 如果用的是 HarnessAgentTaskStarter 并且配了 Workspace 工厂，还会额外声明 workspace-definition-v1AgentScopeAdapter.java:163-185。

    反过来，基类 FrameworkAdapter 的默认实现是直接抛 UnsupportedOperationExceptionFrameworkAdapter.java:165-168，默认能力也只有 context-queryFrameworkAdapter.java:174-176。这就是「不要用空实现换 capability 标志」的源码依据：控制台会按 capability 点亮按钮，点了就 501FrameworkAdapter.java:37-39。

    Python 的情况要单独记一笔：当前内置适配器没有实现 handle_agent_task，它们可以接入观测与各自实现的会话能力， 但不会自动获得 Issue/Team 派发能力external-agent-frameworks.md:31。框架名相同也不代表 External 与 Hosted 能力相同，例如 Claude Agent SDK 集成和 Runtime Host 启动 Claude Code CLI 是两条路径。

    业务结果只有四种，而且每种都有校验条件，不是随便填个字符串AgentTaskOutcome.java:27-46：

    Outcome必须满足含义
    succeededresult 不能为空，必须是真实交付物有明确交付且执行可完成
    waitingreason 不能为空，pendingTaskIds 不能为空等待真实存在的后台任务或委派任务
    blockedreason 不能为空缺少信息或能力，保留已完成部分
    failedreason 不能为空执行失败，需要读错误后决定是否重试

    Harness 场景里，模型通过 task.submit_result 工具提交意图，工具描述里写得很清楚：提交这个工具本身不会把任务标记为成功， 只有适配器才能提交物理生命周期AgentTaskOutcomeTool.java:31-39。工具只负责把四项参数写进本次派发的 State，由适配器校验后再提交AgentTaskOutcomeTool.java:61-68。

    最后是 generation。控制面在派发时冻结 agentId、bindingId、选中的 instanceId、generation、capabilities 与约束， 之后的目录变更不会改写这次 Attemptadr-0002-service-v5-agent-identity.md:27。旧执行返回时必须接受控制面的过期身份检查，不能把旧结果重新贴成另一任务的成功external-agent-execution.md:43。收到取消也要向框架传播并观察最终状态——HTTP 响应成功不证明业务执行已经停止。

    最小可跑：从 0 到控制台可见

    下面这条路径只做「目录 + 会话」，不接任务。先把它跑通，再决定是否加 ASDP。

    1. 准备四项输入
      向管理员拿注册范围、Service HTTP 地址与 bootstrap 凭据；为当前副本定一个稳定的 instanceKey；确认控制面能访问应用的 host:portregister-agentscope-agent.md:14-21。
    2. 加依赖
      只加 agentscope-extensions-aistio，版本与应用使用的 agentscope.version 对齐。
    3. 在 build 时挂 middleware
      要让事件流可用，先把 adapter.middleware() 放进 Agent 的构建链；只想读会话，可以跳过这一步，但别事后期待事件。
    4. 启动并自查合约
      先访问 /agentscope/health，再访问 /agentscope/info。前者只证明端口通了，后者才告诉你 contractLevel 与 capabilities。
    5. 注册并在目录确认
      启动日志出现 aistio: registered ... 后，在控制台按 tenant / namespace 找到 agentKey，核对实例与合约地址。
    6. 跑一轮对话，再读历史
      从应用自身发起一轮对话，然后 GET /agentscope/sessions 与 .../messages。读不到先查合约 URL 与控制面回连，不要先怀疑适配器。

    完整的 Java 接入片段如下，和官方示例等价，只是把 adapter 显式传了进去：

    AgentScopeAdapter adapter = new AgentScopeAdapter();

ReActAgent agent = ReActAgent.builder()
        .name("report-service")
        .model(model)
        .middleware(adapter.middleware())   // 要事件流就必须在这里挂
        .build();

SessionBridge bridge = Aistio.instrument(agent,
        AistioConfig.builder("report-service")
                .controlPlaneHttp(System.getenv("AISTIO_CONTROL_HTTP"))
                .internalToken(System.getenv("AISTIO_BOOTSTRAP_TOKEN"))
                .tenant(System.getenv("AISTIO_TENANT"))
                .namespace(System.getenv("AISTIO_NAMESPACE"))
                .instanceKey(System.getenv("AISTIO_INSTANCE_KEY"))
                .contractHttpPort(18090)
                .publicBaseUrl(System.getenv("AGENT_CONTRACT_URL"))
                .startHttpRegister(true)
                .startGrpc(false)          // 只注册与会话，不接任务
                .build(),
        adapter);

Runtime.getRuntime().addShutdownHook(new Thread(bridge::close));

    如果不想在构建时挂 middleware，也可以直接用官方的两参数版本 Aistio.instrument(agent, config)， 它会内部 new 一个 AgentScopeAdapterAistio.java:56-59。代价是第二条路注释里写的那句：没有 Level-2 事件。

    合约自查用两条 curl 就够，不需要控制台：

    curl --fail-with-body "$AGENT_CONTRACT_URL/agentscope/health"
# {"status":"ok"}

curl --fail-with-body "$AGENT_CONTRACT_URL/agentscope/info"

    只有 health 通、info 不通，说明 HTTP 服务起来了但 provider 还没接上 adapter；两个都通但目录没卡片，才轮到注册参数。 这条排查顺序能省掉大量「反复换 token」的时间。

    要接 Issue / Team，再单独走第二步：把 startGrpc(true)、controlPlane(host:port) 配上， 并给 adapter 设置真实的 AgentTaskStarter。官方把这件事写成独立能力，而不是注册的附赠品external-agent-frameworks.md:16；接入教程也明确「仅注册目录和暴露会话信息不会自动获得任务执行能力」register-agentscope-agent.md:35。

    端到端：一条 Issue 怎么落到你的进程

    把前面的零件按时间顺序排起来，一条派发的完整路径是这样：

    • 应用启动 构建 Agent 时挂 middleware；instrument 绑定 adapter，计算 capabilities（bridge 固定两项 + adapter 声明项）SessionBridge.java:366-375。
    • 合约监听 在 18090 起 /agentscope/*；如果配置了 internal token，写请求开始要求 X-Builder-Internal-TokenSessionBridge.java:189-201。
    • 注册 POST /api/v1/agent-registrations，带 bootstrap 或 registration credential；拿到 Agent / Binding / Instance / generation 与控制面签发的新凭据HttpSelfRegistration.java:195-233。
    • 保活 每 15 秒心跳；404 或网络失败就重新注册。控制面同时按 routingKey 回连合约，拉会话与能力HttpSelfRegistration.java:163-193。
    • 控制面选实例 Issue → Run → AgentTask → Attempt；按 binding 能力、实例健康和 generation 选一个实例，冻结这次 Attempt 的身份adr-0002-service-v5-agent-identity.md:27。
    • ASDP 下行 bridge 收到 ExecutionAttempt：先 ack，取消就直接 cancelled；否则 start、开 15 秒租约心跳，再进业务SessionBridge.java:704-747。
    • 你的 Starter 执行 用任务范围凭据读上下文、建隔离执行、发评论与 Artifact，最后提交四种 outcome 之一external-agent.md:101。
    • 回报与收尾 bridge 上报成功/失败/取消，Run node 收敛；应用退出时注销实例，服务端返回 204dataplane_handler.go:75-95。
    方向走哪条通道典型失败现象
    应用 → 控制面HTTP 注册与心跳目录无卡片；日志反复 retry
    控制面 → 应用HTTP /agentscope/*有卡片但会话读不到；401 / 连接拒绝
    应用 ↔ 控制面ASDP 长连接能聊天但不能接 Issue；事件流为空

    这三条通道是独立的。任何一条断了，都只影响对应的能力，不会让另外两条「一起坏」；反过来，一条通了也不代表另外两条通。 排障时先问「现在缺的是哪一层的能力」，再去看对应的通道。

    这张表里的「HTTP 只读、ASDP 派发」不是文档措辞的推论，而是源码结构：ContractHttpServer 没有任何任务提交路由， ExecutionAttempt 只由 SessionBridge.onExecutionAttempt 处理。

    六个坑，先看方向再看代码

    坑一：startGrpc(false)，却期待 Issue 派发。注册和会话都正常，控制台也能看到 Agent， 但任务永远不来。原因不是 Starter 没写，而是派发通道根本没开——ExecutionAttempt 只走 ASDPSessionBridge.java:702-718。先确认部署是否提供 ASDP listener，再谈代码。

    坑二：AGENT_CONTRACT_URL 留空或填 localhost。注册请求是应用「向外打」，能成功； 控制面回连是「向内打」，打不进来。bridge 的兜底是 http://localhost:<port>SessionBridge.java:317-327，在容器里等于指向容器自己。现象是「目录有卡片，点进去没有会话」。

    坑三：所有副本共用一个 instanceKey，或者每次重启换一个。前者会让多个进程争同一份副本身份， 心跳与 generation 互相覆盖；后者会让「普通重启复用身份」失效，历史会话找不到原实例。官方要求不同副本不同值、同一副本重启保持稳定external-agent-configuration.md:46。

    坑四：只验证了应用 → Service 一个方向。注册成功只证明这个方向通；控制面 → 应用的合约、应用 → ASDP listener 是另外两条链路external-agent-configuration.md:36-40。只开单向网络，最常见的结果就是「注册成功但什么都读不到」。

    坑五：Agent 已经 build 完，再 instrument，然后等事件。会话查询、上下文、历史、命令都能用， 但 Level-2 事件不会出现，因为 middleware 列表已经固定Aistio.java:46-48。要事件就回到构建处挂 adapter.middleware()。

    坑六：把 bootstrap token 当 Endpoint API key，或反过来。两者都是平台凭据，但用途完全不同： bootstrap 只用于首次注册，asep_ 才是调用 Endpoint 的凭据；注册凭据是 asreg_ 前缀，由控制面签发agent_catalog_handler.go:89-96。Endpoint key 能在授权范围内再次 revealservice-v5-api-contract.md:76，注册凭据的明文只在签发时返回一次service-v5-api-contract.md:18；拿错了只会得到 401，换多少次都没用。

    自测：三个判断题

    只做 HTTP 注册（startGrpc(false)），能接 Issue 吗？

    不能。HTTP 合约只提供查询与会话命令，没有任务提交路由；ExecutionAttempt 只从 ASDP 的 onExecutionAttempt 进入SessionBridge.java:702-718。要接 Issue/Team，必须同时具备 ASDP 通道与真实的 AgentTaskStarter。

    注册返回 201，控制台也能看到卡片，但会话列表是空的，先查什么？

    先查控制面能不能回连 AGENT_CONTRACT_URL。注册成功证明「应用 → Service」通，不证明「控制面 → 应用」通； localhost、错误端口、DNS 不可达都会让合约拉取失败external-agent-configuration.md:36-40。token 在这条链路上不是第一嫌疑。

    两个副本用同一个 agentKey、不同 instanceKey，会创建两个 Agent 吗？

    不会。逻辑身份是 (tenant, namespace, agentKey)，扩容只创建新的 AgentInstance，不会创建第二个逻辑 Agentadr-0002-service-v5-agent-identity.md:25。反过来说，instanceKey 相同才是问题：那不是扩容，是身份冲突。

    练习：注册一个只读 Agent，再做一次故障演练

    目标不是「跑通」，而是能独立判断每一层坏在哪。建议 25 分钟，按顺序做，每步都留证据：

    1. 先验合约，不注册
      只起 HTTP 合约（startHttpRegister(false)），访问 /agentscope/health 与 /agentscope/info，记录 contractLevel 与 capabilities。此时目录里应该没有卡片。
    2. 打开注册，核对三件套身份
      打开注册，日志出现 registered 后，记录 agentId、bindingId、instanceId 与 generation。刷新目录，确认范围与 agentKey 一致。
    3. 重启一次，只改 generation
      保持 instanceKey 不变重启，确认 agentId / bindingId 不变、generation 变化。如果 agentId 变了，说明身份没有复用。
    4. 扩一个副本，只改 instanceKey
      再起一个进程，agentKey 相同、instanceKey 不同，确认目录里是同一个 Agent 下的两个实例，而不是两个 Agent。
    5. 跑一轮对话，读三层数据
      依次读 /sessions、/sessions/{id}/state、/sessions/{id}/messages?limit=5，记录 phase 与消息条数。读不到就按「合约 URL → 端口 → token」顺序查。
    6. 故意打断回连
      把 AGENT_CONTRACT_URL 改成一个控制面不可达的地址重启，观察目录与日志的差异；再改回来。把两次现象写进自己的排障笔记。
    7. 可选：接一次任务
      如果部署有 ASDP，打开 startGrpc(true)、配 controlPlane 与 AgentTaskStarter，提交一个最小 Issue，分别验证成功与取消。没有 ASDP 就停在上一步，不要用 HTTP 路径硬凑。

    下一章看什么

    到这里，External 的三层边界已经拆完：目录身份靠注册事务，会话视图靠 HTTP 合约，任务派发靠 ASDP + Starter。 它和 Managed 最大的差别不是「谁更聪明」，而是责任落在谁身上：模型循环、工具凭据、任务幂等都在你的进程里。

    下一章看 Hosted Agent 与 Runtime Host：同样是「不把 Agent 交给 Dataplane」，Hosted 换了一种做法—— 不注册一个应用，而是把一台已经安装并登录 Coding Agent provider 的主机接进来，由 Service 发现、调度和恢复。 它和 External 的边界，正好是「应用」与「主机」的差别。
