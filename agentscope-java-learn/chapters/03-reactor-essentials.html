03 · 响应式必修

Mono、Flux、.block()、.blockLast() 这四个东西，如果你不弄明白， 后面每一章的示例都会「看起来能跑、但什么都不输出」。本章只讲框架真正用到的那部分，不铺全套 Reactor。

读完你能做到

  • 解释为什么 agent.call(...) 少写一个 .block() 就完全没有反应
  • 用 streamEvents(...).doOnNext(...).blockLast() 写出一个边生成边打印的控制台程序
  • 判断一段代码该用 block、blockLast 还是 subscribe，并说出在哪个线程里写 block 会卡死

先说为什么：Agent 调用是「流水线」，不是「函数」

普通函数调用像去窗口点餐：你递钱，然后站在那儿等，直到饭做好（返回值）。Agent 调用更像下单后 拿一张取餐凭证：对方立刻给你一张凭证（Mono），你去干别的；什么时候想看结果，再拿凭证去取 （.block()）。而流式输出更像看厨房直播：每个动作都变成一条推送（Flux），你爱看 多久看多久，也可以随时关掉。

如果 API 是同步阻塞的 Msg call(...)

  • 一次调用 30 秒，Web 服务的请求线程就被占 30 秒，并发 10 个就把线程池打满
  • 用户想「算了别答了」时，你没有任何把手可以停下来
  • 想边生成边显示？没法在函数返回前插进去

框架实际给的 Mono<Msg> / Flux<AgentEvent>

  • 返回的是描述，不是结果：不订阅就一行代码都不执行
  • 能取消、能超时、能与其他流组合（timeout、zip）
  • 流式场景天然合适：每个 token 是一条 onNext

框架里两个最核心的返回值就是这个形态：call(...) 给 Mono<Msg>ReActAgent.java:849，streamEvents(...) 给 Flux<AgentEvent>ReActAgent.java:1133。官方文档一句话总结了两者关系：call 在内部消费所有事件，等智能体完成（或因外部交互暂停）后返回最终 Msgagent.md:273。

最小可跑：边生成边打印

沿用第 01 章的两段依赖（agentscope-core + agentscope-extensions-model-dashscope，或直接 agentscope-harness），主程序如下。写法与官方示例 BasicChatExample.java 的流式段完全一致，只是把「从控制台读输入」换成了固定问题： 

import io.agentscope.core.ReActAgent;
import io.agentscope.core.event.TextBlockDeltaEvent;
import io.agentscope.core.message.UserMessage;
import io.agentscope.core.tool.Toolkit;

public class StreamOnce {
    public static void main(String[] args) {
        ReActAgent agent = ReActAgent.builder()
                .name("Assistant")
                .sysPrompt("You are a helpful AI assistant. Be friendly and concise.")
                .model("dashscope:qwen-plus")
                .toolkit(new Toolkit())
                .build();

        agent.streamEvents(new UserMessage("用三句话解释什么是 ReAct。"))
                .doOnNext(event -> {
                    if (event instanceof TextBlockDeltaEvent e) {
                        System.out.print(e.getDelta());
                    }
                })
                .blockLast();
        System.out.println();
    }
}

官方原版（带交互式输入循环）：BasicChatExample.java:86；TextBlockDeltaEvent.getDelta()：TextBlockDeltaEvent.java:59

同样的效果，用 call 只改三行

只要最终文本、不要过程时，把流式那段换掉即可：

import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.message.Msg;
import java.util.List;

Msg answer = agent.call(List.of(new UserMessage("用三句话解释什么是 ReAct。")),
        RuntimeContext.empty()).block();
System.out.println(answer.getTextContent());

逐行解读：这 5 行是整个响应式的心脏

这一行 容易懵的点 实际上
agent.streamEvents(...) 我调了它，为什么控制台没动静？ 它返回的是一个冷流：描述「将来会产生哪些事件」，本身不启动任何工作。真正启动发生在订阅那一刻。
.doOnNext(event -> ...) 这是不是「消费」事件？ 不是。它只是旁路观察，事件仍会继续往下游走。所以你可以把多个 doOnNext 串起来各干各的， 互不影响。
event instanceof TextBlockDeltaEvent e 为什么不直接用 getTextContent()？ 流式阶段还没有「完整消息」，只有增量片段。TextBlockDeltaEvent 携带的是这一小段文本TextBlockDeltaEvent.java:59，要自己拼。这是 Java 17 的模式匹配写法，等价于 if (event instanceof X) { X e = (X) event; ... }。
.blockLast() 为什么不是 .block()？ block() 是 Mono 的（取那唯一一个值）；Flux 有 0~N 个元素，要说清「等到最后一个 元素到达为止」，就是 blockLast()。返回类型是最后一个元素，这里用不到所以直接丢弃。
.toolkit(new Toolkit()) 空工具箱有什么意义？ 显式声明「这个 agent 没有任何工具」。不传也行，但显式写出来能避免「以为是框架没给工具，其实是我没注册」的误判。
最关键的一句话：不订阅 = 不执行

响应的「惰性」不是性能优化，而是语义：没有订阅者，框架就没有理由去花你的 token。所以看到「程序秒退、 什么也没打印」时，第一个要检查的不是模型配置，而是流有没有被订阅。

端到端：一次 blockLast() 到底触发了什么

  • 你的线程
    调用 streamEvents(msg)，拿到 Flux<AgentEvent>——此刻零副作用
  • 订阅
    blockLast() 内部 subscribe()：从这一步开始，请求才真正进入 agent 生命周期
  • 推理
    模型按流式返回，每个增量文本块转成一条 TextBlockDeltaEvent，推给下游
  • 你的回调
    doOnNext 对每条事件同步执行一次——它跑在发布事件的那个线程上
  • 工具（若有）
    模型要调工具时，事件流里会出现工具调用开始/结束事件，循环继续，直到模型不再要求调工具
  • 完成
    流发出 onComplete，blockLast() 返回，你的线程继续往下走
  • 出错
    流发出 onError，blockLast() 在这里抛出异常（不是返回 null）
响应式：三个信号
  • onNext(value)：来了一条数据（可能很多条）
  • onComplete()：正常结束，不会再有数据
  • onError(e)：异常结束；之后不会再有数据，也不会再 onComplete
阻塞式：你熟悉的对应物
  • block()：onNext 有值 → 返回；空流 → 返回 null；onError → 抛异常
  • blockLast()：等到 onComplete → 返回最后一个值；onError → 抛异常
  • collectList().block()：把整条流收成一个 List 再返回

取消、超时、中断：响应式换来的三个能力

既然拿到的是句柄而不是结果，就能做同步 API 做不到的事。框架把「一次执行」抽象成 AgentRun<T>： prepareRun(...) 拿事件流句柄，prepareCall(...) 拿最终回复句柄，都带一个唯一 runId()；创建句柄不会执行，订阅 stream() 才开始agent.md:215。 

import io.agentscope.core.agent.AgentRun;
import io.agentscope.core.agent.RuntimeContext;
import io.agentscope.core.event.AgentEvent;
import io.agentscope.core.message.UserMessage;
import java.util.List;

RuntimeContext ctx = RuntimeContext.empty();
AgentRun<AgentEvent> run = agent.prepareRun(List.of(new UserMessage("你好")), ctx);

String runId = run.runId();          // 先登记到你的运行管理器
run.stream().subscribe(this::onEvent, this::onError);

// 另一条请求链路（比如用户点了「停止」）可以根据 runId 找到它并取消
run.cancel();
你想要的 怎么写 出处
跑一次并等结果 agent.call(msgs, ctx).block() ReActAgent.java:849
跑一次并看过程 agent.streamEvents(msg).doOnNext(...).blockLast() ReActAgent.java:1133
最多等 60 秒 .block(Duration.ofSeconds(60)) 或 flux.timeout(Duration) Reactor 原生算子
拿可取消/可查状态的句柄 prepareRun(...) / prepareCall(...) ReActAgent.java:1101 / ReActAgent.java:1106
立即取消（订阅前也行） run.cancel() AgentRun.java:128
在检查点协作式中断（会带恢复消息） agent.interrupt(target) / agent.interrupt(target, msg) ReActAgent.java:929
查状态 / 等终态 run.status()、run.termination() AgentRun.java:113 / AgentRun.java:123
cancel() 与 interrupt() 不是一回事

cancel() 立即取消响应式执行，订阅者会收到 CancellationException；interrupt() 是在下一个检查点（推理开始、工具开始、每个流式 chunk）才生效，agent 会返回一个带 GenerateReason.INTERRUPTED 标记的 Msg，并且对话上下文会保存下来，下次同 session 可以从中断点继续 agent.md:255。要做「优雅停止」用后者， 要「立刻不管了」用前者。

只记这 10 个算子

算子 作用 用在本框架的哪里
subscribe() 触发执行，不阻塞 Web 服务里想把事件推给 SSE 时
block() 阻塞取 Mono 的唯一值 call(...) 后面
blockLast() 阻塞到流结束 streamEvents(...) 后面
block(Duration) 最多等这么久；超时抛 IllegalStateException（cause 是 TimeoutException），不是返回 null 命令行工具里防止挂死
doOnNext 旁路观察，不改数据 打印/计数/埋点
doOnError 旁路观察错误 日志，然后继续往上抛
map 一对一转换 把 Msg 转成 DTO
flatMap 一对一转换并「摊平」一个内部流 拿到结果后再发起一次调用
onErrorResume 出错时切换到备用流 降级到小模型/固定答案
timeout 超时抛 TimeoutException 给整条流设上限

陷阱与窍门

1. 程序秒退，什么都不打印
你会看到
命令运行完立刻结束，没有报错，也没有输出。
因为
你写了 agent.call(...) 或 agent.streamEvents(...)，但没订阅——Mono/Flux 是描述，不订阅就不执行。
改成
Mono 加 .block()，Flux 加 .blockLast()，服务端场景用 .subscribe(...) 并接住异常。
2. 在 doOnNext 里再调 .block()
你会看到
程序卡住不动，或者抛 IllegalStateException: block()/blockFirst()/blockLast() are blocking, which is not supported in thread ...
因为
回调跑在事件发布线程上，你在「流内部」等这条流自己完成——自己等自己，永远等不到；Reactor 检测到在非阻塞线程上 block 时也会直接拒绝。
改成
回调里只做轻量累积（List.add、StringBuilder、计数）；需要「拿到结果再干一件事」请用 flatMap，不要在回调里阻塞。
延伸
这句异常的完整上下文与三种解法：附录 B · 在非阻塞线程里 block。
3. 在 UI 线程 / 事件循环线程里 block()
你会看到
桌面程序界面完全无响应；Web 服务里所有请求一起变慢直到超时。
因为
block() 会一直占住当前线程。Swing 的 EDT、JavaFX 的 Application Thread、Netty 的 event loop 都不能被占用。
改成
UI 里用 subscribe(value -> SwingUtilities.invokeLater(...))；服务端直接把 Flux 交给框架的响应式管道。
4. subscribe() 只传一个参数，异常被吞掉
你会看到
调用发出去了，界面没有任何反应，日志里只有一行不太显眼的 onErrorDropped。
因为
subscribe(consumer) 没提供错误处理，错误被丢弃（dropped），不会抛到你的调用栈上。
改成
至少写两参版本：subscribe(onNext, onError)；生产代码再补 onComplete 与 doFinally 做清理。
5. 不设超时，模型一慢就永久等待
你会看到
程序卡在 block() 上很久，看起来像死机。
因为
block() 无参版本会一直等；网络层默认超时可能长达数十秒到分钟级。
改成
命令行工具用 block(Duration.ofSeconds(60))；流式用 .timeout(Duration.ofSeconds(90))，并在 onErrorResume 里给出可读提示。

自检三问

agent.call(msg) 返回的是结果吗？

不是，返回的是 Mono<Msg> 这个描述。真正执行发生在订阅（block / subscribe）时。

为什么 streamEvents 要用 blockLast() 而不是 block()？

因为它是 Flux（0~N 个事件）。block() 是 Mono 的 API，对 Flux 语义上要说「等到最后一个元素」，对应 blockLast()。

cancel() 和 interrupt() 该怎么选？

想立刻停止、不需要恢复消息时用 cancel()；想「优雅停下并把当前进度存下来」时用 interrupt()——它会返回 带 INTERRUPTED 标记的 Msg 并保存上下文agent.md:256。

20 分钟动手练习

  1. 把死代码救活
    把 StreamOnce 里的 .blockLast() 删掉再跑一次，确认「什么都不输出」。然后把 doOnNext 也删掉、只留 blockLast()，确认「程序确实跑了，只是没打印」——这两种「没输出」的原因完全不同。
  2. 加上耗时统计
    用 long t0 = System.currentTimeMillis(); 包住整条流，结束后打印总耗时；再在 doOnNext 里统计事件条数。你会直观看到「一次回答 = 几十到几百个事件」。
  3. 给一个必定失败的调用加超时
    把 model 改成不存在的 id，用 .timeout(Duration.ofSeconds(5)) + onErrorResume 捕获并打印一行 「抱歉，模型暂时不可用」。这一步就是 11 章综合案例的容错雏形。
